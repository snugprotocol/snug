## What and why

Binding B (ADR-0065 §2 B — the local host, the ONLY binding with connected apps) is delivered as a **plugin-bundled local MCP server** instead of a launch script the user runs by hand. When the `snug` plugin is installed in Claude Code, Cowork (desktop) or Codex, the host spawns the process at session start over stdio and connects to it — verified 2026-09-06: Claude Code starts plugin MCP servers automatically when the plugin is enabled and runs the Node dependency install in the plugin's version directory (`code.claude.com/docs/en/plugins-reference`); Cowork runs local plugin MCP servers through the desktop app only; Codex supports stdio `command` servers in a plugin `.mcp.json` but has no plugin-root variable (openai/codex #22842 — relative paths resolve from cwd), so Codex needs `npx -y @snugprotocol/host-mcp` once the package exists, an absolute path until then.

The process has exactly three jobs:

1. **Serve the kit on loopback** — the `local-host` binding of `apps/host`, opened in the user's browser, with the user's file at `~/Snug/user.snug` on disk.
2. **Be the network side of the executor.** The page's executor (`packages/auth/src/connected-fetch.ts`) stays THE seat that reads a credential and calls fetch, with all ten gates unchanged. What crosses to the process is the platform's raw `fetchImpl` — the same seam Snug Desktop fills with native `plugin-http` — plus the `oauth` loopback transport and the `userdbBackend` file seam. The process is Snug Desktop's Rust side written in Node and reached over `127.0.0.1`, nothing more. This is the whole point: apps built in the kit get connected fetch, with or without credentials (API keys, OAuth, signed requests, LAN pins per the registry), through one proxy the plugin ships, and the browser's CORS ceiling disappears exactly as it does on desktop.
3. **Expose a small control-plane tool surface to the agent** — status, open, hand-in, list. No data-plane tool, ever (see the hard rules).

Nothing here makes Snug "built on MCP" (ADR-0061). MCP is the spawn-and-connect channel the hosts already offer plugins; the proxy and the file are plumbing; the copy stays "Snug apps run inside Claude Code / Cowork / Codex." Product copy never says "Snug MCP server."

## Hard rules (each becomes a test or a lint)

- **C1 stays where it is.** The executor is not moved into Node and not duplicated. The process's `/fetch` receives the request AFTER the page's gates and injection, and it is value-blind in the desktop sense: it never logs, persists or echoes a URL, header or body; error messages pass through `packages/auth`'s scrubber before they return. Defense in depth is still required on the process side because anything on the machine can open a loopback socket: re-check https-only (LAN exception only via the `lanFetch` seat with a pin, as on desktop), `isForbiddenNetHost` from `packages/auth/src/net-guards.ts` (import it — never a second copy), `redirect: 'manual'`, the 1 MiB read cap, the 60 s wall clock. These are the executor's own gates run twice, not a new policy.
- **The LLM is never a network principal.** The MCP tool list contains NO tool that fetches, proxies, reads a credential, or runs SQL against the user file. A test enumerates `tools/list` against an allowlist of tool names and fails on any addition; the data-plane routes (`/fetch`, `/oauth/*`, `/userdb/*`) are reachable only from the page. This is C1's "never reach the LLM" clause applied to the agent that spawned us.
- **Loopback only, authenticated, origin-bound.** Bind `127.0.0.1` on an ephemeral port. A per-launch 256-bit bearer is handed to the page in the launch URL **fragment** (never the query — logs) and must be present on every data-plane call; `Origin` must equal the served origin; CORS allows that origin only; `Sec-Fetch-Site`/`Sec-Fetch-Mode` checked where the browser sends them. Missing bearer → 401, wrong origin → 403, both with no body detail. Never bind `0.0.0.0`; never trust a `Host` header.
- **One process, one file.** A lock file under `~/Snug/` records `{port, pid, token-hash, startedAt}`; a second session attaches to the running server instead of spawning another (two Claude Code windows = one Snug). The user file follows the A/B-slot + magic-check discipline the desktop backend uses (lesson 2026-08-03); if Snug Desktop already holds `~/Snug/user.snug`, this process opens **read-only and says so** in the custody chip — no silent second writer. Never write state under the plugin directory (`${CLAUDE_PLUGIN_ROOT}` changes on every update).
- **OAuth loopback = the desktop posture.** Reuse `buildLoopbackRedirectUri` and `SNUG_DESKTOP_OAUTH_PORT` (41420) from `packages/auth/src/desktop-transport.ts` so every registry entry's `desktopRedirectPosture` and every console walkthrough already written for desktop applies unchanged. The listener binds 41420 only while a flow is pending, exactly as `tauri-plugin-oauth` does; a busy port is a named error, not a fallback to another port.
- **D4 holds.** The artifact and widget kits (`snug-host.html`, `snug-host-micro.html`) still ship with `connections:false` and without the wizard, executor or registry. Connected apps exist ONLY in the `local-host` build (decision D-B1 below).
- **Owner acts stay owner acts.** No `npm publish`, no `@snugprotocol` scope registration, no marketplace submission, no push to the distribution repo, no `gh release`, no deploy. Prepare and print; never perform.

## Acceptance criteria

1. **Spawn and connect.** With the plugin installed from a local marketplace path, a fresh Claude Code session shows the server connected (`/mcp`), `tools/list` returns exactly `snug_status`, `snug_open`, `snug_hand_in`, `snug_list_apps`, and `instructions` carries the launch protocol text generated from the prompt store (D6 — the `instructions` string is emitted by the same generator as `SKILL.md`, byte-compared by `check-skill-sync`). Note in the plan that claude.ai chat drops `instructions`; Claude Code and Codex read it.
2. **Serve.** `snug_open` (or the printed URL) opens the `local-host` kit; the probe reports `binding:'local-host'`, `connections` allowed, the brain chip says "Claude · your CLI" (or "demo brain — no host brain found" when the shim is absent), the custody chip says "on this Mac — ~/Snug/user.snug".
3. **Connected fetch, no credential.** The `weather`-shaped starter (or the e2e stub) performs a `net-request` that reaches a stub HTTPS server through the process, with the page's executor gates logged as run and the process's re-checks logged as run. Response headers obey the protocol whitelist; the 1 MiB cap trips on an oversize body.
4. **Connected fetch, with credential.** An API-key starter (Ledger, per the T3 row: "executor/wizard/starters unchanged — Ledger still connects") completes the wizard, stores the credential in the page's `auth:` secrets, and its injected request reaches the stub through the process. The credential value appears in exactly one place on the wire — the outbound request from the process — and in no log, lock file, MCP message, or tool result (grep-tested with a canary value).
5. **OAuth.** The connection-wizard OAuth journey completes through the process's 41420 listener (aware of the journey-4 popup/self-close flake recorded in `docs/next-steps.md` 2026-08-26 and 2026-09-03 — assert on the wizard's own connected state, not the popup's navigation). A 401 on a connected call triggers the executor's single refresh-retry through the same seam.
6. **Negative security.** Data-plane calls without the bearer → 401; with a foreign `Origin` → 403; to a private/loopback/link-local host → refused with `NET_INVALID_REQUEST`-class code; a redirect is not followed; `tools/list` allowlist test; a process-side "log everything" debug flag does not exist (test that no such env var is read).
7. **Single instance + custody.** A second spawn attaches to the first (same port, no second listener); with Snug Desktop holding the file, the kit opens read-only and the chip says so; killing the host closes the process within the stdin-close grace and releases the lock.
8. **Hand-in.** `snug_hand_in({bundle})` delivers a `snug-app-bundle/1` to the open page (SSE or long-poll from the page to the process — plan decides), and the page applies it under ADR-0045's rules exactly as Binding A does (unedited-only auto-apply; connections in a bundle are still a hard refusal at hand-in — the user connects through the wizard, never through a bundle).
9. **Brain.** The `claude` shim from the program's D5 lands in this process as a module (`/v1/chat/completions` on the same loopback origin, bearer-gated, spawning the user's own `claude -p` with the exact flags D5 pins — never `--bare`, child env stripped of `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN`), reached through the playground's `local` mode with the bearer key. This is the "no bearer path exists for `local` mode" first commit the program shares with Option C — whichever lands first owns it; check the branch state before writing it. `codex`/`hermes`/`openclaw`/`ollama` shims stay in T3's remainder.
10. **Codex parity, documented.** `.codex-plugin/plugin.json` + its `.mcp.json` validate with the `npx` form and a documented absolute-path interim; Cowork desktop is walked once by me and the result (where the process runs, whether `open` works from the sandbox) is journaled — not assumed.

## Decisions to make at Gate 2 (defaults; overturn only with a reason in the journal)

- **D-B1 — Which page is served.** Default: a second entry of `apps/host` (`snug-host-local.html`, connections compiled in, served only ever from this process) rather than the playground dist or a build mode of the playground (ADR-0065 rejected build modes; the sibling-entry pattern is the desktop precedent). The artifact/widget kits are untouched.
- **D-B2 — Where the code lives.** Default: `apps/host-mcp/` (a Node package: `src/server.ts` stdio MCP via `@modelcontextprotocol/sdk`, `src/loopback.ts` HTTP data plane, `src/fetch-proxy.ts`, `src/oauth-loopback.ts`, `src/userdb-file.ts`, `src/brain-claude.ts`, `src/lock.ts`), built to a single `dist/snug-mcp.mjs` that the plugin ships; the skill's `scripts/` gets the built file, never the source. Dependency policy per `docs/conventions.md` and `scripts/audit-deps.mjs` — the SDK goes on the allowlist with a reason; everything else is Node stdlib.
- **D-B3 — Executor placement.** Default: executor in the page, `fetchImpl` over loopback (desktop parity, one seat, existing tests). The alternative — executor in Node with the credential store in Node — is rejected unless Gate 2 finds the loopback hop breaks a gate; write down why if so.
- **D-B4 — Page↔process channel for hand-in and status.** Default: the page subscribes to `/events` (SSE, bearer-gated); the process pushes `hand-in`, `status`, `shutdown`.
- **D-B5 — Plugin layout.** `.claude-plugin/plugin.json` + `.mcp.json` `{"mcpServers":{"snug":{"command":"node","args":["${CLAUDE_PLUGIN_ROOT}/scripts/snug-mcp.mjs"]}}}`; scoped tool names `mcp__plugin_snug_snug__*`; `.codex-plugin/plugin.json` from the same constants module (D7). Both emitted into the distribution repo by the existing generator; this monorepo carries the source.
- **D-B6 — Optional spike, NOT in the AC: the agent as brain over tool calls.** Because the process lives inside the agent's session, an app's think could ride as a tool result and the answer return as a `snug_reply` tool call — silent, on the user's subscription, no child `claude -p`. The 2026-09-04 memo judged this viable in Claude Code only (long calls survive ~28 h, auto-background at 2 min) and unviable in Claude Desktop. If Gate 2 has room, add S12: one Chess move round-trips this way; measure latency and whether the turn stays usable. Go/no-go decides whether a later task adds a `tool-call` brain leg. MCP sampling is NOT an option — deprecated in the 2026-07-28 spec and unsupported by Claude Code.
