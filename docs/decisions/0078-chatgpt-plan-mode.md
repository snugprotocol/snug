# 0078 — "Use my ChatGPT plan": a third desktop mode on OpenAI's Sign in with ChatGPT, with per-machine token custody outside the user file

- **Status:** **draft** (written at Gate 2 of TASK-20261023-siwc-chatgpt-plan; becomes *accepted* when the owner approves the plan — the interview's four answers may amend §4–§6 by one word each)
- **Date:** 2026-10-23
- **Task:** TASK-20261023-siwc-chatgpt-plan
- **Amends:** **ADR-0014** (custody — one scoped exception: a per-machine, rotating credential lives beside the file, not in it) · **ADR-0021 §7** ("Desktop ships BYOK/local only" → BYOK, local and the ChatGPT plan; §2's loopback core gains a redirect *path* and the callback's `client_id`) · **ADR-0046 §1–§2** (a third mode with its own default-model row) · **ADR-0059** (a new brain joins the one derivation and the chip's label map)
- **Relates to:** ADR-0036 (pins), ADR-0067/0070 (model + thinking level in the brain's own vocabulary, never a mapping), ADR-0071 §3–§4 (never switch vendor without a user act; no API-key env — the `codex` driver already rides a ChatGPT login on Binding B), ADR-0074 (scheduled steps), ADR-0055 (privacy disclosure)

## Context

The desktop app offers two ways for apps to think: a key the user pastes (BYOK — Anthropic or OpenAI, Chat Completions) or a local model (Ollama). Most people who would try Snug already pay for ChatGPT and have no API key. OpenAI's **Sign in with ChatGPT** open-source / locally-hosted track lets such an app run on the user's own plan: a public PKCE client registered dynamically on first sign-in (`client_id=dynamic_agent_client` → an issued `oaiapp_…` client bound to a per-host id), tokens from `auth.openai.com`, inference through `POST https://api.openai.com/v1/responses` with `store:false` and `stream:true`, usage counted against the user's plan and manageable in ChatGPT → Settings → Usage. It is a **preview**. It is self-serve for open-source, locally-run apps (*"needs neither a client secret nor a partner API key"*); paid or remotely hosted apps need OpenAI's interest form. `snugprotocol/snug` is public and MIT (verified 2026-10-23), so Snug fits the track as documented.

A wire spike (2026-10-23, `spikes/siwc/`, outside the repo) measured the whole path: dynamic registration and re-auth on a different port; a token response with `access_token, refresh_token, id_token, expires_in=3600, scope, token_type, earliest_refresh_at`; a rotating refresh token; an RS256 ID token with an `aud` array and **no plan-type claim**; `/v1/models` with `slug / display_name / visibility / supported_reasoning_levels`; a streamed answer and a complete function-tool round trip with full-context resend; 400s for `temperature`, `store:true`, `stream:false` (body `{detail}`); a 401 whose message **echoes the bearer**; CORS `*` from `tauri://localhost`; and a stream delivered with **no `content-type` header**. The docs were re-read the same day; the deltas are in the task file.

Three facts about today's code shape the decision:
- Credentials live in `snug_secrets` in the user's own file (ADR-0014) — which is why they roam to a personal Dropbox and into `includeSecrets` exports. That is the right property for an API key and the wrong one for a **rotating, per-host** session: a copy on a second machine logs one side out (`refresh_token_reused`) and belongs to a client registered for another host id. ADR-0071 rejected copying Codex's `auth.json` for the same reason; ADR-0070 §5 keeps per-machine brain facts out of the file.
- The routing decision is ONE derivation (`adapterKindFor`) consumed by the constructor, the chip, the provenance stamp, the scheduled-step gate and the data-lane door — and that derivation is copied in four places (lesson L287). A new brain either rides every copy or lies somewhere.
- `packages/auth` already holds the reviewed primitives this needs: PKCE S256, HMAC-signed state, the loopback transport core (TTL, single active flow, cancel-old), a credential POST that never follows a redirect and scrubs its own submitted secrets from provider error bodies. What it lacks: a redirect path other than `/callback`, delivery of the callback's `client_id`, dynamic registration, and a single-flight refresh.

## Decision

1. **A first-class third mode, `PlaygroundMode = 'chatgpt'`, desktop only.** It appears wherever `byok` and `local` appear — the desktop Welcome (a third card), Settings' "where the agent runs" segment, the brain chip, the model selectors, the scheduled-step gate, the data-lane door — and nowhere else: `availableModes()` offers it only where the platform carries the custody seat (`SnugPlatform.chatgptPlan`), so the hosted playground, the web kit and the local-host kit never show it, and a roaming file that stores `mode:'chatgpt'` is coerced on those platforms with the existing divergence note, the stored row untouched (the subscription-coercion precedent). **Not** a BYOK provider variant: BYOK's shape is "a key the user pasted" and every one of its seats (the `byok:` secret rows, key-presence derivation, keyless → demo fall-through) would misdescribe an account session.

2. **Custody: a per-machine credential, held by the shell in a `0600` file, outside the user file.** `~/Snug/chatgpt-plan.json` (directory `0700`, temp+rename+fsync like `userfile.rs`) holds the host id, the issued client id, the token set, the verified account identity (`sub`, email, name), the plan-granted flag and the cached model list. It is readable and writable by exactly three Tauri commands — `chatgpt_session_read / write / clear` — main-window only like every command, proven unreachable from an app frame by the in-shell gate. **The webview runs the protocol** (sign-in, exchange, ID-token validation, refresh, revocation) in `packages/auth`'s new DI-pure session module, reads the access token from the keeper per send and holds it only in memory — the same altitude at which the host page holds a BYOK key today. The token never enters `snug_secrets`, so it is structurally absent from every export, sync push, share bundle and the share scan; it never enters `TurnAdapterConfig`, a URL, the inspector's request snapshot (which has no header field by type) or a log. **This is a scoped exception to ADR-0014's "every credential lives in `snug_secrets`"**, recorded here as that ADR requires: the clause exists for portability, and for a rotating per-host session portability is the defect. The custody *claim* is unchanged and still honest — *your tokens never reach our servers; they stay on this computer* — and is stated per machine rather than per file.

3. **Who calls the API: the host page, through the platform fetch, behind `runAgentTurn`.** A new `openaiResponsesAdapter` in `packages/adapters` (the Chat Completions adapter is untouched) takes a `getBearer()` / `refreshBearer()` seam rather than a key, sends `instructions` + full-context `input` items + top-level function tools + `store:false` + `stream:true` (+ `reasoning.effort` when a level is chosen), none of the documented rejected parameters, detects a stream by status (never by header), succeeds only on `response.completed`, maps `response.incomplete` and a client-side output ceiling to `stopReason:'max_tokens'` with partial text (the only cap available while `max_output_tokens` is rejected), and scrubs the bearer from every error body before it becomes a message. The desktop's native fetch already runs with `maxRedirections:0` and a scope of `https://*:*` with loopback denied; the API base is pinned to `https://api.openai.com/v1` and `backend-api` is never called.

4. **Refresh is single-flight and rotation-safe.** One in-flight refresh per page realm (the five `runAgentTurn` call sites and the scheduler share it; `tauri-plugin-single-instance` guarantees one shell per file). Refresh when within 60 s of expiry **and** past `earliest_refresh_at`; a forced refresh after a 401 first checks the failing token is still current; the rotated set — access token, expiry, scopes, refresh token, ID token, `earliest_refresh_at` — is persisted together **before** the new ID token is re-verified (a JWKS outage must not lose the only valid refresh token); the refresh runs on its own timeout, never a turn's abort signal. `invalid_grant` / `refresh_token_reused` clear the tokens, keep the registration and name the state; a transient network failure keeps everything.

5. **Disclosure and failure are named, and nothing ever reroutes.** The chip reads *ChatGPT plan*; its popover and the Settings card say *Using ChatGPT plan* with a *Manage usage* link (`https://chatgpt.com/settings/usage`), OpenAI's required indicator. Four host-level error codes — `CHATGPT_SIGN_IN_NEEDED`, `CHATGPT_PLAN_NOT_GRANTED`, `CHATGPT_USAGE_LIMIT`, `CHATGPT_USAGE_UNAVAILABLE` — each with one sentence a person can act on; the limit message's primary action is Manage usage. `adapterKindFor({mode:'chatgpt'})` is `'chatgpt'` whether or not a session exists: a missing session is a **named result from the adapter**, never a fall-through to the demo brain, a key or a local model. This deliberately differs from BYOK's keyless → demo fall-through, for the owner's rule (never fall back silently), for ADR-0071 §4's rule (a brain that is not ready is NONE, never another brain) and because the chip must never say "demo brain" when the user chose their plan. A grant without `chatgpt.tokens.use.direct` is kept as signed-in-with-plan-disabled (OpenAI's guidance), refused by name for thinks, with a one-click re-consent (`prompt=consent`).

6. **Models and thinking levels come from the account, in OpenAI's vocabulary.** `GET /v1/models` after each sign-in and on Settings open; `visibility:'list'` entries only, server order, `slug` as the id, `display_name` as the label, `supported_reasoning_levels` / `default_reasoning_level` as the level vocabulary — measured, undocumented, used failing soft (no levels → no control, ADR-0070's Haiku rule). No hardcoded catalogue (ADR-0070 §4) and no mapping onto any other brain's words (§3). The default model and level are settings rows in the user file (`providerModel:chatgpt`, `providerEffort:chatgpt` — ADR-0046 §2's shape); per-app pins reuse `appModel:<appId>` model-only (the local-mode shape); an id outside the plan's list is shown as such and still routes. What ANSWERED is shown from the completed response's `model` (ADR-0059 rule 2).

7. **Sign-out** best-effort revokes the refresh token at the discovery document's `revocation_endpoint` (empty 200 = success; an unconfirmed revocation is told), deletes the tokens and the cached models locally, **keeps the registration** (client id + host id — OpenAI: *"Revoking this session does not delete the registered client"*; the next sign-in reuses it and omits `agent_name_hint`), and points to ChatGPT → Settings to disconnect the app entirely. Disconnects made there are not announced and are detected on the next failure.

8. **Scheduled "ask the AI" steps** treat a signed-in plan as a real brain (owner's default, reversible): allowed, limits refused by name, refresh unattended under §4; a signed-out plan is refused by name exactly as a keyless key is today.

9. **Nothing from OpenAI's DevKit is copied.** `@siwc/local` / `@siwc/react` are under a Noncommercial licence; this implementation is written against the docs and the measurements, with the DevKit read only as reference. The "Continue with ChatGPT" button uses OpenAI's published button format and logo asset (not the DevKit's), with provenance noted beside the asset.

## Alternatives considered

- **A BYOK provider `'chatgpt'`.** Rejected (§1): the refresh token would sit under `byok:` and roam; the key-presence derivation and the per-provider rows would misdescribe an account; sign-in/out, consent, limits and rotation have no seat in BYOK.
- **Tokens in `snug_secrets` (the ADR-0014 default).** Rejected (§2): rotation + per-host registration make the roaming copy a defect, not a feature; it would also need a new strip rule in every export/sync/share path.
- **The whole flow in Rust (reqwest streaming proxy + a JWT crate), the webview never seeing a token.** Deferred, not rejected: it is OpenAI's strongest guidance, but it duplicates reviewed TypeScript (PKCE, state, redirect guard, echo scrub, SSE parsing) with new unreviewed Rust on a credential path and two new crates, for a gain the threat model does not rate highly (R-1: a compromised host page already holds every BYOK key). Revisit with the keychain question.
- **macOS Keychain custody.** Deferred: R-3 places keychain wrapping out of scope pre-1.0; a new crate needs its own ADR; the `0600` file matches OpenAI's documented minimum and Codex's own `auth.json`. Queued.
- **Keyless/signed-out → demo brain, as BYOK does.** Rejected (§5).
- **A pinned model catalogue for the route.** Rejected (§6, ADR-0070 §4).
- **Ship behind a build flag until the public flip / ask OpenAI first.** The flip already happened; the track is self-serve for open-source local apps; a flag nobody flips is dead weight. Owner's call at the interview.

## Consequences

- Positive: a person with a ChatGPT plan and no key can use Snug on the desktop; the custody story stays local and honest; the mode rides every existing seat (pins, disclosure, scheduler gates, egress scrub) rather than a parallel path; the Responses adapter is reusable for a later host-kit brain.
- Negative / residuals (recorded in `docs/security/threat-model-delta-chatgpt-plan.md`): the session file is plaintext at rest, outside `.snug` passphrase encryption; the access token lives in host-page memory per send; the output ceiling is client-side and spends usage up to the abort; the Plus five-hour limit is shared across all the user's apps (their lever is a per-app limit in ChatGPT settings); the preview may start enforcing what the docs already forbid, which the adapter already respects; `packages/adapters` has never had a security lane (threat model §9) — this task's security review covers the new adapter and names that gap.
- Docs owed by the task: this ADR accepted; the delta + ledger (v3.14, R-124…); architecture (modes; the dependency-graph bullet now lists desktop and host as adapters' consumers); code-map rows; lessons (a stream is not its header; the zsh and Node-22 gate rules promoted from memory); next-steps deferrals; the privacy table row; the owner-walk runbook; ADR-0014/0021/0046/0059 status-line pointers to this ADR.
