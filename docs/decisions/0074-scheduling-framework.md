# 0074 — Scheduled tasks: one scheduler in every runner, kept in the user's file, honest about when it can run

- **Status:** proposed (owner-delegated 2026-10-09: Q1–Q10 of `TASK-20261009-scheduling-framework` are the defaults taken here, each reversible by one word; becomes `accepted` when the task's PR-A merges)
- **Date:** 2026-10-09
- **Task:** TASK-20261009-scheduling-framework
- **Relates to:** ADR-0011 (the agent is a capability) · ADR-0016/0017 (who may propose; requirement/grant) · ADR-0019 (scratch reads, approved writes) · ADR-0031 (cards are UI, not approval gates) · ADR-0033 + SPEC §17 (standing approvals — cited, not widened) · ADR-0034 (push hints, never content) · ADR-0036/0046/0063 (settings-keyed host state; no v7) · ADR-0062 (module stores outlive views) · ADR-0072 (one kit; `hostCapabilities()`; availability). No existing ADR is amended; the knowledge base's "never think on a timer" rule is amended in prose (§6).

## Context

A Snug app lives in the user's file and thinks through the user's own brain, but nothing happens unless the user is looking. The owner asked (2026-10-09) for a scheduling framework in every runner — the web playground, Snug for Mac, the host kit under both bindings — where the user schedules any task that may touch several apps, an app may schedule for itself with the user's say-so, the UI is plainer than ChatGPT's or Gemini's while cron runs underneath, missed runs are found and offered on the next open without redundant calls, and all of it lives in the `.snug` file.

Read from the code:

- **No Snug host is always-on.** Snug for Mac quits when its window closes (no tray, no autostart, no notification plugin — `apps/desktop/src-tauri/Cargo.toml`, `lib.rs:180-226`); the local host process exits a few seconds after its last agent session (`apps/host-mcp/src/runner.ts:359-381`) and never opens the database; a tab runs only while open, and a hidden tab's timers are throttled to about once a minute.
- **The storage rule exists.** SPEC-1.0 §8.1: host-side state that is neither app data nor a grant goes into `snug_settings` under a namespaced key; a new `snug_` table is a portable-format change. A v7 stamp would make every fielded v6 hub refuse the file (`packages/db/src/userdb/userdb.ts:1386-1394`; sync pulls `BAD_IMPORT` at `:3365-3372`) — ADR-0063's plan review killed exactly that.
- **Both channels an app needs already exist.** `snug:host-event` (host→app; no `instanceId`; R7: hints, never content) and `snug:app-event` (app→host; `packages/runner/src/host.ts:717-718`, passed through `SnugAppFrame`, no consumer in the playground). New event NAMES change no schema bytes; a new FRAME would change `schemas/`, the spec, the website pages and the whitepaper's frame inventory.
- **There is no headless runner** (`createRunnerHost` needs a live iframe; `RunView` is the one mount), but the data lane runs without the frame (`agent/{chatRouter,intentContext,dataTools}.ts`, `scratchRun` read-only by construction) — its turn body only has to be lifted out of `useBuilderChat.send`.
- **The standing-approval gate exists, unarmed, in memory** (`apps/playground/src/state/net.ts:192-226`; ADR-0033; SPEC §17 provisional). **The knowledge base forbids thinking on a timer** (`80-cdn-compatibility.md`, `10-overview-and-contract.md`). **Nothing cron-shaped is a dependency**, and `docs/conventions.md` wants an ADR for any new one.
- **Every proposal seat is strict**: a `schedules` field on `snug-app-bundle/1` would make older hubs refuse the whole bundle.

## Decision

1. **Scheduling is a host feature, not protocol.** A host that never schedules is still conforming. Nothing enters `packages/protocol/schemas/`, the envelope, the runtime contract or the local host's tool list. The spec is touched in the §8.1 transparency list of settings keys (the file format is spec) with a changelog entry, and the whitepaper gains one non-normative paragraph: the schedule lives in the user's file, so it travels with the file. The shapes (`packages/protocol/src/schedule.ts`) are an internal draft like `chat-intent.ts`, out of the published SOURCES.

2. **The file is the record, through namespaced settings rows.** `schedule:<taskId>` (the task), `scheduleRuns:<taskId>` (one bounded row per task — newest first, ≤ 50 entries, ≤ 64 KiB; `needs-you` rows survive until seen), `schedulerState` (watermark, leader, global pause, quiet hours). Typed accessors in `packages/db/src/userdb/schedules.ts`; keys single-homed in `app-settings-keys.ts`; ≤ 200 tasks, ≤ 16 KiB each; a credential-shaped string in a task is a parse refusal. `deleteApp` sweeps a task whose every step names the app and marks a surviving task's dead step. Export carries tasks and runs; **import disables every task** unless byte-identical to a local one (a task is executable intent, like endpoint settings and connections), while a trusted-origin pull keeps them.

3. **The host reaches an app over the channels it already has, as hints.** For an `app-run` step the host writes the input into the app's own kv (`snug:schedule:<runId>`), posts `host-event 'schedule-run' { taskId, runId }`, and reads the app's `app-event 'schedule-result'` (bounded, strict-parsed). An app proposes with `app-event 'schedule-request'`. R7 holds (the event carries ids, the content rides the kv); no new frame, no `host-ready` flag; an older host simply never sends the hint and an app's listener never fires.

4. **The proposal ladder — nothing but the user's act sets `enabled`.** The user (the Schedule page; the app's run header). The builder LLM (a `schedule_propose` tool whose single per-turn proposal is staged on the message like a data-write card — never `present_card`, which ADR-0031 keeps out of approvals). The app-attached chat (a `schedule` intent and lane). Running app code (propose-only: steps may name only the sender app, one pending per instance, a host-rendered confirm card, declines remembered per `(appId, proposalHash)`, at most five app-proposed tasks per app). Bundles carry no schedules: an app that wants one proposes it for itself on first run, which also covers starters and hand-ins through one mechanism.

5. **What a task may do, and the catch-up semantics.** Steps are `notify`, `app-run` (the app's own code, in a hidden frame with RunView's exact sandbox and CSP, or in the live frame when the app is open), and `app-think` (the app's brain under its runtime contract with the data lane's context; authored `SELECT`s run on the scratch copy so a tool-free brain still sees data; proposals wait on the run). A chain is a later think step citing earlier summaries. One engine (`apps/playground/src/schedule/`, a module store with `threadSessions`' swap discipline) ticks to the minute boundary but derives "due" from the wall clock; one ticker per origin by `navigator.locks` or a storage heartbeat; `reconcile()` runs at boot, on visibility/focus/online and when a tick fires far too late. Within a 15-minute grace a run is merely `late`; older occurrences are missed and **collapsed per task to one** candidate (`collapsedCount`), then handled by the task's policy — `ask` (the catch-up card; the default), `run-once`, `skip` (a `skipped` run so it is never asked again); a one-off task is always asked. The watermark advances only after every candidate is recorded. A run is keyed `(taskId, dueAt)` and never repeated; the queue runs one at a time under a bound; an interrupted run is recorded as such. Every run records which host ran it, and the UI says in words what this host can do.

6. **The unattended posture is structural.** A scheduled run uses a confirm gate that refuses outside an armed scope instead of parking a dialog, so a mutating connected call answers `NET_CONFIRM_REQUIRED` and the run is `needs-you`; data writes are proposals approved later through the existing card; no credential crosses the kv handshake or the result (parse refusal + scrub). Self-protection: pause after five consecutive failures, pause after thirty results nobody opened, a per-task daily AI-call cap, a global pause, quiet hours. **The knowledge base's rule becomes:** an app never calls the agent from its own timers; the host's scheduler is the one timer, and a task exists only because the user created or enabled it.

7. **Dependencies and seats.** Cron is hand-rolled (`schedule/cron.ts`: 5-field, no `L/W/#`; occurrences in the task's IANA zone via `Intl.DateTimeFormat`, DST gap skipped, overlap once). `tauri-plugin-notification` is the one new dependency (Rust + `@tauri-apps/plugin-notification`), behind an optional `platform.scheduler` seat with web and host fallbacks (web asks for permission only on an explicit Settings opt-in); `hostCapabilities()` gains `schedule: true`. The app-side hook ships in the module SDK and as a KB snippet; the embedded block changes in the starter release wave together with `useHostEvents`.

8. **Deferred, by name.** Desktop background mode (tray, keep running after close, launch at login — the next High task; it rewrites the close-flush handshake). Per-task standing approvals for unattended writes (ADR-0033's arm; SPEC §17). Published frames or a capability flag (a later wire revision if a second implementation asks). Bundle-carried schedules.

## Alternatives considered

- **Tables + a v7 bump.** Honest-looking; strands every fielded hub and contradicts §8.1. Rejected.
- **New published frames (`schedule-run`/`schedule-result`/`schedule-request`) and a `host-ready` flag.** Cleanest typing; costs a spec minor, the website pages, the whitepaper's frame inventory and an owner push before the first app can use it. Rejected for v1; the kv handshake gives the same contract on the channels that exist.
- **A scheduler in the local host process.** It never opens the database, dies with its session, and serves one binding. Rejected.
- **Periodic Background Sync / a service worker.** Chrome-only, discretionary, PWA-gated. Rejected; catch-up on open is the universal mechanism.
- **A cron library.** ~15–40 KB for a grammar this task uses a fifth of; the dependency policy prefers purpose-built code. Rejected.
- **Standing approvals in v1.** The gate exists, but arming needs a persisted, scoped grant with a kill switch and its own disclosure — an ADR's worth. Deferred (8).
- **`schedules[]` in bundles and starter manifests.** Strict bundles would make older hubs refuse the whole file; the app-proposes-for-itself ladder covers the same cases with one mechanism. Rejected.
- **A hub-wide "always allow" for scheduled network writes.** Far wider than any need; ADR-0033's reasoning verbatim. Rejected.

## Consequences

- Positive: one engine and one UI for every runner; schedules roam with the file; nothing on the wire changes; every unattended act is refused, proposed or journaled — never silently done; the knowledge base finally has a sanctioned timer.
- Negative / residuals: a task runs only while some Snug is open until background mode lands; two hosts on diverged copies can both run one occurrence before syncing (bounded to one extra call — writes are proposals); hub sync is whole-file CAS, so run-history appends on two devices surface as a divergence the user resolves; a hidden frame's run spends the user's brain while they are not looking (capped, paused when ignored, disclosed in the inbox); third-party app code can now run unattended inside the sandbox (C2 unchanged; the threat-model delta names the residuals).
- Docs owed: architecture (a scheduling section + the dependency graph note), code-map rows, glossary (schedule, task, run, catch-up, proposal, watermark), `docs/security/threat-model-delta-scheduling.md` + the fold, SPEC §8.1 line + spec-changelog, the whitepaper paragraph, product-vision, next-steps (Hue's sunset item unblocked; the background-mode task queued; the standing-approval follow-up).
