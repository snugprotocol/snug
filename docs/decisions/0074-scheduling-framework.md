## Context

A Snug app lives in the user's file and thinks through the user's own brain, but nothing happens unless the user is looking. The owner asked (2026-10-09) for a scheduling framework in every runner — the web playground, Snug for Mac, the host kit under both bindings — where the user schedules any task that may touch several apps, an app may schedule for itself with the user's say-so, the UI is plainer than ChatGPT's or Gemini's while cron runs underneath, missed runs are found and offered on the next open without redundant calls, and all of it lives in the `.snug` file.

Read from the code:

- **No Snug host is always-on.** Snug for Mac quits when its window closes (no tray, no autostart, no notification plugin — `apps/desktop/src-tauri/Cargo.toml`, `lib.rs:180-226`); the local host process exits a few seconds after its last agent session (`apps/host-mcp/src/runner.ts:359-381`) and never opens the database; a tab runs only while open, and a hidden tab's timers are throttled to about once a minute.
- **The storage rule exists.** SPEC-1.0 §8.1: host-side state that is neither app data nor a grant goes into `snug_settings` under a namespaced key; a new `snug_` table is a portable-format change. A v7 stamp would make every fielded v6 hub refuse the file (`packages/db/src/userdb/userdb.ts:1386-1394`; sync pulls `BAD_IMPORT` at `:3365-3372`) — ADR-0063's plan review killed exactly that.
- **Both channels an app needs already exist.** `snug:host-event` (host→app; no `instanceId`; R7: hints, never content) and `snug:app-event` (app→host; `packages/runner/src/host.ts:717-718`, passed through `SnugAppFrame`, no consumer in the playground). New event NAMES change no schema bytes; a new FRAME would change `schemas/`, the spec, the website pages and the whitepaper's frame inventory.
- **There is no headless runner** (`createRunnerHost` needs a live iframe; `RunView` is the one mount), but the data lane runs without the frame (`agent/{chatRouter,intentContext,dataTools}.ts`, `scratchRun` read-only by construction) — its turn body only has to be lifted out of `useBuilderChat.send`.
- **The standing-approval gate exists, unarmed, in memory** (`apps/playground/src/state/net.ts:192-226`; ADR-0033; SPEC §17 provisional). **The knowledge base forbids thinking on a timer** (`80-cdn-compatibility.md`, `10-overview-and-contract.md`). **Nothing cron-shaped is a dependency**, and `docs/conventions.md` wants an ADR for any new one.
- **Every proposal seat is strict**: a `schedules` field on `snug-app-bundle/1` would make older hubs refuse the whole bundle.

## Decision

1. **Scheduling is a host feature, not protocol.** A host that never schedules is still conforming. Nothing enters `packages/protocol/schemas/`, the envelope, the runtime contract or the local host's tool list. The spec is touched in the §8.1 transparency list of settings keys (the file format is spec) with a changelog entry, and the whitepaper gains one non-normative paragraph: the schedule lives in the user's file, so it travels with the file. The shapes (`packages/protocol/src/schedule.ts`) are an internal draft like `chat-intent.ts`, out of the published SOURCES.

2. **The file is the record, through namespaced settings rows.** `schedule:<taskId>` (the task), `scheduleRuns:<taskId>` (one bounded row per task — newest first, ≤ 50 entries, ≤ 64 KiB; `needs-you` rows survive until seen), `schedulerState` (watermark, leader, global pause, quiet hours). Typed accessors in `packages/db/src/userdb/schedules.ts`; keys single-homed in `app-settings-keys.ts`; ≤ 200 tasks, ≤ 16 KiB each; a credential-shaped string in a task is a parse refusal. `deleteApp` sweeps a task whose every step names the app and marks a surviving task's dead step. Export carries tasks and runs; **import disables every task** unless byte-identical to a local one (a task is executable intent, like endpoint settings and connections), while a trusted-origin pull keeps them.

3. **The host reaches an app over the channels it already has, as hints (PR-B).** For a *Run [app]* step the host writes the input into the app's own kv through a new host-side `kvSet/kvGet(namespace, key, value)` on the shared driver (`snug:schedule:<runId>`, ≤ 1 KiB, cleared with `null`), posts `host-event 'schedule-run' { taskId, runId }`, and reads the app's `app-event 'schedule-result'` — accepted only from the frame that received the hint, only for the one outstanding `runId`, only once, length-capped before the strict parse; stale keys are swept at boot. An app suggests with `app-event 'schedule-request'`. R7 holds (the event carries ids, the content rides the kv); no new frame, no `host-ready` flag, no new error code. Today neither SDK form can listen to a host event or send an app event, so the module SDK gains a subscription and `useSnugSchedule` (a new file; `types.ts` untouched) and the knowledge base ships the same shape as a snippet beside the copy-exactly block; an older host simply never sends the hint.

4. **The proposal ladder — nothing but the user's act sets `enabled` (PR-B).** The user (the Schedule page's sentence-first create bar; the editor route; the app's run header). The builder LLM (a `schedule_propose` tool whose single per-turn proposal is staged on the message like a data-write card — never `present_card`, which ADR-0031 keeps out of approvals). The app-attached chat (a `schedule` intent and lane, chosen by an EXHAUSTIVE lane switch so no lane can fall through to the builder's tools; and, on every brain, a deterministic offer when a message reads like a schedule). Running app code (suggest-only: steps may name only the sender app, one pending per frame generation, at most one request a minute, rendered as a run-header STRIP — never a modal — with *Schedule it* / *Not now* / *Stop suggestions from this app*; two declines mute the app, a Settings switch mutes every app, at most five app-suggested tasks per app, the hash over the semantic fields only). Every channel lands on ONE consent surface that shows what will run — prompt, queries, input, app, hosts, daily cost — and ONE writer. Bundles carry no schedules: an app that wants one suggests it for itself on first run, which also covers starters and hand-ins through one mechanism.

5. **What a task may do, and the catch-up semantics.** Steps are *Remind me* (`notify`), *Ask [app]'s AI* (`app-think`: the app's OWN transport — its runtime contract, its model pin, the R-9 scrub — with NO tools and NO connected calls; the host assembles the app's overview, its DDL, the step's user-typed `SELECT`s run on the scratch copy, and the prompt; the reply is text, and a fenced proposals block is dry-run on the scratch copy into pending *changes waiting for your OK* that the engine never executes) and, in PR-B, *Run [app]* (`app-run`: the app's own code in a hidden `SnugAppFrame` — the same component as RunView, so the same sandbox and CSP — or in the live frame when the app is open; the hidden frame never registers as the app's live host, a visible open aborts it, it is refused where R-5 is open). Steps are INDEPENDENT: no step's content enters another step's prompt or another app's vendor — a multi-app schedule is several steps on one result page. One engine (`apps/playground/src/schedule/`, a module store with `threadSessions`' swap discipline, idempotent boot joined to every re-init chain) ticks to the minute boundary re-armed from the wall clock, derives "due" from the clock, and is the one ticker per origin and file (a blocking `navigator.locks` request keyed on the file's uuid; where locks are absent or reject — an opaque origin, `file://` — this context leads and says sibling tabs cannot be seen); `reconcile()` runs at boot, on visibility/focus/online and when a tick fires far too late, over the window `(max(watermark, enabledAt, startsAt), now]`. Within a 15-minute grace a run is merely `late`; older occurrences are missed and **collapsed per task to one** candidate (`collapsedCount`); a candidate older than the schedule's freshness window (one period, at most 7 days) is written `skipped` without a card; the rest follow the schedule's policy — `ask` (a PERSISTED `pending` run row the missed card reads), `run-once`, `skip` — whose default is derived from cost: a reminder-only schedule catches up silently, anything that spends the brain or the network asks; a one-off is always asked. The watermark advances only after every candidate row is written. A run is CLAIMED as `running` before anything executes and keyed `(taskId, dueAt)`; a task's `ranThrough` is the dedupe record that survives pruning; the queue runs one at a time under a bound; an interrupted run is recorded as such and stale `running` rows are swept at boot. Time follows the device by default and may be pinned to a zone. Every run records which host ran it, and the UI says in words what this host can do — in the editor and on the empty page, not only in Settings.

6. **The unattended posture is structural — no NEW powers.** A scheduled run's net handler carries a STANDALONE confirm gate that always refuses a mutating call (it never consults the session-remember or standing gates, so a remembered or armed grant cannot leak into an unattended run), answering the existing `NET_CONFIRM_DENIED` with a scheduled message; the run is `needs-you` with one action (*Run now and review*, which opens the app visibly under the ordinary gate). The AI never writes data: proposals are stripped from run rows on every import, pull and export, expire after seven days, and re-dry-run on approval, so a foreign file can never plant an approval card. No credential crosses the kv handshake, a task, a result or an inbox entry (parse refusal, plus the value scrub against the stored secrets). Notifications are host-decided: plain text, length-capped, prefixed with the app's name, generic by default, rate-limited; an app's `notify` is a suggestion. Self-protection: frequency floors (15 min for app-, builder- and chat-proposed schedules, 5 min for the user's own), global daily ceilings on AI and network calls with an 80 % warning (the hidden frame's own thinks are counted by a capping transport), pause after five consecutive failures, pause after thirty results nobody opened (seen only by a user gesture), a global pause, a shared or agent update of a named app pausing the schedule until re-enabled. The one accepted residual: a scheduled *Run [app]* runs the app's own code with the powers it already has over its own data. **The knowledge base's rule becomes:** an app never calls the agent from its own timers; the host's scheduler is the one timer, and a task exists only because the user created or enabled it.

7. **Dependencies and seats.** Cron is hand-rolled (`schedule/cron.ts`: 5-field, no `L/W/#`; occurrences in the task's IANA zone via `Intl.DateTimeFormat`, DST gap skipped, overlap once). `tauri-plugin-notification` is the one new dependency (Rust + `@tauri-apps/plugin-notification`), behind an optional `platform.scheduler` seat with web and host fallbacks (web asks for permission only on an explicit Settings opt-in); `hostCapabilities()` gains `schedule: true`. The app-side hook ships in the module SDK and as a KB snippet; the embedded block changes in the starter release wave together with `useHostEvents`.

8. **Deferred, by name.** Desktop background mode (tray, keep running after close, launch at login — the next High task; it rewrites the close-flush handshake). Per-task standing approvals for unattended writes (ADR-0033's arm; SPEC §17). Published frames, a capability flag or a new error code (a later wire revision if a second implementation asks). Bundle-carried schedules. Step chaining and cross-app content flow (its own disclosure). Per-task caps and quiet hours. A pre-run snapshot with undo for *Run [app]*. The weather starter's suggestion rides its own owner-timed PR (a starter edit re-pins the published package — ADR-0073).

## Alternatives considered

- **Tables + a v7 bump.** Honest-looking; strands every fielded hub and contradicts §8.1. Rejected.
- **New published frames (`schedule-run`/`schedule-result`/`schedule-request`) and a `host-ready` flag.** Cleanest typing; costs a spec minor, the website pages, the whitepaper's frame inventory and an owner push before the first app can use it. Rejected for v1; the kv handshake gives the same contract on the channels that exist.
- **A scheduler in the local host process.** It never opens the database, dies with its session, and serves one binding. Rejected.
- **Periodic Background Sync / a service worker.** Chrome-only, discretionary, PWA-gated. Rejected; catch-up on open is the universal mechanism.
- **A cron library.** ~15–40 KB for a grammar this task uses a fifth of; the dependency policy prefers purpose-built code. Rejected.
- **Standing approvals in v1.** The gate exists, but arming needs a persisted, scoped grant with a kill switch and its own disclosure — an ADR's worth. Deferred (8).
- **`schedules[]` in bundles and starter manifests.** Strict bundles would make older hubs refuse the whole file; the app-proposes-for-itself ladder covers the same cases with one mechanism. Rejected.
- **A hub-wide "always allow" for scheduled network writes.** Far wider than any need; ADR-0033's reasoning verbatim. Rejected.
- **Running *Ask the AI* on the builder chat's data lane.** It is a different brain (the builder prompt, tools, a session-bound closure in `useBuilderChat`) with a different scrub; lifting it costs a refactor nobody needs. Rejected for the app's own transport, tool-free.
- **A modal confirm for app suggestions.** Fires mid-use right after a first fetch — the nag channel ADR-0016 feared, and two surfaces for one act. Rejected for the run-header strip.
- **Persisting executable proposals in the file.** An imported `.snug` could plant a host-looking approval card over real data. Rejected: proposals never roam.

## Consequences

- Positive: one engine and one UI for every runner; schedules roam with the file; nothing on the wire changes; every unattended act is refused, proposed or journaled — never silently done; the knowledge base finally has a sanctioned timer; three PRs, each walkable on its own.
- Negative / residuals: a task runs only while some Snug is open until background mode lands; two hosts on diverged copies can both run one occurrence before syncing (bounded to one extra call — writes are proposals); hub sync is whole-file CAS, so run-history appends on two devices surface as a divergence the user resolves; a hidden frame's run spends the user's brain while they are not looking (capped, paused when ignored, disclosed in the inbox); third-party app code can now run unattended inside the sandbox (C2 unchanged; the threat-model delta names the residuals).
- Docs owed: architecture (a scheduling section + the dependency graph note), code-map rows, glossary (schedule, task, run, catch-up, proposal, watermark), `docs/security/threat-model-delta-scheduling.md` + the fold, SPEC §8.1 line + spec-changelog, the whitepaper paragraph, product-vision, next-steps (Hue's sunset item unblocked; the background-mode task queued; the standing-approval follow-up).

## Amendment (2026-10-09, TASK-20261009 Gate 5 — PR-A's diff review folded)

Two fresh-context lenses (security 13 findings, maintainability 22) over the PR-A diff; the
folds that change what this ADR says:

- **§2 — the import guard compares executable INTENT, not bytes.** `canonicalScheduleIntent`
  (steps, spec, cron, window, policy, alert, owner, provenance, title) is the byte-identical
  check; the counters and `ranThrough` are engine state, so a run between a backup and its
  restore no longer disarms every schedule. The engine never stamps `updatedAt` (only user acts
  do). An untrusted import also drops every `pending` and `needs-you` entry of a demoted task,
  retires any claim dated in the FUTURE, drops future-dated run entries and clamps `ranThrough`
  to now — a planted candidate can never be offered as "missed".
- **§2 — a `needs-you` row the user has opened is history** (prunable, clearable); unseen ones
  are not. A refused claim write is surfaced (`lastError`, a counted failure), never silent.
- **§4/§6 — one enable path for an imported schedule.** The row's switch routes an imported
  schedule to the editor's consent panel; `setTaskEnabled` runs the frequency floor and refuses
  `imported` until reviewed; `runNow` refuses a disabled schedule; catch-up acts skip disabled
  schedules; the queue never claims a disabled task except for the user's own manual run.
- **§5 — a promoted tab reloads.** A follower's in-memory copy is stale after the leader's
  writes, so promotion marks `needsReload` and idles behind a strip instead of reconciling; the
  writer-lock + re-open hand-over is queued (threat model R-60).
- **§5 — proposals name their app.** Every pending data change carries the `appId` of the step
  that produced it; the approval surface applies it to that app or refuses. A nested
  `SELECT`/`FROM` inside a proposed statement is refused (literal-valued DML only).
- **§5 — `until … for N times` counts recorded runs**, not calendar slots, so a paused-then-
  resumed schedule still gets its remaining fires. A window the 400-day bound truncates is
  clamped to the freshness window first.
- **§6 — the custom-cron floor is computed from the parsed fields**, never sampled (a sparse-
  then-dense minute set passed a nine-occurrence sample at 24 fires an hour).
- **§6 — the app-drift pause (`noteAppVersion`) is PR-B's**: its callers are the shared-update
  and hand-in apply paths, which PR-B wires with *Run [app]*. PR-A exports the hook and tests
  the rule.
  *(Landed in PR-B's Gate-5 fold: the pause moved to the db altitude — `schedule/appDrift.ts`
  `pauseSchedulesForAppVersion`, which the host kit's hand-in (`apps/host/src/handin.ts`, the silent
  update and the taken offer) and the shared-shelf update (`share/installShared.ts`) call with the db
  they hold; `noteAppVersion` delegates to it. Both update confirms name the schedules the update will
  pause — `run/UpdatePausesNote.tsx`.)*
- Templates have ONE registry (`editorModel.templateFill`); status words and relative time have
  one home each; the hidden "never let apps suggest schedules" switch waits for PR-B's reader.

*§3, §4 and §7 are implemented in PR-B (2026-10-09) — threat delta `docs/security/threat-model-delta-scheduling-proposals.md` (model v3.5, R-61 … R-69). The §6 value scrub against the stored secrets stands at the EXECUTOR for the scheduled handler as for RunView's (`packages/auth` `connected-fetch.ts`; pinned at the Gate-5 fold by `scheduledGate.test.ts`'s echo row — R-54 closed). *Amended 2026-10-09 by the owner (TASK-20261009-scheduled-run-open-app): **a scheduled job runs on time, without asking, whether or not the app is open.** §4's Gate-5 refusal of an unattended run of an OPEN app and PR-B's abort-on-open are retired; an unattended *Run [app]* always runs in its own hidden frame under the refusing gate and the counting transport, beside a visible copy if there is one, never in the live frame. Unchanged: a mutating connected call in an unattended run is still refused by name (*needs you*). Accepted residual: two instances of one app over one store (threat model R-70).*

*Amended 2026-10-10 by ADR-0075 (TASK-20261010-cross-app-access): §8's deferral "published frames, a capability flag or a new error code (a later wire revision if a second implementation asks)" is superseded for ONE class of capability. Access between apps carries app-authored SQL in and up to 192 KiB of another app's rows out — content that must cross the bridge in-band and transiently, which the kv handshake cannot carry (`HOST_KV_VALUE_MAX_BYTES` ≈ 1.3 KiB) and must not persist in the reader's namespace. The trigger for a wire revision is therefore stated as: a capability whose content must cross the bridge in-band and transiently gets frames; a capability whose content is ids plus a small input the app already owns keeps the kv handshake. Scheduling stays off the wire; ADR-0075 is the first wire revision after 1.0.*
