# 0077 — One instance per app: a scheduled or on-demand run executes where the app lives

- **Status:** proposed (TASK-20261010-host-broker PR-1, 2026-10-10; owner-delegated — Q5–Q7 of the task file are the defaults taken here, each reversible by one word). Becomes `accepted` when PR-1 merges; the same commit sets ADR-0074's status to `accepted (amended by 0075, 0077)`.
- **Date:** 2026-10-10
- **Task:** TASK-20261010-host-broker
- **Amends:** ADR-0074 §4's Gate-5 fold ("a run the user did not start never rides an open app — presence is not consent") and its 2026-10-09 amendment ("an unattended *Run [app]* always runs in its own hidden frame … beside a visible copy if there is one, never in the live frame"). The principle stands; the mechanism changes: a run rides the live frame only under a gate that asks the present user and never a remembered approval. Retires threat-model R-70 for the delegated case (the headless case has no second instance to collide with).
- **Relates to:** ADR-0074 §5/§6 (the executor, the refusing gate, the counting transport, the ceilings — all kept for the headless path), ADR-0033 (the standing gate a delegated run must NOT consult), ADR-0062 (module stores outlive views — the placement store), ADR-0076 §6 (a refresh is a run and uses this placement).

## Context

The owner saw a scheduled job run while the app was open and a second copy of the app appear beside it (2026-10-10): "it struggles and tries to instantiate another db copy, which is not the right approach." Read from the code:

- `executeAppRun` (`apps/playground/src/schedule/appRun.ts:311-319`) chooses on the trigger alone: `manual` → the live frame (no announce wait, uncounted, the page's ordinary gate); `due`/`late`/`catch-up` → a hidden `SnugAppFrame` ALWAYS, open app or not. Two instances of one app then share ONE sql.js connection; the hidden one's binding refuses transactions and imports (`scheduledDbDriver.ts`), the visible one's does not — threat-model R-70 and the open-app delta's R-a. A hidden run's 401 lights the open copy's reconnect chip (R-b).
- The Gate-5 fold that put the hidden frame there guarded a real hazard: the live frame's net handler is bound at COMPOSE time to the standing→session gate chain (`state/net.ts:340,360`; `run/appRuntime.ts:120`; RunView passes no gate), so a timer-driven run on the live frame could have a remembered or armed approval answer an unattended write. "Presence is not consent" (lesson `:211`) is right. The hidden frame was the mechanism, not the principle.
- The live registry (`state/appHosts.ts`) registers on MOUNT, before the frame announces, with no generation and no readiness; *run now* navigates then hints before the app's listener exists — a 90 s `failed`.
- The knowledge base already requires scheduled handlers to be idempotent by `runId` and warns "you may not be the only instance" (`85-scheduled-runs.md:106-136`).
- The host kit and the desktop render the playground's `App`, so one engine runs everywhere; `ScheduledRunHost` is mounted once at `App.tsx:360`.

## Decision

1. **One instance per app, per tab.** At any moment an app has at most one running instance in this tab: the visible frame when the app is open, the hidden frame otherwise, or none. Two frames of one app never share the connection again. (The leader tab runs the scheduler; an app open in a FOLLOWER tab is not live here — a residual the delta names. "Headless" in the task's prose means the hidden frame; the noun in code and copy stays *hidden frame*.)

2. **Placement is the host's, by one rule.** `schedule/runPlacement.ts` decides for every unattended run and every on-demand run (a refresh, ADR-0076 §6): the registry HAS the app (registered in this tab) → **delegated** to the live frame, which then waits for the frame to be announced (≤ the hidden path's own 10 s, else `no-handler`); otherwise → **hidden** (today's hidden path, unchanged: the refusing gate, the counting transport, `scheduledDbDriver`, the generation-0 session-grant rule). Presence means "RunView mounted", not "the tab is visible": in a backgrounded tab the dialog below simply times out to *needs you*. Host-native work (ADR-0076 §9) needs no frame and does not enter placement.

3. **A delegated run rides a run-scoped ask gate, and the frame stays ask-only afterwards.** The live frame's net handler (the frame path only — the wizard probe, the provider tools and the sidecar pump keep the ordinary chain) is composed once with a gate that consults a module store PER REQUEST: while a run is in flight for this app, a mutating connected call skips the session-remember AND the standing gates and goes to the ordinary confirm dialog under a host-composed title ("a schedule wants to make a change") whose body quotes the schedule and says in one breath that this was not the user's click, that *allow once* means once and that silence means no; no answer within 60 s → `NET_CONFIRM_DENIED` → the step is `refused`, *needs you*, with a sentence that says whether the user declined or nobody answered. One outstanding ask per run: a second mutating call while one is parked, or any call after a refusal, is refused at once. A parked scheduled confirm is withdrawn the moment its run ends. **Sticky:** once a delegated run has begun on a frame generation, every later mutating call from that generation — until the frame retracts or remounts — is asked once too (a handler cannot post its result first and POST afterwards into a remembered grant); the user's own *remember for this session* is unavailable on that frame until they reopen the app. The access handler closes the same way for the run's window: an app ask is answered `ACCESS_UNATTENDED` and a read needs the grant's *also while I'm away*. Outside a run and off a touched frame the ordinary chain applies unchanged. GET and HEAD never reach a gate, as today. A human clicks, or nothing happens — presence is still not consent.

4. **Counting follows the run.** Calls on the live frame while a run is in flight are counted on the run row (`calls.ai`, `calls.net`), never refused mid-run; the day's ceilings are enforced BEFORE dispatch (`capped` without dispatch, when either counter has no headroom for one more call); tallies are summed across a handover; a tally that crosses a ceiling inside the window marks the run `capped` without stopping app code. A user's own click inside the ≤ 90 s window may be over-attributed; accepted and recorded in the threat delta (nothing on a row discloses placement in PR-1). Auth-shaped failures inside any scheduled run are attributed to the run, and the reconnect chip says so (R-b closed).

5. **A run follows the app — once, and never after a change went out.** Opening the app while a hidden run is in flight cuts that attempt and re-dispatches the SAME `runId` to the live frame once the hidden frame has unmounted and the live one has announced; closing the app mid-delegated-run re-dispatches hidden. At most one handover per run (a second ends the step `failed` by name). A delegated attempt in which the user allowed a mutating call is never handed over: a retraction after that ends the step `failed` ("closed after a change was sent") rather than running a handler whose POST already went out. A frame remount mid-run is not a handover in PR-1 (the attempt ends by the result bound, as a manual run does today). One deadline per step: a re-dispatch runs inside what the first dispatch left of the 90 s. The kv input is written per dispatch and cleared once at the end; the KB's idempotency rule is what makes the re-dispatch safe, and its text now says why.

6. **Readiness is explicit.** Registry entries carry `{generation, announced}`; registration stays keyed on the app (a remount must never read as a retraction), a separate effect sets the generation and clears `announced`, and RunView marks `announced` from the announce; every hint — manual too — waits for it ≤ 10 s (the hidden path's own bound) else `no-handler`. A `schedule-result` settles a delegated run only from the generation that was hinted. The *run now* race closes with it.

7. **What stays.** `ScheduledRunHost`, `scheduledDbDriver` (cheap defence against a crash-stranded transaction), `scheduledConfirmGate` and `scheduledTransport` for the headless path; the hidden frame's generation-0 rule (D30, R-78); `manual` runs ride the live frame under the ordinary gate exactly as today (R-62).

## Alternatives considered

- **Keep the hidden frame beside the open copy (today).** Honest about the gate but two instances over one connection (R-70) and the UI the owner rejected. Rejected.
- **Refuse unattended runs while the app is open (PR-B's S1).** The owner reversed it on 2026-10-09 for a reason: a 07:00 schedule must not fail because the app is open at 07:00. Rejected.
- **A lock between the two instances.** Serialises statements but not intent (a visible transaction still captures a scheduled write), and keeps the second copy. Rejected.
- **Recomposing the live frame's handler per run.** The runtime is composed once with the frame; a swap mid-session is a remount. Rejected for a gate that consults a store per request.
- **Letting the delegated run use the page's remembered approvals.** The hazard the Gate-5 fold named. Rejected.
- **Waiting for a headless run to finish before the app opens.** Up to 90 s staring at a chip. Rejected for handover.

## Consequences

- Positive: the owner's R2 verbatim; R-70 retires for the delegated case and R-b closes; one copy of an app ever touches its data; the user sees at most a run-header chip ("running *Morning forecast*…") and, for a write, a dialog that names the schedule.
- Negative / residuals (the delta names them): a delegated run spends the user's brain and network in the open app's name (counted, capped before dispatch, not stopped mid-window); over-attribution of a user's click during a run; a handover costs one re-dispatch and relies on idempotent handlers (the KB rule, now explained); a user who declines the dialog gets *needs you* exactly as before; a frame that hosted a scheduled run loses *remember for this session* until reopened; the live frame's ordinary db binding and unscrubbed replies are the open app's own powers; one instance holds per TAB, and presence is "mounted", not "visible".
- Docs owed: ADR-0074 status + this amendment line; `docs/threat-model.md` R-62 and R-70 rewritten and a new delta; lessons `:211` amended; KB 85 rules + the SDK header; architecture + code-map + glossary (*delegated run*, *headless run*, *handover*, *placement*).

## Folded from the Gate-2 reviews (2026-10-10)

Four fresh-context plan reviews of PR-1's contract (security 16 findings, feasibility 20, design 13, scope 18; five blockers) tightened the decision without changing its shape. What changed, so the ADR reads true against the contract (the task file's "PR-1 — Gate-2 contract v2" carries the reasoning):

- **The gate's window is the frame generation, not the run** (security blocker 1): a handler could defer a POST past the run's end into a remembered grant; the ask-only posture now sticks to the generation that hosted a delegated run.
- **The access door closes for the run's window** (security blocker 2): a timer-fired run could otherwise park a cross-app consent sheet and read a session grant as *attended*.
- **A parked scheduled confirm is withdrawn when its run ends, and one ask is outstanding per run** (design blocker 1, feasibility blocker 2, security 4): a timed-out dialog otherwise stayed at the queue head, blocked every other confirm, and could send a POST for a run already recorded.
- **Registration never retracts on a remount** (feasibility blocker 1, security 7): the generation is set by its own effect; the remount handover is dropped (scope 5) — it was the whole reason for the readiness surface.
- **One deadline per step** (scope blocker 1): a handover could otherwise run past the queue's 120 s bound and be recorded `interrupted`.
- **Never hand over after a grant; sum tallies across attempts; accept a result only from the hinted generation; await the hidden frame's unmount before the live hint** (security 5, 6, 8, 9; design 6).
- **Only the frame path takes the run-scoped gate as its default** (security 3, feasibility F7): the chat's provider lane, the wizard probe and the sidecar pump keep the ordinary chain.
- **Manual runs also wait for readiness** (feasibility F4, scope 2): the *run now* race IS a manual run.
- **Fewer seams** (scope 6–8, 12): the placement store carries the run's record (calls, refusals, grants); no `placed` seam, no `RunningView.placement`, no new dispatch file in PR-1; `mode: 'manual' | 'unattended'`.
- **Copy** (design 2–4, 9–10, 13): a host-composed title; "run" stays a verb; three *needs you* sentences that say whether the user declined, nobody answered, or the app asked again; the app's display name on the tag; the capped reason names its limit.
- **The noun is "hidden frame"** (scope 15); `Placement = 'live' | 'hidden'`.
