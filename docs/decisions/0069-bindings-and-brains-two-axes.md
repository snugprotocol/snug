# 0069 — Bindings and brains are two axes; MCP is Binding B's spawn channel, never a binding and never a brain

- **Status:** accepted (the owner's direction of 2026-09-13: "focus on path 2 first; record the other path for a later phase; keep the distinction clear"; the naming half is Q1 of the task and lands with it)
- **Date:** 2026-09-13
- **Task:** TASK-20260913-binding-b-marketplace-plugin
- **Amends:** ADR-0065 §2 (the binding table gains its second axis) · ADR-0068 (naming; the brain shim's lifetime; the readiness states)

## Context

The owner re-read Binding B on 2026-09-13 and saw two paths in it:

1. **The artifact path.** The kit boots as a Claude artifact (Binding A). The artifact page cannot fetch anything, so connected apps would need a *local* process as their network side, reached through the artifact runtime's `mcp` capability — which only exists where a local process can run (Claude Desktop, Cowork), never on claude.ai.
2. **The plugin path.** The plugin makes the agent's host spawn the local process; the process serves the kit on `127.0.0.1` with connections on, proxies the executor's network side itself, and runs the apps' thinks on the user's own `claude` CLI as a child process — no key, no mode, no configuration. Slower per think than the viewer-billed `sample`, but it works for every CLI-shaped agent (Claude today; Codex, Hermes, OpenClaw, Ollama next) and it is the path a non-technical user can walk: install one plugin, open Snug.

The owner's questions were which path to build first, whether the second one "really needs MCP" or is "another AI mode altogether", and whether it should be a separate binding.

**What is actually merged (PR #177, `730198c`) is path 2.** ADR-0068's process is the plugin path exactly: `.mcp.json` → the host spawns `snug-mcp.mjs` → the local page → `/fetch` proxy → `claude -p`. MCP's whole role in it is the four-tool control plane (`snug_status`, `snug_open`, `snug_hand_in`, `snug_list_apps`) and the fact that a plugin's `.mcp.json` is the one declarative "run this process for the user" channel that Claude Code, Cowork and Codex all honour. MCP is not the brain (sampling is deprecated and unsupported — ADR-0068) and not the network path (the page's executor calls the process over loopback). The confusion came from the names: `apps/host-mcp`, `snug-mcp.mjs`, `check-host-mcp`, `@snugprotocol/host-mcp` all say "mcp" for a thing whose identity is "the local host process". The owner read the plumbing as the product — exactly what ADR-0061 says a name must not do.

Measured this session, on the owner's Mac:

- **A cold `claude -p` costs ~3.5 s of process overhead per call on 2.1.270** (5.0 s wall against 1.5 s of model time). **One warm child on `--input-format stream-json` answers follow-up turns in ~1.3–1.4 s** — the model time alone — keeps the conversation (turn 2 answered from turn 1), reuses the prompt cache, and streams token deltas under `--include-partial-messages`. Startup to the first `system/init` event is ~2.8 s and costs no tokens, so a child can be warmed before it is needed.
- **The owner's CLI had silently stopped working.** 2.1.211 answered every call with `400 … does not support this model; version 2.1.251 or newer is required. Run 'claude update'`. ADR-0068's probe would have reported that as `unknown`. The brain can break between sessions without anyone touching Snug, so `outdated` is a named state with the CLI's own remedy.
- **A GUI-spawned process has no user PATH.** `launchctl getenv PATH` is empty on this Mac; `node` and `claude` both live under nvm. A plugin whose `.mcp.json` says `command: node` would fail under Claude Desktop/Cowork on the very machine it was built on, and `claude` on the same PATH would read as `absent`.
- **Claude Desktop ships no macOS `claude` CLI.** What it keeps under `Application Support/Claude/claude-code-vm/<version>/claude` is a Linux ARM64 executable for Cowork's VM. A Cowork user who never installed Claude Code has no brain for Binding B until they run the one-line installer and `/login`. The Agent SDK is not a way around that: it authenticates with an API key, not the user's subscription (verified 2026-09-13), which ADR-0065 D15 excludes.
- **The community plugin marketplace is the open door.** Anthropic's curated marketplace has no submission process; the community one takes a form and pins a commit SHA. Plugins are cloned whole, so a ~5 MB distribution repo is fine.

## Decision

1. **Two axes, stated once.** A binding is *where the body runs and how the host reaches it*: **A** the kit as an artifact page, **B** the kit served on loopback by a plugin-spawned local process, **C** a widget. A brain is *what answers the apps' thinks*: the viewer-billed `sample` / `window.claude.complete` (A only); **the user's own agent CLI as a child process** (B; `claude` today, `codex exec` / Hermes / OpenClaw / Ollama as T3's remainder); the demo brain (the fallback everywhere). The tables in ADR-0065 §2 and the program record read with both axes from now on. **Path 2 is Binding B with the child-CLI brain — it is not a new binding letter.** Relettering merged, threat-modelled work to say what ADR-0068 already says would be churn with no reader.

2. **Binding B is the primary path for Claude Code, Claude Desktop/Cowork and (T9) Codex.** It is the one binding with connected apps, the one with the file on disk, the one that needs no BYOK, and the one whose brain is portable across agents. Binding A stays what it is — the zero-install demo inside claude.ai and the fallback recipe when no local process can run.

3. **MCP is named for what it does, nowhere else.** The process is the **local host process**; the package, the bundle, the gate and the npm name follow: `apps/local-host`, `dist/snug-local-host.mjs`, `check-local-host`, `@snugprotocol/local-host` (Q1 — recommended and executed as the task's last, separately revertible commit, before anything is published; after the first publish the npm name is frozen). "MCP" appears in exactly two places: the `.mcp.json` file the hosts require, and the `src/mcp/` directory holding the JSON-RPC framing. Product copy is unchanged: "Snug apps run inside Claude Code / Cowork / Codex", never "Snug MCP server" (ADR-0061, ADR-0068 §9).

4. **Path 1 is recorded as a later phase, merged with the queued MCP-connector item: "Binding A-connected".** Same mechanism either way — the artifact page calls out through the runtime's `mcp` capability — differing only in who answers (a hosted connector, or a local process the desktop app runs). It stays out of scope until the marketplace milestone ships, and its spike must answer three questions before any design: does the artifact runtime's `mcp` capability reach a *local* stdio server under Claude Desktop/Cowork at all; does a page-initiated call transit Anthropic's servers (a credential held by the page would then leave the machine — a C1 question, not a UX one); and what, if anything, the model sees of such calls. The other later-phase remedy recorded here is **S12, the agent as the brain over the control plane** — the only way a Cowork user with no CLI gets a brain without a key — deferred with its threat-model row still owed (ADR-0068).

5. **The child-CLI brain keeps a warm child.** `brain-claude` owns a pool keyed by the system prompt (each app's runtime contract is its own system prompt — ADR-0018): one **pre-warmed** child per system prompt that has been started but sent nothing (free: no tokens until the first turn); a request whose messages **extend the transcript** a child already holds sends only the new user turn (the builder's chat, prompt-cached); a single-turn request takes a virgin child and **never inherits** a previous turn (an app's think is self-contained by ADR-0018 — a used child is not reused for an unrelated request). Every child is reaped on stop, on parent death, on an abort, on an error, and after an idle TTL; the count is capped. The shim **streams** the child's text deltas to the page as SSE chunks, so a 90-second app build shows its tokens instead of a silent wait; the seat's `streaming` flag stays an app-facing declaration, untouched. The child env allowlist, never `--bare`, and the argv posture of ADR-0068 §5 stand.

6. **Readiness names five states and finds the binary itself.** `probeBrain` returns `ready | logged-out | outdated | absent | unknown`, each with a one-sentence remedy in the CLI's own words where it has them. The binary is resolved from PATH **and** the known install roots (the native installer's `~/.local/bin`, `~/.claude/local`, Homebrew, nvm/volta/fnm), because the process's PATH under a desktop host is not the user's shell PATH. The same rule launches the process: `.mcp.json` runs `sh ${CLAUDE_PLUGIN_ROOT}/scripts/snug`, a POSIX launcher that finds a Node ≥ 20 in the same roots and execs the bundle, or prints the one-line remedy and exits non-zero. Downloading a self-contained runtime when none exists (the WhatsApp helper's ADR-0060 pattern) is the next step, gated on a Release — an owner act.

7. **The plugin is the distribution repo's root.** `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json` (a marketplace of one whose source is `./`), `.mcp.json`, `skills/snug/SKILL.md` + `references/`, `scripts/{snug, snug-local-host.mjs, snug-host-local.html, snug-host.html}`, `README.md`, `LICENSE`. `scripts/build-plugin.mjs` assembles it from sources on every gate run into the gitignored `dist/plugin/`; nothing generated is committed here (D6's committed staging tree is superseded — it bought reviewability the gate now provides, and 4.5 MB of pages per change is not a diff anyone reads). The SKILL.md **source** lives in the prompt store (`packages/knowledge/prompts/skills/snug/SKILL.md`, ADR-0004) and is **excluded from `content.ts`** by name (D6's "not in every bundle" holds); its `references/` are the app-authoring KB rendered by the knowledge package (headers stripped, placeholders resolved, headings preserved). Both kits ship inside the plugin for now; D11's Release-asset fetch waits for the release it needs.

8. **Marketplace = the community marketplace, prepared and printed.** The distribution repo (`snugprotocol/snug-skill`) is created and pushed by the owner from the assembled tree; the submission form is filled by the owner with the product-vision wording (C4); every command is printed by the task and performed by nobody else.

## Alternatives considered

- **Reletter path 2 as a new binding (D) and keep B for the artifact-plus-MCP path.** Rejected: B *is* path 2 in the code, the ADR, the threat-model delta and eleven e2e specs; the artifact-plus-MCP path is unbuilt and unmeasured. Renaming the built thing after the unbuilt one inverts the record.
- **Keep the `host-mcp` names and fix the confusion in prose.** Rejected: the owner is the first reader and read them as the identity; the names are cheap to change before the first publish and expensive after.
- **The Agent SDK as the brain.** Rejected: it does not reuse the user's login (API key or a cloud provider), which is precisely the configuration D15 forbids asking a user for; the CLI is the user's subscription.
- **A compiled single-file process (Node SEA) so the plugin needs no Node.** Deferred: ~100 MB per architecture in a git-cloned plugin; the helper-runtime download (ADR-0060) is the proven shape and needs only a Release.
- **Hooks instead of `.mcp.json` to spawn the process.** Rejected: hooks are not uniform across the target hosts and give the agent no control plane; the four tools are the point.

## Consequences

- Positive: one vocabulary (binding × brain) that answers "is this another AI mode?" — yes, the brain axis — without inventing a binding; the merged work stays merged; a plugin that starts under a GUI-spawned PATH; a brain that names its own failure; builds that stream; follow-up turns 3–4 s faster each.
- Negative / residuals: a Cowork user without Claude Code has the demo brain until they paste one install line and log in (the chip says so); warm children are long-lived `claude` processes (memory, `ps`-visible argv — ADR-0068's residual, multiplied); the rename touches ~30 files in one commit; the community marketplace's review is Anthropic's, on its clock; D6's committed staging tree is gone, so a reviewer of the distribution repo reads generated files by design.
- Docs owed (this task): ADR-0065/0068 status lines; architecture (the two axes), code-map, glossary ("binding" and "brain" as separate entries, "local host process"), the threat-model delta (the warm child), the program record's T3/T6/T8 rows, next-steps.
