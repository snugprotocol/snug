# 0075 — Access between apps: one app reads another's tables through a grant the user gives, scopes, times, revokes and can audit

- **Status:** proposed (owner-delegated 2026-10-10: Q1–Q11 of `TASK-20261010-cross-app-access` are the defaults taken here, each reversible by one word). Becomes `accepted` when the task's PR merges; the spec-repo push (1.1) follows the merge.
- **Date:** 2026-10-10
- **Task:** TASK-20261010-cross-app-access
- **Relates to:** ADR-0010 (physical per-app isolation — kept; this ADR adds the ONE sanctioned crossing) · ADR-0016/0017 (who may propose; the requirement/grant split — the consent-then-freeze shape, reused) · ADR-0019 (reads on an isolated copy — reused, scoped) · ADR-0034 (hints, never content — the `access-changed` hint) · ADR-0036/0046/0063/0074 (host state as namespaced `snug_settings` rows; no v7) · ADR-0045 §7 / ADR-0074 E8 (an update pauses what trusted the old code — applied to grants) · ADR-0050 (spec 1.0 publication; this is the first post-1.0 minor) · ADR-0063 (app sharing — a different "share"; the vocabulary here is *access*). No existing ADR is amended.

## Context

A Snug app's data is physically its own: its tables live under `app_<token>__*`, are materialised into its own runtime database, and the runner hands a frame only the `dbNamespace` the HOST assigned (ADR-0010). Nothing on the wire lets one app read another's rows, and that is a security property the threat model leans on (C2, §5 "LLM-authored SQL cannot reach hub tables or other apps' data"). It is also a product gap the owner named on 2026-10-10: the user's own apps cannot cooperate — a budget app cannot see the ledger, a planner cannot see the pantry — and the only workaround is to rebuild one app inside the other.

The owner asked for cross-app data sharing where **the user is in full control and has complete transparency**: explicit permission, one-time or timed or indefinite, revocable at any moment; the user told what is shared and **where the data could reach** (the reader's outbound calls); frictionless after consent until expiry; **logs kept by the app giving access**; one-to-many and either direction; **auto-discovery** of relevant apps, with permission; a UI that is simpler than Apple's permission sheets and raises the bar for the industry; native in every shell from one source; and the spec bumped with the whitepaper to follow.

Read from the code:

- **The pattern for a governed capability exists three times** — db, net, open-url: a frame pair, a host-assigned binding on the runner (`dbNamespace`, `netAppId`), a value-blind router, a `host-ready` flag, a host-side handler that is the one seat with authority (`createNetHandlerFor`), and a confirm surface the iframe cannot draw over. Access is the fourth instance, not a new shape.
- **Reads on an isolated copy already exist** (`scratchRun`, ADR-0019): export the app's materialised bytes, open them in a throwaway sql.js, run the statement, discard. Scoping it means dropping every object outside the grant before the statement runs — absence, not a name filter.
- **Consent-then-freeze exists** (connections, ADR-0017): the user approves a requirement into a frozen grant; the executor reads the grant per use; a staged change never widens silently. A grant here freezes `{source, tables, duration}` the same way.
- **An app that asks at runtime exists, bounded** (`scheduleRequest.ts`, ADR-0074 §4): one pending per frame generation, a rate limit, declines remembered by semantic hash, two declines mute, a Settings switch mutes all. Access reuses the rules.
- **An update pauses what trusted the old code** (`pauseSchedulesForAppVersion`, three call sites). A grant trusts the reader's code the same way.
- **Host state is settings rows** (§8.1): a new `snug_` table would be a v7 stamp that strands every fielded hub (ADR-0063/0074's reasoning). Grants and logs are namespaced rows.
- **The spec is at 1.0 and additive changes bump the minor.** Adding frames changes `schemas/`, §2's inventory, Appendix C, the website's generated pages and the whitepaper's frame count (`check-whitepaper` AC4 pins thirteen).

## Decision

1. **Access is protocol — a fourth governed capability.** Two **strict** published frames, `snug:access-request` (`op ∈ request | query | list | release`) and `snug:access-response`, in the ordinary 256 KiB class, plus an optional `host-ready.capabilities.access` flag. The runner routes a request to a host-assigned `AccessHandler` bound by `accessAppId` (≡ `dbNamespace`'s discipline: never the announce's `appId`) and posts whatever it answers; it stays value-blind. Spec **1.0 → 1.1**: §2's inventory becomes fifteen, a new **Part VII — Access between apps** (§21 the model · §22 the grant record · §23 the frames · §24 host obligations) sits at the end so no existing section number moves, Part VI gains conformance rows, Appendix A the `ACCESS_*` codes, Appendix B the constants, Appendix C sixteen schema files. The whitepaper becomes edition 4.

2. **A grant is read-only, per table, user-written.** `AccessGrant = { id, readerAppId, sourceAppId, scope: { tables }, access: 'read', purpose, duration, status, provenance, readerVersion, timestamps, counters }`, persisted as `accessGrant:<id>` in `snug_settings` (≤ 100 per file, ≤ 4 KiB each, strict at every level, a credential-shaped purpose a parse refusal). Only the user's act on a host surface writes one — the consent sheet (opened by an app's `request` or by the user from a header sheet or Settings). `access` is a one-member enum: writes are deferred (§8), not implied. `snug_kv` is never in scope; columns are disclosed, not filtered.

3. **Four durations; one of them never touches the file.** *Just this once (while the app is open)* is a MEMORY grant bound to the reader's frame instance — it dies with a reload and never reaches a hidden scheduled frame; *for a day*, *for a week* and *until I turn it off* persist (`duration: until | always`). `expired` is derived from `expiresAt` at read, never stored. Every read is logged whatever the duration.

4. **Discovery is host-ranked and shown to the user, never to the app.** A `request` carries the reader's `purpose` and optional `hints` (words, table names). The host ranks the user's apps by a deterministic match over table names, column names, app name and description — no brain call — and the consent sheet shows them with their tables, columns and row counts, matched tables pre-selected. The app learns only what was granted: the source's display name and icon, the granted tables with their columns, the duration and expiry — never the inventory, never a library id. Apps with no tables and apps holding a sidecar connection fact are listed with the reason they cannot be sources.

5. **A read is one SELECT on a scoped scratch copy.** `scratchRunScoped(sourceAppId, statement, { tables })` exports the source's materialised bytes into a throwaway sql.js instance, DROPS every table, view and trigger outside the granted set (`snug_kv` included), sets `PRAGMA query_only`, refuses anything but one read-only `SELECT`/`WITH` (the shared `isReadOnlySelect` + `forbiddenStatementReason`), caps rows (500) and bytes (192 KiB) with `truncated`, and discards the copy. Non-granted data is **absent**, not filtered. A string cell matching a high-confidence credential shape is masked before it crosses the bridge (C1 belt). Rate: ≤ 60 queries a minute per reader instance; ≤ 1 `request` per 10 s.

6. **The source keeps the log.** `accessLog:<sourceAppId>` — one bounded row per source (≤ 200 entries, ≤ 64 KiB; ≤ 1 MiB across sources; consecutive reads of one grant within a minute coalesce with a `count`): `granted`, `read` (the statement's first 200 chars, rows, `attended` — a visible frame or a hidden scheduled one), `refused`, `revoked`, `expired`, `released`, `suspended`. Shown in the source's header sheet and in Settings; travels with the file; kept on every import.

7. **"Where this can go" is derived, not written.** The consent sheet names the reader's brain (the per-app route: demo → nothing leaves; a provider by name with the key's presence; a local endpoint; the host brain's label; the hub), every host its APPROVED connections may call, every DECLARED one as *may connect later*, the sidecar helper by name, or "no network of its own" where the host offers none — from `resolveProviderForApp`/`resolveActiveBrain` and `listConnections`, the same derivations the brain chip and the shelf already trust. The sentence that reads stay on this device and are logged in the source closes the block.

8. **Revocation is everywhere and immediate; nothing survives a doubt.** *Stop* in the source's sheet, the reader's sheet or Settings; `release` from the reader itself. The next `query` answers `ACCESS_REVOKED`; the reader's live frame is rung `host-event 'access-changed' { grantId }` (ids only, ADR-0034). A shared, agent or starter **update of the reader suspends its grants** (`reader-updated`) and the update confirm names them (ADR-0074 E8's hook, a sibling call); the user's own builder edit does not. An **untrusted import** lands every grant `suspended / imported` unless its canonical intent equals a local grant's (the scheduling guard's rule, applied to `{id, reader, source, scope, access, purpose, duration, provenance}`); a trusted pull keeps them; declines, mutes and the asking switch are the user's own answers and are dropped on an untrusted import, kept on a pull. **Deleting either app** sweeps the grants between them, the deleted app's log, declines and mute, inside the cascade. A reader may ask only while someone is looking: a hidden frame's `request` is refused; its `query` under a persisted grant is served and logged `attended: false`.

9. **Dependencies and seats.** No new dependency. `hostCapabilities().access = true` and `HostSurface` gains `'access'` — every shell runs the engine from the playground source; the artifact bindings included (the read is in-page; no `connect-src`). The SDK gains `useSnugAccess` (module form) and the knowledge base a snippet beside the copy-exactly block (`87-cross-app-access.md`); the embedded hooks block is unchanged until the starter release wave (ADR-0073). `isReadOnlySelect` and the record credential walk move to `record-guards.ts`, re-exported by `schedule.ts`.

10. **Deferred, by name.** Write access (`access: 'write'` — INSERT-only proposals under their own consent copy, R-70 considered). Column-level scope. Sharing `snug_kv`. Live change hints from source to reader (the doorbell). A builder-time access declaration (the connection-directive analogue). Grants inside shared bundles. Sidecar-fact sources. Absorbing the hook into the embedded block. A hub tile badge. Windows.

## Alternatives considered

- **A host feature on the existing frames** (kv handshake + `host-event`/`app-event`, the ADR-0074 shape). Cheapest spec cost, but a read is a request/response with rows and a request carries app-authored text and SQL — exactly the shape the strict net frames exist for; smuggling that through the open event channel would put untyped content on R7's hint channel. Rejected; the owner asked for the spec to carry it.
- **Four frame pairs** (discover / grant / query / release). Cleaner per-op typing; four rows in §2, eight schema files, eight frames in the whitepaper's inventory. The db frames already carry five ops on one pair with a discriminator. Rejected for two frames.
- **Letting the app see the inventory** (a `discover` op answering the user's apps and tables). Frictionless for the app and a privacy leak with no consent moment; rejected — the sheet is the discovery.
- **An LLM ranking the candidates.** Spends the brain on every ask and makes the ranking unexplainable; a deterministic match over names and columns is auditable and good enough for a picker the user reads. Rejected.
- **A parser-based table allowlist on the full scratch copy.** A SQL parser in a regex is a bypass waiting to happen; dropping the objects makes the control physical. Rejected.
- **Writes in v1.** Consent copy, the data-write doctrine and R-70's two-instances problem each want their own ADR's worth; "bidirectional" is two read grants. Deferred.
- **A `snug_access_grants` table.** Honest-looking; a v7 stamp strands every fielded v6 hub (ADR-0063/0074). Rejected for settings rows, normatively described.
- **Grants that follow the reader's version only by the user's say-so** (no auto-suspend on update). A shared update is third-party code inheriting a data grant — the lineage-forgery shape R-39 names. Rejected; suspend and re-ask.
- **Reusing ADR-0063's "share" vocabulary.** Two "share" controls in one header. Rejected: *access*.

## Consequences

- Positive: the user's apps can finally cooperate, from one engine in every shell; every read is user-granted, scoped, bounded, logged and revocable; nothing crosses a network and no planted file can arm it; the spec gains its first post-1.0 minor with a self-contained Part VII.
- Negative / residuals (the threat delta names them): the reader's brain sees what it reads; a reader with an approved connection can carry data to that host in a GET the confirm gate never sees; rows are prompt-injection input to the reader's model (R-8's class); the user's own builder edits of the reader keep its grants (R-7's class); two instances of the source can make a read observe mid-write state (R-70's class); session grants do not survive a reload and persisted grants do survive a device sync; a `request` outside a user gesture is a nag the KB forbids and the rate limit bounds.
- Docs owed: architecture (a section + the dependency note), code-map rows, glossary (access, grant, reader, source, scope, access log), product-vision (one sentence), `docs/security/threat-model-delta-cross-app-access.md` + the fold (v3.7, R-71 …), SPEC-1.1 + spec-changelog, whitepaper edition 4, next-steps (the deferrals), lessons at Gate 6.
