# 0068 — Binding B is a plugin-bundled local process: the desktop's native side, in Node, on loopback

- **Status:** proposed (drafted at Gate 2 of TASK-20260907-binding-b-plugin-host; becomes `accepted` with the owner's plan approval and answers to Q1–Q5; amends ADR-0065 §2 B when it lands)
- **Date:** 2026-09-07
- **Task:** TASK-20260907-binding-b-plugin-host (re-scopes T3 of TASK-20260904-skill-only-snug)

## Context

ADR-0065 §2 B delivers the local host as `scripts/snug-host.mjs` — a script the user runs by hand that serves the playground on `127.0.0.1`, starts a brain shim, and pre-wires the page through a boot config. Every target host of the program (Claude Code, Cowork desktop, Codex) already offers plugins one channel a user never has to run by hand: a stdio server the host spawns at session start (verified 2026-09-06 against `code.claude.com/docs/en/plugins-reference`; Cowork runs local plugin servers through the desktop app; Codex supports stdio `command` servers in a plugin `.mcp.json`, without a plugin-root variable — openai/codex #22842). ADR-0065's alternative "an MCP server as the host" was rejected because it would define Snug through MCP (ADR-0061) and need a server in every deployment; ADR-0066 A9 rejected a remote server as the brain's tool source for the same family of reasons. Neither rejection is about a process the plugin ships and the host spawns for the user, whose only external interface is a four-tool control plane — and Binding B needs a process anyway: connected apps need a network side that is not a browser tab (CORS, `redirect:'manual'`, a loopback OAuth listener, a file on disk), which is exactly what Snug Desktop's Rust side is (ADR-0021).

## Decision

1. **Binding B is delivered as a plugin-bundled local process, `apps/host-mcp` → one `dist/snug-mcp.mjs`**, spawned by the host over stdio. It serves a second build of the kit (`snug-host-local.html`, connections compiled in, served only ever by this process) on `127.0.0.1:<ephemeral>`, and it fills the three platform seams Snug Desktop fills natively — `fetchImpl` (`/fetch`), `oauth` (the 41420 loopback listener, `buildLoopbackRedirectUri` + `createDesktopOAuthTransport` reused unchanged) and `userdbBackend` (`createFileBackend` over an HTTP `FileBackendFs` with the desktop `userfile.rs` rules: bare names, temp + fsync + rename + directory fsync, absence = ENOENT only). The page's executor stays THE seat that reads a credential and calls fetch; the process re-runs the executor's own gates (https-only, `isForbiddenNetHost` imported, no redirect followed, 1 MiB while reading, a self-naming 60 s wall clock, error text through `scrubAuthValues`) as defense in depth — the desktop's `maxRedirections: 0` posture in Node, not a new policy.
2. **The LLM is never a network principal.** The MCP tool list is exactly `snug_status`, `snug_open`, `snug_hand_in`, `snug_list_apps`, frozen by an allowlist test. Data-plane routes exist only on the TCP listener and require the page's per-launch 256-bit bearer plus a same-origin proof (`Origin` equal to the served origin, or `Sec-Fetch-Site: same-origin`; no CORS headers; `Host` ignored); the control plane for attached sessions and the human CLI exists only on a `0600` unix socket under `~/Snug/host/` and carries no bearer. The bearer lives in the primary's memory and the page's `sessionStorage`; it rides to the page in the launch URL fragment, which the page strips before its router boots; it is never in a tool result, a lock file, a log or an MCP message — `snug_open` makes the process open the browser, and the printed fallback is a command the USER runs in a terminal.
3. **One process, one file.** `~/Snug/host/lock.json` (`port`, `pid`, `tokenHash`, `startedAt`, `socket`); a second session attaches over the socket after the lock's `tokenHash` matches the live server's; a stale lock (dead pid, or a live pid whose socket does not answer with that hash) is taken over. The primary's lifetime is the union of attached sessions: stdin close or a changed ppid starts the exit grace only when no client remains. If Snug Desktop is running (the `snug-desktop` binary on the process table — the only holder signal that exists), the file is served read-only and the custody chip names the holder; a shared holder marker written by both products is queued as the durable answer.
4. **The MCP framing is hand-rolled over `node:` stdio** (`initialize`, `notifications/initialized`, `ping`, `tools/list`, `tools/call`; `-32601` otherwise) **with the official SDK as a dev-only interop client** — subject to the owner's Q1. Measured 2026-09-07: the SDK 1.30.0 declares 17 runtime dependencies and a minimal stdio server bundles to 796 KB (372 KB minified); `docs/conventions.md` asks for fewer dependencies with an ADR per addition, and a marketplace plugin is a scrutiny target. The shipped bundle's runtime dependencies are the workspace's `@snugprotocol/auth` and `@snugprotocol/protocol` and nothing else; the bundler is `vite build` in SSR/library mode, the repo's one bundling tool.
5. **The brain rides the T2 brain seat, not `local` mode.** The `claude -p` shim (`/v1/chat/completions` on the same origin, bearer-gated; D5's flags; never `--bare`; the child's env stripped of every Anthropic/Claude override, enumerated) is reached by the page through `platform.brain = {kind:'host', adapter: localAdapter({baseUrl, apiKey: bearer})}` — `localAdapter` already accepts `apiKey`, and the host arm of `createTurnAdapter` reads no key and skips F15. The program's "bearer for `local` mode + presets + boot config" text is superseded for Binding B; the `codex`/`hermes`/`openclaw`/`ollama` shims remain T3's remainder.
6. **Test hooks live in a second build.** The proxy's resolver is a constructor parameter; `dist/snug-mcp.test.mjs` reads a test-only env var and injects one; the release bundle is swept for the env name and the symbol (`check-host-mcp`), the desktop's `gate:release` transposed. A resolved-address re-check is NOT added: the executor's gate 5 is literal-only, so it would be a new policy, and it would have refused the very stub the e2e needs.
7. **The `instructions` string lives in the process's own source, not the prompt store.** `packages/knowledge/scripts/gen-content.mjs` compiles every `.md` under `prompts/` into a committed `content.ts` that the playground, the desktop and the host kit all import, and ADR-0065 §8 (D6) forbids the skill's assets riding in it. So `apps/host-mcp/src/instructions.md` is the one source; `check-host-mcp` byte-compares the shipped bundle against it, and T6's skill build reads the same file rather than a second copy. This is a tool's own control-plane instruction text, not an assembled LLM prompt, so ADR-0004's "nothing prompt-shaped lives elsewhere" is not in tension with it.
8. **Manifests come from one constants module** (`scripts/lib/plugin-manifests.mjs`): `.claude-plugin/plugin.json` + `.mcp.json` (`node ${CLAUDE_PLUGIN_ROOT}/scripts/snug-mcp.mjs`) and `.codex-plugin/plugin.json` + its `.mcp.json` (`npx -y @snugprotocol/host-mcp`, with an absolute-path interim until the package exists). This task assembles a local plugin directory for installs from a path; T6 emits the same module into the distribution repo (ADR-0065 §8).
9. **Copy.** "Snug apps run inside Claude Code / Cowork / Codex." Never "Snug MCP server", never "built on MCP" (ADR-0061). The glossary term is "local host process".

## Alternatives considered

- **Keep the by-hand launcher (`snug-host.mjs`).** Rejected: setup is the owner's second ask ("as easy as possible") and every target host already spawns plugin processes; a launcher the user must run is a second install step with its own drift (the process lives on when the launcher's terminal closes, or dies with it).
- **The executor in Node with the credential store in Node.** Rejected (D-B3): it moves C1's one seat, duplicates ten gates with their suites, and gains nothing — the loopback hop carries a request AFTER injection exactly as the desktop's IPC does.
- **A data-plane tool for the agent (`snug_fetch`, `snug_sql`).** Rejected as a rule, not a deferral: an agent that can fetch with the user's credentials or read `snug_secrets` is a principal C1 forbids; on a sandboxed host the bearer would be a new capability.
- **A token file on disk for attached sessions.** Rejected: the unix socket gives attached sessions and the CLI a credential-free control plane with `0600` as the whole story (ADR-0032's posture); nothing then needs the token but the page.
- **MCP sampling as the brain.** Not an option — deprecated in the 2026-07-28 spec and unsupported by Claude Code. The "agent as brain over tool calls" spike (S12) is deferred with its own threat-model owed.

## Consequences

- Positive: connected apps on the skill-only path with zero by-hand setup; one process serves every session; the desktop's transport posture (redirects, OAuth port, file atomicity) reused rather than re-derived; the kit twins stay honest (the artifact kit is untouched, gate and all).
- Negative / residuals: a loopback TCP listener is reachable by any local process (the bearer and the same-origin proof bound browsers, not same-user processes — the standard desktop trust boundary); the holder signal is a process-table check until a shared marker exists; the `claude -p` argv is `ps`-visible (as the desktop's authorize URL is); 41420 squatting is availability-only, as on desktop; DNS rebinding is not claimed defended (as on desktop); the `instructions` string is byte-compared by `check-host-mcp` until T6's `check-skill-sync` owns it; Codex needs an absolute path until `@snugprotocol/host-mcp` is published (an owner act).
- Docs owed: ADR-0065 §2 B amendment; `threat-model-delta-local-host-process.md` + ledger; architecture/code-map/glossary; the program record's T3 row and D12 table.
