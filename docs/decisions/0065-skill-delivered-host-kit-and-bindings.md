# 0065 — A skill-delivered host kit and the host bindings: Snug apps run inside the agent the user already has

- **Status:** proposed (draft at Gate 2 of the program; becomes `accepted` when the owner approves the plan and T7 lands the documentation)
- **Date:** 2026-09-05
- **Task:** TASK-20260904-skill-only-snug (program) — children T1–T9

## Context

Snug today runs in two hosts of its own: the hosted Playground and Snug Desktop (ADR-0021 — the same React tree behind a platform seam). Every host supplies three things an app needs: a **body** (a sandboxed page that speaks the bridge, ADR-0006/0008), a **brain** (an `AgentTransport` that answers `[SNUG_APP_REQUEST]` envelopes), and a **file** (the one portable SQLite, ADR-0007). The agents people already use — Claude (Code, Cowork, claude.ai chat), Hermes, OpenClaw, Codex — each offer a different combination of those three without any server: Claude artifacts give a static page plus a viewer-billed completion call (`claude.use("sample")` on hosted artifacts, `window.claude.complete` in chat) and page-owned storage; Hermes gives a localhost preview pane and an OpenAI-compatible endpoint; OpenClaw gives a 256 KB sandboxed widget with a prompt relay and an OpenAI-compatible gateway; Codex gives a shell and a CLI.

The Agent Skills standard (a `SKILL.md` folder with `references/`, `assets/`, `scripts/`) is implemented by all of them, and Snug's knowledge base (ADR-0004) is already the `references/` tree of such a skill. A skill has no runtime of its own, so "a skill instead of a server" is three designs, not one — and the honest shape is **one skill, one host kit, three bindings**. The owner's asks (2026-09-04/05): Claude surfaces first, then Hermes and OpenClaw; then Claude and ChatGPT marketplace packaging; setup as easy as possible; the skill launches the runner itself; the runner looks like the Playground (claude.ai) or Snug Desktop (desktop-class hosts); and the skill **attaches to the host's brain** — the user is never asked to choose a mode, key, model, provider or account.

## Decision

1. **The host kit is a new app, `apps/host`, built the way `apps/desktop` is built** (alias into the playground source, its own entry, platform object and router, its own Vite config that inlines everything including the sql.js WASM). It emits `snug-host.html` (full: runner + user DB + starters + import/export; no builder chat — the agent is the builder) and `snug-host-micro.html` (≤ 256 KB, no sql.js, state-in-page). The playground gains only capability flags that hide surfaces, a `wasmBinary` path in the DB driver, and platform-injected transports/backends. The Playground and Snug Desktop are unchanged.
2. **Three bindings, chosen by a boot-time capability probe** — brain: `claude.use('sample')` → `window.claude.complete` → a configured loopback OpenAI-compatible URL → the demo brain; storage: the artifact's own files (`artifact.publish` files form) → `window.storage` → OPFS → memory:
   - **A — artifact.** A1 hosted (Claude Code, Cowork): the kit is published from a file as an artifact titled `Snug`; thinks run on the viewer's own Claude through `sample`; the SQLite bytes live as a data file of the artifact (published without reloading the view; a publicly shared artifact cannot save and runs read-only). A2 chat (claude.ai, Claude Desktop chat): a Claude-authored bootstrap loads the kit from an allowed CDN; thinks run through `window.claude.complete`; state lives in memory until the artifact is published and in `window.storage` after.
   - **B — local host.** The existing playground served on `127.0.0.1` by `scripts/snug-host.mjs`, with the brain reached through the existing `local` mode via OpenAI-compatible **shims around the user's own agent CLI** — `claude -p` (never `--bare`, never an API key in the child env), `codex exec`, or passthrough to Hermes `:8642`, OpenClaw `:18789`, Ollama — behind a per-launch bearer token on loopback, pre-wired by the launcher. **This is the only binding with connected apps**; the `.snug` is on disk.
   - **C — widget.** OpenClaw `show_widget` only: the micro-runner with a `WidgetBridge` whose `openclaw` implementation turns `db-request` frames into `openclaw.state.emit` notices (executed by `scripts/snug-db.mjs` against a real `.snug`) and thinks into `openclaw.prompt.send` on a user gesture; the agent answers by re-rendering. An `mcp-apps` implementation is an interface only.
3. **Nothing in A or C claims connected apps** (`net:false`, `auth:false`; the wizard, executor and registry are not in the kits; connected starters run their sample mode). A scope decision, not a technical one.
4. **The kit attaches to the host's brain and never asks.** No mode segment, BYOK rows, local-URL field, default model/provider, per-app model picker, hub account or demo-brain choice exists in the kit or in a host the skill launched. The brain chip (ADR-0059) stays as disclosure only, stamped per turn from the probe's result; the demo brain is the one fallback when no host brain exists and the chip says so. Settings in the kit are: your file (export / import / protect), appearance, about.
5. **Custody is disclosed beside the brain**: a "your file" chip — "on this Mac" / "in this artifact (Anthropic-hosted, export any time)" / "in Claude's page storage (deleted if unpublished)" / "kept by the agent" — copy pinned by tests. Export is `snug-user.snug.json` (a wrapper, because the artifact `downloads` allowlist has no `.snug`) plus per-app `snug-app-bundle/1` (ADR-0063).
6. **Apps are handed in as bundles.** The agent embeds `snug-app-bundle/1` documents in the page; the kit installs a new lineage as an owned, versioned, editable app and applies a changed html as a new version through ADR-0045's update act, data kept. `scripts/snug-embed.mjs` merges bundles into a live page mechanically so an edit is a republish, never a second runner.
7. **The skill launches the runner.** `SKILL.md` carries a mandatory launch protocol: detect the surface from the tools present → find the existing runner (artifact titled `Snug`, a running local host, a pinned widget) → create it if absent → open it where the host can → hand the app in → say in one line how to reach it.
8. **The skill's source of truth is the prompt store** (`packages/knowledge/prompts/skills/snug/`, ADR-0004); a build script emits a committed `skills/snug/` at the repo root and `check-skill-sync` (manifest + sha256, a byte-compare) gates drift. Kits are GitHub Release assets, content-pinned in the skill and fetched on first use (ADR-0060's pattern) — unless a spike shows a target sandbox cannot download, in which case they are committed at release points. Root manifests `.claude-plugin/plugin.json` + `marketplace.json` (the repo is a marketplace of one) and `.codex-plugin/plugin.json` derive from one constants module.
9. **The ChatGPT deliverable is the same skill packaged as a Codex plugin**, running Binding B with the `codex` shim; ChatGPT has no in-chat page runtime that can call the model (re-verified when that task starts).
10. **Naming.** Kits `snug-host.html` / `snug-host-micro.html`; runner artifact title `Snug`, favicon 🔥; skill `snug`; CLIs `snug-host`, `snug-db`; npm `@snugprotocol/host` only if the chat binding needs it (the scope must be registered first). Copy: "Snug apps run inside Claude / Hermes / OpenClaw" — never "built on MCP", never "Claude Code" in product names (ADR-0061).
11. **Order.** A1 → A2 → the skill on Claude → B (Claude Code local + Hermes) → C (OpenClaw) → docs → Claude marketplace packaging → ChatGPT/Codex packaging. Every publish, release, deploy and submission is an owner act, prepared and printed by the session, never performed by it.

## Alternatives considered

- **An MCP server as the host.** Rejected for this program: it defines Snug through MCP (ADR-0061), needs a server in every deployment, and none of the target surfaces need it for body + brain + file. MCP Apps remains a possible later binding of the same kit.
- **A Vite build mode of `apps/playground` for the kit.** Rejected: every mode-scoped exception would live in the file the production deploy reads; the desktop precedent (a sibling app over the same source) is proven and gives the kit its own suite and gate.
- **Embedding the SQLite in the page html and republishing on every save.** Kept only as the fallback: the html form reloads every open view on each save; the files form does not.
- **Bundling an Agent SDK brain helper in the skill.** Rejected: that is Option C's Snug Desktop path with a different distribution posture; here the brain is the user's own installed CLI, and no third-party login is offered.
- **A brain/mode picker in the kit.** Rejected by the owner: the host is the brain; choosing is the Playground's job, disclosure is the kit's.
- **Committing the kits unconditionally.** Deferred to a spike: multi-megabyte blobs per kit change versus a network dependency at first use.

## Consequences

- Positive: zero-install Snug on every Agent-Skills host; the knowledge base travels with the skill; every invariant stays where it is (sandbox, file, credential boundary); one React tree serves the Playground, Snug Desktop and the kit (parity by construction).
- Negative / residuals: data custody ranges from a file on disk (B) to Anthropic-hosted page storage that dies on unpublish (A2) — disclosed, not hidden; the runtime contract rides as a user turn on `sample`/`complete` (an authority downgrade versus the system slot); viewer-billed inference and its rate limits belong to the host; a public hosted artifact cannot save; nesting the runner inside a foreign sandbox is unproven until spike S1 and has an in-page fallback that must be disclosed; the widget binding is turn-based only and approval-bound; marketplace supply-chain posture (ClawHub's history) makes a skill that generates HTML a scrutiny target; the commercial terms of viewer-billed inference are a professional question, not an engineering one.
- Docs owed (T7): a non-normative "Host bindings" appendix in the spec draft (spec-sync, owner push), `threat-model-delta-host-bindings.md` + its ledger row, architecture / code-map / glossary / product-vision claims discipline, positioning tests extended to every new surface.
