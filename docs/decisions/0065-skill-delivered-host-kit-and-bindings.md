# 0065 — A skill-delivered host kit and the host bindings: Snug apps run inside the agent the user already has

- **Status:** proposed (the owner approved D0–D15 on 2026-09-05 — "go ahead with defaults"; becomes `accepted` when T7 lands the documentation)
- **Date:** 2026-09-05
- **Task:** TASK-20260904-skill-only-snug (program) — children T1–T9

## Context

Snug today runs in two hosts of its own: the hosted Playground and Snug Desktop (ADR-0021 — the same React tree behind a platform seam). Every host supplies three things an app needs: a **body** (a sandboxed page that speaks the bridge, ADR-0006/0008), a **brain** (an `AgentTransport` that answers `[SNUG_APP_REQUEST]` envelopes), and a **file** (the one portable SQLite, ADR-0007). The agents people already use — Claude (Code, Cowork, claude.ai chat), Hermes, OpenClaw, Codex — each offer a different combination of those three without any server: Claude artifacts give a static page plus a viewer-billed completion call (`claude.use("sample")` on hosted artifacts, `window.claude.complete` in chat) and page-owned storage; Hermes gives a localhost preview pane and an OpenAI-compatible endpoint; OpenClaw gives a 256 KB sandboxed widget with a prompt relay and an OpenAI-compatible gateway; Codex gives a shell and a CLI.

The Agent Skills standard (a `SKILL.md` folder with `references/`, `assets/`, `scripts/`) is implemented by all of them, and Snug's knowledge base (ADR-0004) is already the `references/` tree of such a skill. A skill has no runtime of its own, so "a skill instead of a server" is three designs, not one — and the honest shape is **one skill, one host kit, three bindings**. The owner's asks (2026-09-04/05): Claude surfaces first, then Hermes and OpenClaw; then Claude and ChatGPT marketplace packaging; setup as easy as possible; the skill launches the runner itself; the runner looks like the Playground (claude.ai) or Snug Desktop (desktop-class hosts); and the skill **attaches to the host's brain** — the user is never asked to choose a mode, key, model, provider or account.

## Decision

1. **The host kit is a new app, `apps/host`, built the way `apps/desktop` is built** (alias into the playground source, its own entry, platform object and router, its own Vite config that inlines everything including the sql.js WASM). It emits `snug-host.html` (full: runner + user DB + the starter shelf + import/export **+ the builder — amended 2026-09-05 at T2's Gate 2 on the owner's point 5: the kit is a clone of the playground / Snug Desktop minus the brain, model/provider and account controls, so the builder chat stays and runs on the pinned host brain; starters load on click from the content-pinned `@snugprotocol/starters` package because the page inside an artifact cannot fetch GitHub**) and `snug-host-micro.html` (≤ 256 KB, no sql.js, state-in-page). The playground gains only capability flags that hide surfaces, a `wasmBinary` path in the DB driver, and platform-injected transports/backends. The Playground and Snug Desktop are unchanged.
2. **Three bindings, chosen by a boot-time capability probe** — brain: `claude.use('sample')` → `window.claude.complete` → a configured loopback OpenAI-compatible URL → the demo brain; storage: the artifact's own files (`artifact.publish` files form) → `window.storage` → OPFS → memory:
   - **A — artifact.** A1 hosted (Claude Code, Cowork): the kit is published from a file as an artifact titled `Snug`; thinks run on the viewer's own Claude through `sample` (measured 2026-09-05: `quick` median 1.2 s, 48/48 legal Chess moves, consent once; every `quick` reply code-fenced, so the kit parses `sample()` text through Snug's graduated parser); the working copy lives in the artifact origin's browser bucket and the durable record is the page's own html republish with the SQLite bytes embedded (2 MiB in 1.8 s, the view reloads) — the files form is `capability_disabled` in the owner's view and is only retried at boot; the runner is nested (`<iframe sandbox="allow-scripts" srcdoc>`, proven in both runtimes; `RUNNER_CSP` enforcement inside it measured in the hosted runtime, verified in chat at T4), and the embedder narrows the app CDN allowlist to jsDelivr `/npm/` + cdnjs with inline CSS and fonts. A2 chat (claude.ai, Claude Desktop chat): a Claude-authored bootstrap loads the kit from jsDelivr `/npm/` (`@snugprotocol/host` on npm is a prerequisite; jsDelivr `/gh/` is blocked); thinks run through `window.claude.complete` (detected, not yet measured); state lives in `window.storage` once the artifact is published (a never-published artifact was not measured — the contract says storage is published-only), which persists across reloads but is **per view**: the in-chat view and the published link hold separate stores; export is copy-as-text only.
   - **B — local host.** The existing playground served on `127.0.0.1` by `scripts/snug-host.mjs`, with the brain reached through the existing `local` mode via OpenAI-compatible **shims around the user's own agent CLI** — `claude -p` (never `--bare`, never an API key in the child env), `codex exec`, or passthrough to Hermes `:8642`, OpenClaw `:18789`, Ollama — behind a per-launch bearer token on loopback, pre-wired by the launcher. **This is the only binding with connected apps**; the `.snug` is on disk.
   - **C — widget.** OpenClaw `show_widget` only: the micro-runner with a `WidgetBridge` whose `openclaw` implementation turns `db-request` frames into `openclaw.state.emit` notices (executed by `scripts/snug-db.mjs` against a real `.snug`) and thinks into `openclaw.prompt.send` on a user gesture; the agent answers by re-rendering. An `mcp-apps` implementation is an interface only.
3. **Nothing in A or C claims connected apps** (`net:false`, `auth:false`; the wizard, executor and registry are not in the kits; connected starters run their sample mode). A scope decision, not a technical one.
4. **The kit attaches to the host's brain and never asks.** No mode segment, BYOK rows, local-URL field, default model/provider, per-app model picker, hub account or demo-brain choice exists in the kit or in a host the skill launched. The brain chip (ADR-0059) stays as disclosure only, stamped per turn from the probe's result; the demo brain is the one fallback when no host brain exists and the chip says so. Settings in the kit are: your file (export / import / protect), appearance, about.
5. **Custody is disclosed beside the brain**: a "your file" chip — "on this Mac" / "in this artifact (Anthropic-hosted, export any time)" / "in Claude's page storage (deleted if unpublished)" / "kept by the agent" — copy pinned by tests. Export is `snug-user.snug.json` (a wrapper, because the artifact `downloads` allowlist has no `.snug`) plus per-app `snug-app-bundle/1` (ADR-0063).
6. **Apps are handed in as bundles.** The agent embeds `snug-app-bundle/1` documents in the page; the kit installs a new lineage as an owned, versioned, editable app and applies a changed html as a new version through ADR-0045's update act, data kept. `scripts/snug-embed.mjs` merges bundles into a live page mechanically so an edit is a republish, never a second runner.
7. **The skill launches the runner.** `SKILL.md` carries a mandatory launch protocol: detect the surface from the tools present → find the existing runner (artifact titled `Snug`, a running local host, a pinned widget) → create it if absent → open it where the host can → hand the app in → say in one line how to reach it.
8. **The skill's source of truth is the prompt store** (`packages/knowledge/prompts/skills/snug/`, ADR-0004); a build script emits a committed `skills/snug/` at the repo root and `check-skill-sync` (manifest + sha256, a byte-compare) gates drift. **Amended 2026-09-05 (T2 Gate 2, owner pick A1): that committed tree is the staging copy; a release-time script pushes it to a generated distribution repo `snugprotocol/snug-skill` — `SKILL.md` at its root, the plugin manifests beside it, the kits as its Release assets, never edited directly (the `spec` posture) — because Claude Code and Cowork clone the whole marketplace repo (this monorepo is 75 MB and growing), OpenClaw's git install expects `SKILL.md` at the source root, and a small reviewable repo is the right posture for marketplace scrutiny.** Kits are GitHub Release assets, content-pinned in the skill and fetched on first use (ADR-0060's pattern) — unless the Cowork spike (S9, still owed) shows that sandbox cannot download, in which case they are committed at release points. Loading the kit straight from the repo through jsDelivr `/gh/` is impossible: both artifact viewers' CSPs allow only the `/gh/python-visualization/` prefix (measured 2026-09-05), so the chat binding needs the npm package or a cdnjs listing. Root manifests `.claude-plugin/plugin.json` + `marketplace.json` (the distribution repo is a marketplace of one — amendment above) and `.codex-plugin/plugin.json` derive from one constants module.
9. **The ChatGPT deliverable is the same skill packaged as a Codex plugin**, running Binding B with the `codex` shim; ChatGPT has no in-chat page runtime that can call the model (re-verified when that task starts).
10. **Naming.** Kits `snug-host.html` / `snug-host-micro.html`; runner artifact title `Snug`, favicon 🔥; skill `snug`; CLIs `snug-host`, `snug-db`; npm `@snugprotocol/host` — required by the chat binding (S2, 2026-09-05; the `@snugprotocol` scope must be registered first, an owner act). Copy: "Snug apps run inside Claude / Hermes / OpenClaw" — never "built on MCP", never "Claude Code" in product names (ADR-0061).
11. **Order.** A1 → A2 → the skill on Claude → B (Claude Code local + Hermes) → C (OpenClaw) → docs → Claude marketplace packaging → ChatGPT/Codex packaging. Every publish, release, deploy and submission is an owner act, prepared and printed by the session, never performed by it.

### Amendments — 2026-09-05/06 (TASK-20260905-binding-a-artifacts, plan review + owner approval as amended)

> **Owner direction, 2026-09-06 (recorded here as a pointer; the decision itself will be its own ADR):** point 3 — "nothing in A or C claims connected apps" — is to be superseded for Binding A by an **MCP-connector binding on the page** (the artifact runtime's `mcp` capability: the page calls the viewer's own connected connectors with the viewer's credentials). Queued in `docs/next-steps.md` with the design questions and the spike it owes; ordered after the page-tools task (ADR-0066 A9).

- **§2 (A1 storage).** The files form of `artifact.publish` is a residual, not a boot probe: it answered `capability_disabled` on the owner's private artifact (S4), and a success would create a second durable location the html-block boot never reads (plan review A2). Its precondition, if ever revisited, is the S4(b) re-run. The durable act fetches the page's CANONICAL source (`fetch(location.href)`) and verifies it with the shared tokenizer before republishing — never the live DOM, which the viewer injects its runtime into (`artifact.d.ts` 0.2.41). A fifth binding, `artifact-static`, names the page served top-level on the artifact host (every `use()` `null`): nothing saves there, no brain, and the chip says so. The builder under the 64 KiB cap budgets or refuses (S11: a cut context plus "write the ENTIRE file" re-invents the app's tail) and skips the router classifier (every call bills the viewer).
- **§5 (custody).** The "your file" chip's copy is derived from the platform seats and the record's state, with a direction on a divergence (the block's save counter) and the two acts; the wrapper `snug-user-file/1` is sniffed by a byte prefix (`format` first) and re-sniffed as a user file after unwrapping — the sha proves only self-consistency.
- **§6 (hand-in).** Auto-apply is UNEDITED-ONLY: an edited copy is offered in the run header through ADR-0045 §7's confirm; a deleted app stays deleted (`agentDismissed:<lineage>`); a bundle carrying connections is a hard refusal (D4); the bundle's lineage also resolves to the app it was lifted from. **The trust boundary, stated:** under Binding A the page is the publisher's output — whoever can republish the artifact can replace the kit's own JavaScript — so a consent gate on bundle blocks would defend nothing against a page writer; the boundary is the artifact's write permission (private by default), and the guards that hold are the ones inside it (no connections, no silent supersession, every version revertable, the hub note, the tombstone). Three sentences the Gate-5 review added: the seed TRUSTS the block (its sha proves self-consistency, never provenance); `verifyKitPage` is a shape check on the fetched source, not a security control; and the viewer's own bridge is a residual — an app frame can post a runtime-shaped message to `top`, the kit page never answers one, and whether the viewer does is answerable only by the hosted walk (the contract 0.2.41 says nothing about nested frames). T7's threat-model delta carries an R-39 row for this.
- **§2 (A2 delivery).** The kit is ONE html page; a chat bootstrap cannot iframe it (opaque origins cannot reach `parent.claude.complete` — the very property C2 relies on), so the chat delivery is a script build (`snug-host.js`) that executes in the bootstrap's own window: a new child task ahead of T6's A2 recipe. T4 ships and tests the chat brain and storage on the page itself.
- **Consequences added:** the output ceiling of `sample` was not reached at a 54 KB reply (S11) and stays undocumented; the runtime contract rides as a leading user turn on both host brains (an authority downgrade versus the system slot, ADR-0018 D3 — the bytes are the same assembly, validated by the same schema and caps).

## Alternatives considered

- **An MCP server as the host.** Rejected for this program: it defines Snug through MCP (ADR-0061), needs a server in every deployment, and none of the target surfaces need it for body + brain + file. MCP Apps remains a possible later binding of the same kit.
- **A Vite build mode of `apps/playground` for the kit.** Rejected: every mode-scoped exception would live in the file the production deploy reads; the desktop precedent (a sibling app over the same source) is proven and gives the kit its own suite and gate.
- **The files form of `artifact.publish` as the primary hosted store.** Preferred on paper (a version without a reload) and kept as a boot-time probe, but it answered `capability_disabled` on the owner's own private artifact (S4, 2026-09-05), so embedding the SQLite in the page and republishing the html — a reload per save, debounced to explicit acts — became the primary mechanism.
- **Bundling an Agent SDK brain helper in the skill.** Rejected: that is Option C's Snug Desktop path with a different distribution posture; here the brain is the user's own installed CLI, and no third-party login is offered.
- **A brain/mode picker in the kit.** Rejected by the owner: the host is the brain; choosing is the Playground's job, disclosure is the kit's.
- **Committing the kits unconditionally.** Deferred to a spike: multi-megabyte blobs per kit change versus a network dependency at first use.

## Consequences

- Positive: zero-install Snug on every Agent-Skills host; the knowledge base travels with the skill; every invariant stays where it is (sandbox, file, credential boundary); one React tree serves the Playground, Snug Desktop and the kit (parity by construction).
- Negative / residuals: data custody ranges from a file on disk (B) to Anthropic-hosted page storage (A1: every save is a version and a reload; A2: per-view `window.storage`, copy-only export) — disclosed, not hidden; the embedder's CSP narrows what artifact-bound apps may load (a skill rule + lint, and a contract-vs-schema finding that the `quick` tier follows contract prose over the envelope's schema 28/30); the widget floor is 149 KB, so 4 of 12 starters need the compact variant; the chat binding depends on an npm publish; the runtime contract rides as a user turn on `sample`/`complete` (an authority downgrade versus the system slot); viewer-billed inference and its rate limits belong to the host; a public hosted artifact cannot save; nesting the runner inside a foreign sandbox is unproven until spike S1 and has an in-page fallback that must be disclosed; the widget binding is turn-based only and approval-bound; marketplace supply-chain posture (ClawHub's history) makes a skill that generates HTML a scrutiny target; the commercial terms of viewer-billed inference are a professional question, not an engineering one.
- Docs owed (T7): a non-normative "Host bindings" appendix in the spec draft (spec-sync, owner push), `threat-model-delta-host-bindings.md` + its ledger row, architecture / code-map / glossary / product-vision claims discipline, positioning tests extended to every new surface.
