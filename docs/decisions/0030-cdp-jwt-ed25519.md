# 0030 — `cdp_jwt` signs Ed25519 (EdDSA) only; ES256 dropped with the registry re-pin

- **Status:** accepted (2026-08-15, TASK-20260815-coinbase-ed25519 — implemented, Gate-5 verified 21/21 root tasks; the owner's live hardware verification (AC8) is the closing test, tracked in next-steps)
- **Date:** 2026-08-15
- **Task:** TASK-20260815-coinbase-ed25519
- **Supersedes:** ADR-0022 §2's "ES256 only at v1" clause and its key-import amendment
  (SEC1→PKCS#8 wrap). ADR-0022's other sections (request/testRequest seats, queryTemplate,
  auth-shaped failure surfacing) stand untouched; its status line gains a pointer here in
  the same change (ADR-0027 practice).

## Context

ADR-0022 pinned `cdp_jwt` to ES256 on a 2026-08-12 recon note that read Coinbase's docs
as "Ed25519 keys are NOT accepted on the Coinbase App surface". Coinbase's current docs
and portal say the opposite: **Ed25519 is the default and recommended CDP key type,
ECDSA/ES256 is legacy** ("use only when required by specific SDKs"). The CDP portal now
issues Ed25519 keys by default, delivering the secret as base64 (64-byte seed‖pubkey).
Consequences observed on the owner's machine (the open PR-#42 verification thread):
market data (public endpoints) renders while the credentialed portfolio path never
connects — a portal-default Ed25519 key is exactly what `es256-key.ts` rejects, and our
registration walkthrough was steering users to create a legacy key type. The owner also
reports **no visible error** at verify time; whether the probe's error surfacing has a
gap is a diagnostic step of the task, not assumed here.

Verified against Coinbase's own `coinbase-advanced-py` `jwt_generator` (primary
reference for `api.coinbase.com`): the claim shape ADR-0022 pinned is already correct —
header `{alg, kid:<key name>, typ:'JWT', nonce:<random hex>}`, payload `{iss:'cdp',
sub:<key name>, uri:'<METHOD> <host><path>', nbf:now, exp:now+120}`, no `aud` on the
Advanced Trade REST surface (the `aud:['cdp_service']` in the JWT-auth docs page belongs
to the CDP *platform* API). Only the algorithm and key-import posture change.

## Decision

1. **`cdp_jwt` v2 signs `EdDSA` from an Ed25519 secret — and nothing else.** ES256 is
   dropped, not auto-detected (owner decision 2026-08-15: one signing path, smallest
   surface; pre-launch, the sole existing credential is re-created once). The helper
   name, arity, lint rule (both args declared field keys), claim shape, and
   fresh-JWT-per-render behavior are unchanged.
2. **Accepted secret shapes — every shape the portal has delivered, auto-detected,
   ARMOR FIRST.** Detection order (plan-review amendment — a naive "PEM else base64"
   order would send an EC SEC1 paste to the base64 decoder and earn "not valid base64"
   instead of the fix-naming error): any `-----BEGIN` armor → the PEM family — PKCS#8
   with the Ed25519 OID (1.3.101.112) accepted; SEC1 `BEGIN EC PRIVATE KEY` or PKCS#8
   with id-ecPublicKey → the EC fix-naming error ("create an Ed25519 API key in the CDP
   portal — ECDSA keys are Coinbase's legacy format"); other armor → typed error. No
   armor → base64, WHITESPACE-NORMALIZED first (a trailing newline is the default shape
   of a copy from a key file; `base64ToBytes` rejects whitespace by regex): 64 bytes =
   seed‖pubkey (first 32 sign), 32 bytes = bare seed, a 48-byte PKCS#8-prefixed DER (an
   armorless PEM-body paste) has its seed extracted; base64url-alphabet pastes and
   other lengths earn typed errors naming the fix ("paste the key exactly as the portal
   delivered it; include the BEGIN/END lines if you pasted from the PEM file"). **Every
   accepted shape canonicalizes to the 32-byte seed**, re-wrapped by us in the fixed
   16-byte PKCS#8 DER prefix (`302e020100300506032b657004220420`) →
   `crypto.subtle.importKey('pkcs8', …, {name:'Ed25519'}, false, ['sign'])`,
   non-extractable. `es256-key.ts` is replaced by an `ed25519-key.ts` with the same
   honest typed-error contract, and **no error ever echoes pasted content** (C5).
3. **Native WebCrypto Ed25519 required; absence fails LOUDLY — and the rule is TOTAL.**
   Same posture as ADR-0022's ECDSA rule (the desktop subtle-fallback implements HMAC
   only; no hand-rolled curve math, C5), strengthened by the plan review: because every
   accepted shape canonicalizes to a blob WE construct from a validated seed (§2), ANY
   `importKey`/`sign` failure after validation IS a runtime failure and surfaces the
   honest runtime error — never "re-create your key". This matters concretely: the
   desktop subtle-fallback throws a plain `Error`, not `NotSupportedError`, so an
   error-name allowlist (the es256-key.ts pattern) would misdiagnose the one runtime
   most likely to lack Ed25519. WebCrypto's raw 64-byte Ed25519 signature is exactly
   the JWS EdDSA format — no conversion, the same happy property ES256 had. Supported
   by current Node (CI pins 22; spike-verified v22.13.1), Safari/WKWebView 17+, Chrome
   137+, Firefox 130+ — every runtime we ship to.
4. **The Coinbase registry entry re-pins the credential pair for Ed25519 — and the
   secret field is RENAMED, not relabeled: `private_key` → `ed25519_private_key`.**
   The rename is load-bearing (plan-review blocker finding): the drift-migration and
   re-approve digests read FIELD KEYS ONLY (`requirementFieldKeysDigest`,
   `connectionWizard.ts:470-472`; `fieldSetChanged` routing `:589-591`), so a
   label-only change either returns `'none'` on a registry-provenance row (no healing
   ever) or, on a borrowing-channel row, re-approves to `'done'` with the stale EC
   secret still stored — a silent promotion. Renaming the key makes the old shape
   refuse admission and the digest change, which is exactly the invalidation mechanism
   §5 relies on. Template arg renames with it
   (`Authorization: Bearer {{cdp_jwt(api_key, ed25519_private_key)}}`); label and
   description name Ed25519 and both paste shapes; registration instructions walk the
   Ed25519 creation path and warn off the legacy ECDSA choice; `testRequest` stays
   byte-unchanged (`GET /api/v3/brokerage/accounts`).
5. **The pinned-shape change invalidates the saved credential, and orphaned secrets
   for dropped fields are DELETED at re-approval** (owner decision 2026-08-15;
   ADR-0028 pre-promotion-invalidation precedent). The field-key rename (§4) makes the
   EC-era row refuse re-admission → the registry's current shape is staged → the wizard
   walks the credential half again instead of leaving a zombie "saved but never
   connects" row. At re-approval, stored credential secrets whose keys are no longer
   declared fields are deleted BEFORE `db.reapproveConnection` lands (same ordering
   argument as ADR-0028's token invalidation: a throw after promotion would strand the
   orphan unreachable forever). This deliberately INVERTS the prior "old secrets for
   dropped fields stay in storage" contract (`connectionWizard.ts:1287-1298` docstring
   + the pinned assertion in `registryDriftMigration.test.tsx:310` both update with
   this task) — a dead secret in `snug_secrets` is C5 weight with no reader, and the
   owner chose invalidate-and-re-prompt over zombie state.

## Consequences

- The founding Coinbase starter becomes connectable with a portal-default key — the
  owner's manual portfolio verification (open since PR #42) is the closing test.
- Anyone holding a legacy EC key gets an honest, fix-naming error, not a silent failure.
- One signing family per helper stays the rule: no runtime algorithm negotiation, no
  downgrade surface. If Coinbase ever retires EdDSA the registry re-pins again.
- The `AUTH_TEMPLATE_HELPERS` enum, template grammar, and protocol schemas are untouched
  — no spec-sync. The internal auth spec-draft's ES256 wording updates with this task
  (AL-12 push still HELD).
