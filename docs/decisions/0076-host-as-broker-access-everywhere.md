## Context

ADR-0075 shipped access between apps as a protocol capability for APP CODE: a reader's frame posts `snug:access-request`, the runner's value-blind seat routes it, the host exports the source, a dedicated Worker makes a scoped copy and runs one SELECT. The host was already the only path between two apps — nothing app-to-app exists — but only an app's own code could walk it, and ADR-0075 §10 deferred fourteen things by name, among them the two that matter most to a person using Snug: the chat beside an app cannot see another app's data, and nothing can write.

The owner's requirements (2026-10-10), read as product: the host is the proxy for sharing, reads AND writes (R1); the host acts on the user's behalf across many apps within every permission the user granted (R3); the host can make a source app PULL new data, not just serve what it has (R4); all fourteen deferrals, with the complexity and the security abstracted from the user (R5). And, read from the code:

- **One engine, three callers already exist in separate shapes.** The frame handler closes its `query` over the frame (`accessHandler.ts:144`, `ownsSession`/`attended`); the data lane has `data_query` over `scratchRun` (one app's bytes, main thread, no clock — ADR-0019's accepted shape); the scheduler's think step runs user-typed SELECTs on the same scratch. None knows about grants.
- **The one write path exists and is playground-level**: `executeApprovedWrite` (class check → fresh dry run → count-drift halt → transaction through the driver with a host instance id). It has no notion of a target other than the chat's own app, no row cap, no undo, no busy check.
- **A declaration cannot ride the bundle.** `snug-app-bundle/1` is `strictObject` at every level; a new field makes every 1.1 hub refuse the whole bundle. The HTML inside it travels unchanged.
- **The caps are the bridge's.** 500 rows / 192 KiB exist because rows cross `postMessage` into an iframe; a host-internal copy never does, and the brain only ever sees `data_query`'s capped result (200 rows / 32 KiB / 8,000 chars).
- **Standing approvals have a gate and no arming surface** (ADR-0033): explicit gesture, frozen scope, host guardrails, disclosure, journal, instant revocation — the exact shape any unattended write must cite.
- **Nothing signals a write.** `markDirty` fires on reads too; a change hint needs `getRowsModified`/statement class in `runExec`.

## Decision

1. **One Access Service, one policy, three doors.** `access/service.ts` is the only code that reads or writes another app's data; `access/policy.ts` is the one `authorise(caller, act)` every door calls — grant status and expiry, attendance and duration, mute and decline, rate, source restriction, busy. The callers are `{kind:'frame', appId, generation, attended}` (today's handler, now a thin mapper), `{kind:'chat', appId, threadId}` (the data lane) and `{kind:'schedule', taskId, runId, appId, attended}` (the scheduler's steps). Every history line carries `via`. The user never learns there are doors: the same grant, the same sheet, the same history.

2. **The chat's brain sees the granted tables as tables.** With a live read grant the data lane's scratch copy holds `<alias>__<table>` (alias = the source's display name, slugified, collision-suffixed), materialised THROUGH the Worker — drops, withheld columns, masked values and the drift check all run there before a row exists on the main thread — under an in-host cap (`ACCESS_MATERIALISE_MAX_ROWS` 5,000 / `ACCESS_MATERIALISE_MAX_BYTES` 2 MiB per table; truncation stated in the DDL block). The DDL block lists them under *From <Source> (read-only · access until …)*; `data_query` may JOIN across them; a `read` line is written BEFORE any row reaches the brain; rows reach the brain inside `<query_result>` with the not-instructions trailer (R-71's class, now at the chat door). A write proposal naming an alias table is routed to the Write Broker under a write grant (§4) or refused by name. The chat's brain can also ASK: an `access_propose` tool stages one proposal per turn as a card whose *review* opens the consent sheet through the one user-ask recipe — the brain proposes, the user allows.

3. **The scheduler's think step sees the same tables**, tool-free on every brain, for grants whose `unattended` rule admits the run's attendance; and (§9) may carry tools where the data lane exists.

4. **A write grant is a standing, scoped, undoable authority.** The consent sheet gains one toggle per table, *can also change rows* (add, change and remove as one — no per-op grid), off by default and offered when the ask carried `access: 'write'` or the user opens *more…*. The record becomes `scope.tables[].{name, columns, withheld?, write?}` plus `kv?` and `refresh?` (strict, additive, defaults off; a 1.1 hub treats a v2 row as unreadable — fail closed — and the changelog says so). The sheet says, in one breath, that every change is listed in <Source>'s history and can be undone for seven days.

5. **One Write Broker for every write not typed by the user's own hands inside the app.** `packages/db/src/brokered-write.ts` (pure) + `access/writeBroker.ts`: one DML statement; table within the write scope, columns within the scope minus withheld and credential-named; literal-valued, no subquery or CTE; an UPDATE or DELETE without WHERE is refused ("names no rows — do that from the app"); a fresh dry run on a scratch copy must count ≤ `ACCESS_WRITE_MAX_ROWS` (200); a target whose frame holds an open transaction answers `ACCESS_BUSY` (retryable); the undo plan is captured first (UPDATE/DELETE: the affected rows by rowid; INSERT: the new rowids) and a plan over 64 KiB refuses the write as "too large to undo"; then `BEGIN IMMEDIATE` → exec → `COMMIT` through the driver with instance `host-brokered-write`; the `wrote` line lands in the source's history before the answer leaves; *undo* runs the inverse through the same path, writes `undone`, and is not itself undoable; ≤ 20 undo entries per source, 7 days. `executeApprovedWrite` becomes a caller with `authority: {kind:'user-approval'}`; the authorities are `user-approval` (the chat's card, the result page's *apply*), `write-grant` (an attended app frame's `write` op) and `task` (§9).

6. **Refresh on demand.** `op: 'refresh' {grantId}` under a grant whose `refresh` is ticked (*may ask <Source> to fetch new data first*) has the host run the SOURCE where it lives (ADR-0077's placement) with `input {kind:'refresh', requestedBy: <reader display name>}` over the schedule handshake (`taskId: 'access-refresh'`, a real `runId`), under the unattended posture (GET-only connected calls; a mutating call is refused by name), counted against the day's ceilings, at most once per source per `ACCESS_REFRESH_COOLDOWN_MS` (5 min; within it the answer is `ok, fresh:false, reason:'recent'` and nothing runs), logged `refreshed` with who asked. A source without a handler answers `ACCESS_REFRESH_FAILED` (not retryable); a busy source, retryable. The chat and the scheduler get *fetch new data first*; the source's ⋈ sheet gets *fetch now*.

7. **Discovery is a class, never a name.** `op: 'discover' {hints?}` answers `candidates: 'none' | 'one' | 'several'` and records nothing — the one fact an app needs to show or hide its *use my ledger* button. The host, which sees the inventory, does the rest: Settings *apps that could work together* (deterministic pairs from `relevance.ts`, one tap), the source's ⋈ sheet *let another app read this…*, a Hub tile ⋈ badge with the live-grant count either direction.

8. **Doorbells, ids only.** `access-source-changed {grantId}` to every live reader of a source whose namespace saw a successful mutating statement (from `getRowsModified`/statement class in `runExec`, coalesced ≥ 2 s); `access-read {grantId}` to the source's live frame; `data-changed {table}` to the target's own live frame after a brokered write, so an open app re-reads. No event carries a row or a value (ADR-0034).

9. **Host-native jobs and the first standing write authority.** The *Ask [app]'s AI* step gains `tools: true` ("look things up and act"): it runs on the data lane's machinery with `data_query`, `data_propose_write`, a GET/HEAD-only `fetch_connection` (connection-relative, approved connections only, ≤ 64 KiB, counted, scrubbed — no method parameter exists) and the shared tables; ≤ 8 tool calls a run; replies through the scheduled scrub. It is available where the data lane is (BYOK direct brains); under host or subscription brains the step runs tool-free with the shared tables and the result says so. Its proposals wait for the user as today UNLESS the task carries a **write authority** — ADR-0033's shape, armed on the one consent surface (*let it apply its changes · up to 200 rows a run · you can undo any run*), stored on the task, enforced by the Write Broker with `authority: {kind:'task', taskId}`, disclosed on the result with *undo*, killed globally in Settings or per task, DISARMED by any untrusted import. The editor and the chat offer the two shapes in words: *Ask <App>'s AI* (host-native, no frame) and *Run <App>'s own routine* (app code, ADR-0077's placement).

10. **Chosen columns and the key-value store.** `withheld` columns are NULLed on the copy exactly like credential columns (D27's fail-closed withhold) and ignored by the drift check; the sheet shows per-column ticks, pre-ticked. `kv: true` keeps a FILTERED `snug_kv` on the copy — credential-named keys, credential-shaped values and `snug:`-prefixed host keys dropped — queryable as `snug_kv(key, value)`; the sheet's tick reads *settings & notes*.

11. **Declarations propose; the user grants.** An app may declare at build time what it would like to read: `<meta name="snug:access-wants" content="<json ≤ 2 KiB>">` inside its HTML — `[{purpose, hints}]`, ≤ 4 entries, strict-parsed at install, update and hand-in into `accessWants:<appId>` — never a bundle field. The host shows it on the install preview ("would like to read tables like `transactions`"), on the Hub tile when a match exists ("works with your ledger"), and pre-fills the sheet. It never writes a grant (ADR-0016).

12. **Deferred, by name.** Sidecar-fact sources — the design is "taint follows data": a reader holding a live grant from a restricted source inherits the source's egress restriction (scrubbed brain AND refused connected calls while the grant is live); it needs its own ADR and copy because a GET URL can carry rows and cannot be scrubbed. Write access on a source-initiated grant (the source offers READ). A per-op write grid. Step chaining across apps inside one schedule.

## Alternatives considered

- **A separate `access_query` tool for the chat instead of materialised tables.** Keeps every read inside the Worker, but the brain cannot JOIN a budget to a ledger — the product value — and must learn a second tool. Rejected; the Worker still produces every row.
- **Attaching the source's scoped bytes to the scratch copy.** sql.js has no second-database VFS for an in-memory copy; inserting the Worker's rows is the honest equivalent. Rejected for the insert.
- **Per-write approval for every cross-app write.** Keeps today's doctrine whole and kills "frictionless after consent"; the chat keeps it (the user is there), the frame and the scheduler get the standing shape with undo. Rejected as the only mode.
- **A per-op (insert / update / delete) grid.** Apple-sheet complexity for a toggle most users read as "can change". Rejected for one toggle; the row cap and undo are the protection.
- **Standing authority per GRANT for unattended writes.** Ties an unattended power to the reader rather than to the schedule the user can see fire; ADR-0033 binds the authority to the ACT. Rejected for the task-level authority.
- **A declarative job language (fetch → map → write steps).** Invents a second brain; the data lane with tools is the agent Snug already has. Rejected.
- **A `wants` field on the bundle.** Strict bundles make every 1.1 hub refuse the file. Rejected for the HTML meta.
- **Letting apps discover by name or count.** The sheet is the discovery; a class is the floor. Rejected beyond the class.
- **Refresh as a new frame pair.** The schedule handshake already carries "run with this input" to an app; a new frame costs a spec minor's worth of surface for one op. Rejected for `op: 'refresh'`.

## Consequences

- Positive: a person says "compare with my ledger" in a budget app's chat and the host does the rest, with the user's one allow; apps cooperate without bespoke code; writes across apps and inside scheduled runs are bounded, journaled and reversible; the first standing write approval lands with a kill switch and an undo; declarations make an app's wishes visible before it runs; spec 1.2 is one additive minor; every unattended act is still refused, asked or journaled.
- Negative / residuals (the threat deltas name them): the chat's brain sees another app's rows (R-71 at a second door) and the chat path has no R-9 scrub (sidecar sources are excluded by construction; the reader's own sidecar data in its chat is pre-existing and recorded); a standing write authority is a power exercised while nobody looks — bounded by the row cap, the undo journal, the ceilings and the kill switch, disclosed on every result; a refresh spends the source's connections and the user's brain on a reader's behalf — once per cooldown, counted, logged; a 1.1 hub cannot read a v2 grant (fail closed); the materialisation copies up to 5,000 rows per table per turn on the main thread (cached 10 s per grant).
- Docs owed per PR: architecture (the broker section), code-map rows, glossary (*door*, *materialised table*, *write grant*, *undo*, *refresh*, *declaration*), product-vision (the sentence that ends "but never apply them" gains its exception), threat deltas and the fold (R-71 extended; new rows for writes, refresh, declarations), SPEC 1.2 + changelog, whitepaper edition 5, KB 00/10/85/87 + the skill, next-steps pruned.

## Folded from the Gate-2 reviews (PR-2, 2026-10-11)

Four fresh-context plan reviews of PR-2's contract (security · design · feasibility · scope; the task file's "PR-2 — Gate-2 contract v2" holds the fold record) changed HOW §1–§3 land, never what they decide:

- **An unbound session grant is readable by nobody.** A *while it's open* grant allowed from host chrome or a chat while the reader is closed binds to the reader's NEXT frame and is read by no door until then — the chat door owns a session grant only while the reader's view is open in this tab at the same generation; the scheduler door never. A chat ask reviewed while the reader is closed seeds the sheet to *for a day* so the default allow is one the chat can use now (the one-word reversal of ADR-0075's session default for that case).
- **A session grant is never read without someone present**, whatever *also while I'm away* says (D30 as a policy rule, not a sheet affordance).
- **The brain's ask walks the ask ladder.** `access_propose` is offered and answers under the same rungs an app's ask meets — the Settings switch, the per-app mute, a recorded decline by the ask's semantic hash, one pending per reader — and the chat ask's sheet offers *don't allow*, so "won't ask this again" is true. The purpose is quoted and display-ruled; the grant's provenance stays `user` until spec 1.2.
- **The dump writes no history line; a line is written when rows are about to reach a brain.** The chat door records a `read` (with the statement) only when `data_query` names a shared table — attach and line together, lazily; the scheduler door records once per step. The history coalesces identical sql-less reads within the minute like identical statements.
- **The type text of a source's columns never reaches a prompt or a CREATE**: the dump keeps a declared type only from an allow-list of SQLite affinity names; alias tables are created untyped.
- **One cap on the materialised SET** (8 MiB, grants in order; a grant past it is skipped and said), beside the per-table caps; the scheduler door shares one row budget across shared tables.
- **Aliases are de-collided against the reader's full object names** (registry tables and views, runtime tables, `snug_kv`, `sqlite_*`), so no alias table can exist on the reader's real database and a write naming one fails by absence.
- **The chat egress line is derived**: it appears only where the chat door can open (a keyed BYOK or local route), and the away line names the scheduled *ask <Reader>'s AI*.
- **The chat door stays open during a delegated run** (the user typed; rows reach the user's brain, never the frame); the scheduler door always reads the away set, *run now* included.
