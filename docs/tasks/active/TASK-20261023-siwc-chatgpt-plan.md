## Spec (what & why)

**What.** The Snug desktop app (macOS, Tauri) gains a third way for apps to think, beside *a key* (BYOK) and *a local model* (Ollama): **the user's own ChatGPT plan**, through OpenAI's *Sign in with ChatGPT* open-source/locally-hosted track. The user presses **Continue with ChatGPT** once; the system browser signs them in; from then on app thinks, builder turns and (per the owner's answer) scheduled "ask the AI" steps run on their plan through `POST https://api.openai.com/v1/responses`, with no API key anywhere. The hosted playground, the web kit and the local-host kit never offer it.

**Why.** Most people who would try Snug already pay for ChatGPT and do not have, or want, an API key. The owner's ask: *"an alternative to BYOK & local only on the Snug desktop app."* OpenAI's track is self-serve for open-source, locally-run apps (confirmed against the docs on 2026-10-23: *"This direct flow needs neither a client secret nor a partner API key"*; *"ChatGPT plan usage is available to open-source projects, personal projects that run locally, and selected private apps"*). `snugprotocol/snug` is **public and MIT** (verified 2026-10-23 with `gh repo view`: `visibility: PUBLIC`, licence `mit`), so Snug fits the open-source track as written; the session prompt's "private until the public flip" premise is stale (the flip happened 2026-08-26).

**What it is not.** Not a hosted custody model (ADR-0014 clause 4 stands: no broker, no server). Not a new brain for the host kit (Binding B's `codex` driver already rides a ChatGPT login via the CLI — ADR-0071; a direct Responses brain for the kit is a later, separate task). Not a fourth place for routing to drift: the mode rides the ONE derivation (`adapterKindFor`) and every seat that copies it.

### Acceptance criteria (each becomes at least one test; owner's ten, refined at Gate 1)

1. **Three choices on the desktop, two elsewhere.** `availableModes()` returns `['byok','local','chatgpt']` on the desktop platform and never includes `chatgpt` on web, the hosted build, or the host kit. The desktop Welcome shows three cards (key · local · ChatGPT plan) and Settings' "where the agent runs" segment shows three buttons; the web Settings segment shows two. A roaming file whose stored `mode` is `chatgpt` opened on a platform without the capability is **coerced** to the best available mode with the existing divergence note (`modeCoercedStore`), the stored setting untouched — the subscription-coercion precedent.
2. **Sign-in completes on the loopback, with dynamic registration persisted.** "Continue with ChatGPT" opens the authorize URL in the **system browser** with redirect `http://127.0.0.1:<ephemeral port>/auth/callback` (IP literal, `/auth/callback`, never `localhost`, never `/callback`), PKCE S256, a fresh `state` and `nonce` per attempt, `resource=https://api.openai.com/v1` and the six scopes. The first sign-in sends `client_id=dynamic_agent_client`, `agent_name_hint=Snug` and a stable opaque `ext_agent_host_id` (`urn:uuid:…`, minted once per machine); the callback's issued `oaiapp_…` client id and the host id persist. A second sign-in sends the issued client id, **omits** `agent_name_hint`, accepts a callback that omits `client_id`, and **refuses** one naming a different client. The code exchange is form-encoded, no secret, includes `code_verifier` and the same `redirect_uri` and `resource`. A re-auth on a different port works (measured).
3. **The ID token is validated; a grant without the plan scope is refused by name.** Signature against `https://auth.openai.com/.well-known/jwks.json` (RS256, by `kid`), `iss`, `aud` containing the issued client id, `exp`, `nonce`. A returning account's `sub` must match before tokens are replaced. A grant lacking `chatgpt.tokens.use.direct` leaves the session **signed in but plan-not-granted**: thinks refuse with `CHATGPT_PLAN_NOT_GRANTED` and its sentence, Settings offers "allow plan usage" (re-authorize with `prompt=consent`) and the key/local alternatives; nothing routes anywhere else.
4. **Thinks and builder turns stream on the plan, disclosed.** Every turn goes to `POST https://api.openai.com/v1/responses` with the bearer, `store:false`, `stream:true`, the system prompt in `instructions`, function tools as top-level `{type:'function', name, description, parameters}` (measured working 2026-10-23), the whole conversation as input items every turn (`function_call` / `function_call_output` for the tool loop), `reasoning.effort` only when a level is chosen, and **none** of `temperature, top_p, max_output_tokens, max_tool_calls, metadata, user, truncation, previous_response_id, background, conversation, moderation, multi_agent, prompt, prompt_cache_retention, safety_identifier, top_logprobs` and no system-role input item. The builder's tool loop (KB consult → `artifact_write` → sign-off) completes against recorded fixtures. The brain chip reads **ChatGPT plan**; its popover and the Settings card say **Using ChatGPT plan** with a **Manage usage** link to `https://chatgpt.com/settings/usage`.
5. **An expiring token refreshes once under concurrency.** With N concurrent thinks and a scheduled run arriving on a token inside the skew window, exactly **one** `grant_type=refresh_token` POST is made (issued `client_id`, `refresh_token`, `resource`, no `scope`); every caller proceeds on the rotated token; `access_token`, `expires_in`, `scope`, `refresh_token`, `id_token` and `earliest_refresh_at` are replaced **together and atomically** (persisted before the new ID token is re-verified, so a JWKS outage cannot lose the only valid refresh token); no refresh is attempted before `earliest_refresh_at`; a turn's abort never cancels a refresh in flight.
6. **Revoked access or a failed refresh is a named sign-in-needed state; nothing reroutes.** `invalid_grant` or `refresh_token_reused` on refresh, or a 401 (`invalid_api_key` / `subscription_sharing_invalid_user`) that survives one refresh-and-retry, clears the tokens (keeping the registration) and sets `CHATGPT_SIGN_IN_NEEDED`; the mode stays `chatgpt`, the chip shows the remedy, and no turn is sent to a key, a local model or the demo brain. A **transient** network failure keeps the tokens and returns a retryable error.
7. **A usage limit is a named message whose primary action is Manage usage; nothing reroutes.** `response.failed` mid-stream with `error.code = subscription_sharing_usage_limit_exceeded` (or HTTP 429 before the stream) → `CHATGPT_USAGE_LIMIT`, copy *"Usage limit reached — Review your plan or this app's limit in ChatGPT settings."*, primary action **Manage usage**; `subscription_sharing_usage_unavailable` (or 503) → `CHATGPT_USAGE_UNAVAILABLE`, retryable with bounded backoff, tokens kept. A scheduled step hitting either is **refused by name**, never rerouted.
8. **Models and levels come from the account.** After sign-in `GET /v1/models` (bearer) fills the list from `models[]` entries with `visibility:'list'` — `slug` as the id, `display_name` as the label, `supported_reasoning_levels` / `default_reasoning_level` as the level vocabulary — in the server's order, refreshed on each sign-in and on Settings open, cached per machine, failing soft to the last list. No hardcoded catalogue. The default model and level are settings rows (`providerModel:chatgpt`, `providerEffort:chatgpt`); per-app pins (`appModel:<appId>`, model-only like local) keep working, resolve per send, and a pinned id absent from the plan's list is still shown as "(not on your plan)" and still routes (fails visibly), never hidden or re-routed.
9. **Sign-out leaves no token behind.** It best-effort revokes the refresh token at the discovery document's `revocation_endpoint` (`token`, `token_type_hint=refresh_token`, `client_id`; empty 200 is success; an unconfirmed revocation is **told to the user**), deletes the tokens from the Rust store and memory, keeps the registration (client id + host id) so the next sign-in reuses it, clears the cached model list, and shows the pointer *"to remove Snug from your account entirely, disconnect it in ChatGPT → Settings."*
10. **Tokens never reach an app, an export, a share, the inspector or a log.** Negative tests: an app envelope cannot carry an `Authorization` header to the plan route; `exportUserDb({includeSecrets:true})` bytes and a share bundle contain no token (they live in neither `snug_secrets` nor any table); the inspector's round-trip request has no header field by type and its display redaction masks a bare JWT (`eyJ…`) shape; a 401/400 body that echoes the bearer is scrubbed to `***` before it becomes an error `message`; no `console.*` on the auth or adapter paths; the Rust session file is `0600` in a `0700` directory, written temp+rename, and readable by **no** command other than the three `chatgpt_session_*` commands; the in-shell gate proves those commands are unreachable from a sandboxed app frame.
11. **The one-time notice shows once.** After the first successful sign-in on this file: heading *"You're using your ChatGPT plan"*, body *"Eligible usage in this app uses your ChatGPT plan. Manage usage in your ChatGPT settings."*, button *"Got it"* — never again (settings row `chatgptNoticeShown`).
12. **The adapter is honest about streams and caps.** A 2xx with **no `content-type` header** is parsed as SSE; `response.metadata` and unknown events are ignored; a stream ending without `response.completed` returns `STREAM_DROPPED` with partial text; `response.incomplete` with `incomplete_details.reason = max_output_tokens` returns `stopReason:'max_tokens'`; a turn whose output exceeds the ceiling (`maxOutputTokens` when the caller sets one, else the adapter's default) is **aborted client-side** and returns `max_tokens` with the partial text — the only cap available while `max_output_tokens` is rejected by the docs.
13. **The desktop gate stays green with the new surface.** The in-shell hard gate gains rows proving `chatgpt_session_read|write|clear` are unreachable from an app frame and dispatchable from the main window; `cargo test` covers file mode, atomic write and clear.
14. **Scheduled "ask the AI" steps** follow the owner's interview answer (recommended default: a signed-in plan is a real brain — allowed, with limits refused by name; a signed-out plan is refused by name like a keyless key).

**Out of scope** (each queued in next-steps at close): the host kit / Binding B brain on this route (ADR-0071's `codex` driver stays as is); multiple ChatGPT accounts per machine (one session; the docs' multi-registration rules are recorded for later); image/file inputs; a web-search tool; macOS Keychain custody (R-3 says keychain wrapping is pre-1.0 out of scope; the `0600` file follows OpenAI's documented minimum and Codex's own `auth.json` posture); the hosted/web playground; Windows; a per-app effort pin; `id_token_hint`/`login_hint` reauth shortcuts; a "forget this computer" that also drops the registration; a desktop release (its own explicit ask, ADR-0047 — this ships in v0.1.4 or later).

## Plan

### §1 Decisions (each justified; the ADR carries the long form)

**D1 — Mode shape: a first-class third `PlaygroundMode = 'chatgpt'`, not a BYOK provider variant.** BYOK's whole shape is "a key the user pasted" — `byok:<provider>` secret rows, key-presence derivation, per-provider default rows, the keyless → demo fall-through. A ChatGPT session is an *account*: sign-in/out lifecycle, rotation, consent, usage limits. Grafting it onto `ByokProvider` would put a refresh token under `byok:` (which roams to Dropbox and into `includeSecrets` exports) and make "which provider has a key" lie. A third mode rides every seat the other two ride: `DirectMode`, `AdapterKind`/`ADAPTER_KINDS`, `ActiveBrainKind` and the chip's label map (ADR-0059's AC1 matrix test is the tripwire), `availableModes()`, the W2b coercion, `resolveModelForApp`, `egress.ts`'s `chatDoorOpen`/`readerBrainRoute`, `appThink.ts`'s `keylessBrainGate`, `webllm.ts`'s `resolveTurnMode`, `ModelSelect`/`BuilderModelSelect`, Settings and Welcome. The derivation is copied in four places today (lesson 2026-09, L287) — the plan enumerates every one (§3 L4) and a test asserts the new kind appears in each.

**D2 — Custody: the tokens are a per-machine credential, held by the Rust side in a `0600` file; the webview runs the protocol and holds a token only in memory per use. They are NOT written to the user file.** Three reasons, any one sufficient: (a) **rotation** — the refresh token rotates on every refresh, so a copy that travelled with the `.snug` file to a second machine (Dropbox, export-with-secrets) would log one side out and trip `refresh_token_reused` (ADR-0071 rejected copying Codex's `auth.json` for exactly this); (b) **per-host registration** — the issued client is bound to this machine's `ext_agent_host_id`; (c) **OpenAI's rule** — *"Keep tokens out of browser storage… logs… Never put tokens in URLs"*, and the DevKit keeps decrypted credentials out of renderer processes. This is a scoped, recorded exception to ADR-0014's "every credential lives in `snug_secrets`" (which exists for *portability*; here portability is the bug), and it follows ADR-0070 §5's precedent that per-machine brain facts never enter the user file. **Division of labour:** Rust = custody only (`chatgpt_session_read/write/clear` over `~/Snug/chatgpt-plan.json`, dir `0700`, file `0600`, temp+rename+fsync like `userfile.rs`; no policy, no network, nothing logged); `packages/auth` = the protocol (PKCE, state, discovery, exchange, ID-token validation, refresh single-flight, revocation) as a DI-pure, fixture-tested module reusing the reviewed primitives (`generatePkceVerifier`, `pkceChallenge`, `signState`/`verifyState`, `postForm`'s redirect guard and echo scrub, the loopback transport core). The access token is read from the keeper per send, like `CredentialStore` ("no long-lived plaintext token cache"), and never enters `TurnAdapterConfig` (no `key` for this mode) — the adapter receives a `getBearer()` seam. **Alternatives weighed:** the user file (rejected above); the whole flow in Rust (reqwest streaming proxy + a JWT crate: more unreviewed Rust on a credential path, duplicates reviewed TS — ADR-0021's own reasoning against hand-rolled listeners); macOS Keychain (deferred: new dependency + ADR; the file follows OpenAI's documented minimum). **Residual, recorded in the delta:** the file is plaintext at rest and outside `.snug` passphrase encryption (R-3's posture), and a host-page compromise (R-1) holds the access token in memory exactly as it holds BYOK keys today.

**D3 — The Responses adapter** (`packages/adapters/src/openai-responses.ts`), behind `runAgentTurn`, injected `FetchLike`, fixture-only tests. Request: `{model, instructions: system, input, tools?, reasoning?: {effort}, store:false, stream:true}`; `input` maps `user` → `{role:'user', content}`, assistant text → `{role:'assistant', content}`, assistant tool calls → `{type:'function_call', call_id, name, arguments}`, tool results → `{type:'function_call_output', call_id, output}` — `runAgentTurn` already resends the whole conversation each iteration, which IS the full-context rule. Stream: detect by 2xx (never the header); `response.output_text.delta` → `onDelta`; function calls assembled from `output_item.added` + `function_call_arguments.delta/.done` (ordered by `output_index`); `response.completed` → ok (+ `usage`, wire `model`); `response.incomplete` → ok with `stopReason:'max_tokens'` when the reason is `max_output_tokens`, else an error naming the reason; `response.failed` → the named codes (D5) or `HOST_ERROR` with the scrubbed message; `error` events likewise; unknown events ignored; end-without-terminal → `STREAM_DROPPED` + partial. Pre-stream HTTP: 400 `{detail}` → `HOST_ERROR` (scrubbed, 200 chars); 401 → one single-flight refresh + retry, then `CHATGPT_SIGN_IN_NEEDED`; 403 codes → named, non-retryable; 429 → `CHATGPT_USAGE_LIMIT`; 503 → `CHATGPT_USAGE_UNAVAILABLE` retryable. **Output cap without `max_output_tokens`:** a client-side ceiling — abort the stream once accumulated output passes `maxOutputTokens × 4` chars (or the adapter default), return `max_tokens` + partial — the same contract a provider cap gives the bridge (ADR-0018 D4), honestly a soft cap (usage is spent up to the abort). The loop's `DEFAULT_MAX_ITERATIONS` still bounds tool loops. **Caching:** `cache` is ignored (the route reports `cached_tokens` on its own). **Never** `backend-api`; base URL pinned to `https://api.openai.com/v1`.

**D4 — Single-flight refresh** in the auth module's session keeper: one in-flight promise shared by every caller (five `runAgentTurn` call sites + the scheduler live in the one page realm; `tauri-plugin-single-instance` guarantees one shell per file, and the Rust write is atomic). `getAccessToken()` refreshes when `now ≥ expiresAt − 60 s` AND `now ≥ earliest_refresh_at`; a forced refresh (after a 401) first checks the failing token is still the current one (another caller may already have rotated it) and otherwise reuses the new token; the rotated set is persisted **before** the new ID token is re-verified (crash-safe rotation — the DevKit's pattern); the refresh runs on its own 15 s timeout, never on a turn's `signal`; `invalid_grant` / `refresh_token_reused` → clear tokens, keep registration, `sign-in-needed`; network failure → keep everything, retryable error; before `earliest_refresh_at` with an expired access token → `sign-in-needed` (never a storm). AC5's test drives N concurrent `complete()`s and asserts one refresh POST.

**D5 — Disclosure and failure, named, never rerouted.** New host-level codes exported from adapters: `CHATGPT_SIGN_IN_NEEDED`, `CHATGPT_PLAN_NOT_GRANTED`, `CHATGPT_USAGE_LIMIT`, `CHATGPT_USAGE_UNAVAILABLE` (apps render unknown codes as `HOST_ERROR` honouring `retryable` — R5). `adapterKindFor({mode:'chatgpt'})` is `'chatgpt'` whether or not a session exists — the mode is the user's explicit choice and **a missing session is a named result from the adapter** (the `hostBrainGone` pattern: a result, never a throw, never the demo script standing in). This deliberately differs from BYOK's keyless → demo fall-through: the owner's rule is *never fall back silently*, scheduled jobs already refuse keyless brains by name, and the chip must never say "demo brain" when the user chose their plan. The chip: label *ChatGPT plan*; sub-line *sign in needed* / *plan not allowed* / *limit reached*; popover *Using ChatGPT plan · <email>* + Manage usage + model/level + sign out. Each named state has one sentence a person can act on (lesson L449). The limit message's primary action is Manage usage everywhere it renders (builder chat, run view, schedule step).

**D6 — Models and effort from the account, in OpenAI's vocabulary** (ADR-0070 §3/§4: no invented mapping, no hardcoded list). The session keeper exposes `listModels()`; the list and the per-model levels are cached in the Rust session file's non-secret section (per machine, like ADR-0070 §5) and in memory; `providerModel:chatgpt` and `providerEffort:chatgpt` are settings rows in the user file (the precedent for defaults — ADR-0046 §2 — a roaming file on a machine with no session simply shows sign-in needed); per-app pins reuse `appModel:<appId>` model-only (the local-mode shape — no `appProvider` row, because a pin here is not a byok routing); a model id passes `isModelId` (leading alnum, no whitespace/control) at the settings boundary (C5, ADR-0070 review). The chip's level picker renders only when the resolved model has levels (ADR-0070 amendment's Haiku rule). What ANSWERED is shown from `response.completed.response.model` (ADR-0059 rule 2).

**D7 — Sign-out** = best-effort revocation (discovery `revocation_endpoint`, host-ceilinged to `auth.openai.com`, `redirect:'manual'`, 5 s timeout, outcome told), local delete via `chatgpt_session_clear` (tokens + cached models; registration kept), memory cleared, and the pointer to ChatGPT → Settings to disconnect the app. Disconnects made in ChatGPT are not announced: detected on the next failed request/refresh (AC6).
