## Spec (what & why)

**What.** The Snug desktop app (macOS, Tauri) gains a third way for apps to think, beside *a key* (BYOK) and *a local model* (Ollama): **the user's own ChatGPT plan**, through OpenAI's *Sign in with ChatGPT* open-source/locally-hosted track. The user presses **Continue with ChatGPT** once; the system browser signs them in; from then on app thinks, builder turns and (per the owner's answer) scheduled "ask the AI" steps run on their plan through `POST https://api.openai.com/v1/responses`, with no API key anywhere. The hosted playground, the web kit and the local-host kit never offer it.

**Why.** Most people who would try Snug already pay for ChatGPT and do not have, or want, an API key. The owner's ask: *"an alternative to BYOK & local only on the Snug desktop app."* OpenAI's track is self-serve for open-source, locally-run apps (confirmed against the docs on 2026-10-23: *"This direct flow needs neither a client secret nor a partner API key"*; *"ChatGPT plan usage is available to open-source projects, personal projects that run locally, and selected private apps"*). `snugprotocol/snug` is **public and MIT** (verified 2026-10-23 with `gh repo view`: `visibility: PUBLIC`, licence `mit`), so Snug fits the open-source track as written; the session prompt's "private until the public flip" premise is stale (the flip happened 2026-08-26).

**What it is not.** Not a hosted custody model (ADR-0014 clause 4 stands: no broker, no server). Not a new brain for the host kit (Binding B's `codex` driver already rides a ChatGPT login via the CLI — ADR-0071; a direct Responses brain for the kit is a later, separate task). Not a fourth place for routing to drift: the mode rides the ONE derivation (`adapterKindFor`) and every seat that copies it.

### Acceptance criteria (each becomes at least one test; owner's ten, refined at Gate 1)

1. **Three choices on the desktop, two elsewhere.** `availableModes()` returns `['byok','local','chatgpt']` on the desktop platform and never includes `chatgpt` on web, the hosted build, or the host kit. The desktop Welcome shows three cards (key · local · ChatGPT plan) and Settings' "where the agent runs" segment shows three buttons; the web Settings segment shows two. A roaming file whose stored `mode` is `chatgpt` opened on a platform without the capability is **coerced** to the best available mode with the existing divergence note (`modeCoercedStore`), the stored setting untouched — the subscription-coercion precedent.
2. **Sign-in completes on the loopback, with dynamic registration persisted.** "Continue with ChatGPT" opens the authorize URL in the **system browser** with redirect `http://127.0.0.1:<ephemeral port>/auth/callback` (IP literal, `/auth/callback`, never `localhost`, never `/callback`), PKCE S256, a fresh `state` and `nonce` per attempt, `resource=https://api.openai.com/v1` and the six scopes. The first sign-in sends `client_id=dynamic_agent_client`, `agent_name_hint=Snug` and a stable opaque `ext_agent_host_id` (`urn:uuid:…`, minted once per machine); the callback's issued `oaiapp_…` client id and the host id persist. A second sign-in sends the issued client id, **omits** `agent_name_hint`, accepts a callback that omits `client_id`, and **refuses** one naming a different client. The code exchange is form-encoded, no secret, includes `code_verifier` and the same `redirect_uri` and `resource`; the issued client id is persisted **only after** the exchange succeeds and the ID token's `aud` contains it. A re-auth on a different port works (measured). A declined or cancelled sign-in (`?error=access_denied&state=…`) ends the flow by name, and the UI offers a visible cancel while the browser is open.
3. **The ID token is validated; a grant without the plan scope is refused by name.** Signature against `https://auth.openai.com/.well-known/jwks.json` (`alg` must be RS256 — `none`/HS256 refused — the key imported as RSASSA-PKCS1-v1_5/SHA-256 regardless of the header, JWKs filtered by `kty:RSA`/`use:sig`, a `kid` miss refetches once), `iss`, `aud` containing the issued client id (`azp` checked when `aud` has more than one entry), `exp` with a bounded skew, `nonce`. A returning account's `sub` must match before tokens are replaced; a refresh's ID token is checked for `iss`/`sub`/`aud` equal to the stored values (no nonce). A grant lacking `chatgpt.tokens.use.direct` leaves the session **signed in but plan-not-granted**: thinks refuse with `CHATGPT_PLAN_NOT_GRANTED` and its sentence, Settings offers "allow plan usage" (re-authorize with `prompt=consent`) and the key/local alternatives; nothing routes anywhere else.
4. **Thinks and builder turns stream on the plan, disclosed.** Every turn goes to `POST https://api.openai.com/v1/responses` with the bearer, `store:false`, `stream:true`, the system prompt in `instructions`, function tools as top-level `{type:'function', name, description, parameters}` (measured working 2026-10-23), the whole conversation as input items every turn (`function_call` / `function_call_output` for the tool loop), `reasoning.effort` only when a level is chosen, and **none** of `temperature, top_p, max_output_tokens, max_tool_calls, metadata, user, truncation, previous_response_id, background, conversation, moderation, multi_agent, prompt, prompt_cache_retention, safety_identifier, top_logprobs` and no system-role input item. The builder's tool loop (KB consult → `artifact_write` → sign-off) completes against recorded fixtures. The brain chip reads **ChatGPT plan**; its popover and the Settings card say **Using ChatGPT plan** with a **Manage usage** link to `https://chatgpt.com/settings/usage`.
5. **An expiring token refreshes once under concurrency.** With N concurrent thinks and a scheduled run arriving on a token inside the skew window, exactly **one** `grant_type=refresh_token` POST is made (issued `client_id`, `refresh_token`, `resource`, no `scope`); every caller proceeds on the rotated token; `access_token`, `expires_in`, `scope`, `refresh_token`, `id_token` and `earliest_refresh_at` are replaced **together and atomically** (persisted before the new ID token is re-verified, so a JWKS outage cannot lose the only valid refresh token); no refresh is attempted before `earliest_refresh_at`; a turn's abort never cancels a refresh in flight.
6. **Revoked access or a failed refresh is a named sign-in-needed state; nothing reroutes.** `invalid_grant` or `refresh_token_reused` on refresh, or a 401 (`invalid_api_key` / `subscription_sharing_invalid_user`) that survives one refresh-and-retry, clears the tokens (keeping the registration) and sets `CHATGPT_SIGN_IN_NEEDED`; the mode stays `chatgpt`, the chip shows the remedy, and no turn is sent to a key, a local model or the demo brain. A **transient** network failure keeps the tokens and returns a retryable error.
7. **A usage limit is a named message whose primary action is Manage usage; nothing reroutes.** `response.failed` mid-stream with `error.code = subscription_sharing_usage_limit_exceeded` (or HTTP 429 before the stream) → `CHATGPT_USAGE_LIMIT`, copy *"Usage limit reached — Review your plan or this app's limit in ChatGPT settings."*, primary action **Manage usage**; `subscription_sharing_usage_unavailable` (or 503) → `CHATGPT_USAGE_UNAVAILABLE`, retryable with bounded backoff, tokens kept. A scheduled step hitting either is **refused by name**, never rerouted.
8. **Models and levels come from the account.** After sign-in `GET /v1/models` (bearer) fills the list from `models[]` entries with `visibility:'list'` — `slug` as the id, `display_name` as the label, `supported_reasoning_levels` / `default_reasoning_level` as the level vocabulary — in the server's order, refreshed on each sign-in and on Settings open, cached per machine, failing soft to the last list. No hardcoded catalogue. The default model and level are settings rows (`providerModel:chatgpt`, `providerEffort:chatgpt`); per-app pins (`appModel:<appId>`, model-only like local) keep working, resolve per send, and a pinned id absent from the plan's list is still shown as "(not on your plan)" and still routes (fails visibly), never hidden or re-routed.
9. **Sign-out leaves no token behind.** It best-effort revokes the refresh token at the discovery document's `revocation_endpoint` (`token`, `token_type_hint=refresh_token`, `client_id`; empty 200 is success; an unconfirmed revocation is **told to the user**), deletes the tokens from the Rust store and memory, keeps the registration (client id + host id) so the next sign-in reuses it, clears the cached model list, and shows the pointer *"to remove Snug from your account entirely, disconnect it in ChatGPT → Settings."* A separate **"forget this registration"** act in Settings drops the client id and host id too (for the case where a ChatGPT-side disconnect deleted the client and the kept registration would lock the user out).
10. **Tokens never reach an app, an export, a share, the inspector or a log.** Negative tests: an app envelope cannot carry an `Authorization` header to the plan route; `exportUserDb({includeSecrets:true})` bytes and a share bundle contain no token (they live in neither `snug_secrets` nor any table); the inspector's round-trip request has no header field by type and its display redaction masks a bare JWT (`eyJ…`) shape; a 401/400 body that echoes the bearer is scrubbed to `***` before it becomes an error `message`; no `console.*` on the auth or adapter paths; the Rust session file is `0600` in a `0700` directory, written temp+rename, and readable by **no** command other than the three `chatgpt_session_*` commands; the in-shell gate proves those commands are unreachable from a sandboxed app frame.
11. **The one-time notice shows once.** After the first successful sign-in on this file: heading *"You're using your ChatGPT plan"*, body *"Eligible usage in this app uses your ChatGPT plan. Manage usage in your ChatGPT settings."*, button *"Got it"* — never again (settings row `chatgptNoticeShown`).
12. **The adapter is honest about streams and caps.** A 2xx with **no `content-type` header** is parsed as SSE; `response.metadata` and unknown events are ignored; a stream ending without `response.completed` returns `STREAM_DROPPED` with partial text; `response.incomplete` with `incomplete_details.reason = max_output_tokens` returns `stopReason:'max_tokens'`; a turn whose output exceeds the ceiling (`maxOutputTokens` when the caller sets one, else the adapter's default) is **aborted client-side** and returns `max_tokens` with the partial text — the only cap available while `max_output_tokens` is rejected by the docs.
13. **The desktop gate stays green with the new surface.** The in-shell hard gate gains rows proving `chatgpt_session_read|write|clear` are unreachable from an app frame and dispatchable from the main window; `cargo test` covers file mode, atomic write and clear.
14. **Scheduled "ask the AI" steps** follow the owner's interview answer (recommended default: a signed-in plan is a real brain — allowed, with limits refused by name; a signed-out plan is refused by name like a keyless key).

**Out of scope** (each queued in next-steps at close): the host kit / Binding B brain on this route (ADR-0071's `codex` driver stays as is); multiple ChatGPT accounts per machine (one session; the docs' multi-registration rules are recorded for later); image/file inputs; a web-search tool; macOS Keychain custody (R-3 says keychain wrapping is pre-1.0 out of scope; the `0600` file follows OpenAI's documented minimum and Codex's own `auth.json` posture); the hosted/web playground; Windows; a per-app effort pin; `id_token_hint`/`login_hint` reauth shortcuts; a "forget this computer" that also drops the registration; a desktop release (its own explicit ask, ADR-0047 — this ships in v0.1.4 or later).

## Plan

### §1 Decisions (each justified; the ADR carries the long form)

**D1 — Mode shape: a first-class third `PlaygroundMode = 'chatgpt'`, not a BYOK provider variant.** BYOK's whole shape is "a key the user pasted" — `byok:<provider>` secret rows, key-presence derivation, per-provider default rows, the keyless → demo fall-through. A ChatGPT session is an *account*: sign-in/out lifecycle, rotation, consent, usage limits. Grafting it onto `ByokProvider` would put a refresh token under `byok:` (which roams to Dropbox and into `includeSecrets` exports) and make "which provider has a key" lie. A third mode rides every seat the other two ride: `DirectMode`, `AdapterKind`/`ADAPTER_KINDS`, `ActiveBrainKind` and the chip's label map (ADR-0059's AC1 matrix test is the tripwire), `availableModes()`, the W2b coercion, `resolveModelForApp`, `egress.ts`'s `chatDoorOpen`/`readerBrainRoute`, `appThink.ts`'s `keylessBrainGate`, `webllm.ts`'s `resolveTurnMode`, `ModelSelect`/`BuilderModelSelect`, Settings and Welcome. The derivation is copied in four places today (lesson 2026-09, L287) — the plan enumerates every one (§3 L4) and a test asserts the new kind appears in each.

**D2 — Custody: the tokens are a per-machine credential, held by the Rust side in a `0600` file; the webview runs the protocol and holds a token only in memory per use. They are NOT written to the user file.** Three reasons, any one sufficient: (a) **rotation** — the refresh token rotates on every refresh, so a copy that travelled with the `.snug` file to a second machine (Dropbox, export-with-secrets) would log one side out and trip `refresh_token_reused` (ADR-0071 rejected copying Codex's `auth.json` for exactly this); (b) **per-host registration** — the issued client is bound to this machine's `ext_agent_host_id`; (c) **OpenAI's rule** — *"Keep tokens out of browser storage… logs… Never put tokens in URLs"*, and the DevKit keeps decrypted credentials out of renderer processes. This is a scoped, recorded exception to ADR-0014's "every credential lives in `snug_secrets`" (which exists for *portability*; here portability is the bug), and it follows ADR-0070 §5's precedent that per-machine brain facts never enter the user file. **Division of labour:** Rust = custody only — `chatgpt_session_read / write / clear` over **`~/Snug/.chatgpt-plan/session.json`** (a dot-prefixed subdirectory the shell creates `0700`; the file `0600` via `OpenOptions::mode(0o600)` + `create_new` on the temp, then rename + fsync; payload treated as opaque bytes with a size cap, no serde — a serde type error would quote the offending string back; no policy, no network, nothing logged). **Why a dot directory (Gate-2 blocker, both reviews):** `userfile.rs`'s `valid_name` admits any bare name in `~/Snug`, so a plain `chatgpt-plan.json` would have been readable and overwritable by the existing `read_user_file` / `write_user_file` commands; `valid_name` refuses a leading `.` and any separator, so the dot-dir path is unreachable by them — pinned by `cargo test` on both impl functions. `~/Snug` itself is NOT chmod'ed (it holds `user.snug` and the sidecar socket). `packages/auth` = the protocol (PKCE, state, discovery, exchange, ID-token validation, refresh single-flight, revocation) as a DI-pure, fixture-tested module reusing the reviewed primitives (`generatePkceVerifier`, `pkceChallenge`, `signState`/`verifyState`, the loopback transport core, and `postForm`'s redirect guard + echo scrub **extracted to a free function that also returns the parsed OAuth `error` code** — a refactor of a reviewed security seat, so characterization tests of today's scrub and redirect behaviour are written FIRST, TDD rule 6). **The keeper holds no long-lived token in memory** (the `CredentialStore` rule): every use reads the file inside **one serial mutation queue with a session epoch** — refresh, model-cache update, sign-in and sign-out all pass through it, so a sign-out racing an in-flight refresh cannot be resurrected by the refresh's late write (the epoch bump makes the refresh's result discarded AND revoked), and a model-cache read-modify-write can never write a stale refresh token back. Memory holds only status, account display data, the cached model list, the epoch and the in-flight promise. The access token never enters `TurnAdapterConfig` (no `key` for this mode) — the adapter receives a `BearerSource` seam (§2). **The IPC wall, stated correctly (security review):** Tauri capabilities do not scope custom commands (no `AppManifest` in `build.rs`); the wall for these three commands is the invoke key, exactly as for `read_user_file`, which already returns every BYOK key — unreachable from a sandboxed frame on macOS (ADR-0021 §8 / D8), proven by the gate rows (AC13). `capabilities/main.json` is unchanged; an `AppManifest` listing commands is queued, not done here. **Alternatives weighed:** the user file (rejected above); the whole flow in Rust (reqwest streaming proxy + a JWT crate: more unreviewed Rust on a credential path, duplicates reviewed TS — ADR-0021's own reasoning against hand-rolled listeners); macOS Keychain (deferred: new dependency + ADR; the file follows OpenAI's documented minimum). **Residual, recorded in the delta:** the file is plaintext at rest and outside `.snug` passphrase encryption (R-3's posture), and a host-page compromise (R-1) holds the access token in memory exactly as it holds BYOK keys today.

**D3 — The Responses adapter** (`packages/adapters/src/openai-responses.ts`), behind `runAgentTurn`, injected `FetchLike`, fixture-only tests. Request: `{model, instructions: system, input, tools?, reasoning?: {effort}, store:false, stream:true}`; `input` maps `user` → `{role:'user', content}`, assistant text → `{role:'assistant', content}`, assistant tool calls → `{type:'function_call', call_id, name, arguments}`, tool results → `{type:'function_call_output', call_id, output}` — `runAgentTurn` already resends the whole conversation each iteration, which IS the full-context rule. Stream: detect by 2xx (never the header); `response.output_text.delta` → `onDelta`; function calls assembled from `output_item.added` + `function_call_arguments.delta/.done` (ordered by `output_index`); `response.completed` → ok (+ `usage`, wire `model`); `response.incomplete` → ok with `stopReason:'max_tokens'` when the reason is `max_output_tokens`, else an error naming the reason; `response.failed` → the named codes (D5) or `HOST_ERROR` with the scrubbed message; `error` events likewise; unknown events ignored; end-without-terminal → `STREAM_DROPPED` + partial. Pre-stream HTTP: **401 and 403 never forward provider prose** — they map to the named code with a fixed sentence (the measured 401 echoes the bearer; OpenAI's masked-prefix echoes defeat value scrubs); 401 → one single-flight refresh + retry, then `CHATGPT_SIGN_IN_NEEDED`; 403 codes → named, non-retryable; 429 → `CHATGPT_USAGE_LIMIT`; 503 → `CHATGPT_USAGE_UNAVAILABLE` retryable; 400 `{detail}` and stream `response.failed` messages → `HOST_ERROR` carrying the detail only after **(1)** `BearerSource.redact(text)` — the auth side's `scrubAuthValues` over the bearer **of the attempt that failed** (after a refresh-and-retry the second 401 echoes a different token), applied after any `JSON.parse` extraction (lesson L206) and **before** the 200-char cap (a token straddling the cut would otherwise leave an unmatched prefix) — and **(2)** a JWT-shape backstop (`eyJ…`.`…`.`…` → `***`) whose regex is **single-homed in `packages/protocol`** beside the existing key-shape guard (R-24) and imported by both the adapter and the playground's `credentialShapes` display mode (lesson L191: one home for a shape). **Output cap without `max_output_tokens`:** a client-side ceiling — abort the stream once accumulated output passes `maxOutputTokens × 4` chars (or the adapter default), return `max_tokens` + partial — the same contract a provider cap gives the bridge (ADR-0018 D4), honestly a soft cap (usage is spent up to the abort). The loop's `DEFAULT_MAX_ITERATIONS` still bounds tool loops. **Caching:** `cache` is ignored (the route reports `cached_tokens` on its own). **Never** `backend-api`; base URL pinned to `https://api.openai.com/v1`.

**D4 — Single-flight refresh** in the auth module's session keeper: one in-flight promise shared by every caller (five `runAgentTurn` call sites + the scheduler live in the one page realm; `tauri-plugin-single-instance` guarantees one shell per file, and the Rust write is atomic). `getAccessToken()` refreshes **proactively** when `now ≥ expiresAt − 60 s` AND `now ≥ earliest_refresh_at`; a **forced** refresh (the token is expired, or a 401 came back) treats `earliest_refresh_at` as **advisory** (fresh-context review: its value was never recorded — the spike's refresh ignored it and succeeded — so a hard floor could force a sign-in every hour; the owner may record the offset with the spike's new `capture` command) and lets the server decide — a server "not ready" answer is `refresh_not_ready`, **retryable, tokens kept, never a sign-in**; a forced refresh first checks the failing token is still the current one (another caller may already have rotated it) and otherwise reuses the new token; the rotated set is persisted **before** the new ID token is re-verified (crash-safe rotation — the DevKit's pattern); after persist, a JWKS **network** error keeps the tokens and retries verification later, a bad signature or a `sub` mismatch clears them and names `sign-in-needed`; the refresh runs on its own 15 s timeout, never on a turn's `signal`, and a timeout earns **at most one retry** before `sign-in-needed`; `invalid_grant` / `refresh_token_reused` → clear tokens, keep registration, `sign-in-needed`; network failure → keep everything, retryable error. All of it inside the serial queue + epoch of D2, and the desktop's close-requested flush handshake (`lib.rs` `close_flush_done`) **awaits an in-flight persist** so a window close cannot land between the token POST and the write. AC5's test drives N concurrent `complete()`s and a scheduled run and asserts one refresh POST; a second test defers the refresh fetch, signs out, resolves it, and asserts no token in the file or memory; a third interleaves a model-cache write with a refresh and asserts the rotated refresh token survives.

The chip: label *ChatGPT plan*; sub-line *sign in needed* / *plan not allowed* / *limit reached*; popover *Using ChatGPT plan · <email>* + Manage usage + model/level + sign out.
