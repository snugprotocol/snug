## Spec (what & why)

Today every Snug app is an island: its data lives as `app_<token>__*` tables materialised into its own runtime database, its `dbNamespace` is host-assigned, and no frame lets one app see another's rows. That isolation is a security property (ADR-0010, C2) and a product gap: a budget app cannot read the ledger, a meal planner cannot read the pantry, two apps the same person built cannot cooperate. The owner asked for **cross-app data sharing where the user is in full control and has complete transparency**: App A reads App B's data only with the user's explicit permission; that permission can be one-time, time-limited or indefinite, revocable at any moment; the user is told plainly what is shared and **where the data can go**; once allowed, reads are frictionless until expiry; **the app giving access keeps the log**; one app may share with many, in either direction (two grants); a running app can **discover** relevant apps — with the user's permission; a UI that is plainer than Apple's permission sheets yet more transparent, native to the runner, shipped in every shell from one source; the spec bumped and the whitepaper to follow.

The design in one paragraph (ADR-0075): an **access grant** is a host record — `{ reader app, source app, tables (with their columns), read-only, purpose, duration, unattended?, status }` — written **only by the user's act on a host surface the app cannot forge**, kept as a namespaced `snug_settings` row so it travels with the file. A reader asks over a new frame pair (`snug:access-request`, strict, `op ∈ request | query | list | release` / `snug:access-response`, tolerant), routed by the runner to a **host-assigned** access handler exactly as db/net are (value-blind runner; the announce `appId` never identifies anyone). An app's `request` renders a **strip** above its frame ("Budget wants to read another app's data · Budget says: “…” · review · not now · stop asking") — never a modal (ADR-0074 §4's rule for app-originated asks); `review`, a user act on host chrome, opens the **consent sheet**: who is asking (the library row's name and tile, plus a provenance line the host derives — built here · installed from a share link · handed in by your agent · a starter), the user's apps ranked by relevance to the stated purpose with their tables, columns and row counts, a duration (while it's open · a day · a week · until I stop it — the session grant is the default), an optional *also while I'm away* for scheduled runs, and **where Budget can send what it reads** (its AI by name, each connection by provider, "any link it asks you to open", the sentence that the copy is made here and the source keeps a history of every read). The app learns only what was granted. `query` runs ONE read-only `SELECT` on a **scoped scratch copy of the source's data from which every trigger, view, non-granted table and `snug_kv` has been physically dropped**, inside a **dedicated Web Worker with its own sql.js instance under a 2 s wall-clock bound** (sql.js has no interrupt; an unbounded recursive query would otherwise hang every shell), rows and bytes capped, credential-named or credential-shaped cells masked, every read **logged on the source's row**. Revoke anywhere — the source's header sheet, the reader's, Settings, or the reader itself (`release`) — takes effect on the next query and rings the reader a hint (`host-event 'access-changed'`, ids only). An untrusted import lands every grant **suspended** unless intent-identical to a local one; a shared or agent update of the reader suspends its grants and the update confirm names them; a change to a granted table's columns suspends; a source that gains a WhatsApp fact suspends; deleting either app sweeps. The app↔host exchange is in-page postMessage routed by `event.source` and the read is in the host page's own engine — there is no network hop between the two apps to intercept; persistence rides the file's existing custody line (R-3, R-40), and the import path is where a planted grant is disarmed.

## Design (the contract every implementation lane reads)

### Vocabulary

- **Access** — the user-facing noun. "Budget has access to Ledger's transactions · until Oct 17 · 14 reads". Verbs: *allow* · *stop*. The reader *reads*; the source *is read by*. **History** — the user-facing word for the log.
- **Access grant** (spec: always qualified — Part III's *connection grant* is a different record; code: `AccessGrant`). **Reader** · **Source** · **Scope** (the granted tables with their columns) · **Access log** (`accessLog:<sourceAppId>`).
- Never "share" for this feature in UI copy (ADR-0063 owns *share*); never *grant*, *reader*, *scope*, *log* in a UI string (the vocabulary scan).

### Security posture (the delta's spine)

Identity is host-assigned (`accessAppId` ≡ `dbNamespace`); the runner is value-blind; limits key on the host-assigned id + frame generation (a re-announce cannot mint a fresh slot). The read is a scoped scratch copy in a Worker with its own sql.js under a wall clock — non-granted objects are ABSENT, writes refused twice, an unbounded query terminated, a wasm abort cannot reach the live user DB. Consent is host UI the iframe cannot draw over (C2), opened by a user act on host chrome (the strip's *review*), armed against tap-jacking, naming the reader by its library row and provenance. A grant is written only by the user's act; the import path demotes every grant not intent-identical to a local one; a shared/agent update of the reader, a column change on the source, or a sidecar fact on the source suspends; deleting either app sweeps. Logs are the source's and travel with the file (imported entries tagged). The app↔host exchange has no network hop; persistence rides the file's custody line (R-3, R-40). Disclosed residuals: the reader's AI sees what it reads; a reader can carry rows to an approved host in a GET or into a link it asks the user to open (both named in the sheet); rows are prompt-injection input to the reader's model (R-8's class); the user's own builder edits of the reader keep its grants (R-7's class); two instances of the source (R-70) can make a read observe mid-write state; session grants die with a reload; persisted grants survive a trusted sync.

## Decisions & surprises

- D1 **"access", not "share"**; UI says *history*, never *log*. (Gate 2; design lens)
- D2 **Two frames with an `op` discriminator**; **the request strict, the response tolerant** (`z.object`, the db-response shape) — a strict host→app frame would make every reserved growth seat a MAJOR bump, because the SDK drops what `parseFrame` rejects. (Gate 2; scope lens)
- D3 **Part VI — Access between apps (§21–§24) inserted after Part V; Conformance re-lettered Part VII**; the seven `Part VI` references, the stability table, the spec README ("seven parts") and `sync-spec`'s index text updated. (scope lens; supersedes the Gate-2 "Part VII at the end")
- D4 **Scoped scratch, physical absence** — triggers first, then views, then tables + `snug_kv`; `PRAGMA query_only`; `isReadOnlySelect` THEN `forbiddenStatementReason`. (Gate 2; security + feasibility lenses)
- D5 **Session grants bind to the reader's frame GENERATION** (host-owned), never `instanceId` (app-rolled); so do the limiters and the pending slot. (security lens)
- D6 **Sidecar-fact apps are not sources — checked at ranking AND at every query** (`source-restricted`). (security lens)
- D7 **Unattended reads are an opt-in on the grant** (`unattended`, default off); a hidden frame's `request` → `ACCESS_UNATTENDED`; its `query` on a grant without the opt-in → `ACCESS_NOT_GRANTED` + a `refused` log line. (security + design lenses)
- D8 **`record-guards.ts`** carries the shared regex constants too, so `isSingleDmlStatement` keeps one definition. (feasibility lens)
- D9 **The draft is renamed `docs/spec-drafts/SPEC.md`** (version in the header; a pointer stub at `SPEC-1.0.md`); live consumers updated, history untouched. (scope + feasibility lenses)
- D10 **The read runs in a dedicated Web Worker with its own sql.js under 2 s** — sql.js exposes no interrupt (probed: `Database.prototype` has none), so a synchronous main-thread read was a C2-class hang; the kit turns `access` off where no blob Worker constructs. (security lens — blocker)
- D11 **The reader is named by its library row plus a provenance line the host derives** (`installSource` + versions), never by the announce; collisions are said. (security lens — blocker)
- D12 **Strip first, sheet on `review`** — ADR-0074 §4's rule for app-originated asks; three negative acts (*not now* records nothing; *don't allow* records the hash; *stop asking* mutes); no "second decline mutes". (design lens — blocker)
- D13 **Durations default to the session grant**, labelled *while Budget is open*; *until I stop it*. (design lens)
- D14 **Columns are frozen in the grant**; drift suspends `source-changed`; credential-named columns are never shared and always masked. (security lens)
- D15 **The log coalesces only identical `(grantId, sql)`**, lifecycle entries outrank reads in pruning, imported entries are tagged. (security lens)
- D16 **The access response is tolerant; Appendix C fact 1 states the access pair's precise exception** (the exported schemas are complete for the frames; §24's obligations bind the host, not the parser). (scope lens)
- D17 **The three accumulated draft items are promoted in 1.1** (Q13) and the staged SPEC is diffed hunk by hunk. (scope lens — blocker)
- D18 **E8's rule, not a wider one**: shared and agent updates suspend; starter and own do not; ONE `onAppVersionChanged` fan-out replaces the two separate calls. (feasibility + scope lenses)
- D19 **`ACCESS_NO_SOURCES` and `ACCESS_UNATTENDED`** are distinct codes so an honest "nothing to offer" or "nobody looking" is never recorded as a decline. (scope + design lenses)
- D20 **`⋈` (a join), between the schedule control and share**, rendered only when the app has access state. (design + feasibility lenses)
- D21 **The spec push is a per-session ask; two commits** (spec, then the whitepaper). (scope lens)
- D22 **`/sync-website` is a judgment walk**: Fable authors the three pages that gain claims. (scope lens)
- D23 **A credential-named column is never in a grant's scope** (W1 fold, review findings 4/11): `isCredentialKeyName` (exported from `security.ts` — the scan's own key rule, ONE definition) decides; `accessGrantSchema` refuses a scope naming one; `describeAppData` flags it `sensitive`; the consent sheet shows it *never shared* and leaves it out; the scoped read's DRIFT check ignores live credential-named columns (a source that gains an `api_key` column is not drift — it was never shareable) and the AC12 mask stays as the belt. The grant's scope is therefore exactly the readable columns and the reader's view says exactly what it may read.
- D24 **The grant view's `access` is an open string** (`string(1..32)`, `'read'` at 1.1) while the RECORD's is `literal('read')` — AC1's own sentence; the SDK derives `AccessGrantView` from the protocol's inferred type, never a retyped literal. (W1 fold)
- D25 **Record invariants the writers must keep** (W1 fold, stricter reading): `suspended` ⇔ `suspendedReason`, `revoked` ⇔ `revokedAt` (clear both when a grant goes back to `active`); `readerAppId ≠ sourceAppId`; no duplicate table or column in a scope; grant ids — including a SESSION (memory) grant's — are lowercase uuid v4 (`crypto.randomUUID()`), because every log entry's `grantId` is parsed by the same rule; app ids ≤ 64 chars.
- D26 **The display rule is total and the walk is wider** (W1 fold, review findings 2/3/7/8/9/10): a purpose, hint word or log reason refuses EVERY `\p{Cc}`/`\p{Cf}` code point plus U+2028/2029, U+034F and the blank fillers, and leading/trailing whitespace; the query/log `sql` refuses bidi controls and C0/C1 other than tab/LF/CR; `findRecordCredential` (now shared with scheduling — the same function) also splits tokens on `= , ( ) < > | ; : %`, strips leading quotes/brackets and recognises a mid-text or quoted `Bearer <token>` pair — scheduling records gain the same refusals (their suites stay green); `accessRequestHash` normalises hint lists (trim, lower-case, de-duplicate, sort) before hashing. W5's spec prose states exactly these sets (the doc comments in `access.ts`/`record-guards.ts` are the source).
- Consciously NOT adopted: moving the schedule's mute-all switch into the file (out of scope; both switches stay per-browser, Q15); `ALTER TABLE … DROP COLUMN` in the scratch (suspend-on-drift is simpler and honest); a host-wide modal arbiter (the yield rule suffices now that app asks are strips); an arming delay on the sibling confirms (filed in next-steps).
