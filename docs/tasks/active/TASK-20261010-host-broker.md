## Spec (what & why)

The owner's requirements (2026-10-10), in product terms:

- **R1 — The host is the proxy.** Cross-app data flows (read AND write) go through the runner/host, never app-to-app, so apps stay sandboxed while the host facilitates everything.
- **R2 — Scheduled work runs where the app lives.** When an app is open, the host asks THAT iframe to run the scheduled job; when it is closed, the host executes the job itself where it can (without instantiating the app), or in the background when app code is required. Never a second copy beside the open one.
- **R3 — The host acts on the user's behalf.** The runner/hub controls many apps, executes, reads and writes for the user, within every policy and permission the user granted.
- **R4 — Fresh data on demand.** The host can make a source app PULL new data (through that app's own connections), not only serve what it already stores.
- **R5 — All of Group 1**, the fourteen deferrals ADR-0075 §10 named; the result must be world-class and intuitive, with the complexity and the security abstracted from the user.

What is true today, so the plan corrects the right thing (read from the code 2026-10-10 — anchors in "Found while planning"):

1. **The host already IS the proxy for reads.** A reader never touches a source's bytes: the frame goes to the runner's value-blind seat, the host handler exports the source, a dedicated Worker makes a scoped copy, runs the one SELECT and the rows come back capped. R1's read half is built; what is missing is that **only app code can use it** — the chat beside an app and the scheduler cannot (deferred by name in ADR-0075 §10 and SPEC §25), and nothing writes.
2. **An unattended scheduled run ALWAYS mounts a hidden frame, even when the app is open** (`appRun.ts:311-319` decides on the trigger alone). That is the two-copy behaviour the owner saw; it is threat-model R-70 and the "open copy" items in next-steps. Only the user's own *Run now* rides the live frame.
3. **Scheduled writes are refused by construction** (ADR-0074 §6): a mutating connected call answers `NET_CONFIRM_DENIED`, the AI's proposals wait for the user. Standing approvals exist as a gate with no arming surface (ADR-0033).
4. **Nothing pulls fresh data on another app's behalf.**

**Goals**

- **G1 — One broker, three doors.** ONE host-side Access Service with ONE policy function serves app code (frames), the chat beside an app (the data lane) and the scheduler (steps). The same grant, the same log, the same disclosure, whichever door asks. The user never learns there are doors.
- **G2 — Writes are brokered, bounded, journaled, undoable.** A write grant is the same consent sheet with one more toggle; every brokered write passes one path (strict parse → dry run → cap → busy check → undo snapshot → transaction → history line → doorbell) and the source's history offers *undo* for seven days. Whole-table writes and writes too large to undo are refused, by name.
- **G3 — One instance per app.** A run executes where the app lives: in the live frame when the app is open (under a run-scoped gate that asks the PRESENT user, never a remembered approval), headless when it is closed, and a run follows the app when that changes mid-flight. Host-native work (think, read, fetch, bounded write) needs no frame at all.
- **G4 — Fresh on demand.** A reader (app, chat or schedule) may ask the host to have the source pull new data first; the host runs the source where it lives, under the unattended posture, once per cooldown, counted and logged.
- **G5 — Discovery with permission.** Apps learn a count class, never names; the user sees ranked candidates in the sheet; the Hub and Settings surface "apps that could work together"; a source can offer itself; an app can DECLARE at build time what it would like to read, and the host turns that into a one-tap allow.
- **G6 — Everything in the file, nothing new on the wire beyond one minor.** Grants, history, undo and declarations are namespaced settings rows; spec 1.2 is additive; PR-1, PR-2, PR-4, PR-5 change no schema bytes.
- **G7 — Honest and plain.** Every surface says what will happen in words a non-engineer reads in one breath; every unattended act is refused, asked or journaled — never silent.
- **G8 — Shippable in six reviewable PRs**, each walkable on its own, the starter wave owner-timed.

### The model, in Chrome's terms (the owner asked for the Chrome architect's view)

| Chrome | Snug | Where it lands here |
|---|---|---|
| The browser process brokers every privileged operation; renderers hold nothing | The host page brokers every cross-app read/write/refresh; iframes hold their own data only | Access Service (`access/service.ts`), one policy (`access/policy.ts`) |
| Mojo IPC | Frames | `snug:access-request` gains `write` · `refresh` · `discover` |
| Site permissions: asked in context, shown in the omnibox chip, managed in chrome://settings | Access grants: the strip + sheet, the ⋈ header, the Settings card | Consent sheet v2 (one more toggle per table) |
| Extensions declare permissions at install, request optional ones at runtime | An app DECLARES what it would like to read (install-time), ASKS at runtime after a user act | `<meta name="snug:access-wants">` → `accessWants:<appId>` |
| One renderer per tab; the browser decides where code runs | One instance per app; the host decides where a run executes | Run placement (`schedule/runPlacement.ts`) |
| A service worker runs without a tab, woken by the browser | The headless frame — used ONLY when the app is closed | `ScheduledRunHost` stays; coexistence ends |
| Background Sync / Periodic Background Sync | The scheduler, plus refresh-on-demand | `access/refresh.ts` |
| Undo close tab / history | The source's history with *undo* on every brokered write | `accessUndo:<sourceAppId>` |

### Principles the plan stands on

- **P1 One broker, three doors.** Nothing cross-app happens outside `access/service.ts`; the frame handler, the data-lane tools and the scheduler steps are CALLERS with a declared attendance and egress, not engines.
- **P2 Declarations propose; only the user grants** (ADR-0016). Declarations travel in bundles; grants never do.
- **P3 One instance per app; the host chooses the executor.** Live frame if open and announced; headless if closed; handover when that changes; host-native work needs neither.
- **P4 Host-native where possible.** Read, think, fetch (GET) and bounded write are host-native; app code runs only for app-authored handlers.
- **P5 One write path.** Every write not typed by the user's own hands inside the app goes through the Write Broker: strict, dry-run, capped, busy-checked, journaled with an undo plan, doorbelled.
- **P6 Caps sit at the egress, not at the grant.** The frame's 500 rows / 192 KiB exist because of the bridge; an in-host materialisation into the chat's scratch copy gets its own, larger cap; the brain only ever sees `data_query`'s capped result.
- **P7 Presence is not consent — but a present user can be asked.** A delegated run never consults a remembered or standing approval; it asks the user who is there, with a timeout to *needs you*.
- **P8 Hints, never content** (ADR-0034). Every new host-event carries ids and names, never rows.
- **P9 Disclosure is derived.** "Where this can go" is computed from the transports that will carry the data, per door.

### Owner questions — recommended defaults (the owner delegated the architecture 2026-10-10: "I want you to be the judge"; each default is reversible by one word and is recorded in ADR-0076 / ADR-0077)

| # | Decision | Default taken | Why |
|---|---|---|---|

| Q4 | Who may write unattended | **The app's `write` op only when ATTENDED** (the visible frame of its generation) **or inside a scheduled run whose task carries an armed write authority**; chat writes stay per-approval cards (the user is there); the scheduler applies the AI's proposals only under the task's authority, else they wait as today | "No new powers" (ADR-0074 §6) is kept as the default and widened only by one explicit arming act the user can see and kill |

| Q7 | Counting on the live frame | **Count, never refuse mid-run**; the daily ceiling is enforced BEFORE dispatch (`capped` without dispatch); over-attribution of a user's own click inside the ≤ 90 s window is accepted and disclosed | Refusing a user's own click because a scheduled run is in flight is the wrong failure |
| Q8 | Host-native jobs ("without instantiating the app") | **`app-think` gains `tools: true`** — the data lane's `data_query` + `data_propose_write`, a GET-only `fetch_connection`, the shared tables; ≤ 8 tool calls a run; proposals apply only under the task's write authority. ### PR-1 decisions (each reversible by one word)

- **D-PR1-1 No persisted shape changes.** The run row, the step result and the task keep their shapes (a new field on a strict settings row makes a fielded 0.1.x hub mark the row unreadable). `handed-over` is NOT a step status — it exists only in summary text. Where a run executed is in-memory only (the placement store). The ADR-0077 line "the run row's `host.binding` records live|headless" is retracted — `binding` is the HOST binding.
- **D-PR1-2 `manual` runs are untouched except the readiness wait.** A manual run still rides the live frame under the page's ordinary gate, uncounted, and fails `the app was closed` on retraction (M18, R-62) — but it now waits for the frame to be READY before the hint (the *run now* race, AC5, is a manual run). Placement, the ask gate, counting, handover and the access-door rule apply to `due` · `late` · `catch-up` only.
- **D-PR1-3 A scheduled dialog never remembers, and a frame that hosted a scheduled run stays ask-only.** The dialog for a delegated run has no *remember for this session* box; the run-scoped gate never calls the session gate's prompt path, so nothing can be remembered (structural: `rememberSession` is only ever written inside `createSessionConfirmGate.confirm`). **Sticky generation (security blocker 1):** once a delegated run has begun on a frame generation, EVERY later mutating call from that generation — during the run and after it, until the frame retracts or remounts — is asked once, never answered by a remembered or armed grant (a handler that posts its result first and POSTs afterwards finds the same dialog). The user's own *remember for this session* is unavailable on that frame until they reopen the app; said in the delta and in the dialog ("nothing is remembered").
- **D-PR1-4 Handover: unattended runs only; hidden → live and live → hidden; at most once; never after a grant; a remount is not a handover.** Opening the app mid-hidden-run cuts the attempt and re-dispatches the SAME `runId` to the live frame once ready (after the hidden frame reports unmounted); retracting the app mid-delegated-run re-dispatches hidden. A second handover ends the step `failed` (`copy.handedOverTwice`). If the gate GRANTED any mutating call during the delegated attempt, a retraction ends the step `failed` (`copy.closedAfterChange`) — never a re-run of a handler whose POST already went out. A `frameEpoch` remount mid-run is not detected in PR-1: the attempt ends by the result bound as the manual path does today (rider in next-steps). The kv input is written per dispatch (same key) and cleared ONCE in the executor's outer `finally`.
- **D-PR1-5 Placement reads registration; readiness is awaited inside the live dispatch; one instance per TAB.** `placeRun` answers `'live'` when the registry HAS the app (registered, announced or not), else `'hidden'`; the live dispatch waits `announced` ≤ `announceTimeoutMs` and answers `no-handler` if it never comes. The leader tab runs the scheduler; an app open in a FOLLOWER tab is not "live" here (ADR-0077 §1 reads "per tab"). Presence means "RunView mounted", not "the tab is visible": in a backgrounded tab the dialog times out to *needs you* (disclosed, not gated).
- **D-PR1-6 The ceiling is asked BEFORE a delegated dispatch; inside the window calls are counted, never refused; the fold still says `capped`.** Before dispatch: if either counter has no headroom for one more call (`wouldExceedCeiling(daily+spent, {ai:1})` or `{net:1}`) → `{ status: 'refused', capped: true, summary: copy.capped(what) }`; `StepOutcome.capped` is copied by `finalizeOutcome` and folded `capped` by the queue (the fold's `reason` carries the step's summary so the card can say which limit). Tallies are SUMMED across attempts (a handover never drops what the first attempt spent). If the summed tally crossed a ceiling inside the window, the outcome carries `capped: true` too (app code is not stopped; the row says so).
- **D-PR1-7 The live frame's reply is not scrubbed by the delegated path, and its db binding is the ordinary one.** The attended frame's transport and db binding are the open app's own (unscrubbed replies, BEGIN/COMMIT allowed); `finalizeOutcome` still scrubs the step's `summary` and `alert`. Named in the delta as "the powers the open app already has". The hidden path keeps `createScheduledTransport`'s scrub and `scheduledDbDriver`.
- **D-PR1-8 The access door closes during a delegated run (security blocker 2).** While a delegated run is in flight for an app, its attended access handler answers `request` with `ACCESS_UNATTENDED`, admits `query` only under a grant's `unattended`, and logs `attended: false` — the hidden frame's posture, for the run's window only (the app's genuine user-driven ask after the run is the ordinary strip, which needs the user's act anyway).
- **D-PR1-9 One outstanding ask per run.** While a scheduled dialog is parked for a run, or after ANY refusal (denied or timed out) for that `runId`, further mutating calls in the window are refused at once and recorded — a handler cannot park N dialogs. A parked scheduled confirm is WITHDRAWN (denied by reference) on timeout and whenever the run ends (result, bound, cancel, handover).
- **D-PR1-10 One deadline per step.** The executor fixes `deadline = now + resultTimeoutMs` at the first dispatch; a re-dispatch's announce and result waits are bounded by `deadline − now`, so a handover never runs past the queue's 120 s bound.
- **D-PR1-11 The noun is "hidden frame".** `Placement = 'live' | 'hidden'`; "headless" appears nowhere in code or copy; ADR-0077 gains the line "headless = the hidden frame".

### Contract v2.1 notes — decided after the three test lanes (2026-10-11; binding for the implementation lanes)

ROLLBACK : no undo for this step` → drop the temp objects → `COMMIT` → `{ steps: [{ table, op, changes, inverse? }], undoable }`. Every path drops the temp objects (`DROP … IF EXISTS` in `finally`). An `undo` is applied through the SAME function with the inverses as plans in REVERSE step order, `requireUndo: false` and no capture (`capture: false`) — an undo is not itself undoable.
  - `inverseOf(parsed, captured)`: INSERT → `DELETE FROM t WHERE rowid IN (?, …)` (the captured new rowids, chunked by 200); UPDATE → per captured row `UPDATE t SET <the SET columns> = ? … WHERE rowid = ?` with the OLD values of exactly those columns; DELETE → per captured row `INSERT INTO t (rowid, <every non-generated column>) VALUES (?, …)` with the whole OLD row. Honest failure modes are named in the delta: an undo whose rowid was reused since fails UNIQUE and the WHOLE undo rolls back ("couldn't undo — <Source> changed these rows since").
- **D-PR3-10 Capture by TEMP trigger, exactly as measured.** Inside the transaction: `CREATE TEMP TABLE snug_undo_rows (r INTEGER, …old columns…)`, `CREATE TEMP TRIGGER snug_undo_trigger BEFORE UPDATE|DELETE ON t BEGIN INSERT INTO snug_undo_rows VALUES (old.rowid, old.c1, …); END` (for INSERT: `AFTER INSERT … VALUES (new.rowid)`); run the statement; read the rows; drop both. The affected set is therefore the statement's OWN (no second evaluation of the predicate, no race with the app), and an explicit `INTEGER PRIMARY KEY` value in an INSERT is captured too. The capture is bounded by `maxChanges` rows × the table's width; a capture that grows past `maxUndoBytes` ends the apply (ROLLBACK, `too-large`) — the plan's preview on the copy is the cheap early answer, the apply's own measure is the rule.

### Residual risks the delta will name
- A standing write permission is a power exercised while the user looks elsewhere (never while nobody is present in PR-3): bounded by one statement, one table, 200 rows, the column rule, the undo journal, the history line, the doorbell, instant revocation.
- The undo journal holds the source's values at rest in the user's own file (never a credential — refused first; never shown to the reader); an undo whose rowid was reused since fails whole.
- A reader can make a source RUN once per five minutes (GET-only during the window, counted on the source's day, logged `refreshed`); `requestedBy` is the reader's display name entering the source's frame as data; a stranded kv key after a crash is inert.
- The driver's write signal tells every live reader WHEN a source changed (ids only) — a timing side-channel the 2 s coalescing blurs; DDL rings nothing.
- The own-mode broker journals an undo only when the statement is capturable; the result says `undoable: false` otherwise.
- A 1.1 hub cannot read a v2 grant (fail closed); a 1.1 host answers the three ops `MALFORMED`; `accessOps` is how a 1.2 app knows.
- `access-source-changed` and `access-read` reach only LIVE frames; a hidden frame is never registered and never rung.

## Decisions & surprises

- **D1 (2026-10-10)** The owner's framing "rather than letting app A directly read from app B" describes a design that never existed: the host has always brokered the read. The plan therefore does not move the broker; it gives the broker two more doors (chat, scheduler) and three more verbs (write, refresh, discover). Said plainly in the Spec so the fresh session does not look for app-to-app code to remove.
- **D2** "Without instantiating the app" is literal only for host-native work (read, think, fetch, bounded write — PR-2/PR-4). App-authored handlers need the app's runtime; the fix for the owner's complaint is ONE instance with placement and handover (PR-1), not the end of the headless frame.
- **D3** PR-2 cannot record `via` or `provenance: 'chat'` without a strict-record change; it records today's shapes and PR-3 adds the fields. The history line for a chat read therefore reads like an app read for the life of PR-2 alone — acceptable because PR-3 follows and the sheet's own copy says where the ask came from. *(PR-2 Gate 2: any `via` or `provenance: 'chat'` key written in PR-2 is a strict-parse REFUSAL — `appendAccessLog` throws and the read is withheld — so none is ever written.)*
- **D4** The refresh cooldown is in-memory per host (a cost control), not a settings row (a security record would be). Two hosts on one file can each refresh once per window — bounded to one extra run, counted on each.
- **D5** `provenance`'s strict enum, the log entry's `via`, the grant's new fields and the undo record are the ONLY reasons PR-3 touches records; every behaviour that could ship off-wire was moved to PR-2/PR-4/PR-5 so the wire PR stays as small as a 1.2 can be.
