## Spec (what & why)

Ship the five **auth-spectrum starters** (roadmap A8b) — the shelf that demonstrates the Dynamic Auth surface end-to-end, one starter per credential shape, so a user can see the connect→approve→inject→scrub path with their own eyes before trusting it with a real key.

The shipped credential union is exactly five kinds (`packages/protocol/src/auth-schema.ts` L130–L202): `oauth2_auth_code`, `oauth2_client_creds`, `bearer_token`, `basic_auth`, `api_key`. **There is no `none` kind at 1.0** and the runtime is fail-closed.

**The KB is the doctrine these starters must match** (a starter contradicting `90-auth-and-connected-apis.md` is a defect, per the handoff). Concretely, each connected starter must:
- call its host through `useConnectedFetch`, never `fetch` directly;

- declare the provider by **name, not endpoint**, with `declaredApiHosts` carrying only that provider's hosts;
- place **no credential in app code** — no key fields, no `Authorization` header authored by the app (C1);
- hold **ONE connected provider per app** (KB §"two or more providers").

**App Autopsy**: unchanged from AL-08's finding — starters ship no pre-seeded build conversation; installing is an app row only. Noted, not built (the idea stays queued in next-steps). These five behave exactly like the existing eight.

## Scope amendment v3 — the starter-declared connection seam (OWNER DECISION, 2026-08-07)

### The gap that forced it (found while building v2's walking skeleton)

**A starter app could never become a connected app.** Connections at 1.0 were reachable ONLY through a build conversation: the builder LLM emits the `auth_wizard` directive → the user clicks the card → the wizard writes the spec. Verified exhaustively at source:

- The **only** non-test `putAuthSpec` call is inside the wizard (`apps/playground/src/state/wizard.ts:328`), and every session-opening path needs either a directive (`RunView.tsx:485`, `BuilderView.tsx:141`), an existing row (`SettingsView.tsx:471` renders from `db.listAuthSpecs()` — empty for a starter → *"no connections yet"*, no button), or a net-error CTA (`RunView.tsx:501`).
- A read-only starter can't even attempt a net call (`net: undefined`, `RunView.tsx:226–236`) and has no chat rail (`:416`).
- An **installed** starter reaches the CTA (`NET_NOT_APPROVED` — the executor checks approval BEFORE the host ceiling, `connected-fetch.ts:298/:307`, and a missing row yields the same code) — but the wizard then opens with **no proposal and no row**: an empty manual review where the user must hand-type provider and hostnames.

Not broken code — three separately-correct designs (AL-08's no-chat starters, AL-04's directive-only proposals, M12's off-ceiling silence) composing into a dead end nobody had hit, because AL-08's starters were keyless and AL-04's wizard was always driven from the builder. The owner chose to close the gap now (over shipping degraded-only starters or pausing AL-09).

### The seam (minimal by construction — every downstream piece already ships)

1. **Protocol (additive-optional):** `appAnnounceSchema` (`packages/protocol/src/frames.ts:7`) gains `authRequired?: authRequiredPayloadSchema` — the AL-04 shape `{providerName, kind, declaredApiHosts?}` built for exactly this ("the display fields an app-side connect CTA needs", `render-directive.ts:119–129`). Strict inner payload; hint-grade trust (≤ `llmProposalSchema`: no registration copy, no headerTemplate, no fields — those exclusions hold structurally since the payload never carried them).
2. **Embedded hooks (one line + byte-lock cascade):** `useSnugApp` forwards `authRequired: m.authRequired` in its announce post (`packages/sdk/embedded/snug-hooks.js:99–117` posts a fixed field set today). Cascade: 13 `examples/*/app.html` re-embeds (scripted, never retyped) + KB hooks-sync — all guarded by existing byte-lock tests.
3. **Host seed (the only new logic):** in the playground's `onAnnounce` path (runner callback, `packages/runner/src/host.ts:43`), when ALL of: the running app is an **installed** app (NEVER a read-only starter — the "browsing writes NOTHING" contract, `starters.spec.ts:184`, extends to this), AND no `snug_auth_specs` row exists for it, AND the validated frame carries `authRequired` → run the **host-side ladder** (B2 discipline): `lookupWellKnownProvider(providerName)` — registry hit → spec built from REGISTRY values, declared hints **discarded**; miss → deterministic transformer over the declared hints (the transformer stays the ONLY spec builder). `putAuthSpec` → row lands **`unapproved`** (`userdb.ts:1421`). First-wins: an existing row of ANY status is never touched.
4. **Everything downstream is shipped, live-verified machinery — zero changes:** unapproved row → app's `useConnectedFetch` → `NET_NOT_APPROVED` → CTA `'connect'` (`netErrorCta` — M12's off-ceiling `null` untouched) → wizard renders the ROW's provider/kind/full derived host list (`AuthWizardSheet.tsx` `pendingSpec = row?.spec`; AL-04 AC7: full punycoded host list on every path) → "plain settings approval approves the stored row as-is" → B1 wall → credentials → connected. The Settings row + approve button also light up (`row.status !== 'approved'`). **No seed/fetch race exists**: missing row and unapproved row yield the identical `NET_NOT_APPROVED`.

### Threat sketch (for the security review to attack)

- **Malicious app declares a registry provider + evil hosts** → registry hit discards declared hosts (B2 parity with poisoned directives, AL-04-tested). Becomes a named test (AC14).
- **Malicious app declares an unknown provider + evil hosts** → unapproved row grants NOTHING (fail-closed executor); the wizard discloses the full derived host list before approval; credentials only after. Posture ≤ `imported_unapproved` (arbitrary foreign specs, already handled). **Open question flagged for the reviewer:** seeded rows take the plain review (disclosure, approve-as-is), not the forced field-by-field `spec_confirm` that inference/user-docs provenance triggers — is disclosure-only sufficient for app-declared hints, or should seeded rows force the strong review?
- **Announced-appId spoofing** → the seed keys on the HOST's route-derived app id, never the announced `appId` (R4: announce is display-only, never a security identity — `host.ts:43`).
- **Re-announce churn / row thrash** → first-wins gate; `putAuthSpec` on an approved row with a changed union throws `HostFreezeViolation` anyway.
- **Read-only starter writes** → seed gated to installed apps; the existing no-writes e2e contract gains the seed case.
- **Provider-name phishing surface** → unchanged parity: LLM-authored provider names already render in the wizard via directives; registration copy still cannot be carried (structural).

## Security review verdict (v3 seam) — FAILED, 2026-08-07

Fresh-context 3-lens adversarial review of the seam DESIGN (trust-boundary / fail-closed / blast-radius), refute-first verification per finding. **15 findings; 13 verified (12 CONFIRMED, 1 REFUTED); 2 unverified when the run hit a usage limit** (recovered from the workflow journal — findings are not lost, and both unverified ones are consistent with facts I re-derived myself). Every load-bearing claim below was **independently re-verified at source by the orchestrator**, not taken on the reviewers' word.

### The three BLOCKERs (any one of them sinks the design as written)

1. **"Registry hit discards declared hosts" is FALSE for static kinds — the seam's central safety claim does not exist in the code.** The registry-host fallback (`explicitHosts.length > 0 ? explicitHosts : wellKnown?.apiHosts`) lives ONLY in the `oauth2_auth_code` branch (`params-to-auth-spec.ts:181`). For `bearer_token`/`basic_auth`/`api_key`/`oauth2_client_creds` the sole host source is `requireDeclaredHosts()` (`:97`), and `provider.name` falls back to the **raw attacker string** (`:65`). So a declaration `{providerName:'GitHub', kind:'api_key', declaredApiHosts:['api.evil.example']}` seeds a spec whose display name is a trusted brand and whose ceiling is attacker-chosen. AC14(d) claims exactly this is prevented; it is not. **The shipped B2 protection I cited as precedent is structurally OAuth-coupled** — `resolveWizardIntent` hard-codes `kindHint:'oauth2_auth_code'` on every registry hit (`wizard.ts:241–248`, its own comment: "the kind is the registry rung's").
2. **The registry rung and D2 are mutually unsatisfiable.** `my-repos` declares `github` + `bearer_token`. Strict B2 parity forces `oauth2_auth_code` (destroying D2/AC12's bearer_token proof vehicle); honoring the declared kind re-opens BLOCKER 1. The registry is structurally OAuth-only (`WellKnownOauthProvider` requires `authorizeUrl`+`tokenUrl`). No shipped ladder satisfies both.
3. **The announce payload is unbounded, and the "hint-grade ≤ `llmProposalSchema`" claim is false in the bounds dimension.** `authRequiredPayloadSchema` is `providerName: z.string().min(1)` and `declaredApiHosts: z.array(z.string().min(1))` — **no max anywhere** (`render-directive.ts:124–128`). `llmProposalSchema` is `authSpecHintsSchema.omit(...)`, and `.omit` PRESERVES validators, so the directive path keeps `providerName.max(120)` and `declaredApiHosts.max(253).max(32)` — bounds added at AL-04 precisely so a proposal "must not smuggle megabytes". Reusing the payload "verbatim" therefore *widens* the trust surface rather than matching it.

### The MAJORs that survived verification

4. **The seam is a strict trust DOWNGRADE vs. the directive path** (answers the open question I flagged, and answers it against me): identical untrusted content gets the FORCED field-by-field `spec_confirm` + "proposed by a model — it is a guess, not an authority" warning when it arrives by directive (`provenance:'inference'`), but a seeded row's session carries **no provenance at all** (`wizard.ts:270`), so `specConfirm` is false (`AuthWizardSheet.tsx:187`) and the user gets the light "approve as-is" review. "Posture ≤ `imported_unapproved`" is wrong on both axes.
5. **Provider-name confusables** dodge the registry: `normalizeProviderKey` strips non-`[a-z0-9]`, so Cyrillic `ѕpotify` → `potify` (MISS) while the display name stays the attacker's string; both `providerName` fields are bare `z.string()` with no charset guard.
6. **AC7 is internally unsatisfiable as pinned:** weather-planner's seeded ceiling is its authored host `api.openweathermap.org`, which can never admit `stub.snug.test`. My own D8/D3 pinning contradicts the v3 AC7 flow.
7. **First-wins is only a call-site convention** — `putAuthSpec` fails OPEN on an existing *unapproved* row (`userdb.ts:1439–1443`: silent full `UPDATE` of spec+hosts, no guard), and `approveAuthSpec` re-derives the union from the LIVE row, so a guard lapse becomes approval of undisclosed hosts. (Verifier REFUTED the specific end-to-end kill-chain as a MINOR, but the fail-open asymmetry is real and must be designed against, not assumed away.)
8. **Revoke stops being terminal:** revoke = `clearApp` + `deleteAuthSpec` with no tombstone (`userdb.ts:1490–1493`), the app stays installed, and `onAnnounce` fires on every re-announce at app-controlled timing — so the declaring app silently re-seeds the row it was just revoked from, reversing the user's decision.
9. **A malformed `authRequired` silently kills the ENTIRE announce:** strict inner payload on a frame whose failure mode is whole-frame MALFORMED (`frames.ts:277–285`); announce is not answerable (`host.ts:575–586`) and MALFORMED frames bypass `onFrame`, so the app loses its display identity with no diagnostic — recreating the dead end the seam exists to close.
10. **Publication-line violation:** `app-announce.json` IS in the published `SOURCES` (`json-schemas.ts:16`), while the entire auth surface is deliberately OUT until Beta. Regenerating it drags a Beta-gated auth shape into the published normative schema set, and `z.strictObject` conflicts with the documented R2 forward-compat rule for published artifacts (`auth-schema.ts:10–19`).
11. **Hooks-cascade inventory incomplete:** the TYPED SDK face (`packages/sdk/src/hooks.ts:34–41`, `SnugAppMeta` in `types.ts:4–13`) cannot express `authRequired` and is named nowhere in the plan; the shared contract suite asserts announce with `toMatchObject`, so both faces stay green while silently drifting.
12. **D7 is factually wrong and is v2 residue:** a fresh installed app with no row gets `NET_NOT_APPROVED` at Gate 3 (`connected-fetch.ts:298`), never `NET_HOST_BLOCKED` — that code is only reachable *post-approval* (Gate 4, `:324`). So the CTA path I claimed was blocked was actually **open all along**, and the v2 "Settings entry" workaround was solving a non-problem. (This does not rescue v3: without a spec row there is still nothing to review — see §Owner decision needed.)

## Decisions

- **D1 — Crypto Portfolio resolves as `api_key` with CoinGecko's demo key (OWNER DECISION, 2026-08-07).** The umbrella row wrote it as "none/CoinGecko", which collides head-on with the 1.0 spec: keyless connected hosts are not expressible (five-kind credentialed union, fail-closed runtime, builder cannot propose fields).
