## Spec (what & why)

Snug's promise on this program is "your apps run inside the agent you already have". Today that is true for one agent on one surface: Claude Code in a terminal. This task makes it true across the board, and makes the product say only true things on every surface:

1. **Binding B under Claude Desktop** (walk #2). The plugin's local runner must start and be usable from the Cowork tab and the Code tab — a GUI-spawned process with no shell PATH, next to a terminal session that may already hold the runner.
2. **Another agent the user already has can be the brain** (ADR-0069's second axis): one brain contract and a registry, with `codex` beside `claude` — a brain, not a binding. **Scope set by the owner mid-session (2026-10-03): "skip the ollama for now … and also skip the OpenClaw and hermes for now"** — those three drivers and the Hermes walk (S5) are deferred to their own task; the registry is built so each is a file.
3. **Binding A2 (claude.ai chat / Claude Desktop chat) is made ready — pending two owner publishes and one walk**: the kit boots where a chat artifact runs, its brain (`window.claude.complete`) has a measured-or-learned prompt budget instead of an assumed one, and the chat delivery (the script build, the npm layout, the bootstrap, the skill recipe) is built and gated. No chat route is VERIFIED until a person walks it in claude.ai: the CDN route needs `@snugprotocol/host` (and `@snugprotocol/starters`) published, the file route has never been observed.
4. **One runner, not one per binding**: one kit page, one boot, one capability table, one hand-in path, one brain contract — the web/desktop/kit parity ADR-0021 established, extended to every binding.
5. **A host never offers what it cannot run**: starter apps and installed apps whose needs the current binding cannot meet are disabled, each with the true reason and where it does run.

**Found while planning (2026-10-03), fixed here because walk #2 cannot pass without them:**

- **The attach path is dead in the shipped build.** `runner.ts:138` wires `commandLineOf: () => undefined`, so `lock.ts` classifies every live holder as a stranger and refuses; `main.ts` then dies before the MCP handshake. Reproduced on the owner's Mac: this very session's `plugin:snug:snug` failed with "Connection closed" while a healthy runner (pid 92272, `clients: 1`) held the lock. "Two windows, one Snug" has only ever worked in tests, which inject the command line.
- **An attached session cannot hand an app in** (`runner.ts:219-244` forwards only `snug_status`/`snug_open`).
- **`absent` does not fall back to the demo brain**: the chip says "demo brain", the seat still routes to the shim, every think is a 502.
- **Binding B hand-ins never reach the hub or the user**: `local/main.tsx` dispatches three `CustomEvent`s nobody listens to; there is no `agentHandIns` seat; `snug_list_apps` is a stub.
- **The only starter gate is a hard-coded `desktopOnly` table** checked against `kind !== 'desktop'`, with one reason string that is wrong for two of the three starters it locks, wrong under Binding B (where the process, not a browser, carries the request), and absent for installed apps and for the run route.
- **The kit would likely crash at a real chat origin**: `main.tsx:39` reads `sessionStorage` unguarded, which throws at an opaque origin; the chat e2e serves the page from loopback http, never from `about:srcdoc`.

**Acceptance criteria** (each becomes at least one test; `→` names the test's home). Five ranges, in dependency order — each range is its own commit range and its own Gate-5 review.

*R1 — the runner's lifecycle (`apps/host-mcp`)*

- **L1.** A second process started against a home whose runner is healthy ATTACHES — proven by spawning the BUILT release bundle twice, never by injected deps. `acquire` probes the recorded socket FIRST: a `tokenHash` match attaches with no command-line read; no answer + a dead pid takes over; a live pid that does not answer is the ONLY place identity is read (`/bin/ps -ww -o command= -p`, absolute path; `/proc/<pid>/cmdline` on Linux). Identity (`identity.ts`) is an accepted LIST of bundle basenames (`snug-mcp.mjs`, `snug-mcp.test.mjs`, `snug-local-host.mjs`) matched against the script argv token — never a substring of the command line — and pinned against `plugin-manifests.mjs` `BUNDLE_PATH` by test. → `mcp-interop.test.ts`, `lock.test.ts`
- **L2.** No failure AFTER Node is found precedes the MCP handshake. A runner that can neither lead nor attach answers `initialize`/`tools/list`; `snug_status` returns `{ running: false, refusal: { code, message, remedy } }`, every other tool returns the same sentence as an error, and the runner re-runs `acquire` on each tool call (rate-bounded) so a fixed cause clears without restarting the agent. The refusal table is derived from the throw sites and each row is proven through the built bundle: `home-unresolved`, `home-unwritable`, `lock-held-by-stranger`, `lock-contended`, `socket-path-too-long`, `socket-in-use`, `listen-failed`, `page-damaged`, `older-build`. (No Node at all is the launcher's sentence, the skill's line and the README's — it cannot be the process's.) → `runner.test.ts`, `mcp-interop.test.ts`
- **L3.** An attached session serves all four tools: one control op `call` runs the PRIMARY's own `callTool` (allowlisted by `TOOL_NAMES`; a bundle is re-validated by `parseAppBundle` and the connection refusal in the primary — C5), so attached and primary cannot drift. One `controlCall(socket, request, { timeoutMs })` replaces the three hand-rolled clients; lines are capped; every op answers a positive ack (`{ ok: true, op }`), an unknown op answers `{ error: 'unknown op' }`, and a `hello` without `build` is an older build → the remedy sentence, never a false success. → `control-socket.test.ts`, `runner.test.ts`
- **L4.** `snug stop` (the human CLI, over the socket) refuses while `pages > 0` unless `--force`, emits `shutdown`, drains in-flight `/userdb` writes, releases the lock, reaps every child and exits within a hard deadline; against an older build it falls back to SIGTERM of the lock's pid only when the socket's hash matches the lock AND the command line is ours, and says which path it took. `snug status` reports `version`, `build`, `pid`, `platform`, `home`, `clients` (persistent sessions), `pages`, the brains. An unknown verb prints usage and exits 2. → `runner.test.ts`, `mcp-interop.test.ts`
- **L5.** The bearer has exactly one way out of the process besides the page: the `launch-url` op, used only by the human CLI, whose output is printed only when stdout is a TTY (otherwise the tokenless address and "run this in your own terminal"). `open` makes the primary open the browser and answers `{ port }` only. A token canary runs over every other op's answer, error answers included. The opener is a per-platform absolute path with an `error` listener; a failure returns the printed fallback naming the launcher's real path. → `control-socket.test.ts`, `runner.test.ts`
- **L7.** Presence and succession — what attach is FOR. An attached session holds ONE persistent control connection; the primary exits (after the grace) only when its own session is gone AND no persistent session remains, re-evaluated on every change; transient ops never arm or cancel the grace. An attached session whose primary is gone re-runs `acquire` on its next tool call, promotes itself, and tells the agent to call `snug_open` again (a new bearer). Proven on the BUILT bundle: primary's stdin closes while an attached process lives → still serving; the attached one closes → the primary exits and the lock is released; primary SIGKILLed → the attached session's next `snug_status` reports running as primary. → `mcp-interop.test.ts`
- **L8.** Take-over cannot kill a healthy runner: a live pid that is ours is signalled only after three failed socket probes spread over ≥ 5 s AND when the recorded port does not answer either; then SIGTERM, then WAIT for the pid to exit (bounded) before unlinking; if it does not exit, refuse with the `snug stop` remedy. Only the canonical `<hostDir>/ctl.sock` is ever unlinked — never a path read from `lock.json`, never a live pid's socket. A stranger pid is never signalled. → `lock.test.ts` (mutants: drop the hash compare, the identity read, the wait)
- **K5.** One `startProcess({ hooks })` composes the release entry and the test entry, so handshake-first, the grace and the parent watch are what the browser specs run; the test entry supplies only the resolver, the holder override and fake brain drivers. `SNUG_MCP_TEST_` is swept from the release bundle as a PREFIX. → `check-host-mcp.mjs`
- **D1.** The gate STARTS what it ships, under a written isolation contract. Positive leg: `env -i HOME=<tmp> SNUG_HOME=<tmp>/Snug PATH=<dirname(process.execPath)>`, cwd `/` → `initialize`, `tools/list`, `snug_status` — whose FIRST assertion is that `file` and `home` are under `<tmp>` and `pid` is the child the leg spawned — then a second process attaches. Negative leg: neither `HOME` nor `SNUG_HOME` → `initialize` still succeeds and `snug_status` is the `home-unresolved` refusal. No leg spawns a CLI (probes are lazy — B1). Both processes are reaped in a `finally`. → `check-host-mcp.mjs`
- **D8.** The served page is pinned: the plugin build writes the page's sha256 beside the bundle; the release entry reads the page ONCE at boot and serves only matching bytes; a mismatch is the `page-damaged` refusal, and that process takes no lock and opens NO listener (amended 2026-10-03: a damaged process that bound the port pushed a healthy install onto an ephemeral one and disabled its OAuth rows — the MCP refusal is the whole channel). (Catches a partial copy or a stale mix; not a same-user writer — recorded as such.) → `page.test.ts`, `check-host-mcp.mjs`
