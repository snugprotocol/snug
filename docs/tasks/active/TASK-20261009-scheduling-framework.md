## Spec (what & why)

Snug apps live in the user's file and think through the user's own brain, but nothing happens unless the user is looking. The owner's ask (2026-10-09): a **scheduling framework inside every Snug runner** — web playground, Snug for Mac, the host kit under both bindings — where (1) the user schedules any task from the runner UI, a single task may touch one or more apps, (2) an app may schedule for itself implicitly — while being built or edited, or from the inline chat beside it — with the user's say-so, (3) the UI offers intuitive choices (a time, weekdays, daily, monthly, …) while cron is the engine underneath, (4) tasks that could not fire because no Snug was open are found on the next open, the user is told and chooses to catch up, with no redundant calls, and (5) every byte of scheduling metadata and history lives in the same `.snug` file. The bar is ChatGPT Tasks / Claude routines / Gemini scheduled actions; the UI must be plainly better than theirs. No code is duplicated across runners.

**Goals**
- G1 **One engine, one UI** in `apps/playground/src/schedule/`, inherited by desktop and the host kit through the existing aliases (ADR-0072). Host differences enter through ONE optional platform seat (`platform.scheduler`) and `hostCapabilities().schedule`.
- G2 **Intuitive first, cron underneath**: a chip-built sentence, a live "next 3 runs" preview, a plain-language box, an advanced cron field — all compiling to one `ScheduleSpec` + 5-field cron + IANA zone persisted together.
- G3 **Honest reliability**: no Snug host is always-on today (measured: the Mac app quits when its window closes, no tray/autostart/notification plugin; the local host process exits ~3 s after its last agent session; a tab runs only while open). So a task runs when due if a Snug is open, and everything missed is **reconciled on the next open** — collapsed per task, handled per policy, deduplicated by `(taskId, dueAt)` on one file copy (across diverged copies at most one extra call — writes are proposals). The honesty line is shown where the user DECIDES (the editor, the empty page), never only in Settings.
- G4 **Unattended posture by construction — no NEW powers**: "the LLM proposes, the human approves, the host freezes." A scheduled run never widens a grant, never answers a confirm gate on the user's behalf (a mutating connected call is refused by name), never lets the AI write data (an ask-the-AI step's proposals wait in the result), and never holds a credential. A scheduled app-run runs the app's OWN code with the powers it already has over its OWN data — that is the one accepted residual, named in the threat delta.
- G5 **Proposal ladder**: the user (always), the builder LLM (a card in the chat rail), the app-attached chat (a `schedule` intent), and the running app itself (a bounded request the host renders as a confirm card). Nothing but the user's act ever sets `enabled`.
- G6 **The file is the record**: tasks, runs, the watermark — all namespaced `snug_settings` rows (SPEC §8.1's own rule), swept on app delete, carried by export/sync, disabled on import.
- G7 **Showcase**: templates on the Schedule page (always shown); a cross-app "Friday review" — one schedule, two apps, each app's own brain summarising its own data on one result page (no step's content ever flows into another app's prompt or vendor); the weather starter takes a morning run and suggests it (its own owner-timed PR, because a starter edit re-pins the published package).

### Advice recorded for the owner (asked 2026-10-09): is scheduling protocol?
No. A host that never schedules is still conforming; scheduling is a host feature and a differentiator for Snug-compatible hosts, exactly like the builder chat or the share sheet (ADR-0011's reasoning: a fact nothing on the wire needs is not recorded on the wire). The spec is touched in two precedent-shaped places only — the §8.1 transparency list of settings keys (because the `.snug` storage surface is spec) and the changelog — and the whitepaper gains one non-normative paragraph: *because the schedule lives in the user's file it travels with the file; the same morning brief fires on whichever host opens the file next, and nobody but the user holds it.* No `snug_schedules` table in the normative DDL, no envelope or runtime-contract field (ADR-0036 D1 verbatim), no MCP tool (ADR-0068: no data-plane tools). Q10 below.

### The model (what the code will say)
- A **task** = `{ id, title, enabled, enabledAt, provenance, ownerAppId?, steps[1..5], spec, cron, startsAt?, endsAt?, missedPolicy, staleAfterMs, alert, appVersions, ranThrough?, counters, pausedReason? }` — `spec` is the intuitive form (persisted so the editor never reverse-parses cron), `cron` the engine's form, both written together by `compileSpec`; `tz` lives in `spec` (`'device'` or a zone).
- A **step** = `notify` | `app-run` | `app-think`; steps are INDEPENDENT (no chaining); a multi-app task is several steps with one result page.
- A **run** = `(taskId, dueAt)` claimed as `pending`/`running` before anything executes + trigger + status + per-step results + `host` + `calls` + pending `proposals` (stripped on every import/pull/export) + `seenAt`.
- **Scheduler state** = watermark + global pause + the daily counters. Leadership is runtime (per origin, per file uuid).
- **The kv handshake (PR-B)**: `snug:schedule:<runId>` written by the host through the shared driver's new host-side kv on the app's namespace; cleared (`null`) after the result; the app never sees anything but a hint on the event channel.
