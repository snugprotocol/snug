## Spec (what & why)

**What.** Binding B (ADR-0065 §2 B — the local host, the ONLY binding with connected apps) is delivered as a **plugin-bundled local MCP server** rather than a launch script the user runs by hand. When the `snug` plugin is installed in Claude Code, Cowork (desktop) or Codex, the host spawns `scripts/snug-mcp.mjs` at session start over stdio. The process has exactly three jobs: (1) **serve the kit on loopback** — a second build of `apps/host`, `snug-host-local.html`, with connections compiled in, opened in the user's browser, the user's file at `~/Snug/user.snug` on disk; (2) **be the network side of the page's executor** — the page's `connected-fetch.ts` stays THE seat that reads a credential and calls fetch with all ten gates unchanged; what crosses to the process is the platform's raw `fetchImpl` (the seam Snug Desktop fills with `plugin-http`), the `oauth` loopback transport (the seam Snug Desktop fills with `tauri-plugin-oauth`) and the `userdbBackend` file seam (the seam Snug Desktop fills with `read_user_file`/`write_user_file`) — the process is Snug Desktop's Rust side written in Node and reached over `127.0.0.1`, nothing more; (3) **expose a four-tool control plane to the agent** — `snug_status`, `snug_open`, `snug_hand_in`, `snug_list_apps`. No data-plane tool, ever. The `claude -p` brain shim (program D5) lands in the same process as a module, reached by the page through the T2 brain seat.

**Why.** Apps built in the kit get connected fetch, with or without credentials (API keys, OAuth, signed requests), through one proxy the plugin ships, and the browser's CORS ceiling disappears exactly as it does on desktop. Spawn-and-connect is a channel every target host already offers plugins; nothing here makes Snug "built on MCP" (ADR-0061) — the proxy and the file are plumbing, and product copy stays "Snug apps run inside Claude Code / Cowork / Codex". Product copy never says "Snug MCP server".

**Hard rules (each becomes a test or a lint — the brief's list, restated as the contract):**

- **C1 stays where it is.** The executor is neither moved into Node nor duplicated. `/fetch` receives the request AFTER the page's gates and injection and is value-blind: it never logs, persists or echoes a URL, header or body; every error message passes `scrubAuthValues` (imported from `@snugprotocol/auth`) against the injected header values it saw before it returns. Defense in depth on the process side because anything on the machine can open a loopback socket: https-only (no LAN rung in this task — below), `isForbiddenNetHost` (**imported, never a second copy**), no redirect followed (`node:https` never follows one; the 3xx is returned as data), the 1 MiB cap **while reading**, the 60 s wall clock that names itself. The executor's own gates run twice — not a new policy (so NO resolved-address check: the executor's gate 5 is literal-only, and a resolved-IP rule would be a new policy the desktop does not have either; the DNS-rebinding residual stays where the threat model already records it).
- **The LLM is never a network principal.** `tools/list` returns exactly `snug_status`, `snug_open`, `snug_hand_in`, `snug_list_apps` — an allowlist test fails on any addition. The data-plane routes (`/fetch`, `/oauth/*`, `/userdb/*`, `/v1/*`, `/events`) live ONLY on the TCP loopback listener and require the page's bearer + a same-origin proof; the control plane (attached sessions, the human CLI) lives ONLY on a `0600` unix socket and carries no bearer. **The bearer appears in no MCP message, no tool result, no lock file and no log** — `snug_open` makes the PROCESS open the browser; the URL a tool result shows never carries the fragment.
- **Loopback only, authenticated, origin-bound.** Bind `127.0.0.1:0` (ephemeral). A per-launch 256-bit bearer rides to the page in the launch URL **fragment** (never the query), is stripped from `location` before the router boots, and must be present on every data-plane call (`Authorization: Bearer …` — the SSE stream is read with `fetch`, never `EventSource`, so the header rule has no exception). `Origin`, when present, must equal the served origin; when absent (same-origin `GET` via `fetch` sends none), `Sec-Fetch-Site: same-origin` must be present; neither → 403. No CORS headers are sent at all (the page is same-origin; a foreign page's response stays unreadable AND refused). Missing bearer → 401, wrong origin → 403, both bodies empty. Never `0.0.0.0`; the `Host` header is never consulted.
- **One process, one file.** `~/Snug/host/lock.json` `{port, pid, tokenHash, startedAt, socket}`; a second session attaches over the unix socket instead of spawning; the primary lives while ANY attached session lives and exits within the stdin-close grace once the last one is gone, releasing the lock and the socket. The user file follows `createFileBackend`'s discipline over a `FileBackendFs` the process implements with the desktop's rules (bare-name charset, temp + fsync + rename + dir fsync, absence = ENOENT only, the one-byte-discriminant read); if Snug Desktop is running, the process opens **read-only and says so** in the custody chip. Never a byte of state under `${CLAUDE_PLUGIN_ROOT}`.
- **OAuth loopback = the desktop posture.** `buildLoopbackRedirectUri` + `SNUG_DESKTOP_OAUTH_PORT` (41420) from `packages/auth`; the page runs the SAME `createDesktopOAuthTransport` the desktop runs, with a `LoopbackListener` whose `start`/`stop` are data-plane calls to the process and whose callback URL arrives over `/events`. The 41420 listener binds only while a flow is pending; a busy port is the transport's own named error, never another port.
- **D4 holds.** `snug-host.html` and (later) `snug-host-micro.html` still ship `connections:false` without the wizard, executor or registry reachable. Connected apps exist ONLY in the `local-host` build, which only this process ever serves.
- **Owner acts stay owner acts.** No `npm publish`, no `@snugprotocol` scope registration, no marketplace submission, no push to the distribution repo, no `gh release`, no deploy. Prepare and print; never perform.

**Acceptance criteria** (each becomes at least one test; Gate-2 additions marked ⊕):

1. **Spawn and connect.** With the plugin installed from a local marketplace path (`claude plugin marketplace add <dir>` → `claude plugin install snug@snug-local`), a fresh Claude Code session shows the server connected (`/mcp`); `tools/list` returns exactly the four names; `initialize` carries `instructions` = the launch-protocol text from the prompt store, byte-identical to its source (the generator that T6 will extend; until T6 lands the byte-compare is `check-host-mcp`'s). Note: claude.ai chat drops `instructions`; Claude Code and Codex read it.
2. **Serve.** `snug_open` opens `snug-host-local.html`; the probe reports `binding:'local-host'`; `connections` allowed; the brain chip says "Claude · your CLI" (or "demo brain — no host brain found" when no `claude` binary is on PATH); the custody chip says "on this Mac — ~/Snug/user.snug".
3. **Connected fetch, no credential.** The `weather` starter's (or the e2e stub's) `net-request` reaches a stub HTTPS server THROUGH the process; the page's executor gates and the process's re-checks are both observed to run (the process exposes a per-request check ledger to the e2e through its stderr-free status counters — never a URL); response headers obey the protocol whitelist; the 1 MiB cap trips on an oversize body with a named code.
4. **Connected fetch, with credential.** An API-key starter (Ledger's shape via the e2e stub requirement) completes the wizard, stores the credential in the page's `auth:` secrets, and its injected request reaches the stub through the process. A canary credential value appears in exactly one place on the wire — the outbound request from the process — and in no log, lock file, MCP message or tool result (grep-tested: the process's stdout/stderr capture, `~/Snug/host/*`, the MCP transcript, every tool result).
5. **OAuth.** The wizard's OAuth journey completes through the process's 41420 listener against `fake-idp.mjs` (assert on the WIZARD's connected state, never the popup's navigation — the journey-4 flake in next-steps 2026-08-26/2026-09-03); a 401 on a connected call triggers the executor's single refresh-retry through the same `/fetch` seam (the refresh POST and the retried call both observed at the stub).
6. **Negative security.** No bearer → 401 (empty body); wrong bearer → 401; foreign `Origin` → 403; no `Origin` and no `Sec-Fetch-Site` → 403; a private/loopback/link-local/`.local` target → refused with `NET_INVALID_REQUEST`-class code before any socket opens; `http://` → refused; a 3xx is returned as data, never followed; `tools/list` allowlist; **no debug/log-everything env var exists** (a test enumerates every `process.env` read in the release bundle against an allowlist of exactly `HOME`, `PATH`, `SNUG_HOME` (test isolation of `~/Snug`) and `NODE_EXTRA_CA_CERTS` is Node's own — and asserts the test-hook env name is ABSENT from the release bundle's bytes); the control socket refuses a data-plane path; the TCP listener refuses a control-plane path.
7. **Single instance + custody.** A second spawn attaches (same port, no second listener, `snug_status` from both reports the same `startedAt`); the primary survives the first session's stdin close while the second is attached and exits within the grace after the last; a stale lock (dead pid, or a live pid whose socket does not answer with the lock's `tokenHash`) is taken over; with Snug Desktop running (`snug-desktop` on the process table — the only holder signal that exists today), the page opens read-only and the chip names the holder; killing the host closes the process within the stdin-close grace and releases lock + socket.
8. **Hand-in.** `snug_hand_in({bundle})` delivers a `snug-app-bundle/1` to the open page over `/events`; the page applies it under ADR-0045 exactly as Binding A does (unedited-only auto-apply; edited copy offered; tombstone honoured; a bundle carrying connections is a hard refusal — pre-checked in the process for a clear tool error, decided by the page); with no page connected the bundle is queued (bounded) and the tool result says so.
9. **Brain.** The `claude` shim (`/v1/chat/completions`, bearer-gated, same origin) spawns the user's own `claude -p` with D5's flags — never `--bare`; child env stripped of `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN` (⊕ and `ANTHROPIC_BASE_URL`, `CLAUDE_CODE_*` overrides — enumerated in a constant, pinned by test); reached through the T2 brain seat with `localAdapter({ baseUrl, apiKey: bearer })`. ⊕ **No `local`-mode change is needed** (see D-B7) — Option C has nothing to rebase on from this task.
10. **Codex parity, documented.** `.codex-plugin/plugin.json` + `.mcp.json` emitted from the one constants module in the `npx -y @snugprotocol/host-mcp` form with the absolute-path interim documented; Cowork desktop walked once by the owner (where the process runs, whether `open` works) and journaled.
11. ⊕ **Release inertness.** The shipped `dist/snug-mcp.mjs` contains no test hook: the string sweep for the test-resolver env name and the `lookup` injection symbol is a gate (`check-host-mcp`), the desktop's `gate:release` transposed.
12. ⊕ **Kit twins stay honest.** `check-host-kit` is unchanged and green (the local build lives in `apps/host/dist-local/`); a new structural check on `snug-host-local.html` proves connections ARE compiled in (positive twin: the wizard door renders under `local-host`) while the artifact kit's absence test stays green.

**Out of scope:** the `codex`/`hermes`/`openclaw`/`ollama` shims (T3 remainder); Binding C; ChatGPT; Windows; any wire-protocol, frame or userdb-schema change; a remote/hosted MCP server; any identity provider; moving the credential store out of the page; a raw-fetch or SQL tool for the agent (a rule); **the LAN rungs** (`lanFetch` pinned-TLS and the `lanHttpPrivate` plain-http rung — the page carries neither seat, so the executor's own named refusal answers a LAN row; the desktop's http rung is itself broken (next-steps 2026-09-05) and a Node pinned-TLS transport is its own High task); `share` links from the local page (the relay is reachable from a browser, but no AC covers it — left `false`, queued); streaming from the `claude` shim (D5 pins `--output-format json`; `streaming:false` on the seat is the truth); `probeOllama` on the local page (with the ollama shim).

A shared holder marker written by both products is queued in next-steps as the durable answer (a desktop change, outside this task).
- **D-B11 (new) — Test hooks live in a second build, never in the release.** The proxy takes `lookup?` (the `node:https` request option) as a constructor parameter; the release entry never passes it; a test entry `src/main.test-hooks.ts` → `dist/snug-mcp.test.mjs` reads `SNUG_MCP_TEST_RESOLVE=host=ip[,…]` and passes a resolver, and the stub's self-signed CA rides Node's own `NODE_EXTRA_CA_CERTS`. AC11's sweep proves the release bundle carries neither the env name nor the symbol. Interop and stdin-close tests run the RELEASE bundle; only the connected-fetch e2e runs the test bundle.
