## Spec (what & why)

**What.** Binding B (ADR-0065 §2 B — the local host, the ONLY binding with connected apps) is delivered as a **plugin-bundled local MCP server** rather than a launch script the user runs by hand. When the `snug` plugin is installed in Claude Code, Cowork (desktop) or Codex, the host spawns `scripts/snug-mcp.mjs` at session start over stdio. The process has exactly three jobs: (1) **serve the kit on loopback** — a second build of `apps/host`, `snug-host-local.html`, with connections compiled in, opened in the user's browser, the user's file at `~/Snug/user.snug` on disk; (2) **be the network side of the page's executor** — the page's `connected-fetch.ts` stays THE seat that reads a credential and calls fetch with all ten gates unchanged; what crosses to the process is the platform's raw `fetchImpl` (the seam Snug Desktop fills with `plugin-http`), the `oauth` loopback transport (the seam Snug Desktop fills with `tauri-plugin-oauth`) and the `userdbBackend` file seam (the seam Snug Desktop fills with `read_user_file`/`write_user_file`) — the process is Snug Desktop's Rust side written in Node and reached over `127.0.0.1`, nothing more; (3) **expose a four-tool control plane to the agent** — `snug_status`, `snug_open`, `snug_hand_in`, `snug_list_apps`. No data-plane tool, ever. The `claude -p` brain shim (program D5) lands in the same process as a module, reached by the page through the T2 brain seat.

**Why.** Apps built in the kit get connected fetch, with or without credentials (API keys, OAuth, signed requests), through one proxy the plugin ships, and the browser's CORS ceiling disappears exactly as it does on desktop. Spawn-and-connect is a channel every target host already offers plugins; nothing here makes Snug "built on MCP" (ADR-0061) — the proxy and the file are plumbing, and product copy stays "Snug apps run inside Claude Code / Cowork / Codex". Product copy never says "Snug MCP server".

**Hard rules (each becomes a test or a lint — the brief's list, restated as the contract):**

- **C1 stays where it is.** The executor is neither moved into Node nor duplicated. `/fetch` receives the request AFTER the page's gates and injection and is value-blind: it never logs, persists or echoes a URL, header or body; every error message passes `scrubAuthValues` (imported from `@snugprotocol/auth`) against the injected header values it saw before it returns. Defense in depth on the process side because anything on the machine can open a loopback socket: https-only (no LAN rung in this task — below), `isForbiddenNetHost` (**imported, never a second copy**), no redirect followed (`node:https` never follows one; the 3xx is returned as data), the 1 MiB cap **while reading**, the 60 s wall clock that names itself. The executor's own gates run twice — not a new policy (so NO resolved-address check: the executor's gate 5 is literal-only, and a resolved-IP rule would be a new policy the desktop does not have either; the DNS-rebinding residual stays where the threat model already records it).
- **The LLM is never a network principal.** `tools/list` returns exactly `snug_status`, `snug_open`, `snug_hand_in`, `snug_list_apps` — an allowlist test fails on any addition. The data-plane routes (`/fetch`, `/oauth/*`, `/userdb/*`, `/v1/*`, `/events`) live ONLY on the TCP loopback listener and require the page's bearer + a same-origin proof; the control plane (attached sessions, the human CLI) lives ONLY on a `0600` unix socket and carries no bearer. **The bearer appears in no MCP message, no tool result, no lock file and no log** — `snug_open` makes the PROCESS open the browser; the URL a tool result shows never carries the fragment.
- **Loopback only, authenticated, origin-bound.** Bind `127.0.0.1` on the **fixed port 43127** with an ephemeral fallback (D-B13: the OAuth redirect URI is `${origin}/oauth/callback` and a user registers that string in a provider dashboard, so the origin must survive a restart; a busy 43127 is a named condition that falls back to an ephemeral port and DISABLES the OAuth rows with a reason, never silently changing a registered URI). A per-launch 256-bit bearer rides to the page in the launch URL **fragment** (never the query), is stripped from `location` before the router boots, and must be present on every data-plane call (`Authorization: Bearer …` — the SSE stream is read with `fetch`, never `EventSource`, so the header rule has no exception). `Origin`, when present, must equal the served origin; **when absent the bearer alone admits the call** (review F2: Safari implements no `Sec-Fetch-*`, and `Origin` is omitted on same-origin GET, so an `Origin`-or-`Sec-Fetch-Site` rule would 403 every GET — `/events`, the userdb read leg, `/status` — on the default browser of a Mac). `Sec-Fetch-Site`, when present, must be `same-origin`. The bearer is the guard; the origin rule is the second proof where the browser offers one. **`Host` MUST equal `127.0.0.1:<port>` — reversed by review F1 (D-B18).** Measured this session with headless Chromium under `--host-resolver-rules=MAP evil.test 127.0.0.1`: after a rebind the attacker's page is same-origin in the browser's eyes, its GET carries **no `Origin` and no `Sec-Fetch-Site` at all**, and the ONLY header naming the attacker is `Host: evil.test:59901`. A browser always sends the name from the URL bar and a page cannot forge it, so the `Host` check is the one thing that refuses a rebind — and "never consulted" would have left the data plane open to any domain the attacker points at 127.0.0.1. No CORS headers are sent at all (the page is same-origin; a foreign page's response stays unreadable AND refused). **Every data-plane route MUST require a header or content-type that forces a CORS preflight** (the bearer alone does it) — this is load-bearing, not incidental: a route reachable by a *simple* request would let a foreign page fire the side effect blind, unable to read the answer but able to cause it. `Sec-Fetch-Site`, when sent, must be `same-origin` and never merely `same-site` — measured: a different port on 127.0.0.1 reads as `same-site`, so accepting that would open every other loopback service on the machine as a launcher. Missing bearer → 401, wrong `Host`/origin → 403, both bodies empty. Never `0.0.0.0`.
- **One process, one file.** `~/Snug/host/lock.json` `{port, pid, tokenHash, startedAt, socket}`; a second session attaches over the unix socket instead of spawning; the primary lives while ANY attached session lives and exits within the stdin-close grace once the last one is gone, releasing the lock and the socket. The user file follows `createFileBackend`'s discipline over a `FileBackendFs` the process implements with the desktop's rules (bare-name charset, temp + fsync + rename + dir fsync, absence = ENOENT only, the one-byte-discriminant read); if Snug Desktop is running, the process opens **read-only and says so** in the custody chip. Never a byte of state under `${CLAUDE_PLUGIN_ROOT}`.
- **OAuth = the WEB popup path over the process's own origin (D-B14, changed by review F1 — NOT the desktop transport).** The page leaves `platform.oauth` **undefined**, so the wizard takes its web branch: the blank-popup gesture escape (`ConnectionWizardSheet.tsx:1289`) is preserved, the popup-blocked and popup-closed backstops stay live, and the redirect URI is the existing `${window.location.origin}/oauth/callback` — a route the app already routes (`App.tsx:275`) and the PROCESS serves, delivering over `BroadcastChannel` same-origin exactly as on the hosted playground. **Why the plan's original (install `platform.oauth` + `createDesktopOAuthTransport` + a 41420 listener) is wrong:** `getPlatform().oauth !== undefined` is the wizard's ONE discriminator for "not a browser" and flips three behaviours at once — it skips the pre-opened popup, installs a handle-less pseudo-popup with no null check and no closed-poll (`connectionWizard.ts:2610-2648`), and swaps the register copy. On a real browser page `openExternal` can only be `window.open`, which by then has lost transient activation (the click awaits `crypto.subtle` for PKCE + the state HMAC), returns `null`, and the wizard parks on `awaiting_callback` forever with no error — the precise failure the web branch's `popup === null` arm exists to prevent. So `SNUG_DESKTOP_OAUTH_PORT`/41420 and `createDesktopOAuthTransport` are **out of this task**; the process needs no OAuth listener at all, and `desktopRedirectPosture` is not consulted (the web `webRedirectPosture: 'origin-callback'` seat is). The registered URI is `http://127.0.0.1:43127/#/oauth/callback`'s non-hash twin — pinned by D-B13's fixed port and shown on the register screen as today.
- **D4 holds.** `snug-host.html` and (later) `snug-host-micro.html` still ship `connections:false`, so no door renders and `host-ready.net` is false STRUCTURALLY (D-B33: the executor's bytes are in every build — the exclusion is runtime, not build-time; D4 governs what a binding claims and does). Connected apps exist ONLY in the `local-host` build, which only this process ever serves.
- **Owner acts stay owner acts.** No `npm publish`, no `@snugprotocol` scope registration, no marketplace submission, no push to the distribution repo, no `gh release`, no deploy. Prepare and print; never perform.

A shared holder marker written by both products is queued in next-steps as the durable answer (a desktop change, outside this task).
- **D-B11 (new) — Test hooks live in a second build, never in the release.** The proxy takes `lookup?` (the `node:https` request option) as a constructor parameter; the release entry never passes it; a test entry `src/main.test-hooks.ts` → `dist/snug-mcp.test.mjs` reads `SNUG_MCP_TEST_RESOLVE=host=ip[,…]` and passes a resolver, and the stub's self-signed CA rides Node's own `NODE_EXTRA_CA_CERTS`. AC11's sweep proves the release bundle carries neither the env name nor the symbol. Interop and stdin-close tests run the RELEASE bundle; only the connected-fetch e2e runs the test bundle.
- **D-B12 (new) — the `instructions` text lives at `apps/host-mcp/src/instructions.md`, not the prompt store.** `gen-content.mjs` compiles every `prompts/**.md` into the committed `content.ts` that the playground, the desktop and the host kit all import, so a prompt-store copy would inflate every bundle with process-only text — what ADR-0065 D6 forbids. One source, byte-compared by `check-host-mcp`, read by T6's skill build later. (Full reasoning in Decisions & surprises.)
- **D-B13 (new, review F1/F2) — fixed port 43127, bearer-only for GET.** The origin is a registered OAuth redirect URI, so it must survive a restart: bind 43127, fall back to an ephemeral port only when it is busy and then disable the OAuth rows with a named reason (never silently re-register the user's URI). `Origin` is checked where the browser sends it; where it does not (same-origin GET; Safari sends no `Sec-Fetch-*` at all) the bearer is the guard.
- **D-B14 (new, review F1) — the web OAuth path, not the desktop transport.** See the hard rule above: `platform.oauth` stays undefined, the process serves `/oauth/callback`, and 41420 / `createDesktopOAuthTransport` leave this task's scope entirely. This also deletes the `oauth-loopback.ts` module and the `oauth-callback` SSE event from D-B2's layout and D-B4's event list.
- **D-B15 (new, review F3) — the brain shim MUST speak SSE.** `openaiAdapter` writes `stream: true` unconditionally (`packages/adapters/src/openai.ts:78`) and parses the reply with `parseSse`; a plain-JSON answer yields no events and every turn returns `streamDroppedResult()` — a permanently broken brain. So `/v1/chat/completions` answers `text/event-stream` with at least one `choices[0].delta.content` chunk, a `choices[0].finish_reason`, and `data: [DONE]`, even though `claude -p --output-format json` is non-streaming underneath (the shim buffers the child, then emits). `brain.streaming` stays **false** — it is an app-facing declaration read only by `host-ready` (`state/webllm.ts:112`), never a transport switch. Pinned by a test that drives the REAL `localAdapter` against the real shim.
- **D-B16 (new, review F4/F6) — the client's `Response` and request serialization are their own contract.** Reconstruction passes `null` as the body for the null-body statuses 204/205/304 (a `new Response(bytes, {status:204})` THROWS, and the throw surfaces as `NET_FETCH_FAILED` on a successful DELETE), clamps `status` to 200–599, and drops a `statusText` outside the reason-phrase grammar. The body crosses as base64 of the RAW bytes, never a UTF-8 round trip. On the request side the page-side `fetchImpl` serializes `init.body` for both shapes the callers use — a `string` (the executor, `frames.ts:144`) and a **`URLSearchParams`** (`oauth-service.ts:655`, every token exchange/refresh/revoke; `JSON.stringify` of one yields `"{}"`), and never honours `redirect:'error'` toward the PROXY (`token-claim.ts:126` sets it for the provider hop; a proxy 3xx must return as data, not throw).
- **D-B17 (new, review F5) — the page-side cap is decorative; the process's is load-bearing.** `readBodyCapped` streams and cancels, but a reconstructed `Response` has already fully materialised, so `reader.cancel()` drops nothing. The guard lives in `fetch-proxy.ts`, which must trip at the SAME `LIMITS.MAX_NET_RESPONSE_BODY_BYTES` (`packages/protocol/src/constants.ts:87`) so both sides name one code. D-B3's "exactly as on desktop" is corrected to "the same gates, with the cap's teardown effect on the process side only" — stated in the ADR so no later reader treats the page-side cap as the wall.
- **D-B18 (new, angle-2 F1/F2/F3) — `Host` is the rebinding wall; preflight-forcing is an invariant.** See the hard rule. Three measured facts behind it: a rebound page sends no `Sec-Fetch-*` and an attacker-named `Host`; a different loopback PORT reads as `same-site`, so only the literal `same-origin` may pass; and every data-plane route must force a preflight (the bearer header does), or a foreign page can cause a side effect it cannot read. Non-browser same-user processes bypass all of it — the bearer is the only guard there, disclosed in the ADR.
- **D-B19 (new, angle-2 F4) — the inbound rebind is a NEW residual, not the desktop's inherited one.** The desktop's DNS-rebinding residual is about OUTBOUND fetches to public names; the desktop serves its UI from `tauri://localhost` and has no inbound loopback listener at all. Two protections this process lacks are also recorded: Tauri bakes an HTTP capability allowlist at build time (a ceiling no runtime bug can widen — the Node process has only `fetch-proxy.ts`'s gates), and the desktop page is not on an http origin. The threat-model delta writes its own inbound row rather than citing the desktop's.
- **D-B20 (new, angle-2 F6, CORRECTS the plan's number) — the process's wall clock is 75 s, strictly greater than the executor's 60 s.** At an equal 60 s whichever timer wins is a scheduling race, and when the process aborts first `timeoutSignal.aborted` is false in the page, so the executor's self-naming sentence never runs and the user reads the transport's spelling — the exact defect `next-steps.md` already logs for the LAN leg, reproduced in the other direction. The ordering is an invariant with a test, not just a number. The process's overflow must also map to the executor's `NET_SIZE_EXCEEDED` code, not a generic `ok:false`.
- **D-B21 (new, angle-2 F7 + the earlier env measurement) — the child's environment is built by ALLOWLIST, from scratch.** A denylist against an undocumented, version-varying `CLAUDE_*` namespace drifts silently the next time the CLI adds a variable. The child gets `{HOME, PATH}` plus terminal basics and nothing else, so it falls back to the user's own keychain/OAuth — which is what the brain chip's "your CLI" actually promises. Measured: the inherited env carries `CLAUDE_CODE_MESSAGING_TOKEN` and `CLAUDE_CODE_MESSAGING_SOCKET`, a live IPC channel back into the running session.
- **D-B22 (new, angle-2 F5) — `parent-watch.ts` is NOT imported across app boundaries.** `apps/whatsapp-sidecar` is `private`, declares no `exports` map, sets `rootDir: src`, and its `index.ts` re-export pulls in `baileys` — which `ssr.noExternal` would inline into the release bundle, contradicting the dependency claim and failing the inertness sweep. The 80 lines are copied into `apps/host-mcp/src/parent-watch.ts` **with an equivalence test against the sidecar's copy** (the D-B3 precedent), or moved to a shared package if Gate 4 finds that cheap. Either way one behaviour, pinned.
- **D-B23 (new, angle-2 F8) — the lock is created with `O_EXCL`, and take-over verifies command identity.** `fs.open(path,'wx')` decides the winner BEFORE any bind, closing the simultaneous-spawn race (two ephemeral binds never collide, so both would otherwise succeed and one becomes an unreapable orphan holding the user file). The socket is never `rmSync`'d blindly — that would unlink a live primary's socket out from under it, freezing the client count; a socket that answers belongs to a live primary, and only a proven-dead one is removed. A stale lock's pid is matched by COMMAND LINE before any signal (the desktop's `stale_helper_verdict` shape — pids recycle, and killing a stranger is worse than the conflict it repairs). A new attach during the exit grace CANCELS the grace, or is refused so the newcomer takes over cleanly.
- **D-B24 (new, angle-4 B1 — a data-loss blocker) — the holder check REFUSES TO OPEN, it does not open read-only.** `userdb.ts:1475` and `driver.ts:315` both swallow a failed `backend.save` with a bare `catch { dirty = true }` — no rethrow, no callback, no store, no log — and there is no persist-failure seam anywhere between the backend and the custody chip. So the plan's "answer 423 and set `readOnly`" would let the user install apps, complete a wizard, store credentials and type for an hour while every save silently 423'd, losing all of it on tab close, with the only hint buried in a popover they must click. **Therefore:** when the holder is present the local page does NOT open the db at all — it renders a refusal surface naming Snug for Mac and offering to retry once the desktop is closed. This is what "read-only and says so" honestly means, and it needs no `packages/db` change (which the plan's scope excludes). AC7 is restated accordingly. Adding an `onPersistError` seam to `packages/db` is queued in next-steps as the general fix, since the artifact binding has the same blind spot.
- **D-B25 (new, angle-4 B2) — the custody copy CHANGES an existing pinned assertion.** `copy.ts:88-97` falls `local-host` through to the shared default whose label is hardcoded `'your file: in this browser'` — a lie on this binding — and `hostCopy.test.ts:51` currently pins that string green. `readOnly` IS already read (`copy.ts:56`), refuting the plan's implication that it is ignored; what is missing is a holder NAME, which needs a change to the status ternary, not merely an additive `heldBy` field. There is no desktop twin to pin against: the desktop carries no custody seat at all. So step 4 edits an existing test rather than only adding one, and says so.
- **D-B26 (new, angle-4 B3 — an AC contradiction) — the hand-in's D4 refusal needs a binding-aware arm, and the hub needs a refresh.** Three separate breakages, all confirmed: (a) `handin.ts:91-97` refuses ANY bundle carrying connections with a message reading "not available inside an artifact" — but Binding B is defined as the ONE binding with connected apps, so AC8 and AC4 cannot both hold until that refusal takes the binding into account (`apps/host/src/handin.ts` joins the file list, and the artifact arm's message and behaviour stay byte-identical, pinned); (b) `Composition` (`compose.ts:48`) exposes no post-boot re-entry — `handIn` is called once from `main.tsx:53` and `pendingByApp`/`publishPending` are private closures, so an SSE hand-in needs a new exported seam; (c) `HubView.tsx:186` lists the library once on mount and `refreshAppMeta` only repopulates tile metadata, so a hand-in delivered while the user sits on the hub is invisible until a reload — and an auto-applied update to the app the user is INSIDE swaps v2 bytes under v1 with no `contentEpoch` bump. The SSE path must refresh the hub list and bump the run view's epoch, or say plainly that it did nothing. The `pending`/offered path is already reactive (`useSyncExternalStore`) and needs no work.
- **D-B27 (new, angle-4 F4/F5/F6) — the userdb HTTP client's own contract.** Absence is **404 and only 404**; every other status and every transport error REJECTS, because a client that maps any non-200 to `undefined` opens a pristine empty database over the user's real file and the next write destroys it (lesson 2026-08-03, cited in the backend's own header). The process's `valid_name` copies the desktop's charset verbatim so it admits the quarantine names too (`user.snug.corrupt-<base36>.bak`, `userdb.ts:1366`) and the legacy sidecar — a hand-narrowed two-name allowlist would throw INSIDE the corruption handler and turn a recoverable quarantine into an unrecoverable crash. The `/userdb/*` routes carry their own much larger body limit, never the proxy's 1 MiB (a user file trivially exceeds it; sharing the cap would silently 413 into the swallow above). Save cadence is fine: a 250 ms debounce, single-flighted, plus `pagehide`.
- **D-B28 (new, angle-3 F1 — a false-green gate risk) — `dist-local/**` joins `turbo.json`'s build outputs, and the e2e precondition checks it.** Proven: `turbo.json:4` declares only `outputs: ["dist/**"]`, so a cache hit restores `dist/snug-host.html` and leaves `dist-local/` MISSING — `FULL TURBO` in 26 ms with no local page on disk. The existing e2e precondition (`gate-local.mjs:108`) only stats the artifact kit, so the leg would run against a missing or stale local page rather than reporting CANNOT RUN. Both the turbo output glob and the precondition (plus `apps/host-mcp/dist/`) land in the same commit as the second build.
- **D-B29 (new, angle-3 F2 — blocks AC3/AC4/AC5) — the e2e stubs must EXPORT their CA cert; `NODE_EXTRA_CA_CERTS` is unsatisfiable as planned.** Both fixtures mint a self-signed cert into an ephemeral `mkdtemp` dir and never write it anywhere a caller can find (`net-stub.mjs:79-99`, `fake-idp.mjs:29-43`); the browser only works because Playwright passes `--ignore-certificate-errors`, which `node:https` has no equivalent for (measured: `DEPTH_ZERO_SELF_SIGNED_CERT`). So both fixtures gain an opt-in `SNUG_E2E_CERT_OUT=<path>` that writes the generated cert, and `apps/playground/e2e/fixtures/{net-stub,fake-idp}.mjs` join the files-to-touch list — the plan's "reuse BY PATH, unchanged" was wrong. (Both are otherwise genuinely portable: only `node:` builtins and `os.tmpdir()`, ports fully parameterised, verified running from a foreign cwd. They do shell out to `openssl`.)
- **D-B30 (new, angle-3 F3) — the process DEEP-IMPORTS the two guards; the barrel drags in sql.js.** Measured on the plan's exact Vite SSR config: the two pure functions cost **4,368 B** deep-imported and **329,902 B** through `@snugprotocol/auth`'s barrel, because the barrel reaches `@snugprotocol/db`, whose barrel exports `driver.js`, which imports sql.js (~2,100 lines of Emscripten shim in the output) — plus the whole OAuth provider registry. A 75× amplification of a WASM SQL driver and a provider list the process never uses, on a marketplace-scrutiny target whose D-B2′ argument was minimalism. The bundle imports `@snugprotocol/auth/dist/net-guards.js` and `.../scrub.js`; the identity test imports the BARREL (the `toBe` still holds — same binding) so the deep path can never drift from the public export. `packages/auth` declares no `exports` map today, so the deep path is reachable; a test pins that too. Zod (~168 KB) stays irreducible for `parseAppBundle`.
- **D-B31 (new, angle-3 F4) — the manifests module emits `owner`, `description`, `author` and `version`.** Measured with the real validator: omitting marketplace `owner` is a HARD error (`owner: Invalid input: expected object, received undefined`, exit 1), and `--strict` additionally demands a marketplace `description` and a plugin `author`. Step 5's "green" means `claude plugin validate dist/plugin --strict` exit 0. Marketplace `name` need not match the directory (verified).
- **D-B32 (new, angle-3 F5 — a false-green in the owner's walk) — an installed plugin is a version-keyed COPY, so the dev loop is uninstall → rebuild → install.** Measured: the install copies into `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/` (not a symlink); after editing the source, BOTH `claude plugin install` ("already installed") and `claude plugin update` ("already at the latest version") leave the stale copy in place. Without this step AC1 and the Gate-5 walk silently exercise an old bundle — the exact false-green class the gates exist to prevent. AC1 and the walk instructions name the loop; the alternative is bumping `version` per build.
- **D-B33 (new, angle-3 F6 — CORRECTS AC12 and the D4 wording) — the wizard, executor and registry are ALREADY in `snug-host.html`; `connections:false` is a RUNTIME flag, not a build-time exclusion.** Measured in the shipped artifact page: `NET_AMBIGUOUS_CONNECTION` ×3, the wizard markers ×8, `accounts.spotify.com` ×1. Building the local page with a second config produced **2,274,084 B — the same size as the artifact page**, so the local build needs no larger ceiling and the existing 2,750,000 (475,916 B of headroom) stands. The hard rule's phrase "without the wizard, executor or registry **reachable**" is true only in the runtime-gated sense and is restated that way; AC12's "proves connections ARE compiled in" becomes a RUNTIME assertion (the wizard door renders under `local-host`, `host-ready.net` is true) with the artifact kit's absence twin unchanged. Also: `check-host-kit`'s cited 2,219,519 B is stale — the current build is 2,274,084 B.
