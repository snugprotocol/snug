## Spec (what & why)

**What.** A **host kit** — the Snug runner + user database + bridge, built as a self-contained single-file page (`snug-host.html`, plus a ≤ 256 KB `snug-host-micro.html`) whose `AgentTransport` and `PersistenceBackend` are chosen by a capability probe at boot — and a **skill** (`snug/`: `SKILL.md` + `references/` = the app-authoring knowledge base + `assets/` = the kits and starters + `scripts/` = the local host launcher, brain shims and a `snug-db` CLI) that teaches any Agent-Skills-capable agent to build Snug apps and to run them in one of three **bindings**: **A — artifact** (A1 hosted: Claude Code and Cowork artifacts, brain = `claude.use("sample")`, storage = a working copy in the artifact origin's browser bucket plus the page's own html republish as the durable record; A2 chat: claude.ai / Claude Desktop chat artifacts, brain = `window.claude.complete`, storage = `window.storage`), **B — local host** (Claude Code, Hermes, OpenClaw, Codex/ChatGPT, Ollama: the existing playground served on localhost with the brain reached through the existing `local` mode via OpenAI-compatible shims around the user's own agent CLI — full Snug including connected apps, the `.snug` on disk), and **C — widget** (OpenClaw `show_widget`: the micro-runner with agent-driven storage and a prompt relay). Then the skill is packaged for the **Claude plugin marketplace** (the repo becomes a marketplace of one; Anthropic directory submission prepared) and for the **ChatGPT / Codex plugin directory** (`.codex-plugin/plugin.json`; on ChatGPT the runtime binding is B with a `codex exec` brain shim — ChatGPT has no in-page runtime that can call the model, re-verified at T9's Gate 2).

**Why.** This is the zero-install path to Snug: a user adds one skill from the public repo and can build, edit and run a Snug app **inside the agent they already use**, with that agent as the brain. It carries the knowledge base everywhere, keeps every invariant where it is (the file, the sandbox, the credential boundary — connected apps stay a local-host feature, D4), and it is the local binding every later host story builds on. Nothing here defines Snug through MCP (ADR-0061); no MCP server is built.

**Owner's asks folded into this program (2026-09-04):** (1) order = Claude first (claude.ai chat + Claude Desktop/Cowork), then Hermes and OpenClaw, then Claude marketplace packaging, then a ChatGPT-marketplace binding; (2) setup must be as easy as possible; (3) **once the skill is connected, it must launch the runner itself** — reuse the runner artifact if one exists, else create it and open it, and where it cannot open anything, print clear one-line instructions; (4) the runner must be **as close to the playground's UI/UX as possible** on claude.ai and to **Snug Desktop's UI/UX** on Claude Desktop / Codex / OpenClaw / Hermes. (5, added 2026-09-05) **the skill simply attaches to the host's brain** — the user is never asked to choose byok / local / demo-brain modes, and default model / provider / hub-account settings are hidden in the artifact (and in every host the skill launches).

**Acceptance criteria** (program level; each child adds its own, each becomes at least one test or a journaled walk where no test can reach):

1. **A1 — Claude Code / Cowork.** With only the `snug` skill installed, in one session, a user builds a starter-quality app and sees it running in a hosted artifact whose "think" calls run on the viewer's own Claude through `sample`, whose state survives a reload, and which exports a file the playground imports.
2. **A2 — claude.ai / Claude Desktop chat.** The same, degraded and disclosed: a bootstrap artifact loads the kit from an allowed CDN, thinks run through `window.claude.complete`, state lives in memory until the artifact is published and in `window.storage` after; the custody chip says exactly that.
3. **Runner launch (owner's ask 3).** On every supported surface, the skill's first act after "build me…" is to **find the existing runner** by its stable identity (artifact title `Snug` / a running local host / a pinned widget) **or create it**, open it where the host allows (artifact panel, preview pane, browser tab, pinned widget), and otherwise say in one line how to open it. An app the agent builds or edits appears in the runner without the user copying anything. Pinned by `SKILL.md` text tests, by unit tests on the hand-in mechanism (embed/merge of `snug-app-bundle/1` documents into the page), and by one journaled transcript per surface.
4. **Parity (owner's ask 4).** The kit renders the playground's **own** components (hub → run view → settings subset); there is no parallel UI. A playground-vs-kit screenshot pair is journaled per surface. On local-host surfaces the served page *is* the playground build, which is also Snug Desktop's tree (ADR-0021).
5. **B — Claude Code local.** Build an app, run it locally with the user's own `claude` CLI as the brain, and find the `.snug` on disk.
6. **B — Hermes.** A Hermes Desktop user can `open_preview` the local host and play Chess with Hermes as the brain.
7. **C — OpenClaw.** An OpenClaw user can pin a Snug micro-app widget, take a turn, and see the agent update it.
8. **Honesty, no choosing.** Every binding advertises its capability flags truthfully, discloses the brain and where the user's file lives, never renders a dead control for a missing capability, and **never asks the user to pick a brain, model, provider or account** — the kit's Settings are your file + appearance + about, pinned by a test that the brain section, BYOK rows, local-URL field, model pickers and identity/account surfaces are absent (D15).
9. **The skill.** Validates (`agentskills validate`), description ≤ 200 characters, bundle ≤ 30 MB, and installs on Claude Code (as a plugin from this repo's marketplace), Cowork, claude.ai (zip upload), OpenClaw (`openclaw skills install`) and Hermes (`hermes skills install`).
10. **Claude marketplace.** `claude plugin validate` is green on the repo; the marketplace entry pins a commit; the Anthropic plugin-directory submission is prepared with every review criterion checked and the copy checked against the positioning tests (submission itself is an owner act).
11. **ChatGPT / Codex plugin.** `.codex-plugin/plugin.json` validates; the skill runs on Codex with the `codex` brain shim; the OpenAI plugin-directory (or GitHub marketplace-import) submission is prepared (owner act).
12. **Docs.** The spec draft carries the non-normative bindings appendix; `docs/threat-model.md`'s ledger pins a "foreign hosts" delta; `architecture.md`, `code-map.md`, `glossary.md` and `product-vision.md`'s claims discipline are updated; ADR-0065 accepted.
13. **Acts.** Every release / publish / submission act is journaled (what, when UTC, verification) or explicitly left as an owner act with the exact command printed.

**Out of scope for the program:** an MCP server of any kind; the MCP Apps widget implementation (interface only, D9); ChatGPT in-chat rendering (no non-MCP path exists as of 2026-09-04 — re-verify at T9); Windows desktop; the Agent SDK helper (Option C — its own task); changes to the wire protocol or the userdb schema; connected apps in bindings A and C (D4); the marketplace submissions themselves (owner acts); any commercial-terms question about viewer-billed inference (a professional question, named in the ADR, not engineered around).

## Decisions the owner makes once (recommended defaults in bold; "go with defaults" is a valid answer)

The plan this program was drafted from carried D0–D10; the owner's asks and the code reading changed D0, D1 and D3 and added D11–D14. All fourteen are recorded in the ADR-0065 draft.

- **D0 — Binding order (owner's ask).** **A1 hosted (Claude Code + Cowork) → A2 chat (claude.ai + Claude Desktop chat) → skill v1 on Claude → B (Claude Code local + Hermes; codex/openclaw/ollama shims) → C (OpenClaw widget) → T7 docs → T8 Claude marketplace → T9 ChatGPT/Codex plugin.** A1 before A2 because A1 publishes the kit *from a file* (no CDN, no npm act) and is the fastest demo; A2 depends on a CDN answer (S2) and possibly an npm act.
- **D1 — Kit packaging (changed).** **A new app `apps/host`, built exactly the way `apps/desktop` is built: `@playground` alias into the playground source, its own entry + platform object + router, its own Vite config (single-file inlining, `.wasm` inlined as bytes).** The playground gains only capability flags that hide surfaces (`/build`, identity, feedback, connections, sync, BYOK rows — the pattern `capabilities.subscriptionMode` / `hubAuth` already uses), a `wasmBinary` path, and platform-injected transports/backends. Why not the plan's "build mode of `apps/playground`": the desktop precedent is exactly this shape and is proven; the playground's own Vite config and deploy script stay untouched; the kit gets its own test suite and gate. Alternative (the plan's default): a Vite mode inside `apps/playground` — rejected because every mode-scoped exception (the `.wasm` rule, route subsetting) would live in the file the production playground deploy reads.
- **D2 — App sandbox inside a Claude artifact.** **Nested `<iframe sandbox="allow-scripts" srcdoc>` runner if spike S1 passes; otherwise run the app in the artifact page itself and mark the binding `sandbox:'host'` in `host-ready`, with an ambient disclosure ("this app runs in Claude's sandbox, not Snug's").** No third option. **→ S1 (2026-09-05): clause 1 PASSED in both runtimes (the nested runner loads and talks to its parent; in the hosted runtime `RUNNER_CSP` is enforced inside the nested frame — two `connect-src` violations on a probe fetch; chat-side enforcement not measured, T4 verifies it at boot). Clause 2 FAILED (probe `pass:false`): the embedder narrows `RUNNER_CSP`'s CDN allowlist to jsDelivr `/npm/` + cdnjs, no CDN stylesheets/fonts, no unpkg, no `/gh/`. Decision taken — a third path beyond D2's two, because the in-page fallback runs under the same embedder policy and cures nothing: keep the nested runner and carry the narrowed allowlist as a Binding-A skill rule + an embed-time lint. Owner to confirm at T4's Gate 2.**
- **D3 — Storage per binding and the export name (changed).** **Hosted artifact, personal app: `artifact-files` — the kit publishes the SQLite bytes as a data file of the artifact through the files form of `artifact.publish` (`{"data/user.snug": blob}`), which mints a version WITHOUT reloading the running view; boot loads it with a same-origin fetch.** Fallback if S4 shows binary files or the Artifact tool's html republish do not preserve it: `artifact-html` (bytes embedded base64 in the page, html-form republish, reload per save, debounced to explicit acts). Multi-viewer/shared apps: `artifact-db` (chunked ≤ 200 KiB documents under `{self}`), org-internal only. Chat artifact: `window-storage` (base64 chunks, 20 MB text cap). **A publicly shared hosted artifact cannot save (the files form rejects `capability_disabled` there) — it runs read-only from the published bytes and offers export.** **→ S4/S4b/S10 (2026-09-05, measured): the files form is `capability_disabled` in the owner's own private view too, so the hosted ladder is: working copy in the artifact origin's browser bucket (localStorage proven at 5 ms with a 10 GiB quota; OPFS probed first at boot), durable record = `artifact-html` republish on explicit acts (2 MiB in 1.8 s, view reloads, byte-identical after; ceiling ≈ 11 MiB of user bytes under the 16 MB page cap), `artifact-db` chunks for org-internal shared apps only (~6 s per 2 MiB), the files form retried once at boot. Chat leg: `window.storage` persists across reloads but is PER VIEW (the in-chat view and the published link hold separate stores; a never-published artifact untested); export in chat = `execCommand('copy')` of the wrapper text only (the download link is inert, the async clipboard API blocked). Not measured, carried into T4: the hosted `downloads.save` export and version-history readability (the S4 walk stopped at the files-form refusal); whether a session-side code republish through the Artifact tool preserves the embedded `snug-db` block (`snug-embed` must merge it; the chip must say a republish rewrites the file); the chat brain `window.claude.complete` itself (only detected).** Export everywhere through `downloads.save` as **`snug-user.snug.json`** (`{"format":"snug-user-file/1", sha256, bytesBase64}` — the `downloads` allowlist has no `.snug`; the playground's `sniffSnugFile` learns the wrapper) and per-app as the ADR-0063 bundle. Alternative rejected: `localStorage` for public artifacts (per-viewer, lossy) — last resort only.
- **D4 — Nothing in Binding A or C may claim connected apps.** `net:false`, `auth:false` in `host-ready`; the wizard, executor and registry are not shipped in the kits; connected starters run in their **sample mode** (the `===== <FOLDER>-SAMPLE-BEGIN/END =====` blocks already make them look alive with zero network). A scope decision, not a technical one — the ADR says so.
- **D5 — Binding B brains: shims, not embeds.** `scripts/snug-brain-claude.mjs` (spawns the user's own `claude -p` — subscription usage on the user's own CLI; no third-party login offered; never `--bare`; never `ANTHROPIC_API_KEY` in the child env), `scripts/snug-brain-codex.mjs` (`codex exec --output-schema`), and passthrough presets for Hermes (`127.0.0.1:8642/v1`), OpenClaw (`:18789/v1`) and Ollama — all exposed as OpenAI-compatible endpoints on loopback that the playground's existing `local` mode reaches with a **bearer key** (new; today `localAdapter` hardcodes `'local'` and `transport.ts:136` skips key reads for `local`). Option C's Agent SDK helper stays the Snug Desktop path; this program does not build a second one.
- **D6 — Skill source of truth.** **Authored under `packages/knowledge/prompts/skills/snug/` (ADR-0004: nothing prompt-shaped lives elsewhere) and *generated* into a committed `skills/snug/` at the repo root by a build script, with a drift gate `check-skill-sync` (manifest + sha256 per source, modelled on `check-website-sync`; a byte-compare, never a restatement).** Committed because marketplaces and `claude plugin install` read the repo. `gen-content.mjs` must not compile the kits into `content.ts` — the skill's `assets/` and `scripts/` are assembled from their real homes (`apps/host/dist`, `scripts/`, `examples/`), only `SKILL.md` + `references/` are prompt-store text.
- **D7 — Plugin manifests at the repo root.** **`.claude-plugin/plugin.json` + `.claude-plugin/marketplace.json` (Claude Code + Cowork; also the format OpenAI's marketplace import accepts) in T6/T8, and `.codex-plugin/plugin.json` (Codex/ChatGPT) in T9.** ClawHub gets a `metadata.openclaw` block, Hermes a `metadata.hermes` block — additive, ignored elsewhere. One constants source feeds all three (lesson 2026-07-31: one contract, never two artifacts by convention).
- **D8 — Custody disclosure.** **A "your file" chip beside the brain chip (ADR-0059 extended): "on this Mac" / "in this artifact (Anthropic-hosted, export any time)" / "in Claude's page storage (deleted if unpublished)" / "kept by the agent".** Copy pinned by tests.
- **D9 — Widget target for C.** **OpenClaw `show_widget` only.** The micro-runner's bridge is an interface with two implementations planned (`openclaw`, `mcp-apps`); only `openclaw` ships — the MCP Apps one needs a server this program does not build.
- **D10 — Naming.** Kit files `snug-host.html` / `snug-host-micro.html`; the runner artifact's stable title **`Snug`**, favicon 🔥 (the brand mark); npm `@snugprotocol/host` *if* published (D11 — note the `@snugprotocol` npm scope is **not registered** as of 2026-09-05, an owner prerequisite); skill `snug`; CLI `snug-host`; helper CLI `snug-db`. Product copy: "Snug apps run inside Claude / Hermes / OpenClaw". Never "built on MCP"; never "Claude Code" in product names.
- **D11 — Kit distribution (new).** **Kits are GitHub Release assets, content-pinned in the skill (`assets/kits.json`: tag + sha256 per kit — ADR-0060's pattern), fetched on first use by `scripts/snug-kit.mjs` into a cache and verified before the Artifact tool publishes them; the committed `skills/snug/` stays small (text + scripts).** Alternative: commit the kits — zero-network setup but ~3–5 MB of history per kit change. **Decision rule:** if spike S9 shows Cowork's sandbox cannot download from GitHub, the kits are committed (a `.gitattributes`-tracked blob, rebuilt only at release points). For A2 the kit is loaded from whichever CDN S2 allows (jsDelivr `/gh/` from a pinned tag needs no publish act; `/npm/` needs the scope + an npm publish; cdnjs needs a listing). **→ S2 (2026-09-05): `/gh/` is blocked in BOTH viewers (only the `/gh/python-visualization/` prefix is allowlisted); jsDelivr `/npm/` and cdnjs execute. So A2 requires `@snugprotocol/host` on npm — register the `@snugprotocol` scope, then publish (owner acts) — or a cdnjs listing; the fetch-on-first-use plan for Claude Code stands and S9 (Cowork download) is still owed.**
- **D12 — Runner launch protocol (new, owner's ask 3).** **`SKILL.md` carries a mandatory "launch the runner" section: detect the surface from the tools present → find the existing runner → create it if absent → open it → hand the app in → tell the user in one line.** The table under "Plan → Runner launch protocol" is the contract; every row is pinned by a text test on `SKILL.md` and walked once per surface.
- **D13 — ChatGPT / Codex posture (new, owner's ask 1).** **The ChatGPT deliverable is the same skill packaged as a Codex plugin; its runtime binding is B with the `codex` shim (browser tab), because ChatGPT has no in-chat page that can call the model (Canvas retired 2026-05-28) and ChatGPT skills are Business/Enterprise-only.** Re-verify both facts at T9's Gate 2; if an in-chat runtime has appeared, it becomes its own binding task rather than a change to T9.
- **D14 — Spike execution (new).** **The artifact spikes (S1, S3, S4) run from a Claude Code session with the Artifact tool: probe pages are published PRIVATE under the owner's account, the owner opens each once, and the page writes its measurements into the artifact's `db`, which the session reads back — no copy-paste.** The chat spikes (S2, S10) are pasted by the owner into claude.ai chat. Hermes / OpenClaw / Codex are not installed on this machine (verified 2026-09-05); installing them is an owner act (or an explicit "install them") and gates S5, S6, S8 at the start of T3, T5, T9. **→ 2026-09-05: the loop worked as designed for S1/S3/S4/S4b (results read with `read_db`, zero pastes); the chat spikes cost six pastes. S9 (Cowork) is still owed by the owner. Owner installs: Hermes Desktop + `hermes gateway` for S5 (T3's first commit), OpenClaw for S6 (T5), Codex CLI for S8 (T9).**
- **D15 — The kit attaches to the host's brain; it never asks the user to choose one (owner's ask, 2026-09-05).** **No mode segment (byok / local / subscription), no BYOK key rows, no local-URL field, no default model or provider, no per-app model picker, no hub account or sign-in, no demo-brain choice — none of it exists in the kit or in a host the skill launched.** The boot probe picks the transport (D3's order); the brain chip stays, as **disclosure only** (ADR-0059): "Claude · this artifact's viewer" / "Claude · your CLI" / "Hermes" / "OpenClaw" / "demo brain — no host brain found". The demo brain is the one fallback when no host brain exists (a plain file opened in a browser) and the chip names it — it is never a menu entry. In Binding B the launcher pre-wires the brain (`snug-host.mjs` writes a boot config the page reads: mode `local`, shim URL, bearer, preset name) so the user never opens Settings; the same capability flag hides the brain section there. Model choice inside a binding (for example `sample`'s `modelTier`) is a per-contract host decision made in T4 from S3's numbers, not a control. Settings in the kit = **your file** (export / import / protect) + **appearance** + **about**. The hosted playground and Snug Desktop are unchanged.
