# Lessons ledger (append-only)

Short, forward-looking rules learned the hard way. **The agent reads this when planning (Gate 2).** Newest at top, ≤10 lines each. Entry shape: `## YYYY-MM-DD — <one-line rule>` then **Context**, **What happened**, **Rule**.

---

## 2026-08-06 — Probe browser capabilities on a real origin; about:blank is not a secure context and hides whole APIs
**Context:** AL-07 needed to know whether Playwright/Chrome on this Mac has WebGPU before designing the benchmark and e2e strategy. **What happened:** every probe evaluated on `about:blank` — bundled Chromium, real Chrome, headed, headless, CDP-direct — reported "NO navigator.gpu", which read as "no WebGPU in automation, scale the spike down". All five probes were lying: `navigator.gpu` (like several other APIs) exists only in SECURE contexts, and `about:blank` in a fresh automation profile isn't one. Re-probed against a localhost page: headed bundled Chromium AND even headless real Chrome (`channel: 'chrome'`) have full WebGPU (metal-3); headless bundled Chromium has the API but returns a null adapter — which separately proves a capability probe must demand the ADAPTER, not the API object. A wrong conclusion here would have shipped a "benchmarks infeasible in this environment" journal entry that was simply false. **Rule:** run capability probes on the origin class the product runs on (localhost/https page), never `about:blank`/`data:`; treat "API object present" as nothing — assert the working handle (adapter, context, device); and when a capability looks absent in automation, vary browser channel AND headedness before believing it, because the four combinations genuinely differ.

## 2026-08-06 — jsdom-green can be browser-dead: enumerate what a sandbox flag DISABLES and lint each behavior
**Context:** TASK-20260806-starters-pillars — the first Playwright tests that actually click through starter UIs. **What happened:** two new starters and the SHIPPED habit-tracker drove their inputs through `<form onSubmit>`. The C2 sandbox is `allow-scripts` only, and Chromium blocks a form submission at initiation — BEFORE the `submit` event dispatches — so the React handler never ran: habit-tracker's add-habit and ask-the-agent flows were dead in every real browser while the validate suite (structure checks) and jsdom (which never submits forms) stayed green the whole time. Found only because each new starter got a live-browser interaction test; fixed by switching to `onClick` + Enter `onKeyDown`, and locked by a new validate rule (no form elements). **Rule:** a sandbox/CSP restriction doesn't just close the channel you meant to close — it silently disables whole DOM behaviors (forms, popups, downloads, modals). When adopting one, enumerate what it disables and encode each item twice: a static lint in the artifact validator AND one real-browser probe per interactive flow. "Renders in the sandbox" proves almost nothing about "works in the sandbox".

## 2026-08-05 — Test at the altitude where the DECISION is made, not where the effect is visible
**Context:** TASK-20260804-observability-caching AC12 — prompt caching scoped to builder turns but not app-frame envelopes. **What happened:** every AC12 test asserted at the ADAPTER ("does a `cache_control` breakpoint reach the wire?"). All green — while the feature was wrong in **both directions at once**: the server's one adapter instance served both `/invoke` paths, so the app-frame envelopes D0/Q2 explicitly excluded *were* cached (a 1.25× write premium on every app turn, forever, for a prefix never read), and direct mode was never wired at all. The adapter faithfully did what it was told; the bug lived entirely in *which callers told it what*, an altitude no test occupied. A fresh-context reviewer found both within minutes by asking "which call sites decide this?". **Rule:** when a behavior is conditional, find the line that evaluates the condition and put a test there — asserting the downstream effect proves the mechanism works, never that it fires on the right inputs. If one object serves callers with different needs, the switch belongs on the call (per-request), not on the object (per-instance), and the test belongs on the caller.

## 2026-08-05 — Replacing a bound means re-deriving it, not relocating it: enumerate every growth path
**Context:** the same task removed per-field ingest truncation (so bodies could be shown whole) and replaced it with a global byte budget + oldest-first eviction. **What happened:** the new budget was tested only against the growth shape its author had in mind — big `system` strings on *completed* round trips — and held there. Three other paths walked straight through it: the size function omitted two retained fields (60 entries × 20 long tool names reported **360 bytes** while holding ~60 MB, off by 166,000×); a "always keep the newest entry" guard exempted entries that keep *growing* after admission (25 `artifact_write` results → 25 MB on one entry); and that same guard made eviction drain the entire build history chasing a target it could never reach. The predecessor's reviewer had already flagged "N entries with unbounded per-entry size is unbounded" — the identical bug returned through a different door. **Rule:** when swapping one bound for another, list every field that is retained and every event that can *add* to an existing record, and write one adversarial test per path before implementing — plus a test for the entry the bound cannot satisfy at all (the "keep it anyway" escape hatch is where unboundedness hides). A size function that silently omits a field makes the budget a lie, not an approximation.

## 2026-08-05 — When a surface changes meaning, re-check every signal that feeds it
**Context:** replacing a build-step timeline with a live rotating status line. **What happened:** both read `steps`, which is cleared at turn START but never at turn END. Under the timeline that lingering array was *correct* — it rendered completed steps with checkmarks ("here's what I did"). Driving a live "in flight" indicator from the same array turned it into a lie: after every build the status line rotated forever under a finished app. Nothing in the suite caught it because the render test passed a hand-built `steps` array and never exercised the end-of-turn transition. The honest signal (`busy`, cleared in the `finally`) was already threaded to both call sites. **Rule:** a state variable's correctness is relative to what reads it — when you repoint a surface at existing state, re-ask what that state MEANS at every lifecycle moment (start, mid, end, error, abort), and prefer the signal whose name matches the new question. Component tests that construct props by hand never exercise lifecycle; at least one test must drive the real state through a full turn.

## 2026-08-04 — A guard test must assert the OUTCOME, not a property that merely correlates with it
**Context:** TASK-20260804-hub-polish AC18 — locking the bug where editing a starter forked a hidden app. **What happened:** the guard asked the rendered hub which app ids it links to, and flagged rows nothing linked to. A fresh-context reviewer restored the fork end-to-end and **all three tests stayed green**: a forked app is an ordinary `snug_apps` row, so the hub lists it and renders a tile — it *is* reachable. What made it the bug was being a SECOND, UNWANTED row, which the probe never measured. A "probe self-check" test didn't rescue it either: it proved the helper could flag a row hidden by a spy, a condition the real defect never produces. **Rule:** name the defect in one sentence ("an unwanted extra app row appears"), then assert that sentence directly (`listApps()` is empty / every row carries an `installSource`) — if your assertion measures a proxy (reachability, presence in a list, a count that other things also change), a reviewer restoring the bug will walk straight past it. A guard for the guard is worth nothing if it exercises a state the real bug can't reach.

## 2026-08-04 — Give each adversarial reviewer its own worktree; a shared tree makes them lie to each other
**Context:** five fresh-context reviewers audited one phase each of the same working tree, concurrently. **What happened:** one reported the playground suite flaky/red (naming two specific files); it was neither — 3 full and 3 targeted runs were green. Reviewers mutate code deliberately (revert a hunk, confirm RED, restore); with one shared tree those mutations landed under each other's test runs, so a reviewer measured a suite that another reviewer had temporarily broken. The false report cost real time to chase, and worse, it is the shape of finding that gets a *true* red suite dismissed next time. **Rule:** adversarial reviewers that mutate code get `isolation: "worktree"` (or run strictly serially). Concurrency is safe only for read-only reviewers — and any cross-reviewer claim about global state (suite health, timing, flakiness) must be re-verified in a clean tree before it is believed or acted on.

## 2026-08-04 — Ask of every green test: "would this fail if the code were wrong?"
**Context:** TASK-20260803-hub-ops shipped three tests that passed for the wrong reason — in one session. **What happened:** (1) an AC20 materializer test deleted an already-clean namespace, and `persist` skips clean states, so it stayed green with BOTH resurrection guards disabled; (2) `llmInspectorPersistence.test.tsx` ran in subscription mode, where `onRoundTrip` never fires — it asserted that a marker never fed to the inspector didn't reach disk, and would have passed against an inspector that wrote everything to the DB; (3) a driver assertion sat behind `backend.list?.()`, which `MemoryBackend` does not implement, so it never ran. All three were found by adversarial probing, never by the suite. **Rule:** a test that has never been seen to FAIL has not been shown to test anything — mutation-check every guard test by reverting the fix (or disabling the guard) and watching it go red, and be specifically suspicious of a test that passed on its first run, one whose assertion sits behind an optional call, and one whose subject is only reachable in a mode/state the test does not actually enter.

## 2026-08-04 — A `ReadableStream` body is single-use; one mocked `Response` cannot serve two calls
**Context:** multi-turn SSE tests for the builder's subscription mode. **What happened:** `mockResolvedValue(sseResponse(...))` hands the SAME `Response` object to every call; the first turn drains its stream, and the second turn silently sees zero events — no error, just an empty turn that looks like a product bug and cost ~2 debug cycles. **Rule:** mock streaming responses with `mockImplementation(() => makeResponse())` so each call builds a fresh body; any test double wrapping a one-shot resource (streams, iterators, `FormData`, file handles) must be a factory, never a shared instance.

## 2026-08-03 — INSERT OR REPLACE only replaces under a uniqueness constraint; engine-internal tables may not have one
**Context:** AUTOINCREMENT continuity in the living-apps materializer (TASK-20260803-userdb-v2). **What happened:** `INSERT OR REPLACE INTO sqlite_sequence` silently APPENDED a second counter row — `sqlite_sequence` has no PK/UNIQUE on `name`, so there is never a conflict to replace — and SQLite read the LOWER counter, re-issuing ids of deleted rows after reopen. The suite stayed green because its round-trip test inserted one row and deleted none: registry counter and max-rowid inference coincided, hiding the duplicate. Found only by an adversarial probe that deleted the MAX rows before reopening. **Rule:** never use `INSERT OR REPLACE`/upsert against a table you didn't define without verifying it carries the uniqueness constraint the conflict clause needs (UPDATE-then-INSERT-if-zero-rows is the safe form); and a state-restoration test must exercise the state that DIVERGES from what the system would re-derive on its own (deleted-max rows, moved counters), never the coincidentally-equal state.

## 2026-08-03 — OPFS under page teardown breaks every naive persistence pattern; only new-file writes + fixed-name reads survive
**Context:** the user-DB AC2 e2e gate (TASK-20260803-portable-hub). **What happened:** real-browser testing falsified four assumptions in sequence: in-place `createWritable` truncated the file to 0 bytes when the page died mid-write; `move()`-with-overwrite deleted the destination with the rename pending; directory iteration returned EMPTY while same-directory writes were in flight; and even direct reads failed transiently during another document's teardown. Also: sql.js silently accepts zero-byte input as a fresh DB — turning any of the above into silent total data loss. **Rule:** durable browser storage writes go to a NEW fixed-name file (A/B slots + pointer), reads use only direct fixed-name lookups with completeness (magic) checks and brief retries, and an empty/magic-less read of a file that should exist is CORRUPT (quarantine), never "fresh".

## 2026-08-03 — Playwright ephemeral contexts cannot test OPFS persistence across hard navigations
**Context:** the same AC2 gate kept failing only under suite load. **What happened:** ephemeral-context OPFS lives in memory and did not survive cross-document navigations (bucket cleanly empty after reload); request interception (`page.route`) additionally stalled vite module loading in persistent contexts. **Rule:** a persistence-across-reload claim needs `launchPersistentContext` with a disk-backed profile (own project/worker), a bytes-on-disk wait plus a settle beat before navigation (Chromium commits OPFS lazily), and API-deadness proven separately in an ephemeral context where interception works.

## 2026-08-03 — Parallel agents inventing the same wire constant will disagree; pin shared literals in the task file before fan-out
**Context:** children 4 and 5 built the two halves of the hub sync contract concurrently. **What happened:** the server half required `x-snug-csrf` (double-submit) while the client provider sent `x-csrf-token` — green suites on both sides, dead-on-arrival integration; caught only because the orchestrator wired them together the same day. **Rule:** when work fans out across agents/packages, every shared literal (header names, cookie names, route paths, error codes) is written into BOTH task files verbatim before implementation — or lives in a constants module one side imports; "roughly specified" contracts WILL fork.

## 2026-07-31 — Every child merge gets an independent adversarial review with runnable probes
**Context:** TASK-20260731-build-hub, six child tasks. **What happened:** fresh-context reviewers with permission to run probe scripts found, pre-merge: a C1 credential leak via the envelope's `responseSchema` field, exported JSON Schemas that contradicted the protocol's own forward-compat rule, KB hook code reading db fields at the wrong nesting level (would have broken persistence in every generated app), and a meta-CSP injection bypass. None were caught by the authors' own green suites. **Rule:** High/Medium merges require a reviewer that did not write the code, prompted to attack specific constraint surfaces and to RUN its probes — "tests pass" is not review.

## 2026-07-31 — When one contract lives in two artifacts, add a byte-compare sync test
**Context:** the KB teaches copy-exactly hook code that `packages/sdk` also ships; prompt files carry wire literals. **What happened:** the KB≡SDK sync test caught a data-loss bug (usePersistedState key-change) and the placeholder-injection tests caught retyped constants; the ancestors' 4-way duplicated envelope tag was exactly this failure mode at scale. **Rule:** never let the same contract exist twice by convention — inject from one source or lock the copies with a byte-compare test in CI.

## 2026-07-31 — Browser security APIs lie in their return values; assert the enforcement signal
**Context:** the real-browser CSP gate. **What happened:** modern Chromium returns `true` from `navigator.sendBeacon` even when `connect-src` blocks the send — the check read the boolean and reported a hole that wasn't there. **Rule:** CSP/sandbox tests must assert the enforcement signal (`securitypolicyviolation` events, absence of network effects), not API return values.

## 2026-07-31 — Never trust availability by memory; verify names before proposing them
**Context:** TASK-20260731-bootstrap (naming rounds). **What happened:** ~20 candidate names (Whim, Carve, Knit, Gizmo, Nook, Yurt, Birdhouse, AXP…) all died on verification against GitHub orgs and web search — every "obviously free" name was taken by an active AI product. **Rule:** any public-facing name (package, command, protocol message) gets a GitHub/npm/web check *before* it is proposed, in the same session.

## 2026-07-31 — Port the hardening, not the bugs
**Context:** audits of the prior production systems this work extracts from. **What happened:** those systems contain a broken two-layer OAuth callback (`userLayer` never unwrapped) and an off-by-default strict-host-injection flag (prompt-injection exfiltration path). **Rule:** when extracting, carry forward the DB invariants + host-freeze from the hardened port and the PKCE/refresh/scrubbing from the original — and never reintroduce configurable security (strictness is not a flag).

## 2026-08-02 — `??` fallbacks make empty env vars a silent foot-gun
**Context:** apps/server config + .env.example authoring. **What happened:** `SNUG_MODEL=` (present but empty) defeats a `?? 'default'` fallback — empty string is not `undefined` — so the "default" silently becomes `''`. **Rule:** env templates comment optional vars out rather than leaving them empty, and config readers treat `''` as unset (`value || fallback` or explicit trim-check) for any var with a fallback.
