# Lessons ledger (append-only)

Short, forward-looking rules learned the hard way. **The agent reads this when planning (Gate 2).** Newest at top, ≤10 lines each. Entry shape: `## YYYY-MM-DD — <one-line rule>` then **Context**, **What happened**, **Rule**.

## 2026-08-13 — A fence that RESTATES its data cannot test it; it must EXERCISE it
**Context:** TASK-20260812-desktop-auth-awareness, twice in one week. **What happened:** (1) `hue.pairing.secretPath` shipped as `['success', 0, 'username']` — a literal reading of ambiguous prose — while a real CLIP v1 pairing answer is an ARRAY of result objects OUTERMOST. The path resolved to `undefined` against every real bridge, so pairing would have failed forever while the device answered perfectly; the fence pinning it compared the registry's array to a **retyped copy of itself** and was green against the broken value. (2) The four C1 tests guarding query-credential scrubbing used a fixture key that was URL-safe hex, so percent-encoding was a no-op and they could not exercise the encoding they claimed to guard — the raw/encoded mismatch that leaked base64 keys verbatim into app-visible error messages passed all four. **Rule:** a test that re-states a value and asserts equality proves only that you can type it twice. Drive the value through the code that CONSUMES it (walk the path against a real-shaped response; render the template into a real URL), and choose fixtures that are hostile to the mechanism under test — a fixture that is accidentally well-behaved (URL-safe, single-segment, already-normalized) turns its own test into decoration.

## 2026-08-13 — When a lane spans two packages, the SEAM between them is what neither package's suite watches
**Context:** same task, P5 — and it recurred one lane after being journaled, which makes it a pattern rather than an incident. **What happened:** deleting `lanFetch,` from the desktop platform object left all 80 desktop tests green; one lane later, deleting `lanPair,` left all 83 green. Each side was complete and jointly blind: the desktop tests drive the module function directly, and the playground's suites supply their own fake platform, so the one fact that makes the entire transport reachable in production was unasserted by construction. **Rule:** when work spans two packages, write the wiring test that asserts the seam's IDENTITY from the integrating side (`platform.lanFetch toBe lanFetch`), and mutate the seam — not just the function — to prove it bites. Neither package's suite is structurally capable of seeing this: one owns the implementation, the other owns a stub, and nothing owns the wire between them.

## 2026-08-13 — Co-located guards mask each other: every refusal needs an input that satisfies every OTHER refusal
**Context:** same task, three instances across two lanes. **What happened:** deleting `runLanPairing`'s approved-status check killed nothing — a pre-collection row has no HOST either, so the host guard beside it refuses first and hides the deletion. The discriminating input is a row with a COLLECTED address that is not yet approved: the exact state a user occupies between typing and approving, which no test occupied. The same shape had already appeared as a guard sitting beside a null-safe accessor (`registryHostIndex`'s lanHost skip survived its own deletion because the `?? []` next to it already covered today's hostless entry). **Rule:** mutating a guard proves nothing unless the test input REACHES it — for each refusal in a function, construct an input that passes every sibling refusal and fails only this one. When a mutation does not go red, suspect the fixture before the mutation; and a guard that survives its own deletion is decoration until a test drives it directly.

## 2026-08-13 — A timing "fix" is verified by measuring the failure RATE, not by consecutive green runs
**Context:** same task — my own P3 fix for a probe test flaking ~1 run in 3 at suite scale. **What happened:** I raised `vi.waitFor`'s budget to 10 s inside a test whose own vitest timeout was the **5000 ms default**, so the raise was structurally unreachable — every failure died at 5004 ms with an anonymous "Test timed out in 5000ms" while `waitFor` was still patiently waiting. It passed 6 consecutive runs while being completely inert, and P4 measured it still flaking at 3/12. The mechanism was never slowness: 200 consecutive ES256 imports+signs take 83 ms, failures were BIMODAL (~158 ms or a full hang), and `vi.waitFor` was being called INSIDE `act()` — React's `act` owns the scheduler while pending, so the component could never re-render with the resolved outcome. Every diagnostic `console.log` I added made it pass, by shifting the render ahead of the wait. **Rules:** (a) measure the failure rate before and after — "it passed a few times" is the evidence a structurally inert fix produces; (b) a "budget" fix must check the ENCLOSING budget, or the inner timeout is dead code that looks like diligence; (c) when a symptom is intermittent and every added log makes it pass, that is a scheduler/ordering bug, not a slow operation — "raise the timeout" is what you reach for when you have not found the mechanism yet.

## 2026-08-13 — A lane's own green is a SAMPLE; the integrating forced run at full parallelism is a different test
**Context:** same task — the orchestrator's forced root run caught RED twice, after every lane had reported green. **What happened:** P3's four lanes all reported green; the integrating `turbo run test --force` found playground RED on a probe test that fails ~1 in 3 only at suite scale (95 files sharing one box) and passes every time in isolation. One lane had seen it once and honestly journaled it as an unreproduced flake — it was real. P4's root run then caught the same test still flaking on the committed tree, after a fix that had passed its lane. A per-lane suite runs under different contention, different file counts and a different scheduler; it is a smaller sample of a different distribution. **Rule:** a phase is not green because its lanes said so — the orchestrator runs the forced root suite itself (`Cached: 0 cached`) and treats a lane's green as one sample. Corollary: repeat it. A single forced run that passes is also a sample; the runs that caught these were the fourth and the tenth.

## 2026-08-13 — A new placement seat must ride EVERY surface the old seat rides — including the human review that is the price of admitting it
**Context:** same task, the P6 whole-surface BLOCKER. **What happened:** `queryTemplate` (credentials placed in a URL rather than a header) was wired end to end through the protocol schema, Guard 2b's occupied-seat counting, the template lint, executor injection, and the scrub set — and **not** through the wizard's review screen, which renders `headerTemplate` verbatim. Both shipped registry entries using it were approved by a human who was never shown the placement at all, and a secret in a web address is a different risk story from one in a header. Every phase suite was green over it because each phase tested its own layer. ADR-0017 names verbatim review as the PRICE of admitting credential-prompt seats; a seat that skips review is a seat admitted for free. **Rule:** when adding a capability or placement seat beside an existing one, enumerate every surface the existing seat touches — schema, lint, admission, executor, scrub, **review copy**, migration, export — and either move the new seat through each or state in the task file why it does not belong there. The consent surface is the one most easily forgotten, because nothing fails without it.

## 2026-08-12 — A guard expressed as a FLAG is only as real as the transport's willingness to read it; porting a guard means re-proving the flag is honored, not re-passing it
**Context:** TASK-20260812-desktop-hub-scaffold — the desktop shell injects a native fetch behind the connected-fetch `fetchImpl` seam, which the advisory had pre-blessed as "zero security-model change". **What happened:** the whole-surface review found that `@tauri-apps/plugin-http`'s JS shim reads only `maxRedirections`/`connectTimeout`/`proxy`/`danger` from `init` and **never reads `init.redirect`** — so connected-fetch gate 9 (`redirect:'manual'` → `NET_REDIRECT_BLOCKED`) and oauth-service `postForm`'s B2 guard ("a credential POST never follows a redirect") were both **silently inert on desktop**. Rust installs `Policy::none()` only for `maxRedirections === Some(0)`, else reqwest's default follows ten hops, and reqwest strips only `Authorization`/`Cookie`/`Proxy-Authorization` cross-host — so *injected* credentials (`X-API-Key`, HMAC signature seats) were forwarded to the redirect target while the executor saw only the final 200. One open redirect on an already-approved host = credential exfiltration that the browser build refuses outright. Every package suite was green; the in-shell gate was green; the guard source code was unchanged and looked correct at every call site. **Rule:** when a guard is expressed as a REQUEST OPTION (`redirect`, `signal`, `credentials`, `cache`, TLS verify flags) rather than as code you execute, moving to a new transport voids it by default — read the new transport's option-parsing source and write a test that asserts the option ARRIVES (or that the blocked behavior actually blocks), because "we pass the same init object" proves nothing about what the other side reads. Corollary for seam-based ports generally: a seam guarantees the SHAPE crosses the boundary, never the SEMANTICS.

## 2026-08-12 — Parallel implementers sharing one git index corrupt commit boundaries and can destroy each other's uncommitted work; worktree isolation is for writers too
**Context:** same task — three fix agents dispatched concurrently on file-disjoint lanes in ONE working tree, after the repo had already learned (2026-08-04) to give adversarial *reviewers* their own worktrees. **What happened:** agent A's `git add`/`commit` raced agent B's staging twice, so commit `d021232` carries seven files its message does not describe and a follow-up commit exists purely to say so; separately, an agent's `git stash push` briefly displaced another's in-flight file (restored byte-for-byte, verified). Nothing was lost, and file-disjointness DID prevent content conflicts — but the index is shared state even when the files are not, so "disjoint files" is not the safety property people assume it is. History was left un-rewritten because agents were still working against those commits. **Rule:** any agent that WRITES gets `isolation: "worktree"`, not just any agent that mutates during review — the 2026-08-04 lesson was scoped too narrowly. Disjoint file ownership prevents merge conflicts, not index races; if lanes must share a tree, serialize the commits through the orchestrator instead of letting each agent stage its own.

## 2026-08-12 — An orchestration layer that maps "no work" to an empty list will feed a downstream stage a clean-looking lie; make consumers verify producers RAN
**Context:** TASK-20260812-desktop-hub-scaffold P1 — a Workflow fan-out where two pipelines were seeded with a `[null]` item, which the engine treats as an already-dropped item: zero agents ran and the chains returned `[]`, indistinguishable from "ran fine, found nothing to report." **What happened:** the downstream glue agent received `AUTH: [] DB: []` and was SUPPOSED to build on their symbols; instead of fabricating them it ran `grep`/`git log --all` first, found zero commits and zero symbols, and refused with an "ORCHESTRATION DEFECT" report — turning a silent no-op into a loud one. The fix was a one-word seed change and a resume. The same session's shell gate later caught the only cross-boundary integration bug (a path-shape mismatch between the TS backend and the Rust command) that seven green package suites could not see. **Rule:** when composing agents (or any producer/consumer stages), the consumer's first act is to verify the producer's work EXISTS in the shared substrate (commits present, symbols grep-able) — never to trust the handed-in summary; and treat an empty result from a fan-out as a tool-failure hypothesis before a no-findings conclusion (the empty-grep lesson, one level up). Corollary: budget one integration probe that exercises the REAL seam between independently-green components — the first real boot is a test, and it will find the bug the suites were structurally blind to.

## 2026-08-12 — Billed usage vs delivered bytes is a stream-integrity oracle; check it before blaming the model or the parser
**Context:** TASK-20260812-app-reply-parse-failure — an in-app reply failed `parseAgentReply` with valid-looking JSON on screen; two ranked hypotheses (reply shape, cap truncation) both pointed at generation. **What happened:** the owner's raw capture showed `stop_reason: end_turn` with 215 billed output tokens against ~245 delivered CHARS (impossible at ≥1 char/token), and the delivered tail referenced a CTE (`FROM ordered`) whose definition sat in a never-delivered delta — generation was complete, DELIVERY was not. Every content-level hypothesis was a dead end. **Rule:** when a stream looks truncated or corrupt but the stop reason says it finished, compare `usage.output_tokens` to the delivered text and look for tail-references-to-missing-head before touching any parser; a big gap convicts the delivery path, and no parser change should ever make corrupt bytes "parse".

## 2026-08-12 — Exonerate your own stream layer with an exhaustive byte-boundary replay, not by inspection — and leave it as a tripwire
**Context:** same task — once delivery loss was suspected, our `parseSse` was the natural in-stack suspect. **What happened:** inspection said the chunk buffering was correct, but inspection is how the last three "obviously correct" seams shipped bugs; instead the owner's fixture (interior whitespace padding, doubled `{` delta, byte-faithful) was replayed through the REAL adapter at every possible two-chunk boundary (~2.7k splits) plus one-byte-per-chunk — identical assembly everywhere, exonerating the client with proof and locating the loss upstream (TCP delivers in-order or errors; bytes can't vanish quietly). **Rule:** to clear (or convict) a framing/parsing layer of data loss, replay a real captured stream split at EVERY byte position through the real code and assert byte-identical output; keep the suite — if it ever reds, your layer has ACQUIRED the bug and that is a P0 signal, not a flake.

## 2026-08-12 — Rank hypotheses only against mechanisms you have executed; pin each refutation as a characterization test
**Context:** same task — the diagnosis session ranked "bare ARRAY reply → PARSE_FAILED" #1 on the owner's "it has JSON data" observation. **What happened:** actually reading `balancedObjects` refuted it before any repro: an array of row OBJECTS doesn't fail — the scanner yields the first `{…}` INSIDE the array, so the parser silently "succeeds" with ONE row and drops the rest (a worse, latent silent-corruption hazard, now a pinned characterization test feeding a contract decision); the promoted #2 (truncation) then died against the real bytes too. Two plausible-sounding rankings, both wrong, both cheap to falsify. **Rule:** a hypothesis about a parser/scanner is not "ranked" until the suspect input has been run through the real code (a 3-line test beats an argument); and every refuted hypothesis becomes a characterization test so the next session cannot re-inherit the dead theory — symptom-fit is not mechanism-fit.

## 2026-08-12 — A guard that both REFUSES and REWRITES must drive both from one resolution; scoping only the refusal half is how a user action gets silently rewritten

**Context:** TASK-20260812-auth-kind-choice — letting the user choose between a provider's auth options, where the chosen requirement re-persists through the registry-borrow ban. **What happened:** my plan changed only Guard 2b's REFUSAL half (bless a field list matching any authored variant) and explicitly declared the substitution half out of scope. The fresh-context review proved that half (`applyRegistryValues`) runs unconditionally on every borrow hit on every channel and writes the DEFAULT option's fields — so the user's chosen OAuth variant would have been admitted and then silently rewritten back to the api_key shape between the click and the row: a "choice that does nothing", the exact bug class the task existed to kill. Fixed with ONE matched-option handle feeding both halves, so the blessed list and the substituted shape cannot disagree. **Rules:** (a) when a security guard has a refuse path AND a rewrite path, any change to what it accepts must re-derive what it rewrites from the same resolution — auditing one half of a two-half guard is auditing nothing; (b) an AC that stops at "not refused"/"admission ok" is a tautology whenever a later stage can still rewrite the value — assert on the PERSISTED shape; (c) when a plan says "no changes to X needed", that claim is itself a finding to verify by tracing X's execution, not a scope note to take on faith.

## 2026-08-12 — When a user says "the button does nothing", trace from THEIR entry point — and execute the assumed causal chain before building on it

**Context:** TASK-20260812-registry-authoritative-auth. The owner reported the Coinbase app's connect CTA doing nothing. **What happened:** two independent diagnoses (mine and a fresh-context reviewer's) both traced inward from wizard screens the owner never reached — the swallow site at the connect step, the empty-fields guard at the credentials step — and both were wrong: the owner's click died at `openConnectionWizardForApp`'s zero-row guard, one layer up, before any screen existed. Neither of us asked what the screen actually said until the owner volunteered it. Then at pickup, the plan's assumed root-cause chain ("persist refuses the broken shape → no row") was REFUTED by a ten-minute end-to-end probe: admission on the registry channel substitutes the pinned fields and the row persists fine — with the wrong KIND, a different live defect than the one planned for. The fixes survived; the causal story did not. **Rules:** (a) diagnose a "nothing happens" report from the user's first visible surface inward, never from the component most related to the feature; (b) a root-cause chain with ≥2 links is a hypothesis — execute it end to end on production seams before any fix is written on top of it (the task file's own "P0 proves it" step is what caught this); (c) a store/state written for an error is not surfaced until something RENDERS it — grep for the subscriber before claiming an error path is visible.

## 2026-08-11 — When a gate's only signal is a number, close the statement classes that number cannot describe — and never infer trust from the absence of local state

**Context:** a fresh-context review of PR #35 found one P0 and six other defects in code that was already whole-surface reviewed and green at 2156 tests. **What happened:** (1) the data lane's approval card showed the user affected-row counts, and `sqlite3_changes()` is **0 for all DDL** — so `DROP TABLE expenses` previewed as "would affect 0 row(s)", the TOCTOU drift guard compared 0 to 0 and passed, and the table was permanently gone (the data lane has no revert). The earlier review had fixed the case where the count was *dropped* and moved on; the case where the count is legitimately *0 while the statement is destructive* was the same family, one instance over. (2) `sqlite3_changes()` is also STICKY — it reports the previous modifying statement's count for anything that follows — so a DELETE-then-SELECT batch previewed `[3, 3]` and told the user a SELECT would change 3 rows. The existing test ran that exact batch but asserted `[0].changes` and `[1].rows`, never `[1].changes`. (3) Fixing the "restore into a fresh hub nulls every contract" bug, my first attempt keyed the exemption on "the hub has no apps" — three existing AC-F1-7 tests went red and were RIGHT to: a hostile donor arrives at exactly the same empty hub a legitimate restore does, so emptiness cannot carry that distinction. Re-keyed on the caller (`trustedOrigin`, set only by the recovery restore and the sync pull, absent-means-untrusted). **Rules:** (a) when a human gate's whole impact signal is one metric, statement/operation classes whose blast radius that metric cannot express must be REFUSED, not relabeled — better copy on the card is a mitigation, closing the class is a fix, and the reviewed path for the refused class usually already exists elsewhere; (b) put such a guard where the preview and the executor share ONE definition, or the two ends of an approval can disagree about what was approved; (c) a stateful C API's counter (`sqlite3_changes()`, `errno`, `LastError`) describes the last operation that SET it, so attach it by operation KIND rather than reading it unconditionally — and note the obvious discriminator can be wrong (`total_changes()` cannot tell a zero-row DELETE from a SELECT); (d) **absence of local state is not consent** — a fresh/empty system looks identical to an attacker and to a legitimate restore, so trust must come from a caller that knows the provenance, defaulting to untrusted; (e) when a fix makes existing security tests fail, the tests are the hypothesis to check first — mine were right and my approach was wrong.

## 2026-08-11 — A green package test suite is not a type-clean claim: only `adapters` typechecks in its `test` script

**Context:** TASK-20260811 implementation, three separate times. **What happened:** `pnpm --filter <pkg> test` came back green while the code did not compile — a non-existent `USERDB_ERROR_CODES.SQL_ERROR`, a missing `@snugprotocol/db` export of the scratch types, and a `ChatLogProps` interface that never received its two new fields. Each was caught later by `turbo run build`, not by any test run. The cause is a real asymmetry in the repo: `packages/adapters/package.json` runs `tsc -p tsconfig.test.json && vitest run`, while `packages/db`, `packages/protocol` and `apps/playground` run `vitest run` alone — vitest transpiles per file and never type-checks, so a type error in a module that no test imports (or in an interface whose consumer is a `.tsx` the suite renders loosely) sails through. **Rule:** treat `pnpm --filter X test` as a BEHAVIOR check only. Before claiming a package is green, run `npx turbo run build` (or the root `turbo run test`, which depends on `build`) from the REPO ROOT — running turbo from inside a package directory silently scopes it to that package and its deps, which is how a 19-task run becomes a 4-task run that looks like it passed. The durable fix is to add the `tsc &&` prefix to the other three `test` scripts so the guarantee is uniform; until then this asymmetry is a standing trap, and it is the reason two of this task's phases reported green before they compiled.

**UPDATE 2026-08-11 (same branch, follow-up):** the durable fix is DONE and the asymmetry is closed — `db`, `protocol`, `knowledge` and `playground` each gained a `tsconfig.test.json` (the `adapters` pattern: extend the build config, `noEmit`, `exclude: []` to re-include `__tests__`) and their `test` scripts now run `tsc -p tsconfig.test.json && vitest run`. It was FOUR packages, not the three this entry named: `knowledge` excludes `src/__tests__` from its build tsconfig too. Turning it on surfaced **40 pre-existing type errors across 11 files that every green run had hidden** — and two were real test defects, not cosmetics: a `runtime-contract-render` helper meant to count assembled system blocks was dead code whose `.split()` bound to the wrong template literal (the live security assertion used a correct sibling, so the separator-forging regression test was never actually weakened — but the broken twin sat beside it looking authoritative), and a `dataTools` drift assertion narrowed only on `ok` so the `'failed'` branch would have skipped the check silently and still passed. The rest were unnarrowed unions, `as never` casts that defeated checking entirely, and a frame-builder fixture that had drifted from the real `DbRequestFrame` shape (`type: 'db-request'` + `id` vs the schema's `'snug:db-request'` + `requestId`/`instanceId`) behind an `as` cast. **Rule addendum:** when a type-check guard is finally switched on for a suite that never had one, budget for the backlog and read every error rather than mass-suppressing — the ones worth finding are the two that were silently voiding an assertion, and `as`/`as never` casts in test helpers are where they hide.

## 2026-08-11 — A test matrix that never repeats an operation KIND has a hole in it; and "strip the exact delimiter" is not the same as "remove the primitive"

**Context:** TASK-20260811 P4's whole-surface review (4 traces + 4 adversarial verifiers) found two BLOCKERs that 2100+ passing tests had missed. **What happened:** (1) `scratchRun` computed affected-row counts as a DELTA of sql.js's `getRowsModified()`, assuming it was cumulative per connection. It is `sqlite3_changes()` — the count for the latest completed statement — so every write after the first was wrong, often negative, and the number went straight onto the user's approval card. The TOCTOU drift guard could not catch it because it re-ran the identical arithmetic on both sides and agreed with itself: **corruption that is consistent is invisible to a comparison.** The reason it survived is the sharp part — the one multi-statement test paired a DELETE with a SELECT, and a SELECT leaves `sqlite3_changes()` untouched, so the delta stayed accidentally correct. The bug required two consecutive WRITES. (2) `renderRuntimeContract` stopped a contract forging a system-block boundary by stripping the EXACT separator string; a contract containing the separator padded with extra newlines sailed through, because its own newlines then supplied the blank lines the separator needs. Verified: 5 system blocks where 4 were expected, the fifth attacker-authored, reproducible from every free-text seat and from a settings VALUE. **Rules:** (a) when a test matrix combines operation KINDS, include a case that repeats one kind — a read/write pair can hide a bug that write/write exposes, and stateful C APIs like `sqlite3_changes()` are exactly where that bites; (b) a guard that compares two values computed by the SAME function verifies agreement, not correctness — at least one side must be independently derived, or the guard's failure mode is silence; (c) when neutralizing a delimiter, target the PRIMITIVE (any horizontal-rule line) rather than one spelling of it, because the attacker picks the spelling; (d) a fresh-context whole-surface review at the END of a task is worth its cost even when every phase was reviewed and green — phase reviews are blind to what only appears once the phases are joined.

## 2026-08-11 — Verify the MECHANISM behind a symptom before planning the fix; an observation can be right while its attribution is wrong
**Context:** TASK-20260811-lean-runtime-data-chat planning. The owner observed that every Chess-move LLM message "contains the original context/prompt passed while authoring the app." **What happened:** recon proved no authoring conversation is ever replayed — an app-frame turn is ONE self-contained envelope with no history; the real per-move costs were the app-BUILDER system prompt riding every runtime turn (`transport.ts:57`/`invoke.ts:103`), KB-untaught apps duplicating state into payload, and the 128K output default. A fix built to the reported mechanism ("stop replaying the conversation") would have shipped and changed nothing. The same shape recurred INSIDE the plan: two fresh-context reviews found load-bearing wiring premises false (a `contentEpoch` refresh that does not exist; a copy-forward `saveAppVersion` does not do) even though every file:line citation in the plan was verified accurate — the error lived in the inference drawn from the line, not the line. **Rule:** treat a symptom's attributed cause as a hypothesis and trace the actual code path before designing the fix; and for High-tier plans, have the plan's wiring CLAIMS adversarially re-verified separately from its citations — "the line exists" and "the line does what the plan needs" are different checks with different failure modes.

## 2026-08-10 — A multi-phase rewrite needs a WHOLE-SURFACE review at the end; per-phase reviews are structurally blind to phase-boundary bugs
**Context:** Dynamic Auth v2 (TASK-20260810, P0–P5). Each phase got its own 3-lens fresh-context review and each found real defects — eleven consecutive phases, four BLOCKERs. Then P5's whole-surface lens, told to trace one credential from authoring to wire, found the worst defect of the run. **What happened:** `required: false` credential fields were broken end-to-end. The executor lints a header template against the requirement's **declared** field keys; the engine then re-lints against only the keys whose values were **loaded**. Coinbase's registry entry marks `passphrase` optional, the wizard lets the user leave it blank, and the KB-taught template signs with `{{passphrase}}` — so the wizard reported CONNECTED and every request failed closed with zero fetches. P0 wrote the lint, P1 the executor, P4 the registry entry; **each is correct in isolation**, and no single-phase lens could see the two lints disagreeing about what "declared" means. The suite was green because the only optional-field test used a requirement with no header template and stopped one step short of executing a request. **Rule:** budget a final review whose unit of analysis is the whole data path, not the phase diff, and give it one instruction: at every handoff, ask what the receiver trusts that the sender never guaranteed. Per-phase reviews find defects *within* a boundary and are blind to defects *at* one, by construction.

## 2026-08-10 — A rebuild that deletes a surface silently deletes its test coverage; audit the migration behavior-by-behavior, not by counting
**Context:** same rewrite. P3 rebuilt the wizard from the v3 table onto v4 (120 deleted test cases against 74 new; playground 516 → 489), and P4 repeated the shape one phase later by deleting a test file whose module still shipped three exports. **What happened:** ~55 of the 120 were genuinely obsolete and the OAuth port was faithful — but **14 behaviors that still shipped lost their only guard**, four security-load-bearing. The worst: `isConnectionRepairableNetError`, live in two production paths with zero test references — the allowlist that stops an off-ceiling or SSRF failure from offering a "connect" CTA, i.e. from coaching a user into widening a host ceiling *under attack*. The code was correct; only the guard was gone. Emptying the allowlist left the entire suite green. **Rule:** when a rebuild deletes a surface, classify EVERY deleted test case as MIGRATED (cite the new assertion), OBSOLETE (prove the code is gone), or LOST — and restore the LOST ones with mutation proof. A net test-count drop is a prompt to audit, never an explanation; and "correct today, unguarded tomorrow" is the most dangerous state a security control can be in, because nothing fails until someone edits it.

## 2026-08-10 — `pnpm test` green can be a lie: the turbo cache replays stale results, and packages resolve to `dist/` not `src/`
**Context:** same rewrite, two independent incidents. **What happened:** (1) a mutation-testing pass left a mutant live in a package's build output and the turbo cache replayed a pre-mutation green, so a task file recorded "workspace green" over a genuinely red tree — caught only by a reviewer re-running with `--force`. (2) A reviewer mutating `packages/protocol/src/constants.ts` saw **no test failure at all**: the playground depends on the workspace package by its `"main": "dist/index.js"`, so dependent tests execute the BUILT artifact. The mutation only bit when applied to `dist/`. `turbo.json` does declare `test.dependsOn: ["build"]`, so a suite run *through turbo* rebuilds — the trap is a bare `npx vitest run` or a filtered invocation that bypasses the graph. **Rule:** any green claim made during or after mutation testing must be re-run with `pnpm test -- --force` and show `Cached: 0 cached`. When mutation-testing across a package boundary, mutate `src/` **and rebuild**, or mutate `dist/` deliberately and restore it — otherwise you are proving nothing and will report it as proof.

## 2026-08-10 — A literal NUL byte in a source file makes `grep` silently return nothing; an empty grep result is a claim that needs a second tool
**Context:** verifying that P3 had really deleted the v3 accessors from `packages/db/src/userdb/userdb.ts` (110KB). **What happened:** `grep -c putDeclaredConnection` returned EMPTY while Python found 6 occurrences. Root cause: the file contained one literal NUL byte — a *deliberate and correct* composite-key separator (`` `${appId}\x00${slot}` ``, so `(appId, slot)` cannot collide through ambiguous concatenation) — which makes `file(1)` classify the source as `data`, so grep treats it as binary and prints nothing rather than erroring. The orchestrator's own earlier "the accessors are gone" check had used grep on this exact file and read the empty result as confirmation; the conclusion happened to be right, but **the evidence was worthless**. Fixed by writing the separator as the ` ` escape — byte-identical at runtime, file is text again. **Rule:** an empty grep result on a file you expect hits in is suspect until a second tool agrees (`grep -a`, ripgrep, or Python).
