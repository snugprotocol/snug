- **2026-08-21 — From TASK-20260821-launch-security-review (threat model v3). Findings triaged as NOT launch-blocking, each with evidence.** Four blocking items were fixed in that branch (the OAuth encoded-spelling credential leak, the confirm dialog's missing URL, R-12's per-command IPC row, and a plaintext-codename leak in a knowledge guard test). These remain open, in rough value order:
  1. **`apps/server` has no authorization on `/invoke` and `/artifacts`, even with `SNUG_AUTH=google` on.** Enabling login authenticates `/auth/*` and `/userdb` only; artifacts and threads are one global namespace, so an anonymous caller can list and read every artifact, read another user's thread history into their own turn, and spend the operator's API key. Probed and confirmed. **Bounded by ADR-0013 — the shipped hub is static with zero backend, so nothing we deploy is exposed** — which is why this is not a launch blocker. But `docs/runbooks/enable-google-sso.md` carries no caveat, and a self-hoster following it would reasonably conclude login gates the server. Cheapest correct fix is the runbook caveat; the real fix is a session gate on `/invoke` plus per-user scoping of artifacts and threads.
  2. **An untrusted `.snug` import replaces the whole database; only connections and runtime contracts are reconciled.** `snug_secrets`, `snug_apps`, `snug_app_versions.html` and `snug_sync` are adopted verbatim, with no confirmation gate at `importUserFile`. Worst case: the victim's credentials are destroyed, attacker HTML is installed as apps, and the sync origin is repointed. Requires the user to open a hostile file, and connection-grant demotion does hold. Related to the already-queued R-20.
  3. **Three IPv6-embedding forms bypass the SSRF literal guard** — IPv4-compatible (`::7f00:1`), NAT64 (`64:ff9b::/96`) and 6to4 (`2002::/16`) are not in `net-guards.ts`'s range list. Measured. **Not reachable by an app alone**: gate 5 sits below the approval gates, so the literal must already be in a user-approved frozen ceiling, and only a *bracketed* exotic literal matches. Either add the three ranges or narrow the threat-model row, which currently says "IPv6 forms" unqualified.
  4. **The LAN transport's timeout is 15 s while the executor's is 60 s**, under a Rust comment claiming the two are kept in step, and a test named `the_timeout_matches_the_executors_own_budget` pins the stale value. Fails safe, but the Rust-side abort fires first so the executor's self-naming timeout message never runs — the user gets the raw transport spelling instead. Same "a bound must name itself when it fires" lesson, on the leg that did not inherit it.
  5. **`healMissingTables` false-misses on every healthy file.** `USERDB_TABLES` still lists `snug_auth_specs`, which v5 dropped and `USERDB_DDL` does not create, so `missing` is never empty and `healed` is always true — `markDirty()` fires on every open, which for a protected file means a full container re-seal (up to 64 MiB) per open. The guard can no longer distinguish a damaged file from a healthy one. Not data loss.
  6. **The `SNUGENC1` container layout in the spec is not the layout the code writes.** Spec §11.1 documents 13 bytes per slot; `container.ts` uses `SLOT_LEN = 61` with the wrapped keys stored separately. Since the whole header is the GCM AAD, an independent implementation written from the spec computes a different AAD span and **cannot open reference files** — which undercuts the portability rule the section is normative for. Internally self-consistent, so round-trips work today. Fix the spec draft (preferred) or the code.
  7. **Smaller, each measured:** the pseudonymisation digit floor is documented as 7 but is structurally 8 (`PHONE_PATTERN` needs 8 chars), so a bare 7-digit local number passes; NBSP/zero-width whitespace inside a contact name defeats the identity matcher (an *accidental* occurrence class, so it dents the anti-naive claim rather than only the anti-adversarial one); identity harvest is coupled to HTTP 200 and to the `/chats` route shape, neither documented as a dependency; `RUNTIME_CONTRACT_MAX_BYTES` counts UTF-16 code units, not bytes, so a CJK contract can exceed the stated 2560; and two presentational MUST NOTs in the spec (§12.6, §14.1) bind UI copy and are unenforceable by any test, though Part VI implies every conformance item is test-backed.
