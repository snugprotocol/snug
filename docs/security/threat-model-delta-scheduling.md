# Threat-model delta — scheduled tasks, PR-A (the record, the engine, *Remind me* and *Ask the AI*)

**Task:** TASK-20261009-scheduling-framework · **ADR:** [0074](../decisions/0074-scheduling-framework.md) · **Date:** 2026-10-09

Scheduling puts one engine in every runner — the web playground, Snug for Mac and the host
kit inherit `apps/playground/src/schedule/` by the existing source alias — and keeps its
whole record in the user's `.snug` file as namespaced `snug_settings` rows. A task is
executable intent that runs while nobody is in front of the confirm gate, and it reaches a
hub from an imported file, a sync pull or a hand-edited row as readily as from the editor.
C1 and C2 are unchanged **in policy**: no credential enters an app frame, a task, a run row
or a prompt, and nothing here widens the sandbox or the network ceiling — a scheduled run
has no powers its author did not already hold. What follows are the new *channels* those
policies must survive. This delta covers PR-A only: the storage, the import posture, the
engine, the *Remind me* step and the *Ask [app]'s AI* step. The hidden-frame *Run [app]*
step, the proposal channels (builder tool, chat lane, app suggestion strip) and desktop
notifications are PR-B's delta.

## Accepted residuals

- **R-a. No Snug host is always-on.** Snug for Mac quits when its window closes, the local
  host process exits a few seconds after its last agent session, a tab runs only while open.
  A task runs when due only if some Snug holding the file is open; everything else is found on
  the next open — collapsed per task, handled by the schedule's policy, auto-skipped past its
  freshness window. The honesty line says so where the user decides. Desktop background mode
  is the named follow-up (ADR-0074 §8).
- **R-b. Two file copies may each run one occurrence.** Two hosts on diverged copies of one
  file (two devices before a sync; two tabs at an origin where `navigator.locks` is absent or
  refuses — an opaque origin, `file://`) can both claim the same `(taskId, dueAt)` before
  either sees the other's row. Bounded to ONE extra call per occurrence: a *Remind me* costs
  nothing, an *Ask the AI* step's writes are proposals, and once the copies meet the row and
  `ranThrough` dedupe every later reconcile.
- **R-c. Hub sync is whole-file CAS.** A run row written on one device while another device
  wrote its own makes the next pull a divergence the user resolves (ADR-0009), not a merge; a
  result can be lost that way, never duplicated.
- **R-d. A think step's summary is model-written text.** It is shown to the user as the
  result. A stored row shaped like an instruction is delimited as data, but it can still shape
  the words of the summary and the data changes the reply OFFERS; it can never execute them —
  a proposal is dry-run and pending, applied only by a user act outside the engine.
- **R-e. The VALUE scrub against the stored connected-host secrets lands with PR-B.** Today's
  reply-side wall is the credential SHAPES plus the parse refusal (`finalizeOutcome`, row 2).
  The request itself carries no credential by construction — DDL, rows from the app's own
  tables and the prompt; `snug_secrets` is never read by the engine — and the app's rows go to
  the app's own provider exactly as any think of that app does. `scrubAuthValues` against the
  values a net handler holds is the one seam PR-B's handler introduces.
- **R-f. The kill switch can lag a sync pull.** Disable, pause and delete are rows in the
  file; another device keeps the task as it last pulled it until the next pull lands. Bounded
  by R-b's shape: one run per occurrence, collapsed.
- **R-g. Summaries derived from user data persist in the file and roam with it.** A result
  row's summary is text about the app's rows; it rides every export and every trusted pull.
  `clearScheduleHistory` (the *Clear history* act) drops every result and keeps only what is
  not yet dealt with (`pending`, `needs-you`, `running`); proposals never roam (row 3).
- **R-h. The watermark and the first claim share a persist window.** A `run` action's claim is
  the queue's first write, a microtask after the watermark; a tab that dies between the two
  loses that occurrence — never runs it twice; a claim REFUSED after the watermark advanced is
  surfaced (`lastError`), never silent. Availability only.
- **R-i. Notifications have no limiter of their own.** At most one per run, bounded by the
  frequency floor (5 or 15 minutes) and by catch-up collapse; the body is the user's own
  reminder text. The desktop and kit seats carry no `notify`, and the web seat is inert until
  the Settings opt-in and an already-granted permission both hold at the call (composed into
  `WEB_DEFAULT`, inert until then), so this bounds a channel that is barely open; PR-B's desktop
  plugin inherits the bound.
- **R-j. *Run [app]* and every proposal channel are PR-B's delta.** An `app-run` step is
  refused by name today ("running an app on a schedule arrives in a later release"); the
  hidden frame, the kv handshake, the refusing confirm gate, the builder tool, the chat lane
  and the app suggestion strip each get their rows there. The consent surface, the editor and
  the missed card (R2) are user-facing surfaces over the rows this delta covers and add no
  authority of their own.
- **R-k. A promoted tab runs nothing until it reloads.** The in-memory copy a follower opened
  at boot is stale after the leader's writes, and whole-file persistence would let its first
  save overwrite them; so promotion marks `needsReload` and the engine idles with a visible
  strip. The proper hand-over — a writer lock plus a re-open seam so a follower takes over a
  FRESH copy — is queued (`docs/next-steps.md`). Availability only: no run is doubled, no
  result lost, the user is told.

## What this delta does NOT claim

- It does not claim unattended writes are possible. They are not: an *Ask the AI* step has no
  tools and no connected call, and its data changes wait as proposals. The standing-approval
  gate (ADR-0033, SPEC §17) stays unarmed.
- It does not claim a run fires while every Snug is closed, on any host (R-a).
- It does not claim the macOS desktop shell can raise a notification: its seat names the
  host and promises the page, and `notify` arrives with PR-B's `tauri-plugin-notification`.
  It does not claim the web asks for notification permission on any path but the Settings
  card's click; the web seat IS composed into `WEB_DEFAULT` and inert until both hold.
- It does not claim anything about Windows: the desktop shell ships macOS-only (ADR-0021 D8,
  R-5), and nothing here changes that.
