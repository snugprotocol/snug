# Threat-model delta — writes with an undo, refresh on demand and the doorbells: the one sanctioned crossing widens from read to a bounded, journaled, reversible write

**Task:** TASK-20261010-host-broker (PR-3) · **ADR:** [0076 §4–§8, §10](../decisions/0076-host-as-broker-access-everywhere.md) · **Spec:** 1.2 (§22.4, §24.5–§24.7) · **Date:** 2026-10-11

Until this change the one sanctioned crossing between apps (ADR-0075) was a READ: a reader's
frame, the chat beside it or a scheduled question (the doors, PR-2) ran one SELECT on a scoped
copy of the source that a bounded Worker made and discarded. ADR-0076 §4–§8 and §10 let the
user tick, per table, *can also change rows*: the reader then posts `write` with ONE plain
`INSERT`, `UPDATE` or `DELETE` whose values are literals or bound parameters, and the host —
never the reader's frame — dry-runs it on a scoped copy in the Worker, applies it atomically
on the source's live database through one synchronous driver seat with the rows it changes
captured first into a structured undo journal, writes the `wrote` line, and rings the
doorbells. The user undoes any such change from the source's history for seven days. A grant
may also carry `kv` (the source's key-value store crosses, filtered) and `refresh` (the reader
may have the host run the source for new data, where it lives, under the unattended posture);
`discover` answers a class; the driver's write signal tells every live reader, ids only, that a
source changed. C1 and C2 are unchanged in policy: nothing credential-shaped crosses in either
direction (the column rule is decided from the schema and the scope, every literal and every
captured cell is walked, the key-value store crosses through the ONE credential walk over the
parsed value), and no frame, sandbox or CSP byte changes (the broker is host-side; the frame
only posts a statement and learns a count). What follows are the new channels those policies
must survive.

## What is new

| Surface | The threat | What holds |
|---|---|---|
| **The write op, end to end** (`access/policy.ts` `{ kind: 'write' }`; `access/service.ts` `write`; `access/writeBroker.ts` `brokeredWrite`) | A standing permission is exercised by app code while the user looks elsewhere: a reader changes rows it was never allowed to, more rows than the user imagined, on a table the user never ticked, or after the user stopped it. | The policy's rules 1–3 and 5 are the read's, then: attendance is REQUIRED for every caller in PR-3 (a frame must be present — the visible frame of its generation; a scheduled step is `ACCESS_UNATTENDED`), the named table must carry `write` (else `ACCESS_NOT_GRANTED`, "this access is read-only for that table"), and the write counts in the reader's per-minute window FIRST. `stillWritable` is re-checked at the dequeue of the plan job and again, synchronously, after the plan answers and before the seat — a grant stopped meanwhile answers `ACCESS_REVOKED`/`ACCESS_EXPIRED` and nothing is applied. | **The plan in the Worker** (`packages/db/src/brokered-write.ts` `parseBrokeredStatement` + `planBrokeredWrite`; `access/scopedRead.ts` `scopedPlanWrite`, the `plan-write` job) | A statement reaches the live handle unparsed; a planner on the main thread hangs every shell; a plan over stale bytes previews a different database than the one it will change; the plan's rows leak out of the Worker. | A small tokenizer admits exactly: `INSERT INTO t (cols) VALUES …` (the column list required; no `OR …`, `DEFAULT VALUES`, `ON CONFLICT`), `UPDATE t SET c = <value>, … WHERE <terms>` (no `OR …`, no `FROM`), `DELETE FROM t WHERE <terms>`; a value is a literal or a placeholder; a WHERE is simple comparisons (`=` `<>` `!=` `<` `<=` `>` `>=` `LIKE` · `IN (…)` · `IS [NOT] NULL`) joined by `AND`/`OR`/`NOT` with parentheses; **any other token — a function, `CASE`, arithmetic, a subquery, a CTE, `RETURNING`, a qualifier, a second statement — is refused BY NAME before any dry run**. | **The column rule — three oracles and the masked set** (`planBrokeredWrite`; `packages/db/src/scoped-read.ts` `scopeCopy` reporting `masked`) | A write names a column the reader cannot read and uses the row count as an oracle: `WHERE api_key LIKE 'sk-a%'` with `changes` as the answer; a generated column computed over NULLed inputs; a masked cell compared against a literal. | Every column the statement NAMES (the SET list, the INSERT list, every WHERE term) must be in the table's granted `columns`, minus every GENERATED column (`table_xinfo` hidden 2/3), minus every column `scopeCopy` reports it MASKED a cell in; a withheld, credential-named, generated or masked column anywhere is refused by name BEFORE any dry run — the three oracles are closed at the plan, from the schema and the scope, never from a row's value. The refusal words reveal no source fact ("a column it names isn't shared" · "a computed column can't be used in a change" · "a value in it can't be matched"). |
| **The table facts, at both seats** (`tableFacts` on the RAW copy at the plan, on the LIVE handle at the apply) | A source's own schema turns a bounded write into an unbounded one: a trigger (the app's, or a TEMP one) fans the write out to tables the reader cannot see; a foreign-key action cascades a DELETE; `ON CONFLICT REPLACE` deletes rows the reader never named; a CHECK over an unshared column refuses or admits by that column's value (an oracle); a WITHOUT ROWID or virtual table has no rowid to journal. | The table must exist and be `type = 'table'` (not virtual, not shadow), not WITHOUT ROWID (`pragma_table_list.wr`), with no TEMP object shadowing its name and no column named `rowid`, `oid` or `_rowid_` (such a column shadows the real rowid the capture and the undo key on), carry NO trigger in `sqlite_master` OR `sqlite_temp_master`, no `ON CONFLICT REPLACE` and — when any column lies outside the grant — no `CHECK`; with `PRAGMA foreign_keys` on, no `pragma_foreign_key_list` of any table may name it with an `on_delete`/`on_update` action other than NO ACTION; a DELETE is admitted only on a FULLY shared table (every live column granted — no withheld, credential-named or generated column). The facts are read at the plan (the raw copy — a scoped copy has no triggers) and READ AGAIN on the live handle at the apply; the apply's check is the rule, the Worker's the early answer. The refusal is worded for the reader without the why: "that table can't be changed from another app". |
| **The synchronous driver seat and the transaction record** (`packages/db/src/driver.ts` `brokeredWrite`, the per-namespace transaction record; `applyBrokeredBatch` `BEGIN IMMEDIATE … COMMIT`; `userdb.ts`'s facade; `schedule/scheduledDbDriver.ts`) | The source's open frame and the broker interleave statements on ONE sql.js connection: a frame's `BEGIN` swallows the broker's write, or the broker's `COMMIT` commits the frame's half-done transaction; a hidden frame's binding forwards a brokered write. | The driver is the ONLY way onto the handle and the apply is ONE synchronous span: `tableFacts` → `BEGIN IMMEDIATE` → the capture objects → the statement → the captured rows read and walked → the drop → `COMMIT` — no `await` inside, so no frame statement can interleave. `createDbDriver` keeps a per-namespace TRANSACTION RECORD — the frames an app's own verbs opened, kept from the verbs `runExec` ran successfully (`BEGIN`/`SAVEPOINT` open a frame; `COMMIT`/`END`/`ROLLBACK` close every frame; `RELEASE` closes down to its savepoint, `ROLLBACK TO` keeps it), cleared whenever the connection is reopened (`persist`, the `export` frame, `runImport`) and on a `COMMIT`/`END`/`ROLLBACK` SQLite answers "no transaction is active", so a stale frame can never strand a namespace as busy — and `brokeredWrite` answers `busy` (retryable, `ACCESS_BUSY` — "the other app is in the middle of a change — try again") from the record BEFORE touching the handle; a nested `BEGIN` failing "within a transaction" is the belt. A `committed` flag with `ROLLBACK` in `finally` (errors swallowed), THEN the capture objects dropped, so an injected throw mid-apply leaves no open transaction and no temp object; a throw is answered `failed`. The hidden frame's `scheduledDbDriver` answers `brokeredWrite` `{ ok: false, code: FORBIDDEN_STATEMENT }` as data and never forwards. `executeApprovedWrite`'s own awaited `BEGIN`/exec/`COMMIT` through `handle` goes away with the `instanceId` mechanism (its interleaving hazard with it). |
| **The capture by TEMP trigger** (`applyBrokeredBatch`; `CREATE TEMP TABLE snug_undo_rows_<hex8>` + `CREATE TEMP TRIGGER snug_undo_trigger_<hex8>`) | The host's capture objects collide with an app's own object of the same name (the drop then removes the app's), a target column named `rowid` or `r` shadows the capture's, a crashed apply strands a trigger that later captures every write, the capture misses an explicit-PK insert or a REPLACE-resolved delete. | Per-apply names (eight hex of randomness), created WITHOUT `IF NOT EXISTS` (a creation failure is `failed`; the drop can never remove an object the app made); positional capture columns (`snug_rowid, c0, c1, …`) mapped back by index, so a target column named `r` or `rowid` never collides; TEMP objects live only in this connection and never travel in `export()`; created and dropped inside the one span (the `finally` drops them on every path); measured on sql.js 1.14.1 / SQLite 3.49.1 — a `BEFORE DELETE` trigger with unqualified names captures `old.*` exactly, a `BEFORE UPDATE` captures `old.*` AND `new.*` of the SET columns under `new.rowid` (the rowid the write LEFT — the undo's guard needs it even when the statement moved an INTEGER PRIMARY KEY), and an `AFTER INSERT` the new rowids, explicit `INTEGER PRIMARY KEY` values included; `INSERT OR REPLACE` is refused at the parse so its conflict-delete (which fires no `BEFORE DELETE`) never happens; the affected set is the statement's OWN (`sqlite3_changes()` excludes trigger and foreign-key-action changes — and both are refused at the facts). |
| **The structured undo journal and its per-reader cap** (`accessUndo:<targetAppId>`; `packages/protocol/src/access.ts` `accessUndoEntrySchema`; `packages/db/src/userdb/access.ts` `putAccessUndo`, `listAccessUndo`, `markAccessUndone`) | A journal that holds statement text is a stored program: a planted or hand-edited row from a trusted pull runs SQL at undo time; a reader evicts the undo of its one harmful write with twenty trivial ones; an entry grows past the file's caps; a captured cell carries a credential at rest. | The journal holds ROWS, never SQL — `steps[].{ table, op, columns, rows[].{ rowid, before?, after? } }` (INSERT: `after`; UPDATE: `before` and `after` over the SET columns; DELETE: `before` over every non-generated column) — and the inverse is BUILT at undo time from the structure with every identifier quoted and validated against the live `table_xinfo` and every value a bound parameter (`forbiddenStatementReason` is the belt on every built statement). ≤ `ACCESS_UNDO_MAX_ENTRIES` (20) LIVE entries per (target, reader) — **a strict-mode write whose reader already holds twenty is REFUSED** (`ACCESS_WRITE_REFUSED`, "too many changes are waiting to be undone — undo them or wait") rather than evicting; ≤ `ACCESS_UNDO_MAX_BYTES` (64 KiB) per entry and ≤ `ACCESS_UNDO_MAX_ROW_BYTES` (256 KiB) per row, else the write is refused "too large to undo"; kept `ACCESS_UNDO_TTL_MS` (7 d), expired and undone entries pruned first; swept by `deleteApp`; DROPPED on an untrusted import, kept on a trusted pull (the user's own device). Strict schema (`steps` 1..64, the per-op arity of `before`/`after`), re-validated on every read. |
| **The credential walk per captured cell** (`applyBrokeredBatch` → `findRecordCredential({ [column]: value })` under the cell's own column name; `planBrokeredWrite` over every literal and bound parameter) | A credential-shaped value in a GRANTED column (one the read path masks on the copy) is captured into the journal at rest, or a reader writes a credential into the source under a neutral column name. | Every literal and every bound parameter goes through the ONE record walk at the plan (a hit refuses the write); every captured cell is walked UNDER ITS COLUMN after the statement ran and before the entry is written — a hit rolls the apply back `unsafe` and the reader hears the generic sentence and no count (reachable only by a value in a granted column that the read path already masks, so the answer tells the reader nothing a read would not). The journal therefore never holds a credential: it holds the source's granted-column values (UPDATE/INSERT) and, for a DELETE, a whole row of a table every column of which is shared. |
| **The `wrote` line** (`access/writeBroker.ts` after the seat answers ok; `packages/db/src/userdb/access.ts` `appendAccessLog`, `PROTECTED_KINDS` + `wrote`, `clearAccessLog`) | A change lands with no record, or the record is flooded off the history by reads, or *clear history* erases it; the statement text in the line carries a credential past the cut; a reader's summary enters the person's history. | The line is written AT ONCE after the commit, with the journal entry, before the answer leaves: `via` · `authority: 'permission'` · `changes` · `undoId` · `tables: [<the one table>]` · `sql` as the history keeps it (walked whole, cut at 200, omitted on a hit; shown behind *what it changed*). Pruning never takes the latest `wrote` of a grant the file holds; `clearAccessLog` keeps every non-`read` kind; the line is host-authored but for the walked `sql` seat; `coalesced()` stays reads-only. A storage throw AFTER the commit is the one residual (named below). |
| **The undo** (`access/writeBroker.ts` `undoBrokeredWrite` with `via: 'user'`; `buildUndoStatement`; the `undone` line) | An undo hits a row that has changed since — or, after a rowid renumber (VACUUM on a table without an INTEGER PRIMARY KEY), another row entirely; an undo of an undo; an undo built against a schema the source has since changed; an undo that captures. | Every step's table and columns are re-validated against the live `table_xinfo` (the table exists, every named column exists, none generated) and the table's shape rules on the live handle — minus the two READER-oracle rules (the CHECK over an unshared column and the DELETE's full coverage), since an undo is the user's act, not a reader's probe — the values bound; the built statements — INSERT-undo `DELETE FROM t WHERE rowid = ? AND c1 IS ? AND …` over `after`, UPDATE-undo `UPDATE t SET … WHERE rowid = ? AND c1 IS ? AND …` (SET = `before`, guard = `after`), DELETE-undo `INSERT INTO t (rowid, c1, …) VALUES (?, …)` over `before` — run in REVERSE step order inside one span with `requireUndo: false, capture: false`; **any statement that changed ≠ 1 row rolls the WHOLE undo back** `drifted` ("couldn't undo — <Source> changed these rows since"; nothing changed); a schema mismatch answers "this change can no longer be undone" and the entry is marked undone-failed; `markAccessUndone` makes an undone entry un-offerable (never an undo of an undo); the `undone` line carries `changes`, `via: 'user'`, `tables`. The after-guard is what makes a trusted pull's planted journal row able only to MOVE VALUES into bound parameters of a statement whose shape the host builds — and only where every row still holds what the entry says the write left. |
| **The refresh engine** (`access/refresh.ts` `refreshSource` over the EXPORTED `dispatchLive`/`dispatchHidden` of `schedule/appRun.ts`; `schedule/runPlacement.ts` `posture: 'refresh'`; `schedule/runScopedGate.ts`; `schedule/protection.ts` `countersSoFar` + `foldDailyCalls`) | A reader makes a source RUN: spend the source's connections and the user's brain on a reader's behalf, repeatedly; run it where schedules are off; run it beside an open copy; let the source's handler POST into a remembered grant during the window or after it; let the reader's name enter the source's frame as text; let the handler's summary reach the reader; count it nowhere. | **Three gates before anything:** `allows('schedule')`, an existing `schedulerState` row, `globalPause === false` — else `ACCESS_REFRESH_FAILED` ("schedules are off for this file"); the cooldown stamped AT DISPATCH per source (`ACCESS_REFRESH_COOLDOWN_MS`, 5 min; within it `fresh: false, reason: 'recent'`, nothing run, no line); the pre-dispatch ceiling check over the FILE's day (`wouldExceedCeiling(countersSoFar, { ai: 1, net: 1 })`; capped → `ACCESS_REFRESH_FAILED` reason `capped`, the `refreshed` line written); then ADR-0077's placement — the live frame under `beginDelegatedRun({ posture: 'refresh' })` or the hidden path — with the PR-1 handover loop. | **Withheld columns and the drift rule** (`scope.tables[].withheld`; `scopeCopy` `withholdCredentialColumns` over `withheld` too; `driftOf` over `columns ∪ withheld`) | A column the user left unticked crosses anyway through an alias or `SELECT *`; a withheld column that vanished or a new column the user never saw escapes the drift check. | `withheld` columns are overwritten on the copy with the same fallbacks as credential-named ones (`'***'`, else NULL, else a random value — fail closed), so `SELECT *` shows `***`; `driftOf` compares the live non-credential set against `columns ∪ withheld` — a withheld column that vanished or a new column still suspends `source-changed`; the record refuses a `withheld` entry that duplicates, overlaps `columns` or is credential-named; `withheld` is never on the VIEW; the `sqlite_sequence` belt (`DELETE FROM sqlite_sequence WHERE lower(name) NOT IN (<granted>)`) closes R-76. |

One gather per reader per minute, below `request`'s own gap. |

## What is NOT changed

- C1: no credential crosses in either direction. The read path is byte-identical but for two
  copy rules — a `withheld` column is withheld exactly like a credential-named one, and
  `snug_kv` is kept (filtered through the one walk) only under `kv`; every value a write
  carries or captures is walked; the column rule is decided from the schema and the scope,
  never from a row's value.
- C2: no frame, sandbox or CSP byte changes. The frame posts a statement and learns a count;
  the broker, the planner, the journal, the refresh engine and the doorbells are host-side.
  The hidden path (the refusing gate, the counting transport, `scheduledDbDriver`) is
  unchanged but for `brokeredWrite` answered `FORBIDDEN_STATEMENT` as data.
- The chat door stays READ-ONLY: `data_propose_write` keeps PR-2's refusal of any alias table;
  the chat's cross-app write through its card and the three *fetch* affordances are PR-4's.
- An app's OWN approved write (`executeApprovedWrite`'s two callers) goes through the same
  synchronous seat with `requireUndo: false, capture: false` — atomic, counted, the
  previewed-count drift halt, `data-changed` to its own frame — and keeps NO journal, NO
  history line and NO `undoId` in PR-3 (its undo surface is PR-4's result page); its
  characterisation suite is unchanged.
- No persisted shape changes beyond the three the wire names (the grant record, the log
  entry, the undo entry) plus the defined-not-yet-written `accessWants` row; the scheduled
  task, the run row, `schedulerState`, the chat row's `meta.*` keys and `PendingWriteProposal`
  keep their schemas.
- The frame door's rate limiter, ladder, gather, frame-ends re-check and park are unchanged;
  a write counts in the SAME per-minute window as a read.
- `PROTOCOL_VERSION` stays 1; the frame inventory stays fifteen; no host-ready key is added.

## Residual risks (recorded, not fixed)

- **R-89 — A standing write permission is a power exercised while the user looks elsewhere.**
  Once ticked per table, a reader's frame changes rows without a dialog — never while nobody
  is present in PR-3 (a scheduled step is `ACCESS_UNATTENDED`), but while the user's eyes are
  on the reader, not the source. *Bounded by:* one statement, one table, literal values, 200
  rows, the column rule, the journal, the `wrote` line, the doorbell to the source's open
  frame, instant revocation (re-checked at the dequeue and before the apply), the sheet's
  one breath ("can change up to 200 rows at a time … every change is listed … and can be
  undone for seven days").
- **R-90 — The undo journal holds the source's granted-column values at rest.** For seven
  days the user's own file carries, beside the table, the before/after values of every
  brokered change and, for a DELETE, whole rows of a fully shared table — never a credential
  (every cell walked under its column), never statement text, never shown to the reader.
  *Bounded by:* the journal lives where the table already lives; the caps (20 entries per
  (target, reader), 64 KiB per entry, 256 KiB per row); dropped on an untrusted import; an
  undo changes nothing unless every row still holds the values the write left — and a rowid
  renumber (VACUUM on a table without an INTEGER PRIMARY KEY) makes an undo fail whole rather
  than hit another row.
- **R-91 — A reader can make a source RUN.** Under `refresh` a reader has the host execute
  the source's own app code once per five minutes — GET-only during the window, counted on
  the file's day, logged `refreshed`, refused when schedules are off or paused — and the
  source's connections and the user's brain are spent on the reader's behalf. `requestedBy`
  is the reader's display name entering the source's frame as data, folded to one line; after
  a refresh the source's frame stays ask-only until reopened (D-PR1-3's cost, now reachable
  by another app's act); a kv key stranded by a crash is ≤ 1 KiB of inert kv the SDK never
  reads without its hint. *Bounded by:* the opt-in tick names the mechanism and the limit
  ("through Ledger's own connections, at most once every five minutes, counted on your daily
  schedule limits"); the refusing posture; the cooldown stamped at dispatch; the three gates.
- **R-92 — The write signal is a timing side-channel.** The driver's signal tells every live
  reader WHEN a source changed — ids only, but a reader holding a grant learns the rhythm of
  the user's work in the source. *Bounded by:* the 2 s coalescing blurs it; a hidden frame is
  never rung; DDL rings nothing; the host's own handshake writes ring nothing; the reader
  already holds a grant the user gave with the sheet in front of them.
- **R-93 — A 1.1 hub and a 1.2 grant.** A 1.1 hub cannot read a v2 grant row and holds it
  inert (no access under it), and a 1.1 host answers the three ops and an ask carrying
  `access` `MALFORMED` — so a file carried to an older Snug loses the widened access until the
  hub is updated, and an app written for 1.2 shows its fallback there. *Bounded by:* fail
  closed is the chosen failure; a defaults-off v2 record is byte-identical to a 1.1 record; the
  KB names the fallback sentence.
- **R-94 — Doorbells reach only LIVE frames.** `access-source-changed` and `access-read` ring
  a frame that is registered and announced in this tab; a hidden frame is never registered and
  never rung; a 1.1 source app (no listener) repaints on its next open. *Bounded by:* a hint is
  a hint — the next read sees the truth regardless; the hidden path never needed one.
- **R-95 — A CHECK, UNIQUE or partial index the source wrote over an UNSHARED column.** A
  constraint can admit or refuse a write by a value the reader cannot see. *Bounded by:*
  writes on a table with a CHECK over an unshared column are REFUSED at the facts; a UNIQUE
  over an unshared column cannot collide with a value the reader cannot supply (an INSERT
  leaves it at its default); a partial index changes no row's admission.
- **R-96 — A discover answers a class from the whole library once a minute per reader.** The
  class is computed from an export of every app (`describeAppData` per app) and cached 60 s;
  a reader can keep the host exporting its library once a minute for as long as it is open.
  *Bounded by:* one gather per reader per minute, below `request`'s own gap; nothing recorded,
  nothing shown, never a name or a count.
- **R-97 — The `wrote` line after a commit.** The line is written at once after the commit,
  with the journal entry, before the answer — but a storage throw between the commit and the
  line leaves a change in the table with no line and no undo entry. *Bounded by:* the window
  is the one synchronous span's tail; `data-changed` and `access-source-changed` still ring;
  the next read of the source shows the rows.
- **Pre-existing, named now (not new residuals):** sql.js 1.14.1 `Database.export()` frees
  every statement, closes the connection and reopens it — so a SOURCE frame's open transaction
  is discarded by the next persist (≤ 250 ms after any write), read, dump, plan or
  `describeAppData` (measured: after `BEGIN; INSERT; export()` the row is gone and `COMMIT`
  errors "no transaction is active"); PR-3 does not change the read path and names the
  driver's persistence-without-reopening as its own task. The read path's cell mask
  (`scanForCredentialValues`) is START-ANCHORED (`JWT_SHAPE`, `BEARER_PREFIX`,
  `KNOWN_KEY_PREFIX`) while the journal's and the kv filter's walk is token-split over the
  parsed value — the copy's withhold and mask remain the rule for a read, and the start
  anchor is next-steps' rider.
