# Threat-model delta — the access doors: the chat beside an app and the scheduler's *Ask the AI* read what the user allowed

**Task:** TASK-20261010-host-broker (PR-2) · **ADR:** [0076 §1–§3](../decisions/0076-host-as-broker-access-everywhere.md) · **Date:** 2026-10-11

Until this change only an app's OWN CODE could walk the one sanctioned crossing between apps (ADR-0075):
a reader's frame posts `snug:access-request`, the host exports the source, a dedicated Worker makes a
scoped copy and runs one SELECT. The chat beside an app (the data lane) and the scheduler's *Ask
[app]'s AI* step knew nothing of grants. ADR-0076 §1–§3 gives the same engine two more callers —
"doors" — behind ONE policy (`access/policy.ts`) and ONE service (`access/service.ts`): the frame
handler is now a thin mapper, the chat's brain sees the granted tables as `<alias>__<table>` tables
materialised THROUGH the Worker into its throwaway scratch copy, the scheduler's think step sees the
same tables under the away posture, and the chat's brain can ASK for access through an
`access_propose` tool rendered as a card whose *review* opens the ONE consent sheet. C1 and C2 are
unchanged in policy: nothing credential-shaped crosses — the Worker still withholds credential-named
columns and masks credential-shaped values on the copy BEFORE a row exists on the main thread, and the
dump selects only the scope's recorded columns; the sandbox and CSP are byte-identical (no frame is
touched — the doors are host-side). What follows are the new channels those policies must survive.

## What is new

## What is NOT changed

- C1: no credential crosses any door. The dump runs after the withhold and the mask on the copy and selects only the scope's recorded columns (a credential-named column is never in a scope); the read line's `sql` is walked whole before the cut as today; the card's purpose is credential-walked by the schema.
- C2: no frame, sandbox or CSP byte changes; the doors are host-side. The frame handler's answers are byte-identical (its test suite is untouched and green).
- The frame door's rate limiter, ladder, gather, frame-ends re-check and park are unchanged; the chat and scheduler doors never consult the per-minute limiter (bounded by the user's turns, the run ceilings, the Worker's serialisation, the caps and the 10 s cache).
- No persisted record changes shape: the grant, the log entry and `meta.dataWrite` keep their schemas; `meta.access` is a new key beside `meta.schedule`, re-validated on every read. A `via` or `provenance: 'chat'` key is a strict-parse refusal and is never written (D3 — PR-3 adds them).
- Sidecar-fact sources are excluded by construction at every door (`isLive`); the reader's OWN sidecar data reaching its chat unscrubbed is pre-existing and out of scope (next-steps).
- The data lane's own bound is inherited: host and subscription brains never reach it (`classifierApplies`), so the chat door does not exist there.

## Residual risks (recorded, not fixed)

- **R-71 (extended) — The reader's model sees what it reads, at three doors now.** The chat beside the reader and a scheduled question to its AI see the granted rows exactly as the reader's own code would; the chat path has no R-9 egress scrub (pre-existing — the chat's brain is the user's own route, equal to the app transport's). *Bounded by:* the user chose the source and the tables with the sheet in front of them, which now names the chat and the scheduled question; every read is logged on the source; the mask and the withheld columns keep credentials out of the rows.
- **R-85 — The brain's SQL runs on the main thread over materialised rows.** The frame's read ran in a Worker under a 2 s clock; the chat's `data_query` runs on the reader's scratch copy on the main thread with no clock (ADR-0019's accepted shape), now with up to 8 MiB of another app's rows attached per call. *Bounded by:* what the Worker materialised (the dump under its own 5 s clock, the per-table, per-set caps); the attach happens only for a statement that names a shared table, at most once per `data_query` call (≤ 48 calls a turn); the dump's row count scans every row of a granted table even past the byte cap, under the clock.
- **R-86 — A brain-authored purpose on a user-provenance grant.** Until spec 1.2 the grant record cannot say the ask came from the chat; `askedIn` lives on the pending only, and the record carries the brain's purpose under `provenance: 'user'`. *Bounded by:* the purpose is display-ruled and quoted; the sheet said "asked in <Reader>'s chat:" when the user allowed it; the user's *review* was the act.
- **R-87 — A chat or scheduled read reads as the app's own read in the source's history.** The line carries the reader's name, the tables, the rows and the attendance, never the door (spec 1.2's `via`); the person sees "Budget read transactions" for a turn the user typed beside Budget. *Bounded by:* the line is true about the copy; the glossary, the KB and the skill say so; PR-3 adds `via`.
- **R-88 — The run result is silent about the shared tables.** A person reading Budget's *Ask the AI* result cannot tell the answer drew on Ledger; the outcome row is a persisted shape PR-2 does not widen. *Bounded by:* Ledger's history records the read *while you were away*; next-steps names the result line for PR-4.
- **R-78 (extended) — The scheduler door's away posture.** A scheduled question reads the away set for every trigger, *run now* included, so the user's own click sees no more than the schedule would. *Bounded by:* the opt-in checkbox names both the run and the question; the line is logged *while you were away* either way.
