# Threat-model delta — one instance per app: a scheduled run executes where the app lives

**Task:** TASK-20261010-host-broker (PR-1) · **ADR:** [0077](../decisions/0077-one-instance-per-app-run-placement.md) · **Date:** 2026-10-10

Until this change an unattended *Run [app]* (`due` · `late` · `catch-up`) ALWAYS mounted its own hidden
frame, open app or not — two instances of one app over one sql.js connection (R-70), the visible
copy's reconnect chip lit by the hidden run's 401 (open-app delta R-b), and the user watching a
second copy of their app appear beside the first. The principle the Gate-5 fold named survives
("presence is not consent", lesson 2026-10-09): a run the user did not start still never rides the
open app's REMEMBERED approvals. What changes is the mechanism: the run is delegated to the live
frame under a **run-scoped ask gate** that asks the present user and consults no remembered or
standing grant; the hidden frame is used only when the app is closed; a run follows the app once.
C1 and C2 are unchanged in policy — no credential crosses the handshake, the dialog or a result;
the sandbox and CSP are byte-identical (the hidden path's own frame is untouched, the live frame
is RunView's as before); the daily ceilings still bound what a run spends. What follows are the new
channels those policies must survive.

## What is new

| Surface | The threat | What holds |
|---|---|---|
| **A delegated run on the live frame** (`schedule/appRun.ts` `dispatchLive`; `schedule/runPlacement.ts`) | The run reaches the page's ordinary confirm chain — a remembered session grant or an armed standing grant answers an unattended POST (the hazard the Gate-5 fold named). | The frame path's default gate is the run-scoped gate (`schedule/runScopedGate.ts`, `state/net.ts` `createNetHandlerFor`): while a run is in flight for the app, a mutating call never reaches the session-remember or standing gates — it is parked on the one confirm queue, tagged, under a host-composed title, with no *remember* box; `rememberSession` is structurally unwritable there (the only writer is the session gate's own prompt path, which this gate bypasses). No answer within 60 s → `NET_CONFIRM_DENIED` → *needs you*. Pinned by `netState.test.ts` (a remembered grant AND an armed grant present → the confirm still parks) and `appRunHandshake.test.tsx`. |
| **The window the app controls** | A handler posts its `schedule-result` first (the run ends, the gate's window closes) and POSTs afterwards into the remembered grant; or retries after a refusal. | The ask-only posture sticks to the FRAME GENERATION that hosted a delegated run (`touchedGeneration`): until the frame retracts or remounts, every mutating call from that generation is asked once — the "after a schedule" dialog variant says why. The user's own *remember for this session* is unavailable on that frame until they reopen the app (residual R-79). |
| **The confirm queue** (`state/net.ts` `confirmQueue`) | A timed-out scheduled dialog stays at the queue head after its run is recorded, blocks every other app's confirm, and a late *allow once* sends a POST for a result that said nothing was sent; a handler parks N dialogs. | One outstanding ask per run: a second mutating call while one is parked, or any call after a refusal for that `runId`, is refused at once and recorded (`why: 'already-asked'`). A parked scheduled confirm listens to the run's `signal` and is WITHDRAWN (denied by reference, `denyParkedConfirmByRequest`) on timeout and whenever the run ends — result, bound, cancel, handover. |
| **The access door** (`access/accessHandler.ts`) | The attended access handler, composed once for the visible frame, lets a timer-fired run park a cross-app consent sheet (a stronger authority than a POST) or read a session grant with the source's history saying `attended: true`. | While a delegated run is in flight the handler reads `delegatedRunFor(appId)` per op: `request` → `ACCESS_UNATTENDED`; `query` only under a grant's *also while I'm away*; the history line carries `attended: false` — the hidden frame's posture for the window. After the run the app's genuine ask is the ordinary strip, which needs the user's act anyway. |
| **Handover** (`MAX_HANDOVERS = 1`) | An app opened or closed mid-run makes the host re-run a handler whose POST already went out (a second send, then a *needs you* inviting a third); two instances overlap during the switch; the first attempt's spend is dropped; a forged result from the wrong frame settles the run. | A delegated attempt in which the user ALLOWED a mutating call is never handed over — a retraction ends the step `failed` ("closed after a change was sent"). The hidden→live hint fires only after the hidden frame reports unmounted. Tallies are SUMMED across attempts. A `schedule-result` settles a delegated run only from the generation that was hinted. One handover per run; a second ends the step `failed`. One deadline per step, inside the queue's bound. |
| **Counting inside the window** | The live frame's transport and handler never refuse mid-run, so a run could spend past the day's ceilings. | The ceiling is asked BEFORE dispatch (either counter without headroom for one more call → `capped`, no dispatch); inside the window every AI and net call is counted on the run row; a tally that crosses a ceiling marks the run `capped` (app code is not stopped — residual R-80). The hidden path still refuses per call as before. |
| **Readiness** (`state/appHosts.ts`) | A hint before the app's listener exists (the *run now* race) is a 90 s `failed`; a remount read as a retraction fires the wrong handover and drops session access grants. | Registration stays keyed on the app and never retracts on a remount; a separate effect sets the frame generation and clears `announced`; every hint — manual too — waits for the announce (≤ 10 s, else `no-handler`). |
| **Attribution** (`AuthShapedFailure.via`) | A hidden run's 401 lights the open copy's reconnect chip unexplained (R-b); a user's own 401 during a delegated window is tagged as the schedule's. | The handler tags the failure `via: 'scheduled-run'` when `scheduledRun()` answers true (the hidden frame always; the live frame while a run is in flight); the chip says "a schedule ran into this". Over-attribution of the user's own click inside the window is accepted (R-81). |

## What is NOT changed

- C1: nothing credential-shaped crosses the handshake (the kv input is the step's own ids and input; results are scrubbed by `finalizeOutcome` before the row); the dialog shows host, method and the verbatim URL exactly as the ordinary one (R-8) and never a body or a credential.
- C2: the hidden frame is the same `SnugAppFrame` with the same sandbox and CSP; the live frame is RunView's, composed as before — the ONLY runtime difference for a delegated run is the per-request gate consult and the counting decorators, both host-side.
- The `manual` run (*run now and review*) rides the live frame under the page's ordinary gate, uncounted, exactly as R-62 records — it only gains the readiness wait.
- The hidden path keeps its refusing gate, its counting-and-capping transport, the deliver scrub and `scheduledDbDriver`; the generation-0 session-grant rule (D30, R-78) stands.
- Nothing on a persisted row changes shape; `handed-over` is a word in a summary, never a status.

## Residual risks (recorded, not fixed)

- **R-79 — A frame that hosted a scheduled run loses *remember for this session* until reopened.** The sticky ask-only posture is per frame generation, so the user's own later POSTs from that frame re-confirm once each. *Bounded by:* one extra click per call; the after-run dialog says why; reopening the app restores the ordinary chain.
- **R-80 — Inside a delegated window a run is counted, not stopped.** App code on the live frame cannot be interrupted by the host; a run that crosses a ceiling mid-window is marked `capped` after the fact. *Bounded by:* the pre-dispatch check (a run never starts without headroom); the 90 s bound; the live frame's own budget.
- **R-81 — Over-attribution.** A user's own AI or net call inside the ≤ 90 s window is counted on the run row, and their own 401 is tagged "a schedule ran into this". *Bounded by:* the window's length; the chip's hedged sentence; nothing is refused because of it.
- **R-82 — The open app's own powers are the delegated run's powers.** The live frame's db binding allows BEGIN/COMMIT and `import`, and its replies are not deliver-scrubbed (the step's summary and alert still are). *Bounded by:* these are exactly the powers the open app already exercises for the user's own clicks; the hidden path keeps its narrower bindings.
- **R-83 — One instance holds per TAB, and presence means "mounted", not "visible".** An app open in a follower tab is not live for the leader's scheduler (the hidden frame runs beside it — R-70's shape, in that one case); a RunView in a backgrounded tab receives a delegated run whose dialog nobody sees and times out to *needs you*. *Bounded by:* the follower tab is read-only (`userdb/locks.ts`); the timeout is the honest outcome.
- **R-84 — A frame remount mid-run is not a handover.** The in-flight attempt ends by the result bound (as a manual run does today) — one slow failure, never a double send. *Rider:* a remount handover (next-steps).
