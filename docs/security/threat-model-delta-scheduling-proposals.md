# Threat-model delta — scheduled tasks, PR-B (*Run [app]* in a hidden frame, the proposal channels, desktop notifications)

**Task:** TASK-20261009-scheduling-framework (PR-B) · **ADR:** [0074](../decisions/0074-scheduling-framework.md) · **Date:** 2026-10-09

PR-A's delta (`threat-model-delta-scheduling.md`) covered the record, the engine, *Remind me*
and *Ask [app]'s AI*. This delta covers what PR-B adds on top of that engine: the *Run [app]*
step — an app's OWN code run unattended in a hidden frame, fed over a kv handshake on the
frames that already exist, with a standalone confirm gate that always refuses a mutating call
and a transport that counts every think — and the three ways something other than the user can
PROPOSE a schedule (the builder's tool, the chat's `schedule` lane, a running app's suggestion),
plus the module-SDK hook an app answers with and the desktop's native notification seat.
C1 and C2 are unchanged **in policy**: the hidden frame is the same `SnugAppFrame` with the same
sandbox and CSP, no credential enters it, a task, a run row, a result or a notification, and
nothing here widens a grant or the network ceiling — a scheduled run holds no power its author
did not already hold. What follows are the new *channels* those policies must survive. Every
"what holds" cell names the file and the test that pins it, read from the tree at this write.

## What is new

| Surface | The threat | What holds |
|---|---|---|
| **The hidden frame** (`schedule/ScheduledRunHost.tsx`, driven by `schedule/appRun.ts`) | Third-party app code now runs while nobody is looking: a second iframe composition with its own sandbox or CSP; a frame that registers as the app's live host and gets rung by the wizard; a stale saved draft running instead of what the user committed; two hidden frames at once; a hidden run racing a visible one over the same data; a host that has no seat for it running it anyway | ONE `SnugAppFrame` — the SAME component RunView mounts, so `sandbox="allow-scripts"` and the injected CSP meta are byte-identical and the C2 reach test applies unchanged — rendered 1×1 `visibility:hidden` (never `display:none`: a display-none frame's rAF stalls). It is mounted ONCE in `apps/playground/src/App.tsx` beside `ConnectionWizardNote`, renders only what `hiddenMountStore` holds, and the queue runs one step at a time, so there is at most one; a second mount request while one is up is `failed` ("another scheduled run is still mounted"). It NEVER calls `registerAppHost` — `registerAppHost` stays RunView's (`apps/playground/src/run/appRuntime.ts` lifts the transport, the net handler and the frame bindings out of RunView and deliberately not the registration), so the wizard cannot ring it and `hasLiveAppHost` does not know the app while the hidden frame is up. The frame runs the app's COMMITTED CURRENT html (`db.getAppHtml`, the read RunView makes for an owned app). Before mounting, the executor asks the live registry: if the app is on screen a run the user did NOT start (`due`, `late`, `catch-up`) is `refused` by name — "the app is open — Snug doesn’t run it behind you; close it or run now" — and the row reads *needs you*: no hidden frame, no hint, no kv (Gate-5 fold: presence is not consent). The ONE run that rides the live frame is the user's own *Run now and review* (`manual`): the act opens the app first (`/run/<app>` from the result, the row and the results list), then the hint goes through `notifyAppHost` and the result through the app-events RunView forwards with `publishAppEvent`, under the page's ordinary gate with the person who clicked at the confirm; a manual run of an app that is not open is `refused` ("open <app> and run it again"), never a hidden frame under the ordinary gate; the app closing mid-run settles `failed` ("the app was closed") — pinned by `apps/playground/src/__tests__/appRunHandshake.test.tsx` ("S1 — an unattended trigger never runs behind an open app": "due / late / catch-up with the app LIVE → `refused` with the \"app is open\" sentence: no hidden frame, no runtime, no hint, nothing written", "the refusal folds to `needs-you` through the production executor"; "the live frame — a MANUAL run with the app on screen": "delivers to the LIVE frame under the page’s own gate …", "M18: the app CLOSING mid-run settles the step `failed: \"the app was closed\"` at once"; "a manual run NEVER gets a hidden frame: with the app closed it is refused by name — \"open Weather and run it again\" …"). While a hidden run is up, a RunView mounting the same app (`subscribeAppHosts`) asks the queue to interrupt it (`ctx.interrupt('app opened')`) — the frame unmounts, the key is cleared, the row reads `interrupted`. A platform that composes no `scheduler` seat gets no hidden frame: the step is `blocked` by name (`NO_HIDDEN_FRAME`), no platform `kind` read. The frame gets no `openUrl` (every open-url request is a named refusal) and declares `streaming: false` to match the scheduled transport. Pinned by `apps/playground/src/__tests__/scheduledRunHost.test.tsx` ("C2: the frame is `sandbox=\"allow-scripts\"` EXACTLY and its srcdoc carries the injected CSP meta first — the same component as RunView", "is 1×1 and visibility:hidden — never display:none (rAF stalls in a display-none frame), on the frame AND its wrapper", "never registers as the app's live host (F5): the registry does not know the app while the hidden frame is up", "sits app-level, directly after ConnectionWizardNote — a run can happen on any route"), `apps/playground/src/__tests__/appRunHandshake.test.tsx` ("only the committed CURRENT version runs — a newer saved version is what mounts", "a RunView mounting the same app mid-run asks the queue to interrupt with \"app opened\"; the frame goes and the key is cleared", "ANOTHER app opening does not touch the run", "no scheduler seat on this platform → blocked by name, no mount, nothing written", "delivers to the LIVE frame: no hidden mount, the key written, the hint rung through the registry, the result read from the forwarded events") and `apps/playground/src/__tests__/appRuntime.test.tsx` ("RunView composes its frame through `composeAppRuntime` and no longer calls the transport or net factories itself", "`registerAppHost` stays RunView's — the wizard's seam, never the runtime's"). |
| **The kv handshake** (`snug:schedule:<runId>` on the app's own namespace; `host-event 'schedule-run'`; `app-event 'schedule-result'`) | The host now WRITES into an app's data store and READS what an app posts: a value the task schema would refuse planted through the host seat; a write into a deleted app's namespace that resurrects it; content on the event channel (R7); a result from a VISIBLE copy of the app, from another frame, for another run, a second time, or oversized, acted on as the run's outcome; a key a dead tab left behind that a later run reads as its own input; a result that smuggles a key into the file | The driver gains a host-side `kvSet/kvGet(namespace, key, value)` (`packages/db/src/driver.ts`): the same `snug_kv` table the app's own frames reach, a value capped at `HOST_KV_VALUE_MAX_BYTES` = the task schema's 1 KiB app-input cap and refused `DB_TOO_LARGE` above it, `null` a DELETE (the app's next `kvGet` answers absent, never a stored null), the key held to the frame schema's bounds, errors as data (the seat never throws). The user db's driver face (`packages/db/src/userdb/userdb.ts`) puts the host seat behind the SAME tombstone as a frame: a deleted app's namespace is refused `NOT_FOUND`, and `noteNamespace` keys the write-back so the input lands in the file as the app's own writes do. The executor (`apps/playground/src/schedule/appRun.ts`) writes `{ taskId, runId, input? }` ONLY after the frame announced, rings `notifyEvent('schedule-run', { taskId, runId })` — ids only, the content rides the kv — and reads the app's `schedule-result` through the mount's OWN closure: a result lands only from the frame that received the hint, only after the hint was posted (`hinted`), only once (`seen`), only for this run when it names one (`parseScheduleResult` drops a `runId` that disagrees), length-capped at 8 KiB serialised BEFORE the strict `scheduleResultSchema` parse (`{ ok, summary? ≤ 4 KiB, notify? {title ≤ 80, body ≤ 120}, runId?, taskId? }`, unknown keys a drop). Everything else is dropped without a word — an app is never told why. The key is cleared (`kvSet(…, null)`) on EVERY exit path (`finally`), and the boot sweep clears the key of any claim a dead tab left behind (`sweepStaleClaims` in `apps/playground/src/schedule/scheduler.ts` calls `clearScheduleKey` for every app an `app-run` step names). The reply side of C1 holds as in PR-A: `finalizeOutcome` withholds a credential-shaped summary whole; the kv value is the step's own input and ids — `snug_secrets` is not on the path. No new frame, no `host-ready` flag, no new error code. Pinned by `packages/db/src/__tests__/driver-host-kv.test.ts` ("the cap is the handshake's: HOST_KV_VALUE_MAX_BYTES is SCHEDULE_APP_INPUT_MAX_BYTES (1 KiB)", "`null` CLEARS: the app's kvGet then answers no `value` field at all (absent, never a stored null)", "a value over 1 KiB (serialised UTF-8) is refused DB_TOO_LARGE and the key keeps what it held; exactly 1 KiB lands", "namespaces are isolated: a key written for one app is absent for another", "routes a live app through (the write lands in the file: it survives a flush and a re-open) and refuses a deleted app NOT_FOUND"), `apps/playground/src/__tests__/appRunHandshake.test.tsx` ("mounts the app's CURRENT html, writes exactly { taskId, runId, input } on announce, rings ids only, reads ONE result, clears the key, unmounts", "UNSOLICITED: a result before the hint is dropped; the one after lands", "DUPLICATE: the second result is dropped — the first is the outcome", "FORGED: a result through another frame's closure, or naming another run, never lands on this run", "OVERSIZED: a result past the serialised cap, or past a field's cap, is dropped before and at the strict parse", "other app-events are ignored — only `schedule-result` is read", "a result summary that looks like a credential is WITHHELD whole by the executor's finalize", "the kv value is the step's own input and ids — the file's secrets are not on the path at all") and `apps/playground/src/__tests__/schedulerKeySweep.test.ts` ("a claim older than its bound is retired AND its key cleared; a claim inside its bound (a live sibling) keeps both", "clearScheduleKey clears the key in EVERY app an app-run step names and nothing for a task the file no longer holds"). |
| **The refusing confirm gate** (`schedule/scheduledConfirmGate.ts`, threaded through `state/net.ts`) | An unattended run's net call reaches the page's confirm gate with nobody at the dialog: a POST the user remembered for the session, or armed as a standing grant while present, is answered YES for a run they are not watching; the app's own `ok` papers over a refusal; a scheduled app burns the day's network budget | `CreateNetHandlerOptions` gains `confirmGate?`, threaded into `connectedFetchDepsFor` as the ONE seat where a scheduled run differs from the visible frame — the same executor, the same reader, the same transports, only the decision seat. Absent (the wizard's probe, RunView), the page's ordinary gate answers (the standing gate over the session gate). A scheduled mount hands `createScheduledConfirmGate()`: STANDALONE — it does not import `state/net.ts` at all, so it can consult neither the session-remember nor the standing gate — answers `false` to every mutating call synchronously and RECORDS `{ host, method }`; the executor answers the app with the EXISTING `NET_CONFIRM_DENIED` (no new code), and `outcomeOf` lets the gate's record OUTRANK whatever the app then reports: any refusal → the step is `refused` with `copy.needsYou` ("Ledger needs your OK — Snug doesn't post to api.github.com while you're away"), and the queue folds the run to `needs-you` with one act, *run now and review*. The gate follows the TRIGGER: a `manual` run (the user's own *Run now*) has the user present and composes the runtime with NO gate — the page's ordinary gate parks its confirm for the person at the page, in whichever frame the run lands (the hidden one, or the live one when the app is open); every other trigger (`due`, `late`, `catch-up`, including the missed card's *Run them*) gets the refusing gate. Reads never reach a gate; every call — granted or refused — is COUNTED at the handler through `onNetCall`, which asks the day's network ceiling (the file's counters, plus what this run already spent, plus this step so far) BEFORE the executor is built and refuses by name (`NET_CONFIRM_DENIED`, `NET_CALL_LIMIT_MESSAGE`) at the ceiling without touching anything credentialed. One gate per run, never shared. Pinned by `apps/playground/src/__tests__/scheduledGate.test.ts` ("refuses every mutating method synchronously, consults nothing, and records what it refused", "a remembered session grant does NOT let a scheduled POST through — refused, no fetch, no confirm parked", "an armed standing grant does NOT let a scheduled POST through either", "a GET succeeds through the scheduled handler and is COUNTED at the handler (`onNetCall`, the host-assigned id)", "a refused POST is counted too — the attempt spent a call on the handler, whatever the gate said", "`onNetCall` answering false refuses the call BEFORE the executor — the daily ceiling, by name, with no fetch", "the wizard's probe and the visible frame keep the DEFAULT gate: a handler built without `confirmGate` still parks a confirm"), `apps/playground/src/__tests__/appRuntime.test.tsx` ("threads `confirmGate`: a mutating call through a runtime composed with the REFUSING gate answers NET_CONFIRM_DENIED and parks NO confirm", "without `confirmGate` the page's ORDINARY gate answers: the same POST parks a confirm for the user"), `apps/playground/src/__tests__/appRunHandshake.test.tsx` ("a manual run composes the runtime with NO gate (the page's ordinary gate); every other trigger with the refusing gate", "a refused mutating call makes the step `refused` with the needs-you sentence — even when the app then reports ok", "a refusal followed by silence is still `refused`, not `failed`", "net calls the handler reports ride the outcome; the day's ceiling, PLUS what the run already spent, refuses the next", "the file's counters count too: a day already at the net ceiling refuses the first call"), `apps/playground/src/__tests__/scheduleQueue.test.ts` ("a `refused` app-run step (the refusing gate said no) folds the run to `needs-you` with the step's own sentence as the reason") and, end to end on the built page against the net stub, `apps/playground/e2e/schedule-flow.spec.ts` ("a POST run: the scheduled gate refuses the write unattended — the run is needs you with its one act, run now and review"). |
| **The counting transport** (`schedule/scheduledTransport.ts` over the app's own `createAppTransport`) | The hidden frame's own thinks are an app's calls to the user's brain while nobody is looking: unbounded spend, a reply that echoes a key into the app and from there into a `schedule-result` and the file, a streamed fragment that escapes the scrub | The `share/consentTransport.ts` pattern: the app's transport stays what it is (its runtime contract, its per-app pin, the R-9 egress scrub per send) and the decorator adds what an unattended run needs. CAP: `onCall()` is asked BEFORE every send — the executor's closure reads the day's AI counters plus what this run and this step already spent — and `false` refuses with the EXISTING `HOST_ERROR` (non-retryable, the brain untouched, nothing counted). COUNT: every send that reached the brain is one `calls.ai` on the run row (a `CONSENT_REQUIRED` refusal before anything left the page is not a call — `appThink.ts`'s rule); the queue charges the counts to `schedulerState.daily`. SCRUB: the reply text is shape-scrubbed (`scrubCredentialProse`) and, when it STILL looks like a credential (`findScheduleCredential`, the same walk the run row's parse refuses on), WITHHELD whole behind a named refusal. WHOLE: `onDelta` is never forwarded — a scheduled reply arrives once, after the scrub — and the hidden frame declares `streaming: false` to match. Pinned by `apps/playground/src/__tests__/scheduledTransport.test.ts` ("asks the ceiling BEFORE every send; a send the ceiling admits reaches the brain and counts ONE AI call", "at the ceiling the send is refused BY NAME, non-retryable, and the brain is never touched — nothing counted", "a reply that refused before anything left the page (CONSENT_REQUIRED) is not charged", "shape-scrubs a reply: a bearer token embedded in prose reaches the app redacted, the prose intact", "WITHHOLDS a reply whole when it still looks like a credential after the scrub (a URL with userinfo) — a named refusal, counted", "never forwards `onDelta`: a streamed delta cannot carry an unscrubbed fragment to the app; the signal is forwarded"), `apps/playground/src/__tests__/appRunHandshake.test.tsx` ("AI calls through the hidden frame's transport are counted on the outcome and refused at the ceiling") and `apps/playground/src/__tests__/scheduledRunHost.test.tsx` ("declares streaming:false to the app — the scheduled transport never forwards deltas, so the ready ack must not promise them"). |
| **The builder tool and the chat lane** (`schedule_propose`; the `schedule` intent and lane) | A brain stages a schedule for another app, authors the SQL a scheduled think will run, or stages several per turn; a routed `schedule` turn falls through to the builder's full tool set with `artifact_write` in hand (the lane design's named failure); a persisted card is a crafted row that misrepresents what the user would be enabling; a card acts as an approval gate | `buildScheduleProposeTool` (`apps/playground/src/agent/tools.ts`) is the whole of the chat's `schedule` lane and rides in the builder's set: it cannot create, enable or run anything. | **The app suggestion** (`app-event 'schedule-request'` → `schedule/scheduleRequest.ts` → `schedule/SuggestionStrip.tsx`) | Running app code gains a channel to the user: a nag on every load (the channel ADR-0016 feared); a request that names another app, carries a credential, or is oversized; a read-only starter or a shared preview suggesting a schedule it has no row for; a muted or declined suggestion re-prompting under a new title; one app filling the file with schedules; a modal that interrupts the user mid-use | The runner is untouched: `SnugAppFrame`'s existing `onAppEvent` seam hands the event to `useAppEventConsumer` (one line in `apps/playground/src/run/RunView.tsx`), and `consumeScheduleRequest` decides — each guard a SILENT drop for the app (a refusal cannot be probed) and a named decision for the tests, in this order: another event → `ignored`; ≤ 1 request a minute per INSTANCE (`appId:frameEpoch`, counted on every request that reaches this point, readable or not) → `rate-limited`; length-capped at the task cap (16 KiB) then STRICT-parsed against `scheduleProposalSchema` (a credential is a parse refusal) → `unreadable`; the app must be in the file → `unknown-app`; every app step names the SENDER (`namesOnly`) → `other-app`; the Settings switch (`NO_SUGGESTIONS_KEY`) or the app's mute → `muted`; the proposal's `proposalHash` (semantic fields only — a reworded title is the same suggestion) among the app's recorded declines → `declined`; five app-proposed schedules already → `capped`; a second from the same frame generation while one is pending → `pending`; else `accepted`. | **The SDK hook** (`packages/sdk/src/schedule.ts`; `onHostEvent` in `packages/sdk/src/bridge.ts`; the KB's listener snippet) | The app side of the handshake is where an app author can be wrong in a way that costs the user: a handler that runs twice for one hint (a host that crashed mid-run and asked again), a result that carries data instead of a summary, a throw that leaves the host waiting out its bound, a `proposeSchedule` on every load, a suggestion naming another app, a `notify` the app expects to be shown | `useSnugSchedule(handler)` subscribes to the named `schedule-run` host-event (the bridge's new `onHostEvent`, additive — a malformed hint is ignored), reads the input back through the SAME db frames `usePersistedState` uses (`dbRequest('kvGet', { key: 'snug:schedule:<runId>' })`), runs the handler ONCE per `runId` (remembered BEFORE the kv round trip, so a duplicate arriving mid-flight is ignored too; the latest render's handler runs), and posts exactly ONE `schedule-result`; `normalizeScheduleResult` makes it the shape the host will parse — `ok` a boolean, `summary` cut to the protocol's 4 KiB, `notify` only with both halves and each cut to its bound, every other key DROPPED (a result is a summary, not data); a throw becomes `{ ok:false, summary: <message> }`, nothing escapes. `proposeSchedule` posts ONCE per page, only after host-ready, only a proposal the protocol's strict shape admits (the host enforces the sender; the SDK cannot know its own id). ## Accepted residuals

- **R-a. A scheduled *Run [app]* runs the app's own code with the powers it already holds
  over its own data.** This is the one residual ADR-0074 §6 (G4) names and accepts. Inside the
  hidden frame the app reads and writes ITS OWN tables through the same driver and namespace it
  has when visible; nothing stops its own code from changing its own rows while nobody is
  looking, and there is no pre-run snapshot or undo (deferred by name, §8). The network side is
  held — every mutating call is refused by the standalone gate, every call counted — and the
  brain side is counted and capped; the data side is the app's, as it always was. *Bounded by:*
  the sandbox (C2 unchanged), the committed version only, the user's own enable act with the
  consent surface, the failure and ignored pauses, and the inbox that shows every result.
- **R-b. The user's own *Run now and review* rides the live frame under the page's ordinary
  gate and transport, uncounted.** The ONE run delivered to an open app is the `manual` run the
  user just started from a result, a row or the results list — the act opens the app first, then
  runs (Gate-5 S2): its net calls go through RunView's handler (the ordinary gate, with the person
  who clicked at the confirm) and its thinks through RunView's transport, so the row's `calls`
  are zero and the day's ceilings do not see them. A run the user did NOT start never rides the
  open app: it is `refused` by name ("the app is open — Snug doesn’t run it behind you") and the
  row reads *needs you* with the same act (Gate-5 S1 — presence is not consent). *Bounded by:*
  one run per gesture; the frequency floor; the live frame's own budget; the confirm is answered
  by the person who asked for the run.
- **R-c. The demo brain answers a hidden frame's thinks like RunView's.** Under the demo brain
  (the mock adapter) the hidden frame's `createAppTransport` answers scripted turns exactly as
  it does for the visible app — unlike *Ask the AI*, which refuses the demo brain by name. Each
  such reply COUNTS as one AI call on the run row and against the day's ceiling (the decorator
  cannot tell a mock from a provider) while spending nothing. Harmless by construction: no key,
  no provider, no cost; the count only makes the ceiling conservative.
- **R-d. The stored-secret VALUE scrub stands at the executor, for the scheduled handler as for
  RunView's — closed.** PR-A's R-e named `scrubAuthValues` against the values a net handler holds
  as the one seam PR-B's handler introduces. Read at the Gate-5 fold: the scrub is not a call the
  handler makes but the executor's own — `packages/auth/src/connected-fetch.ts` redacts every
  injected header and query value from the response body and from each whitelisted response
  header (`scrubAuthValues(read.body, scrubCandidates)`, ~L1313–1316) before the frame crosses the
  bridge, and the scheduled handler is the same `createNetHandlerFor` with a different gate, so the
  hidden frame sees exactly what the visible one sees. Pinned for the scheduled handler by
  `apps/playground/src/__tests__/scheduledGate.test.ts` "a connected host that echoes the injected
  credential answers the hidden frame with `***`" (body AND a whitelisted header; the stored value
  appears nowhere). What remains is the executor's documented boundary — a provider that
  RE-ENCODES the value defeats an exact-substring scrub (AL-11's forward-constraint) — plus the
  credential-SHAPE wall on the way to the file (`scheduledTransport` scrubs and withholds a brain
  reply; `finalizeOutcome` withholds a credential-shaped summary). Threat model R-54 closes on this.
- **R-e. An app that does not answer costs the queue its bound.** A frame that never
  announces is `no-handler` after 10 s (`SCHEDULE_ANNOUNCE_TIMEOUT_MS`); one that announces but
  ignores the hint is `failed` after 90 s (`SCHEDULE_RESULT_TIMEOUT_MS`, under the queue's 120 s
  run bound); both count toward the five-failure pause, and the no-handler result tells the
  user in words that the app does not know how to run on a schedule yet. Availability only —
  the queue runs one item at a time, so a silent app delays the next item by its bound.
- **R-f. Suggestion fatigue is bounded by the mute, not removed.** An app may ask once a
  minute per instance and hold one pending per frame generation; a remount is a new instance.
  A user who keeps reopening an app that keeps suggesting sees the strip again until two
  declines mute it, *stop suggestions* mutes it, or the Settings switch mutes every app. The
  cap of five app-proposed schedules per app holds at intake. *Bounded by:* the strip costs the
  app a strip of height and never a modal; a decline is remembered by semantic hash, so a
  reworded title is the same decline.
- **R-g. On the artifact binding a connected *Run [app]* is refused at the runner, not
  graded by the queue.** The kit's artifact bindings run with `connections: false`
  (`hostCapabilities`), so `composeAppRuntime` composes NO net handler for the hidden frame
  (`appMayReachNetwork` — one rule for the visible and the hidden frame; `host-ready.net` is
  false structurally) and the app's connected call is answered by the runner's own refusal
  (`HOST_ERROR`, "this host has no net capability"). The Schedule page grades such a step
  `blocked` in words through the one availability derivation (`ScheduleStates.tsx` over
  `platform/availability.ts` — "needs live connections"), but the QUEUE does not consult
  availability at run time: the step runs, and the row records whatever the app answers
  (typically `failed` with the app's own sentence, or `ok` with a degraded summary). No network
  is reached either way. The run-time grading is a candidate follow-up, not a claim.
- **R-h. The two gate rows prove the plugin is unreachable from a sandboxed frame on macOS
  only.** `ipc-notification-refused` / `-dispatchable` run in the in-shell gate on the shipped
  surface, which is macOS (ADR-0021 D8, R-5); nothing here changes the Windows/WebView2 stance,
  and a scheduled *Run [app]* has no platform-kind refusal of its own — it is refused where the
  platform composes no scheduler seat.
- **R-i. A scheduled result is app-written text shown to the user.** The `summary` on the
  Schedule page is whatever the app's own code answered (≤ 4 KiB, credential-shaped text
  withheld): an app — or a connected host whose response the app echoes — can shape those
  words. It can shape nothing else: a result carries no data, no act and no proposal; the one
  act on a `needs-you` row is the user's own *run now and review*. (R-53's shape, for an app
  instead of a model.)

## What this delta does NOT claim

- It does not claim unattended writes are possible. They are not: a scheduled run's
  mutating network call is refused by a gate that consults nothing, and the standing-approval
  gate (ADR-0033, SPEC §17) stays unarmed. What an app does to ITS OWN tables inside the
  sandbox is R-a, named, not denied.
- It does not claim a run fires while every Snug is closed, on any host (PR-A's R-a; model
  R-50). Desktop background mode is the named follow-up.
- It does not claim a desktop notification is SHOWN under `tauri dev`: macOS keys delivery on
  the bundle identifier, so only the bundled app (`pnpm --filter desktop bundle`) shows one —
  the owner's walk, printed in the task's walk list, is the proof; the suites prove the seat's
  three answers and the gate rows prove the plugin's reach.
- It does not claim a connected *Run [app]* works on the artifact binding (R-g), nor that the
  executor's value scrub catches a RE-ENCODED echo (the exact-substring boundary, R-d).
- It does not claim anything about Windows: the desktop shell ships macOS-only (ADR-0021 D8,
  R-5), and nothing here changes that.
