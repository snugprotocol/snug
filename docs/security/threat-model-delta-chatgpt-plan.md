# Threat-model delta — "Use my ChatGPT plan" (Sign in with ChatGPT on the desktop)

- **Task:** TASK-20261023-siwc-chatgpt-plan · **ADR:** [0078](../decisions/0078-chatgpt-plan-mode.md) (amending [0014](../decisions/0014-credentials-local-first.md), [0021](../decisions/0021-desktop-shell-transports.md), [0036](../decisions/0036-per-app-model-selection.md), [0046](../decisions/0046-multi-provider-byok-and-app-lifecycle-controls.md), [0059](../decisions/0059-brain-disclosure.md)) · **Spec:** none — no `packages/protocol` schema, frame or wire byte (one internal regex bound, below) · **Date:** 2026-10-24 (drafted 2026-10-23 at Gate 2; finalised with the code; amended the same day with the Gate 5 fixes — the owed tests named, R-130 reworded, R-133 and R-134 added) · **Baseline:** `docs/threat-model.md` v3.13 (highest residual R-123) · **Folded into:** v3.14

C1 and C2 are unchanged in policy. This delta adds one credential family the system has not held before — a **rotating, per-host OAuth session** for the user's own ChatGPT plan — and one outbound route (`POST https://api.openai.com/v1/responses`) reached through the existing LLM choke point. It records where the credential rests, who may read it, how it moves, and what it can never touch.

## What changed

- A third `PlaygroundMode`, `chatgpt`, offered only where the platform carries the custody seat (`SnugPlatform.chatgptPlan` — the desktop). The hosted playground, the web kit and the local-host kit cannot construct it; a roaming file that stores it is coerced there with the divergence note, the stored row untouched. In the host kit (web and local-host bindings alike) the ChatGPT-plan modules are not even present: the keeper, its five surfaces and the Responses adapter are swapped for inert stubs at build time (`apps/host/vite.config.ts` `swapResolved` → `apps/host/src/stubs/`, pinned by `apps/host/src/__tests__/kitDeadLanes.test.ts`), so the kit page carries none of the plan's code.
- A session file `~/Snug/.chatgpt-plan/session.json` — a dot-prefixed `0700` subdirectory, a `0600` file written through a `create_new` temp opened `mode(0o600)`, then rename + directory fsync, opaque bytes capped at 64 KiB, no serde, nothing logged — owned by the shell (`apps/desktop/src-tauri/src/chatgpt_session.rs`) and reached by three Tauri commands, `chatgpt_session_read | write | clear`, and by nothing else: `userfile.rs`'s `valid_name` refuses a leading `.` and any separator, so the existing `read_user_file` / `write_user_file` cannot name it (pinned by `cargo test` on both impl functions). `~/Snug` itself is never chmod'ed. The credential is **not** in `snug_secrets`. The commands' wall is the invoke key (capabilities do not scope custom commands — there is no `AppManifest`), the same wall as `read_user_file`'s.
- A DI-pure session keeper in `packages/auth` (`src/chatgpt-plan.ts`, `createChatgptPlanSession`, with its types and total session-file parser in `src/chatgpt-plan-types.ts` and its wire constants and pure helpers in `src/chatgpt-plan-wire.ts`; `src/jwks.ts`, the RS256 ID-token verifier): PKCE S256, signed state, dynamic registration, ID-token validation against OpenAI's JWKS, a **serial mutation queue with a session epoch**, single-flight rotation-safe refresh, revocation, the model list. It holds no token in memory between uses: each use reads the file inside the queue. `src/oauth-service.ts` gained `extractOauthErrorFromPost` (the credential POST's redirect guard and echo scrub as a free function that also returns the OAuth `error` code; `postForm` is its thin caller, characterization-tested first).
- A Responses adapter in `packages/adapters` (`src/openai-responses.ts`, `src/responses-wire.ts`) behind `runAgentTurn`, over a `BearerSource` seam (`src/bearer-source.ts`: `get` / `refresh(stale)` / `redact`) — never a key, never a `TurnAdapterConfig` field. The page adapts the keeper to it (`apps/playground/src/state/chatgptPlan.ts`, `chatgptBearerSource()`).
- The sign-in has **its own loopback transport** (`apps/desktop/src/chatgpt-plan.ts`, reserved appId `chatgpt-plan`) over a **port-filtered** Tauri listener (`apps/desktop/src/oauth.ts` — it subscribes after the plugin reports its bound port and drops payloads for any other port; the wizard's listener gets the same filter). The transport core (`packages/auth/src/desktop-transport.ts`) gained a redirect path (`/auth/callback`; `/callback` callers unchanged), the callback's `client_id`, and error delivery that opts in by the presence of an `onError` handler — the wizard passes none and is byte-for-byte unchanged.
- The protocol's IN-TEXT JWT matcher is **bounded**: `JWT_SHAPE_SOURCE` (`packages/protocol/src/security.ts`) = `eyJ[\w-]{8,4093}\.[\w-]{8,4096}\.[\w-]{8,4096}`. The unbounded form threw `RangeError: Maximum call stack size exceeded` on an 8 MiB unbroken `eyJ…` run (measured on Node 22, 2026-10-24) — a denial of the very scrubs that use it. The adapter's backstop and the inspector's display mask derive from it (`jwtShapeInText()`). The C1 scanner's ANCHORED whole-value rule does **not** (Gate 5 S7): it is `isWholeJwtValue` — a split on `.` into exactly three segments, a char-code walk per segment, the first starting `eyJ`, each at least 8 characters — linear and with NO length limit, because the bound applied to the rule had let a JWT with a 5 KB payload past the scanner.
- New named host-level error codes (`CHATGPT_SIGN_IN_NEEDED`, `CHATGPT_PLAN_NOT_GRANTED`, `CHATGPT_USAGE_LIMIT`, `CHATGPT_USAGE_UNAVAILABLE`, each with one fixed sentence — `CHATGPT_ERROR_SENTENCES`); a one-time notice; *Using ChatGPT plan* + **Manage usage** on the chip and in Settings; a usage-limit message whose primary action is Manage usage in chat, the run view and a scheduled step's result.
- The in-shell gate gains six rows (`ipc-chatgpt-session-{read,write,clear}-{refused,dispatchable}`) and one DEBUG-only sensor, `gate_chatgpt_session_stat` (`apps/desktop/src-tauri/src/gate.rs`: `{ exists, fileMode, dirMode }`, refused outside gate mode, registered in the debug handler list only — a Rust test pins that the release list does not name it). It reports modes, never contents. The dispatchable rows run as effect sensors in the gate's throwaway `HOME` (`gate/run-gate.mjs` spawns the shell under a `mkdtemp` home): seed a fixture that is never a valid session, read and record only `resolved`, clear, stat. Since Gate 5 (A10) the sensors first ask a second DEBUG-only command, `gate_chatgpt_session_marker_present`, whether the gate-home marker `run-gate.mjs` writes into that throwaway home (`.snug-shell-gate-home`) is there — absent, nothing is written, read or cleared and the rows FAIL as skipped (new row `ipc-chatgpt-session-gate-home`) — so a plain `tauri dev` started with the gate's environment can never seed over or clear a real session.

## Assets — the consolidated model's §2 amended

The baseline's §2 says credentials live in `snug_secrets` in the user's own file. From v3.14 that holds for every credential **except one**: the ChatGPT-plan session lives **beside** the user file, in `~/Snug/.chatgpt-plan/session.json` on the machine that signed in, and never inside it — so it never rides an export (with or without secrets), a sync push, a share bundle, or the `.snug` passphrase encryption (ADR-0043). The custody claim is unchanged and stated per machine: the tokens never reach Snug's servers; they stay on this computer.

| Asset | Where it lives | Who may read it | Notes |
|---|---|---|---|
| Refresh token (30 d, rotates on every refresh) | the session file; host-page memory **per use** — `chatgpt_session_read` returns the whole file to the keeper inside its serial queue, for the duration of one send or one refresh, never cached | the shell's three commands; the auth session keeper | never in `snug_secrets`, exports, sync pushes, share bundles, URLs, logs, the inspector |
| Access token (1 h JWT, `aud=https://api.openai.com/v1`) | the session file; host-page memory per send | as above + the Responses adapter via `BearerSource.get()` | the same altitude as a BYOK key today; never a `TurnAdapterConfig` field; never in a 401/403 message (fixed sentences); redacted-then-capped elsewhere; the page's `redact` masks every token handed out this session (a small bounded ring) |
| ID token + verified identity (`sub`, email, name) | the session file (claims subset) | Settings / chip (display) | display data; a returning account must match `sub` before tokens are replaced |
| Issued client id (`oaiapp_…`) + host id (`urn:uuid`) | the session file (survives sign-out; *forget this registration* drops it) | the session keeper | the registration; a re-auth naming a different client is refused |
| Cached model list + levels | the session file (non-secret section) | Settings, selectors, chip | per machine; refreshed per sign-in and on Settings open; failing soft |
| The default model and level | the user file's settings rows `providerModel:chatgpt`, `providerEffort:chatgpt`; per-app pins `appModel:` + `appProvider:<appId> = 'chatgpt'` | the page | a person's preference, not a credential — travels with the file like every model default |
| The user's plan allowance (shared five-hour Plus limit; per-app limits) | OpenAI | — | spent by every think; the user's lever is ChatGPT → Settings → Usage |

## Principals

| Principal | Trust | What this delta lets it do |
|---|---|---|
| The user | owner | sign in / out, allow or decline plan usage, pick model and level, forget the registration, set per-app limits in ChatGPT |
| The host page (playground in the desktop webview) | trusted, as today (R-1) | run the protocol, hold a token in memory per send, call the API through the platform fetch |
| An app frame (`sandbox="allow-scripts"`) | untrusted (C2) | nothing new — no IPC, no header, no token; it sees a turn's text and a named, scrubbed error |
| The LLM (OpenAI, on the plan) | untrusted input source (R-8) | the same prompt and tool surface as the BYOK OpenAI brain; the same R-9 egress scrub |
| A scheduled step | the user's standing intent (ADR-0074) | spend the plan when signed in and granted (owner default); refused by name when signed out or not granted; a live limit refuses the step, not retried |
| OpenAI's auth server / API | the provider | issues, rotates and revokes; may echo submitted values in error bodies |
| A local process on the machine | out of the sandbox's reach | can hit the loopback listener — it cannot complete a sign-in (PKCE binding — ADR-0021 §2) but can END one (R-133) — and, with the user's privileges, read `0600` files (R-3 class) or re-point the custody directory (R-134) |

## What the build taught (recorded at Gate 6)

- **A scrub's own regex can be the denial.** The unbounded JWT shape overflowed V8's backtracking stack on an 8 MiB run, so the masking step meant to protect the inspector would have thrown on a large payload. Bounded at its one home for the in-text matcher.
- **A bound on a security MATCHER must not become a bound on the security RULE** (Gate 5 S7). The first fix derived the C1 scanner's anchored rule from the bounded source too, and a JWT with a 5 KB payload then passed the scanner (the security review measured it). The rule is now a linear charset walk with no length limit; the bound lives only where backtracking does.
- **The gate senses modes, never contents — and only in a home it made.** The dispatchable rows prove the commands work by their effect on a throwaway home through a debug-only stat probe; no session body is ever recorded in gate results; and since Gate 5 they refuse to touch any `HOME` that does not carry the driver's marker.
- **Persist tracking belongs to the parties that persist.** The first build instrumented the seat's store object from the page (WeakSet-guarded), which tracked only writes that had STARTED — a close between a refresh POST's answer and its queued write lost the rotation. Since Gate 5 the keeper's `flush()` covers that window and the seat's `flush?()` covers its own IPC; nothing patches the store.
- **Two shells on one `~/Snug` are still uncoordinated, but no longer destructive to each other.** Nothing locks the session file across processes; `tauri-plugin-single-instance` is the only coordination — it is what forwarded the gate's debug shell to the owner's running Snug.app and quit it — so two keepers reach one session file only when two shells escape it (a build under another identifier). Since Gate 5 every post-POST persist and every clear compare-and-swaps on the refresh token the POST spent, so the loser's `refresh_token_reused` no longer wipes the winner's fresh set (probed with two keepers on one store); what remains is R-130's window. An advisory `flock` around refresh stays queued.

## Accepted residuals

**R-124 — The ChatGPT-plan session file is plaintext at rest.** `~/Snug/.chatgpt-plan/session.json` is `0600` in a `0700` directory, outside `.snug` passphrase encryption (ADR-0043) and outside any keychain; any process running as the user can read it. Same class as R-3. *Bounded by:* OpenAI's documented minimum for local token storage is met; the token never enters the user file, so it never rides an export, a sync push or a share; the Protection card and the plan card say the sign-in sits outside the protected file; sign-out deletes the tokens and the account (the registration — the issued client id and the host id, no secret — stays until *forget this registration*). Keychain custody is queued with its own ADR.

**R-125 — The access token is held in host-page memory per send.** The keeper reads the file per use and the adapter holds the bearer for one send. Same class as R-1: a compromised host page already holds every BYOK key, and the desktop webview runs with `csp: null` (known, R-1). *Bounded by:* no long-lived cache (each use reads the file inside the queue); the token is never a `TurnAdapterConfig` field, a URL, an inspector header or a log line.

**R-126 — The output ceiling is client-side.** `max_output_tokens` is rejected by the documented route, so the adapter aborts its own fetch once output — text AND function-call arguments, since Gate 5 — passes `min(maxTokens, maxOutputTokens) × 4` characters; the model keeps generating until the abort lands, and the plan's usage is spent up to that point. *Bounded by:* an honest `max_tokens` with the partial text to the bridge (ADR-0018 D4's contract); `DEFAULT_MAX_ITERATIONS` still bounds tool loops; the daily AI ceiling bounds unattended steps.

**R-127 — Plan usage is shared and attributed by OpenAI.** The Plus five-hour limit is shared across all the user's apps and their own ChatGPT use, so an overnight schedule can spend what a morning conversation needed; Snug cannot know the remaining allowance or when it resets. *Bounded by:* the limit message never guesses a reset time and its primary action is Manage usage; per-app limits in ChatGPT → Settings → Usage are the user's lever; unattended steps run on the default level and a live limit is not retried.

**R-128 — The preview may change.** Measured behaviour the docs are silent on (top-level function tools, `supported_reasoning_levels`, the `/v1/models` field set) is used; measured behaviour the docs forbid (an accepted `max_output_tokens`, `system`/`developer` items) is never relied on. *Bounded by:* the adapter sends no documented-rejected parameter (a negative test per parameter); the model list fails soft to the last cache; the rejected-parameter list and the models' field set are re-checked at every release that ships the mode.

**R-129 — `packages/adapters` had no security lane before this task** (threat model §9). *Bounded by:* this task's tests and its Gate-5 security review cover the new adapter (`openai-responses.ts`, `responses-wire.ts`, the `errors.ts` additions); the Chat Completions and Anthropic adapters remain as they were, unreviewed by a security lane, and §9 still names the gap.

**R-130 — A rotation-loss window.** If the refresh's 15 s timeout fires after the server has already rotated, or the app dies between the token response and the shell's write, the old refresh token is dead and the next attempt answers `invalid_grant` / `refresh_token_reused`. A refresh still in its POST when the window closes remains in that window. Nothing locks the session file across processes: two shells that share one `~/Snug` while escaping the single-instance plugin (a build under another identifier) are not coordinated and can rotate under each other. *Bounded by:* not a leak — it costs a re-sign-in, by name; persist-before-verify; the close flush awaits the keeper's in-flight refresh (`flush()`) and the seat's in-flight writes (`flush?()`) within its 2 s budget; the one-retry rule (two timeouts keep the tokens); and since Gate 5 every clear and every post-POST persist compare-and-swaps on the refresh token the POST spent, so two keepers on one file no longer wipe each other's fresh set — the loser's rotation is revoked and it answers the standing set. An advisory `flock` around refresh is queued.

**R-131 — First-sign-in account substitution.** Anyone who can read the authorize URL (state, challenge and nonce travel in it) can authorize *their* account against our challenge and deliver that code; on a first sign-in there is no stored `sub` to compare. This needs a same-user process or a browser extension (R-3's class). *Bounded by:* the chip's popover and the Settings card always show the signed-in email; a returning sign-in must match the stored `sub` before tokens are replaced.

**R-132 — Data use on this route is UNSTATED by OpenAI.** Plan traffic carries the same context the BYOK OpenAI brain carries — including rows other apps share with the thinking app — under the user's consumer ChatGPT account. OpenAI's documents (checked 2026-10-23: the SIWC docs, the SIWC Terms of 2026-09-29, the help articles, the API data guide, the consumer privacy policy) never say which training or retention policy governs it; the signals point at the consumer rules (the Terms incorporate the consumer Terms of Use; the usage is billed as ChatGPT usage; Codex on a personal plan follows the "Improve the model for everyone" toggle), while the API's no-training default speaks of API customers, which plan users are not. What is documented is only that the app cannot see the user's conversations or memories and that `store:false` is mandatory. *Bounded by:* the consent band, the in-app privacy row (also rendered on the website's `/privacy`) and the egress line say exactly this and tell the user to assume their ChatGPT data controls apply; the copy never claims "not used for training" or "zero retention" (a negative copy pin over every playground string, `chatgptCopyPins.test.ts`); the user's lever is ChatGPT → Settings → Data controls. Re-checked at every desktop release that ships the mode.

**R-133 — A local process can end a ChatGPT sign-in flow.** The sign-in's loopback listener filters `oauth://url` payloads by its own bound port, but that filter is routing between Snug's two listeners, not a boundary: any local process that reaches `127.0.0.1:<port>` with a request that merely parses settles the one-shot listener, and the waiting sign-in ends. Same class as R-3 (a same-user process). *Bounded by:* completion stays impossible without the HMAC'd single-use state and the PKCE verifier that never leaves memory (P6), so the worst outcome is a denied sign-in — the user presses **Continue with ChatGPT** again; nothing is persisted from a forged callback (P7). (Gate 5 security review, G5-S9.)

**R-134 — `clear` is not symlink-gated.** Since Gate 5 the shell's `write` and `read` refuse a custody directory that is a symlink or not a directory (before any create or chmod), but `clear_impl` does not: a same-user process that replaced `~/Snug/.chatgpt-plan` with a symlink could have a sign-out or *forget this registration* remove a `session.json` elsewhere. Same class as R-3. *Bounded by:* `clear` removes exactly one fixed file name (`session.json`) and never recurses or follows into anything else; a process with that reach already has the user's privileges over the target; refusing the clear would leave *forget this registration* — the user's in-app remedy for a deleted ChatGPT-side client — without a way to work. Gating it, weighed against that remedy, is queued. (Gate 5 lane B2.)

## What this delta does NOT claim

- That tokens "never leave the device" — the access token travels to `api.openai.com` on every think, as a BYOK key does.
- That the host page is a trust boundary against itself (R-1).
- Anything about Windows, the hosted playground or the host kit — none of them can construct the mode (the host kit does not even carry its modules: they are swapped for inert stubs at build time).
- That the user's plan cannot be exhausted by their own apps; it can, and the message says where to look.
- That passphrase protection (ADR-0043) covers this credential — it does not, and the Protection card says so.
- That a source lint pins the keeper away from every credential store and user-DB accessor — it does not exist; the end-to-end AC10 scans (`chatgptLeak.test.ts`, P1/P11/P12) pin the effect instead.
- That the in-shell gate has run — its rows are unit-tested and the live run waits on the owner quitting Snug.app (P2).
- That the baseline's §2 Assets line ("credentials live in `snug_secrets`") still holds without qualification; v3.14 amends it.
