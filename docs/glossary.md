# Snug — Glossary

- **Micro app / Snug app** — a single-file HTML app built by an end user through conversation, run in the sandboxed runner, thinking through the host agent at runtime.
- **Host agent** — the LLM assistant of the embedding product; the "mind" of every Snug app.
- **Envelope** — the versioned JSON message wrapper for app↔agent traffic over postMessage (`[SNUG_APP_REQUEST]` / response). Defined in `packages/protocol`.
- **Bridge** — the parent-window code that relays envelopes between iframe and agent endpoint (`packages/runner`).
- **Runner** — the sandboxed iframe host component (C2 constraints).
- **Per-app DB** — isolated sql.js database per app instance, persisted to OPFS, exportable as `.snug` (`packages/db`).
- **Knowledge base (KB)** — the markdown corpus that teaches an LLM to author bridge-aware Snug apps (`packages/knowledge`).
- **Hooks block** — the code every Snug app carries to talk to its host: `packages/sdk/embedded/snug-hooks.js`, rendered as the fence of KB 20 (`20-html-template.md`) and pasted at the top of each app's babel script, above the RESPONSE SCHEMA banner. Seven numbered sections since TASK-20261010-host-broker PR-6: 1 `SnugBridge` and its one `message` listener (accepting a frame only from `window.parent`) · 2 `useSnugApp` · 3 `usePersistedState` · 4 `useAppDB` · 5 `useConnectedFetch` · 6 `onHostEvent` / `useHostEvents` / `useSnugSchedule` / `proposeSchedule` · 7 `useSnugAccess` (needs 6). ONE rule: **copy exactly** — 1–3 always, 4 and up only when the app needs them, never edited in place; what the app authors starts at the banner (sections 8–9). Held identical, after a per-line-trim normalisation, to the KB fence (`kb-sync.test.ts`), to every starter (`examples/validate.test.mjs`) and to the e2e fixtures (`scripts/sync-starter-hooks.test.mjs`); a change to it is a starter wave (`scripts/sync-starter-hooks.mjs`). The module SDK is its twin, held to the same contract suites. The tool-free brain's *inline core* carries sections 1–5 only (see **Knowledge delivery**).
- **Adapter** — server-side connector from the reference backend to an LLM provider (`packages/adapters`).
- **Broker** — the server-side credential component enforcing the token boundary (v1.1, `packages/auth`).
- **Connection** — an approved credential grant tying one app to one provider and a frozen host list (`snug_connections`; `(app_id, slot)` is the PRIMARY KEY, so an app may hold SEVERAL independent connections). Only an explicit user approval in the wizard ever creates one. Its `requirement` (what the app NEEDS) and its `status`/`allowed_hosts` (what the user ALLOWED) are deliberately separate halves — see **Requirement/grant split**.
- **Auth wizard** — the host-side review surface where a proposed connection is inspected and approved (`apps/playground/src/connections/`). Its **strong** review is field-by-field (`spec_confirm`); its **light** review is approve-as-is, reachable only for a registry-resolved builder directive.
- **Declaration (connection) / install act** — a starter's `examples/<folder>/connection.json`, the third and newest way a connection may be proposed (not the *access declaration*, an app's wish to read another app's data — below): it travels with the *install*, never at runtime, is resolved on demand rather than persisted, and always gets the strong review. See the trust ladder in [architecture.md](architecture.md).
- **Dual-layer auth** — publisher/org credentials (client_id/secret) + per-user OAuth tokens, resolved server-side.
- **Spec-sync** — the process by which this repo publishes protocol changes to `snugprotocol/spec` (SPEC_SYNC.md).
- **Host kit** — `snug-host.html`, the playground's own tree built as one self-contained page for the skill-delivered bindings (ADR-0065, TASK-20260905-host-kit); a clone of the playground / Snug Desktop minus the brain, model/provider and account controls (D15).
- **Binding** — where the host kit woke up and what it attaches to, decided once at runtime by the boot (ADR-0072 §2): `artifact` (a hosted Claude artifact — published by a tool or created in chat, one runtime since 2026-10-03), `artifact-static` (the artifact host serving the page top-level — `window.claude.use` exists but every namespace resolves `null`: nothing saves, no brain), `local-host` (the page served by the local host process — only at the literal `http://127.0.0.1`, and only when that origin answered `/status` as the runner), `file` (no host: a plain file, a loopback static server, a page that meets only the September `window.claude.complete`). Disclosure and recipes read it; capability flags, not the binding, decide what renders.
- **Brain** — what answers the apps' thinks, the second axis beside the binding (ADR-0069): the viewer-billed `sample` (Binding A only), **the user's own agent CLI as a child process** (Binding B — through the **brain registry**: `claude` on pre-warmed single-use children, `codex` built and unverified; Hermes / OpenClaw / Ollama deferred, ADR-0071), or the demo brain (the fallback everywhere). Never MCP: it is B's spawn channel, not a brain.
- **Probe** — the host kit's boot step, before React (`apps/host/src/probe.ts`): the **host namespaces** asked together behind one guard when `window.claude.use` is a function (`sample`, `artifact`, `downloads` — each `resolved` or `null`; nothing prompted, nothing spent); the **binding** decided purely from five facts (protocol, hostname, the `use` global, what the host answered, whether a runner answered); the **storage** TRIED rung by rung with a real write/read round trip (OPFS → IndexedDB → memory — never presence-detected); and the **brain** pinned from what resolved (`sample` → two adapters, envelopes on `quick` and the builder on `default`, the shaper as the ruler, the cap from `limits()` — 262,144 B on contract 0.2.67, 65,536 when it cannot be read; nothing → the demo brain, legs recorded). It runs after the boot has ruled out the OAuth callback and the local runner. Nothing asks the user anything (D15).
- **Your file chip** — the custody disclosure beside the brain chip (D8, ADR-0065 §5; `views/YourFileChip.tsx`): where the user's file lives in THIS host, what the durable copy is, what a republish does to it, and the acts the host's custody seat offers — "save to this artifact", the two divergence acts, dismiss the note. Copy derives from the platform seats and the record's state (`custodyDisclosure`), never from parallel UI state; web and desktop render nothing.
- **Artifact record** — the hosted artifact's durable-copy seam (`apps/host/src/storage/artifactHtml.ts`): the browser bucket stays the WORKING copy; the page's own `snug-db` block is the DURABLE copy, written by one explicit act that fetches the page's canonical source, lifts the kit document out of the platform's wrapper (`unwrapViewerPage` — the measured contract-0.2.67 skeleton or the September viewer's head with its injected runtime; any other shape refused by name), verifies it with the shared tokenizer, splices the file in as base64 and republishes the bare page. Seed-on-empty, divergence with a direction (the save counter), refusals by name, never a timer.
- **Hand-in** — how the agent gets an app into the kit (ADR-0065 §6): `snug-app-bundle/1` blocks embedded in the page (`scripts/snug-embed.mjs` writes them; `scripts/lib/page-blocks.mjs` is the ONE grammar), or, under the local runner, `snug_hand_in` delivered as an event to the open page — both through one core, `applyAgentBundles` (ADR-0072 §3). Each bundle resolves: an `agent:<lineage>` app or the app the bundle was lifted from takes an update (auto-applied only when unedited; an edited copy is offered in the run header behind one confirm), else a new OWNED install; a deleted app stays deleted (the `agentDismissed:` tombstone) unless the runner's explicit hand-in brings it back; a bundle with connections is refused (D4).
- **`snug-user-file/1`** — the artifact export wrapper (`snug-user.snug.json`): the user file as base64 with its sha-256, `format` first so the sniff is a byte prefix; unwrapped by the db package's one reader, which verifies the sha AND re-sniffs the payload as a user file before any import.
- **Knowledge delivery** — how the app-authoring KB reaches a BUILD turn (ADR-0066): `'tool'` (the 30 summary layer tells the model to call the app-builder tool — every brain that has it), `'inline'` (the 35 layer + the five-file KB core as system blocks — a pinned host brain that cannot call tools; this **inline core** renders KB 20 through `inlineTemplate`, which cuts the hooks block's sections 6–7 to one visible comment line, since TASK-20261010-host-broker PR-6), `'none'` (the honest 36 layer — webllm's 4,096-token window, or a host brain whose declared cap cannot hold the core). Decided once per brain by `knowledgeDeliveryFor` and consumed by the system slot, the user-message template and the edit turn's context block alike, so no slot names a tool the brain cannot call.
- **Thinking level** — the artifact runtime's `modelTier` (`quick` answers at once with no thinking first; `default`, the viewer's default, thinks first; `complex` thinks longest), the ONE knob the contract offers (ADR-0067, D15 amended narrowly). The kit's `brains/tierStore.ts` holds the user's choice (`auto` = quick for app replies / default for building; a tier overrides both), read by the sample adapters per call, rendered by the brain chip through the platform's `TierSeat`, kept in this browser at the artifact origin. A tier the viewer's plan lacks is learned only from `modelTierApplied` and is then listed disabled with what answered.
- **Platform brain** — the brain a host PINS through `platform.brain` (`{kind:'demo'}` or `{kind:'host', label, adapter, streaming, tools, maxPromptBytes?}`); the one brain derivation honours it ahead of the webllm flag and the user file, for apps and the builder alike. On an artifact or a file the brain chip discloses it and offers no switch; on the local runner it is a live getter (the host arm while the user's choice resolves to a ready brain, else the demo arm) beside the `brainSwitch` seat the chip renders as a switcher.
- **Starter source** — `starter/starterSource.ts`, the one module that owns the five `examples/` globs behind a `StarterSource` interface; the host kit aliases it to an on-demand implementation so no starter bytes ride the page.
- **Playground** — the hosted demo app (chat → build → run), bring-your-own-API-key.
- **User DB / snug file** — the single portable SQLite file per user: apps + versions (factory pinned), per-app data as native `app_<token>__*` tables with a verbatim-DDL schema registry, per-app wiki docs, chats (bootstrap pinned), settings, secrets, sync config (ADR-0007/0010; spec v0.2 draft schema v2).
- **Materializer** — the userdb driver backend (ADR-0010): at app load it replays the registry DDL into the app's OWN runtime DB (natural names, physical isolation); at write-back it recreates rest tables via `legacy_alter_table` RENAME inside one synchronous transaction, fail-closed on the object-name gate.
- **App wiki / docs** — per-app compounding memory in `snug_app_docs` (vision · requirements · plan · lessons · memory · next-tasks), maintained by the agent on every app change via the `app_doc_write` tool.
- **Factory version** — v1 of a built or installed app, `pinned` and never pruned; "reset to factory" copy-forwards it.
- **Hub provider** — a multi-tenant service provisioning Snug apps per user; optional by construction — apps run from the browser copy of the user DB with no hub backend.
- **Sync origin** — where the user DB replicates (hub `/userdb`, Dropbox, …) via the `SyncProvider` contract; OPFS is authoritative, divergence resolves only by explicit user action (ADR-0009).
- **Execution mode** — `byok` (browser-direct frontier API), `local` (browser-direct localhost LLM), or `subscription` (hub-mediated /invoke); the user DB is client-authoritative in all three (ADR-0008).
- **Per-app model / pinned model** — the LLM model ONE app routes its calls to, chosen in that app's run header and stored as `snug_settings['appModel:<appId>']` (ADR-0036). An app with no pin **inherits** the global Settings model and keeps following it when that changes — inheritance is an absence, never a copy.
- **Effective model** — what `resolveModelForApp(appId)` answers: the app's pin, else the Settings default, else `undefined` (meaning "let the adapter apply its own provider default"). Read per send, never captured at construction.

- **token-claim** — the third pairing family (ADR-0038): a claim-once provider mints a
  permanent `basic_auth` pair from a ONE-TIME setup token the user pastes; the wizard
  decodes it, checks it against the frozen ceiling, claims once, verifies, and writes
  credentials + `claimVerifiedAt` together. SimpleFIN is the first occupant.
- **open-url capability** — the host-mediated way an app opens a website (ADR-0038 D5):
  an internal-draft frame the runner routes to a host confirm dialog; only a real user
  gesture opens the tab (`noopener,noreferrer`), and the sandbox gains nothing (C2).
- **Demo brain** — the zero-key default "AI": the mock adapter's scripted turns
  (`byok` mode + `mock` provider, and the keyless fall-through for a keyed provider).
  Since ADR-0059 it is always ambiently disclosed — the header **brain chip** names
  what's thinking on every route, each scripted assistant turn carries a persisted
  `brainKind` provenance tag, and a first-contact callout introduces it once.
- **Brain chip** — the header status surface (`BrainChip.tsx`) consuming
  `resolveActiveBrain`, the live evaluation of `adapterKindFor` — the ONE adapter
  routing derivation (ADR-0059 rule 2). Where the platform carries `brainSwitch` (the local
  runner) it is the brain switcher: every brain with its state and remedy, `auto` first, and
  what answered.

**App bundle** — one app lifted out of a user file as strict JSON (`snug-app-bundle/1`), carried in a `.snug` file or an encrypted link: the current code, connection *requirements* (shapes, never grants or credentials), the runtime contract, the data schema as `CREATE` DDL (structure, never rows), and the wiki docs the sharer chose. Never carries data, secrets, history or chat (ADR-0063).

**Lineage** — the sharer's app id carried in a bundle, minted by the recipient's installer into `install_source = 'share:<lineage>'`. It is what makes a re-share recognisable as an *update* of an installed copy rather than a second app. Public by construction — anyone holding a bundle knows it (threat-model R-39).

**Shared shelf** — the hub's "shared with you" section between "your apps" and "starter apps". Memory-first: a received bundle persists only after an explicit act (opening an attachment, or "keep" on a link preview), and is inert until install.

**Blind relay** — the one hosted endpoint (ADR-0064): a Worker + R2 bucket that stores app bundles already encrypted in the sharer's browser, with the key carried only in the link's URL fragment. It can neither read what it holds nor substitute it.

**Local host process** — the Node process the agent's host spawns over stdio when the `snug`
plugin is installed (ADR-0068). It serves the host kit's one page on `127.0.0.1` (where it
boots as `local-host`), acts as the network side of the page's connected-fetch executor, and
offers the agent four control-plane tools. It is Snug Desktop's native side written in Node;
it is not a server, a service, or something Snug is "built on" — MCP is only the spawn
channel. Never called an "MCP server" in product copy. It thinks through the user's own agents
via the **brain registry** (`apps/host-mcp/src/brains/` — the `claude` driver's pre-warmed
single-use children are `brains/claude-child.ts`), finds their CLIs off an empty GUI PATH
(`install-roots.json`), and is started by the plugin's `/bin/sh scripts/snug` launcher. Since
TASK-20261003 a second window attaches to the running one, a runner that cannot start answers
with its **refusal table**, and `snug status | open | stop` is its human CLI; its package and
bundle are being renamed `local-host` in a follow-up PR.

- **Auto (brain choice)** — the local runner's default brain choice (ADR-0071 §4): the default brain (`claude`) when it is ready and verified, otherwise none — the demo brain answers and the chip shows the remedy; never another vendor's brain without a user act.
- **Brain driver** — one of the user's own agents behind the runner's one brain contract (`apps/host-mcp/src/brains/brain.ts`, ADR-0071 §1): an id, a readiness probe, a catalogue of models and thinking levels in its own words, validators for both, and the `Brain` a think runs on — tool-free by construction and given only the allowlisted child environment. `claude` and `codex` exist.
- **Brain registry** — the runner's set of brain drivers (`apps/host-mcp/src/brains/registry.ts`), injected into the runner rather than built by it: it probes lazily from the first page contact, reports every brain on `/status`, and resolves which one answers a think, or none.
- **Claim (schedule)** — the `running` run row written for `(taskId, dueAt)` BEFORE any step executes (`schedule/queue.ts`); an existing row for that occurrence in any status but `pending` means it is already recorded — by this host, a sibling tab, or a sync pull — and nothing runs again. A claim whose host died is swept to `interrupted` (`stale claim`) at the next boot; one older than 24 h at import retires the same way.
- **Freshness window** — how long a missed occurrence stays worth catching up: one period of the schedule, clamped to [1 minute, 7 days] (`staleAfterMs`; a one-off keeps a day). A candidate older than it is written `skipped` (`stale`) with a history line and no card, whatever the policy (`schedule/floors.ts`, `plan.ts`).
- **Host passport** — the disclosure beside the brain and "your file" chips on host platforms (`apps/playground/src/views/HostPassport.tsx`, ADR-0072 §4): what this host can and cannot do, in words, from the same offers the shelf obeys; it offers no act.
- **Inbox (results)** — the user-facing list of a schedule's results, newest first, read from the `scheduleRuns:<taskId>` rows; an unread result is one without `seenAt`, which only a user gesture sets (`markSeen`); thirty unread results pause the schedule. *Clear history* drops results and keeps what is not yet dealt with (`pending`, `needs-you`, `running`).
- **Missed / late / collapsed / catch-up (schedule)** — what `plan.ts` makes of an occurrence the clock has passed: within the 15-minute grace it is **late** and runs now (several in the grace **collapse** to one run for the latest); older it is **missed**, and every missed occurrence of a task **collapses** to ONE candidate (`dueAt` = the latest, `collapsedCount` = how many) that is skipped past the freshness window, else handled by the schedule's `missedPolicy` — `ask` (a persisted `pending` row the missed card reads; the user-facing word is *missed*), `run-once` (a **catch-up** run) or `skip`. A one-off is always asked.
- **Offers / needs (availability)** — the one derivation that disables an app a host cannot run (`apps/playground/src/platform/availability.ts`, ADR-0072 §4): an app's needs (`network`, `native-fetch`, `oauth`, `lan`, `helper`) come from its declared connection or its connection rows, a host's offers from the seats its platform carries — never from `kind`.
- **Proposal (data change)** — a pending `INSERT`/`UPDATE`/`DELETE` an *Ask [app]'s AI* step's reply — or, on a step that may *look things up*, its `data_propose_write` call — offered (user-facing: *changes waiting for your OK*): admitted through the one proposal gate (`schedule/proposalGate.ts`: one `INSERT`, `UPDATE` or `DELETE` statement, no unbound placeholder, no credential, the app not mid-change, a dry run on a throwaway copy for its count), at most three per result, stored on the run row with one `expiresAt` (seven days), and stripped from every run row on every import, pull and export so a foreign file can never plant one. The engine executes none UNLESS the schedule may *make changes on its own* (since TASK-20261010-host-broker PR-4): then, when the run finishes uninterrupted, the walk makes the ones its `ok` steps proposed to the schedule's own app's data through the capture seat — they move to *changes it made* with an undo — and every other keeps waiting; one the walk could not make carries a `held` reason (`busy` · `changed` · `cannot-undo` · `full` · `failed` · `over-limit` · `stopped`), and an item for another app's data only ever waits. What was made of them (the run's `applied` group, the user's `approved` entries) leaves a run row only on an untrusted import. Distinct from a *schedule proposal* (`scheduleProposalSchema`), which is what the builder, the chat or an app may suggest and only the user's act turns into a task.
- **Refusal table (runner)** — the nine reasons a local host process can neither lead nor attach, each a message and a remedy (`apps/host-mcp/src/refusals.ts`): the process still answers the MCP handshake, `snug_status` returns the row, and every other tool returns its sentence.
- **Run / result (schedule)** — one execution of a task, keyed `(taskId, dueAt)` in the task's `scheduleRuns:` row: trigger (`due`, `late`, `catch-up`, `manual`), status (`pending`, `running`, `ok`, `failed`, `skipped`, `needs-you`, `interrupted`, `capped`, `no-handler`), per-step outcomes, `host {kind, binding}`, `calls {ai, net}`, pending proposals, `seenAt` — and since TASK-20261010-host-broker PR-4 what was made of them (`applied`, the schedule's own changes; `approved`, the user's) and each step's host facts (`inOpenApp`, `saw`, `tools`, `blockedBy`). The user reads a **result**; "run" is the app verb only (*run Ledger*, *run now*).
- **Schedule** — the user-facing word for one scheduled item (ADR-0074): what runs (*Remind me* / *Ask [app]'s AI* / *Run [app]*), when (a `spec` — once, every N, daily, weekly, monthly, custom cron — with `tz: 'device'` or a pinned IANA zone), what happens if Snug was closed, and how the result is told. Stored as `schedule:<taskId>`; enabled by nothing but the user's act; disabled on an untrusted import unless byte-identical to a local one. Since TASK-20261010-host-broker PR-4 a one-app schedule may also *make changes on its own* — again only by the user's act, and every untrusted import takes that away.
- **Succession (runner)** — when the primary runner goes away, an attached session re-runs the start on its agent's next tool call, becomes the primary, and asks for `snug_open` again, because a new runner is a new bearer.
- **Suggestion (schedule)** — a schedule the builder LLM, the app-attached chat or a running app PROPOSES (`scheduleProposalSchema`: title, steps, spec; `proposalHash` over the semantic fields only). It becomes a task only through the user's act on the one consent surface (`EnableConsent`) and the one writer (`schedule/enableProposedTask.ts`); declines and mutes live as `scheduleDeclined:<appId>:<hash>` / `scheduleMuted:<appId>`. The three channels: the builder's `schedule_propose` tool (a card in the chat rail), the app chat's `schedule` lane (the same tool, alone), and a running app's `app-event 'schedule-request'` (the suggestion strip).
- **Hidden frame (schedule)** — the one `SnugAppFrame` a scheduled *Run [app]* step runs an app's own code in WHEN THE APP IS CLOSED (`schedule/ScheduledRunHost.tsx`, mounted once in `App.tsx`; driven by `schedule/appRun.ts`): the same component as RunView's, so the same sandbox and CSP; 1×1 `visibility:hidden` (never `display:none`); at most one at a time; the app's committed current version; never registered as the app's live host; its db binding refuses transaction control and a whole-database import (`scheduledDbDriver.ts`); it reports when it has unmounted so a handover never overlaps it. Since ADR-0077 it is never mounted beside an open copy of the same app — an open app receives a *delegated run* instead.
- **Handshake (schedule)** — how the host hands a scheduled run to an app over the frames that already exist (ADR-0074 §3): the host writes `snug:schedule:<runId>` = `{ taskId, runId, input? }` into the app's own kv through the driver's host-side `kvSet` (≤ 1 KiB, behind the app's tombstone), posts `host-event 'schedule-run' { taskId, runId }` — ids only, never content — and reads ONE `app-event 'schedule-result'` from the frame it hinted (the hidden mount's own closure, or the live registry's events for that app AND that frame generation), after the hint, once, length-capped before the strict parse. The hint waits for the frame's announce (≤ 10 s, else `no-handler`). The key is written per dispatch and cleared once at the end of the step; a dead tab's key is swept at boot.
- **Refusing gate (schedule)** — the standalone confirm gate a HIDDEN run's net handler carries (`schedule/scheduledConfirmGate.ts`, threaded through `state/net.ts`'s `confirmGate?` seat): it imports neither the session-remember nor the standing-approval gate, answers no to every mutating call (the app reads the existing `NET_CONFIRM_DENIED`) and records what it refused, so the step is `refused` with the *needs you* sentence whatever the app reports. Its sibling for a *delegated run* is the **run-scoped ask gate** (`schedule/runScopedGate.ts`): the live frame's default gate, which asks the present user once per run through the ordinary confirm queue under a host-composed title, consults no remembered or standing grant while a run is in flight or on a frame generation that hosted one (the *sticky ask*), withdraws a parked ask when the run ends, and records why it refused (declined · nobody answered · already asked).
- **Delegated run (schedule)** — an unattended *Run [app]* (`due` · `late` · `catch-up`) executed in the app's OPEN frame because the app is on screen in this tab (ADR-0077; `schedule/appRun.ts` `dispatchLive`): the registry's hint, the frame's own transport and db binding, the run-scoped ask gate, every AI and net call counted on the run row and never refused mid-run (the ceiling is asked before dispatch), the record kept in the placement store (`schedule/runPlacement.ts`: `delegatedRunStore`), the access door closed for the window. The header chip reads *running in <app>*. A `manual` run (*run now and review*) is NOT a delegated run: it keeps the page's ordinary gate and is not counted (R-62).
- **Placement (schedule)** — where the host executes an unattended run: `'live'` when the registry has the app (registered in this tab, announced or not — the live dispatch then waits for the announce), `'hidden'` otherwise (`placeRun`). One instance per app per TAB; host-native work (ADR-0076) needs no placement at all.
- **Handover (schedule)** — a run following its app: an app that opens mid-hidden-run cuts that attempt and re-dispatches the SAME `runId` to the live frame once the hidden frame has unmounted and the live one has announced; an app that closes mid-delegated-run re-dispatches hidden. At most once per run (a second ends the step `failed`); never after the user allowed a mutating call in the delegated attempt (`failed`, "closed after a change was sent"); a frame remount is not a handover (the attempt ends by the result bound). Tallies are summed across attempts; one deadline per step. The KB's idempotency rule is what makes a re-dispatch safe.
- **Sticky ask (schedule)** — the run-scoped gate's posture AFTER a delegated run: the frame generation that hosted it stays ask-only — every later mutating call from that generation is asked once in the host's dialog, never answered by a remembered session grant or an armed standing grant — until the frame retracts or remounts (`touchedGeneration` in `schedule/runPlacement.ts`). The reason: a handler could post its result first and POST afterwards into the remembered grant. The cost, said in the dialog: *remember for this session* is unavailable on that frame until the app is reopened.
- **Suggestion strip** — the run header's strip (`schedule/SuggestionStrip.tsx`, `.connection-note.is-strip`, never a modal) that shows a running app's pending schedule suggestion — "<app> suggests: <when>", the steps in words — with three acts: *schedule it* (the consent surface, inside the strip, then the one writer), *not now* (a decline by semantic hash; the second decline mutes the app) and *stop suggestions from this app*. Fed by `schedule/scheduleRequest.ts`, which admits at most one pending per frame generation and one request a minute per instance.
- **Task (schedule)** — the engine's internal noun for a stored schedule (`scheduledTaskSchema`, the `schedule:<taskId>` row): never shown to the user as a word (`schedule/copy.ts`'s vocabulary scan refuses it in any UI file).
- **Verified (brain)** — a brain driver whose tool-free posture has been walked on a real, logged-in run; an unverified one (`codex` today) answers only when pinned by id, is labelled experimental, and is never chosen by `auto`.
- **Watermark (schedule)** — `schedulerState.watermark`, the instant up to which the file's schedules have been reconciled; each reconcile plans `(max(watermark, enabledAt, startsAt, ranThrough), now]` and writes the watermark LAST, after every candidate row, so a crash between rows loses nothing. A fresh file starts at now (no fabricated backlog); an untrusted import resets it to now; a trusted pull keeps `max(local, imported)`; a global pause leaves it where it is.
- **Access grant** — the host record that lets one app read — or, when the user ticked it per table, change rows in — another app's tables (ADR-0075, widened by ADR-0076; spec 1.1 Part VI, 1.2 since TASK-20261010-host-broker PR-3, which always says *access grant* — Part III's *connection grant* is a different record; code: `AccessGrant`, `accessGrantSchema` in `packages/protocol/src/access.ts`): `{ reader, source, scope, kv?, refresh?, access: 'read' | 'write', purpose, duration, unattended, status, provenance: 'app' | 'user' | 'chat', … }` — `access` DERIVED (`'write'` iff some table carries `write`), every default omitted so a defaults-off record is byte-identical to a 1.1 record, and a 1.1 hub holds a widened record unreadable (fail closed) — written only by the user's act on host chrome. *For a day*, *for a week* and *until I stop it* persist as `accessGrant:<id>` rows in the user's file (≤ 100 live, ≤ 16 KiB, strict, credential-free); *while it's open* — the default — is a memory grant bound to the reader's visible frame generation and never written. Revocable from the source's sheet, the reader's sheet, Settings or the reader itself (`release`); paused (`suspended`) when a shared or agent update replaces the reader, the source's granted columns change, the source holds a WhatsApp fact, the reader's reads time out three times running, or an untrusted import carried it in without a matching local grant; swept when either app is deleted. **The UI never says *grant*, *reader*, *scope* or *log*** (the vocabulary scan in `access/copy.ts`'s test): a person reads *access* (the noun — "Budget has access to Ledger's transactions"), *allow* and *stop* (the verbs), *reads* / *is read by*, and *history*; and never *share*, which ADR-0063 owns for app sharing.
- **Reader** — the app an access grant lets read (`readerAppId`): it asks with a purpose over `snug:access-request`, never names a source, and learns only what was granted — the source's display name and icon, the granted tables with their columns, the duration. Identified by the HOST-assigned `accessAppId` (the `dbNamespace` discipline), never by its announce. Since TASK-20261010-host-broker PR-5 a reader may also say in its own HTML what it would like to read (the *access declaration*), and the user may start its access from host chrome (a suggested pair, or the source's offer) — every grant is still the user's allow on the one consent sheet.
- **Source** — the app whose tables an access grant opens (`sourceAppId`). The source app's code learns only an id-only hint that it was read (`access-read`, since spec 1.2), never what; the HOST keeps the record on the source's own row (the access history). Since TASK-20261010-host-broker PR-5 the user may also start a grant from the source's side — its ⋈ sheet's *let another app read Ledger's data* opens the one consent sheet pinned to it, created read-only (a forged write is refused; *allow again* may later widen it, R-118) — still only the user creates one. An app holding a WhatsApp fact is never a source.
- **Scope (access)** — the granted tables of an access grant, each with its columns disclosed and FROZEN at consent (`scope.tables[].columns` — the columns the user left ticked, the only ones any door may read or a write may name; `withheld` — the non-credential columns the user unticked, withheld on the copy exactly like a credential-named one and counted by the drift check, never on the view; `write?: true` — the user ticked *can also change rows* for that table): a later column change — in `columns` or `withheld` — suspends the grant (`source-changed`); a credential-named column is never in a scope; `snug_kv` is never in `tables` but crosses, filtered through the one credential walk, when the grant carries `kv` (*settings & notes*). A read runs on a scoped scratch copy from which everything outside the scope is physically dropped; a write is dry-run on the same kind of copy and then applied on the live database.
- **Door (access)** — a caller of the ONE access service (ADR-0076 §1; `access/service.ts` over `access/policy.ts`'s `authorise(caller, act)`): the reader's **frame** (today's `snug:access-request` handler, now a thin mapper — its generation and whether anyone is present; since PR-3 the only door with a STANDING write, its own `refresh` op and `discover`), the **chat** beside the reader (the data lane: the granted tables — and the source's filtered key-value store under `kv` — materialised into its scratch copy, a read line when its SQL names one, the brain's `access_propose` card; read-only at 1.2, and since PR-5 (spec 1.3) it may PROPOSE one change to a table ticked *can also change rows*, which the user applies on its card — per card, never standing — and may *fetch new data first* by the toggle beside *send*), and the **scheduler** (*ask <app>'s AI*: the same tables under the away posture, persisted grants ticked *also while I'm away* only — since PR-4 a step that may *look things up* records a grant only when its `data_query` names the table; never a write to another app's data — `ACCESS_UNATTENDED`; a schedule's changes to its OWN app are *make changes on its own*, not a door's; since PR-5 a step may *fetch new data first* from the apps it may read while the user is away, set only by the user's tick). The same grant, the same sheet, the same history, whichever door asks; a person never learns there are doors, but every history line says which one (`via`: `app` · `chat` · `schedule`, and `user` for an act from host chrome such as an undo).
- **Materialised table (access)** — a granted table copied THROUGH the scoped-read Worker (drops, withheld columns, masked values, drift all applied there; only the scope's recorded columns; ≤ 5,000 rows / 2 MiB per table, ≤ 8 MiB per set) into the chat's or the scheduler's throwaway scratch copy as `<alias>__<table>` (`ledger__transactions`; the alias de-collided against the reader's own object names), listed for the brain under *From <Source> (read-only · access until …)*; attached to a `data_query` only when the statement names one; never written directly (the real database has no such table) — since PR-5, on a chat turn that may change data, a table the grant lets the chat change is listed *· can be changed*, and a proposal naming it is renamed to the source's own table and becomes a card the user applies (the scheduler's propose tool still refuses the name).
- **Access history** — the source's record of access to it, kept by the host as `accessLog:<sourceAppId>` (code and spec: the *access log*; the UI says *history*): `granted`, `read` (the statement's first 200 characters unless credential-shaped, rows, whether anyone was looking), `refused`, `revoked`, `expired`, `released`, `suspended`, and since spec 1.2 `wrote` (the table, the rows changed, the statement as *what it changed*, the authority, the journal entry's id while an undo is offered), `undone` (the rows put back; always the user's act, `via: 'user'`) and `refreshed` (who asked and, on failure, a reason from the fixed set — never the source handler's text); every line says through which door (`via`). Bounded (≤ 200 entries / 64 KiB per source), pruned reads-first and never the latest lifecycle line — nor the latest `wrote` — of a grant the file holds; travels with the file, imported entries tagged and shown under their own heading; *clear history* drops reads and keeps the lifecycle lines and every change. The history renders *you* for an act from host chrome and offers *undo* on a `wrote` row whose journal entry is still live. Since TASK-20261010-host-broker PR-5 it crosses a sync: on either resolution of a divergence the losing copy's lines are carried into the winning one by their natural key `(at, kind, grantId, readerAppId)` — a carried `wrote` line without its `undoId`, carried lines giving way first under the caps — and a grant stopped on either side ends stopped; the undo journals follow the winning copy. A chat proposal of a change records a `read` line with the table and no statement; a stopped fetch is a `refreshed` line *Ledger's fetch didn't finish*.
- **Write permission (access)** — the per-table tick *can also change rows* on the consent sheet (`scope.tables[].write: true`; the authority `permission` on the `wrote` line — the standing per-table permission, as against `approval` — the user's approve of one proposed change — and `task`, a schedule's standing authority; since TASK-20261010-host-broker PR-4 both of those are live, for an app's OWN data only — `task` is *make changes on its own*, the task authority, no longer deferred — and both are journaled in the *own undo* journal with no history line; since PR-5 the user's approval of the chat's change to ANOTHER app's table is a `wrote` line with `authority: 'approval'` and `via: 'chat'`, journaled in the source's access journal; a schedule never writes another app's data, and an authority over it is its own task needing a later minor), off by default and offered when the ask carried `access: 'write'` or the user opens *more options…*. Under it a reader's frame posts `write` with ONE plain `INSERT`, `UPDATE` or `DELETE` whose values are literals or bound parameters, naming only granted, non-generated, unmasked columns, and the host dry-runs it on a scoped copy in the Worker, refuses it past 200 rows or past the undo's size, applies it atomically on the source's live database through the one driver seat with the rows it changes captured first, writes the `wrote` line and rings the doorbells; the reader learns only how many rows changed. Never while nobody is present; never on a table with a trigger, a foreign-key action, `ON CONFLICT REPLACE` or a CHECK over an unshared column; a DELETE only on a fully shared table. **The UI never says *write grant*** — a person reads *can also change rows*, *changed 3 rows in transactions*, *read and change*.
- **Undo (access)** — the user's act from the source's history that reverses one brokered change (`undoBrokeredWrite`, `via: 'user'`): the host rebuilds the inverse from the undo journal `accessUndo:<targetAppId>` — which holds ROWS (the new rowids and inserted values; the before and after values of the columns an UPDATE set; a deleted row whole), never statement text — with every identifier checked against the live table and every value a bound parameter, applies it in reverse step order inside one atomic span, and changes nothing unless every row still holds the values the write left (else "couldn't undo — <Source> changed these rows since"); it writes `undone`, marks the entry so an undo is never offered twice, and rings every live reader. Since PR-5 a change the user applied from the chat's card is undone the same way, from the source's ⋈ sheet the card opens in place. Entries are capped (20 live per target and reader — a reader at the cap has its next write refused rather than evicting one; 64 KiB per entry; 256 KiB per row), kept seven days, never a credential, swept with the app, dropped on an untrusted import and kept on a trusted pull. An app's OWN changes — the user's approvals from the chat's card or a result page, and a schedule's changes made on its own — kept no journal at PR-3; since PR-4 they are journaled in the separate *own undo* journal (below), with no history line.
- **Refresh (access)** — a reader asking the host to run the SOURCE for new data before it reads (`op: 'refresh'`; the per-grant tick *may ask <Source> to fetch new data before reading it*; `access/refresh.ts`): the source runs where it lives (ADR-0077's placement — the live frame when open, the hidden frame otherwise) with `input { kind: 'refresh', requestedBy }` over the schedule handshake under `taskId: 'access-refresh'`, with a REFUSING posture (a mutating connected call is refused, never asked; nothing remembered; the frame stays ask-only afterwards as after a scheduled run), only where schedules can run (the seat, the state row, not paused), counted on the file's daily ceilings and refused before dispatch when they would be crossed, at most once per source every five minutes (within it `fresh: false, reason: 'recent'` and nothing runs), logged `refreshed` on the source with who asked; a source without a handler → `ACCESS_REFRESH_FAILED`; the handler's summary reaches nobody. Since TASK-20261010-host-broker PR-5 the chat (a toggle beside *send*) and a schedule's *Ask <App>'s AI* step (the user's tick, stripped from every proposal channel) may *fetch new data first* — through the one service, under the caller's own grants ticked for it (a schedule's also *while I'm away*), at most two sources in turn, counted in the run — and the source's own *fetch now* was cut. One header chip reads *fetching in Ledger* (*+N* for more) with one act: *cancel* on a fetch out of sight, *stop waiting* on one in the open app, which keeps refusing its mutating calls until its result or its deadline; a stop is a `refreshed` line *Ledger's fetch didn't finish*. The UI never says *refresh* — a person reads *fetch new data*.
- **Doorbell (access)** — an id-only hint on `snug:host-event` to a LIVE frame, never a row, a value, a name or a count (ADR-0034, ADR-0076 §8; `access/doorbell.ts` over the driver's write signal `subscribeWrites`): `access-source-changed { grantId }` to every live reader of a source after a successful row-modifying statement on it (coalesced per source — the first rings at once, later ones inside the 2 s window ring once more at its end; a key-value write rings only grants with `kv`), after another reader's brokered write and after an undo (every reader); `access-read { grantId }` to the source's live frame after a read under that grant; `data-changed { table }` (or `{}` when the statement could not name its table) to an app's own live frame after a brokered or approved write, or an undo, landed on its database, so an open app re-reads. The host's own handshake writes (`snug:schedule:<runId>`) ring nothing, a read rings nothing, DDL rings nothing (the next read's drift check pauses the grant), and a hidden frame is never rung. Its sibling is `access-changed`, the 1.1 hint that a grant was stopped or paused.
- **Access declaration** — what an app says, in its own HTML head, it would like to read from the user's other apps: ONE `<meta name="snug:access-wants" content='[{"purpose": …, "hints": {"tables": […], "words": […]}}]'>` before the first `<script>`/`<style>` (≤ 2 KiB, ≤ 4 entries; TASK-20261010-host-broker PR-5, ADR-0076 §11; spec 1.3 §8.1). Never a bundle field and never a grant: the host derives the `accessWants:<appId>` row from the app's current HTML at every version it is given (`packages/db/src/access-wants.ts`, a small grammar — anything ambiguous is none) and re-derives every row on every import, so a file's own row is never read. It shows as one sentence on the shared install preview (*Budget would like to read data like transactions from your other apps — nothing is read until you allow it*), feeds *apps that could work together*, and pre-fills the declared sheet (the app's purpose quoted after *what Budget says it's for:*). An app declares AND asks at runtime, with the same purpose and hints. **The UI never says *declaration*** — a person reads *would like to read*. Not the starter's *Declaration* (`connection.json`, above).
- **Apps that could work together (access)** — the host's suggestions of a reader and a source (`access/pairs.ts` `listPairSuggestions`, PR-5): from access declarations ONLY — a pair needs a table-level match between the reader's hints and the source's registered schema (nothing is exported to rank it), never involves an app that arrived through a share link or an imported file, and never repeats a pair already joined by an access that is not stopped or a wish the user declined. Shown as Settings' *apps that could work together* (*Budget could read Ledger's transactions* · *review…*), the Hub tile's *could read Ledger's data — review…* and the reader's ⋈ sheet; a tap opens the one consent sheet pinned to that source with only the matched tables ticked. Every such act leaves a visible outcome where it was started. A suggestion is never a grant.
- **Arrived with an imported file (imported marker)** — the provenance an untrusted import gives an app it brought in or changed (`appProvenance:<appId>` = `{imported: true, at}`, host-internal; `packages/db/src/userdb/app-provenance.ts`, PR-5): the import drops every marker the file carried and marks every app whose install source or any version (its number, pin and HTML hash) differs from this device's copy; a trusted pull keeps markers, deleting the app sweeps it, no edit clears it, and a marker that cannot be read counts as imported. The consent sheet then says *arrived with a file you imported on 3 Oct · Snug can't tell who made it* in place of any provenance the file could have forged (closing R-77 for imports from PR-5 on), and the app is never suggested in a pair. A restore of a backup onto a new device marks every app.
- **Make changes on its own (schedule) — the task write authority** — the user's standing consent that ONE schedule may make the changes its *Ask <App>'s AI* steps propose to that app's OWN data without waiting for an OK (TASK-20261010-host-broker PR-4, ADR-0076 §9 — ADR-0033's shape, its first arming surface; code: `writeAuthority {rowsPerRun, armedAt, armedVersion}` on the task row, internal, outside `canonicalScheduleIntent`). The one phrase on every surface: the consent's tick *let it make its changes to Ledger’s data on its own — never another app’s · up to 200 rows each time · undo any of it for seven days*, the editor's *changes it suggests:* (*wait for my OK* / *make them on its own*), the row's chip *makes changes on its own*, the acts *stop making changes on its own* and *stop every schedule making changes on its own*; the UI never says *authority*. Offered only for a schedule whose every app step names the same one app and at least one asks its AI (`armableAppOf`); armed only by the user's tick (`armTask` through `armIfTicked`), which is off on every mount and seeded by nothing — not a suggestion, an import or a draft. Disarmed by a save that widens it (its steps, its app, a shorter interval) without the consent again, by the app's version changing from ANY source — the user's own edit included — by every untrusted import, by deleting the app and by the two acts; a disarm the user did not do leaves *no longer makes changes on its own — this app was updated* (or *— arrived with an imported file*) with *review*. Kept across pause and off/on, but nothing is made meanwhile. What it allows is bounded: the schedule's own app's data only (a scheduled step still never writes another app's data — spec 1.2 §24.5 item 18), ≤ 200 rows a run, only changes whose undo can be built (literal values, a WHERE on UPDATE and DELETE, no functions, arithmetic or conflict clause), only from steps that answered `ok` in a run that was not cut short (cancelled, timed out, paused or swapped out), at most 20 changes still undoable at once; never a connected call — a scheduled mutating network call is still refused.
- **Own undo (journal)** — the host-internal journal that lets the user put back a change to an app's OWN data for seven days (TASK-20261010-host-broker PR-4, ADR-0076 §9; `ownUndoEntrySchema` in `packages/protocol/src/own-undo.ts`, internal; the accessors in `packages/db/src/userdb/own-undo.ts`). ROWS, never statement text — the access journal's step schema and 64 KiB entry cap reused — in one `ownUndo:<appId>:<bucket>` settings row per **bucket**: `<taskId>` for each schedule that may make changes on its own (≤ 20 live entries; when full the schedule's next change is held `full`, never an older undo evicted) and `approval` for the user's own approvals from the chat's card or a result page (its oldest live entry gives way — the user was there for each — so an approval is never refused for room); ≤ 256 KiB a row. `ownUndoBelongsIn` decides an entry's bucket (an approval in `approval` with no task id; a schedule's change in its own task's bucket, never `approval`) and is asked before any seat. Written only through the Write Broker's capture seat, whose `admit` parses the exact entry before `COMMIT` — under a schedule a change that could not be undone is never made; an approval it cannot capture is made without an undo and says so. Swept with its schedule and with its app, dropped by an untrusted import, kept on a trusted pull, in every export and in every sync push. No history line: an own change names no other app. User-facing: *undo* on the result page's *changes it made*, in the schedule's changes list at the top of its history, and on the chat's change card. Distinct from *Undo (access)*, the journal of changes made to ANOTHER app's tables.
- **Look things up (schedule)** — an *Ask <App>'s AI* step with `tools: true` (the editor's tick *let it look things up*): instead of one tool-free answer over a snapshot, ONE agent turn the host runs itself (`schedule/appAgent.ts`, TASK-20261010-host-broker PR-4, ADR-0076 §9) with three tools — `data_query` over the app's data and what the user let it read from other apps, `data_propose_write` for changes (they wait for the user's OK unless the schedule may *make changes on its own*), and `fetch_connection` — under at most 8 tool calls and 10 AI calls each time, the day's ceilings asked before every AI call and every fetch. Only where the data lane runs (a keyed BYOK or a local brain): under the host, subscription or WebLLM brain, or for an app holding a WhatsApp fact, the step answers tool-free and says why (`tools.unavailable`); the demo brain, or a BYOK brain with no key, refuses the step whatever it carries. **`fetch_connection`** reads from the app's approved connections: GET only — no method can be expressed — host-pinned (a multi-host connection resolves to the one API host its approved requirement declares, re-asserted before the executor), never a sidecar or LAN-class connection, refused for the rest of the turn once it has read another app's data (the taint; fetch-then-read stays allowed), every answer scrubbed and cut at 16,000 characters. **GET-only is not read-only**: an API that acts on a GET can be driven by what was fetched or shared, so the consent never says *read only* — *it only asks, never posts — but what it asks can carry your data* — and every connection used is named on the result (`tools.fetched`).
